## Body

Addresses **B3** from #77462.

> [!NOTE]
> An earlier revision also included a per-instance `<style>`-emission optimization (**B2**) and a `crossesPortalBoundary` prop. Both were dropped after benchmarking showed a negligible, unmeasurable real-world gain against meaningful added complexity (see discussion below). This PR is now delivery-model only.

## What?

The design-system tokens ship as a prebuilt stylesheet that's always present where components render, and the legacy `--wp-components-*` aliases resolve to those tokens without a runtime `<ThemeProvider>`.

## Why?

Components consuming `--wpds-*` (and the legacy `--wp-components-*`) need the token `:root` block to exist where they render — on plain admin pages and inside the editor iframe, where no `<ThemeProvider>` wraps them. Previously those defaults only appeared once a provider emitted them at runtime.

## How?

- **Stylesheet delivery** — a new `wp-theme` PHP handle ships the prebuilt `design-tokens.css` on every admin page and inside the editor iframe, so the `:root` `--wpds-*` block is always present (`wp-base-styles` depends on it).
- **Legacy fallbacks** — the `--wp-components-*` fallbacks point directly at the design-system tokens (`theme-variables.scss`, mirrored in `colors-values.js`), so components get sensible defaults from the prebuilt stylesheet without a provider.
- **Docs** — document the delivery model (static stylesheet + `<ThemeProvider>`), the `isRoot` prop, and using `<ThemeProvider>` across documents (iframes and other portals).

<details>
<summary>No-regression notes</summary>

The `--wp-components-*` fallbacks now end in the design-system tokens rather than hard-coded values:

- **Build-plugin consumers** (`postcss-ds-token-fallbacks`, esbuild, Vite): no regression — `--wpds-*` references carry a build-time fallback ending in the brand default.
- **`--wp-components-*` without a provider**: covered — the fallbacks in `theme-variables.scss` (and their `colors-values.js` mirror) resolve to `--wpds-*` defaults from the prebuilt stylesheet.
- **Editor iframe** (`<StyleProvider document={iframeDocument}> + <ThemeProvider>`): `wp-theme` is enqueued inside the iframe, so `--wpds-*` are defined at the iframe `:root`.

</details>

3. **Components without a provider** — render a component that uses a legacy `--wp-components-*` color with no surrounding `<ThemeProvider>`; it resolves to the design-system token default from the prebuilt stylesheet (never empty).

### ciampo on 2026-06-16T12:24:34Z

URL: https://github.com/WordPress/gutenberg/pull/78664#issuecomment-4718699217

While testing, I noticed a regression introduced by this PR in portalled overlays: these overlays use `<ThemeProvider />` without props, which (with the changes from this PR) doesn't emit any CSS, and this causes the theme styles not to inherit to the portal as expected; the overlay would fall back to the default colors instead of the surrounding theme. The theme forwarding only kept working for root-level theming, which the browser propagates everywhere anyway, and this was masking the bug until I did some deeper final testing.

To fix it, I added a new `crossesPortalBoundary` prop on `<ThemeProvider>` (that forces the emission of the theme CSS), and applied it to all the `@wordpress/ui` overlay popups:
- Root-level theming is unaffected;
- Overlays now re-emit only when there's an actual non-default in-scope theme to carry across the portal;
- Unthemed overlays still emit nothing.

Added unit tests covering the behavior.

 The `ThemeProvider` redefines some of the design system tokens. Components consuming semantic design system tokens will automatically follow the chosen theme. Note that the tokens are defined and inherited using the CSS cascade, and therefore the DOM tree, not the React tree. This is very important when using React portals.
 
+### `isRoot` and the containing document
+
+By default, the styles a `<ThemeProvider>` emits are scoped to the provider's wrapper `<div>`, so overrides apply only to its subtree.
+
+Setting `isRoot` additionally hoists those overrides to the containing document's `:root`, so anything rendered into that document — including overlays portalled outside the provider's React tree — picks them up.
+
+```tsx
+<ThemeProvider color={ { primary: '#a00' } } isRoot>
+	{ /* …app… */ }
+</ThemeProvider>
+```
+
+Use `isRoot` on the top-level provider for an application or page. It's also the recommended pattern for the topmost provider rendered into a separate document (iframe, popup window). The static design-tokens stylesheet still provides the default values; `isRoot` is only needed when you want a `<ThemeProvider>`'s overrides to reach the whole document.
+
+### Across documents (iframes and other portals)
+
+When you render React content into a different document (typically an iframe), two things must be true for design tokens to work correctly in that document:
+
+1.  **The design-tokens stylesheet is present in the document's `<head>`.** This is the static `:root` block that defines every `--wpds-*` and `--wp-components-*` custom property.
+
+    Inside WordPress, this is enqueued automatically for both the admin page and the block editor's content iframe.
+
+    For custom iframes, the consumer is responsible for loading it — either by importing `@wordpress/theme/design-tokens.css` from a stylesheet that the iframe already loads, by copying the parent document's `<link>` element into the iframe `<head>`, or by injecting the CSS string directly.
+
+2.  **Emotion-based component styles are routed to the iframe document.** Many components in `@wordpress/components` use Emotion, and Emotion needs to know which document's `<head>` to inject into. Wrap the iframe subtree in `<StyleProvider document={ iframeDocument }>`.
+
+The canonical pattern combines both with a `<ThemeProvider isRoot>` to apply any overrides to the iframe's `:root`:
+
+```tsx
+import { __experimentalStyleProvider as StyleProvider } from '@wordpress/components';
+import { ThemeProvider } from '@wordpress/theme';
+import { createPortal } from 'react-dom';
+
+function IframeContent( { iframeDocument, children } ) {
+	return createPortal(
+		<StyleProvider document={ iframeDocument }>
+			<ThemeProvider isRoot color={ { primary: '#a00' } }>
+				{ children }
+			</ThemeProvider>
+		</StyleProvider>,
+		iframeDocument.body
+	);
+}
+```
+
+The static stylesheet inside the iframe provides every default; `<ThemeProvider isRoot>` adds (or omits) overrides on top, exactly like in the main document.
+
+For a full working example, see the **Design System / Theme / Theme Provider / Across Iframes** story in this package.
```
