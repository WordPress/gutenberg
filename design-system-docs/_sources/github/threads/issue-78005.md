## Body

## What problem does this address?

`date-fns` is declared at `^3.6.0` in [`packages/components`](https://github.com/WordPress/gutenberg/blob/trunk/packages/components/package.json), [`packages/dataviews`](https://github.com/WordPress/gutenberg/blob/trunk/packages/dataviews/package.json), and [`packages/dependency-extraction-webpack-plugin`](https://github.com/WordPress/gutenberg/blob/trunk/packages/dependency-extraction-webpack-plugin/package.json), and at `^4.1.0` in [`packages/editor`](https://github.com/WordPress/gutenberg/blob/trunk/packages/editor/package.json). The Syncpack alignment work (#77950, #77954) needs to converge these onto a single version, which means lifting the v3 declarations to v4.

Bumping `date-fns` to `^4.1.0` in `packages/components` causes 50+ unit tests to fail in [`DateTimePicker`](https://github.com/WordPress/gutenberg/blob/trunk/packages/components/src/date-time/date-time/test/index.tsx) and [`TimePicker`](https://github.com/WordPress/gutenberg/blob/trunk/packages/components/src/date-time/time-picker/test/index.tsx) with `Unhandled type passed to MockDate constructor: object`. The root cause is a chain of three libraries:

1. `@date-fns/utc 2.x` defines `UTCDateMini extends Date` (used by [`inputToDate()`](https://github.com/WordPress/gutenberg/blob/trunk/packages/components/src/date-time/utils.ts) for UTC-normalised dates).
2. `date-fns 4.x` rewrote `toDate()` to go through `constructFrom(date, value)` which now does `new date.constructor(value)` for any `Date` subclass — so `startOfMinute( UTCDateMiniInstance )` ends up calling `new UTCDateMini( UTCDateMiniInstance )`.
3. `timezone-mock` (used by the TimePicker tests) has swapped the global `Date` for its own `MockDate`, whose constructor rejects object arguments. The re-construction inside `UTCDateMini`'s `super()` chain trips the assertion.

#77954 includes a narrow workaround for this on the `TimePicker` initialiser only (commit `TimePicker: stop routing UTCDateMini through date-fns/startOfMinute`). That commit unblocks the syncpack alignment but does **not** address the broader v3 → v4 upgrade. There are 17 other date-fns import sites across the repo that haven't been audited:

Most of these likely keep working under v4, but any code path that passes a `UTCDateMini` (or another `Date` subclass) into a `date-fns` v4 helper that internally calls `toDate()` will hit the same construction failure under tests that mock the global `Date`.

## What is your proposed solution?

Audit and upgrade all `date-fns` usage in one coordinated PR:

1. Bump `date-fns` to `^4.1.0` in [`packages/components/package.json`](https://github.com/WordPress/gutenberg/blob/trunk/packages/components/package.json), [`packages/dataviews/package.json`](https://github.com/WordPress/gutenberg/blob/trunk/packages/dataviews/package.json), and [`packages/dependency-extraction-webpack-plugin/package.json`](https://github.com/WordPress/gutenberg/blob/trunk/packages/dependency-extraction-webpack-plugin/package.json).
2. For each of the 17 import sites listed above, identify any call that takes a `UTCDateMini` (or other `Date` subclass) and routes it through a `date-fns` helper that internally calls `toDate()` / `constructFrom()`. Replace with code that operates on timestamps (numbers) or sets fields directly on the `UTCDateMini` instance (which preserves UTC via the `setUTC*` shim) — see [`packages/components/src/date-time/time-picker/index.tsx`](https://github.com/WordPress/gutenberg/blob/trunk/packages/components/src/date-time/time-picker/index.tsx) for the pattern.
3. Audit the [v4 release notes](https://github.com/date-fns/date-fns/blob/main/CHANGELOG.md#v400) for any other breaking changes that affect us (timezone handling, `format` token changes, `isValid` semantics, etc.).
4. Once landed on `trunk`, the narrow workaround commit in #77954 can be reverted or kept — whichever is cleaner with the broader fix.

### Approach for the PR

1. Bump `date-fns` everywhere to `^4.1.0` so the workspaces are aligned.
2. Verify all unit tests pass without modifying assertions.
3. Manually verify the affected UIs in the editor: post date/time scheduling, DateTimePicker / TimePicker / DateCalendar / DateRangeCalendar in Storybook, and DataViews date-range filters.

@manzoorwanijk @vishnupprajapat I'd like to propose an alternative plan.

I don't know yet if there are other breaking changes to address in the update to `v4`, but re. the testing mock incompatibility, I think that a better approach could be to rewrite the test mock to be `v4` compatible.

In fact, the native `Date` constructor does accept a `Date` object. `MockDate` is stricter than the thing it's mocking. . That's a bug in our mock layer, not in our source code or in `date-fns`.

My suggested plan:

#### PR A: let's fix the mock first, without updating `date-fns` or touching any source code.

A quick research via an AI agent suggesting using `mockDateOptions.fallbackFn` (`node_modules/timezone-mock/index.js` lines 42–43, 49–50) — `timezone-mock` already exposes a hook for unhandled types. Setting `timezoneMock.options({ fallbackFn: (p) => new (timezoneMock._Date)(p?.valueOf?.() ?? p) })` once in setup sidesteps the assertion without monkey-patching. This is the cleanest option and uses an existing extension point.

#### PR B: update to `v4`, fix what's broken

Having compatible tests from the previous PR will help keeping the scope small and increasing the confidence in making non-breaking changes. Potential candidates:

- format token changes in v4. v4 changed/removed some Unicode tokens; if any of our tests assert on formatted output we may need small updates. (Most of our formatting goes through @wordpress/date, not date-fns/format, so risk is low — but worth grepping.)
- isValid semantics. v4 tightened isValid for non-Date values; dataviews/src/field-types/utils/is-valid-date-boundary.ts and parse-date-time.ts are worth running explicitly.
- @date-fns/utc 2.x peer-dep. @date-fns/utc@^2.1.1 is pinned to date-fns@^4. While you're on v3 in step 1, leave @date-fns/utc alone — it should still resolve, but be aware syncpack/peer warnings may show up; that's expected and goes away in step 2.


The narrow workaround in #77954 can be removed once these PRs are merged.


What do you think?

@ciampo I've completed an investigation into the points you raised. Here are the findings:

1. @date-fns/utc v1 → v2: The upgrade to v2 is essential for compatibility with date-fns v4. While v2 is more minimal and strictly removes runtime checks (delegating to TypeScript), the core getters and setters used for UTC normalization remain consistent. No direct functional regressions were found in our current usage across @wordpress/components.

2. @wordpress/date and Transitive Breaking Changes: @wordpress/date internally relies on moment and moment-timezone, and does not consume date-fns directly. The "transitive risk" appears minimal because:

The UTCDateMini (v2) instances passed to @wordpress/date still implement the standard Date interface getters (getFullYear, getMonth, etc.) which moment uses for reconstruction.
Formatting logic in @wordpress/date uses PHP-style tokens, meaning the Unicode-style token changes in date-fns v4 won't affect site-facing dates.
3. Direct date-fns/format usage: I grepped the codebase and found that direct usage of date-fns/format is extremely limited, primarily existing in unit tests (e.g., date-picker/test/index.tsx). All critical UI formatting is already routed through @wordpress/date.

Conclusion: Based on this, I believe it's safe to proceed with PR A (Mock Fix) globally in the Jest setup as discussed, followed by the systematic upgrade in PR B.
