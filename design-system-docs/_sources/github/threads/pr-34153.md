## Description

**Requires #36831 to be merged first — some build errors are expected until that PR gets merged, and this PR gets updated to include those changes**

Add the **experimental** `ConfirmDialog` component. 

The goal is to use this component to replace the usage of the native sync `confirm` that is bound to be deprecated at some point (see related issues for more info).

## TODO
- [ ] Test a11y aspects (test with a screen-reader and double-check accessibility standards).
- [ ] Allow the message prop to accept JSX as per @jsnajdr's suggestion [here](https://github.com/WordPress/gutenberg/pull/34153#discussion_r694811092).
- [ ] Discuss the style of the Modal title (see screenshot or screencast above). It doesn't look very nice with long texts: it could use some additional vertical line spacing and perhaps be centered?
- [ ] Discuss the "uncontrolled mode" - the feature that allows the component to be used standalone without the parent controlling it ([see](https://github.com/WordPress/gutenberg/pull/34153/files#diff-e32777881602a705edd80eac60b4cf2c06355834b488d06c61d38010dcb5e3d9) `README` for more details). Is it worth keeping it? Are we even going to use it in practice considering we'll probably use a [wrapper singleton component](https://github.com/WordPress/gutenberg/pull/34153#issuecomment-908342367) later (to be implemented in a follow-up PR) at the app top-level to implement the Confirm in the editor?
- [ ] Discuss the "multiple instances" scenario. Being async, it's possible. Is it important to handle at the component level? Or can we delegate it to a[ wrapper component](https://github.com/WordPress/gutenberg/pull/34153#issuecomment-908342367) at the App top level? More details [here](i).
- [ ] Discuss semantics of closing the dialog vs canceling. Right now, clicking the `x` icon, Cancel, pressing Escape, or clicking the overlay will close the dialog AND call the `onCancel` callback. I think this is correct UX-wise, except that we might not want to close/cancel upon clicking the overlay, as one could argue this is fragile as the user could easily misclick and close + cancel by accident. I do think that closing has a 1:1 relationship with canceling, though, so that if the dialog is closed this effectively means not confirming which means *canceling*.

The Context system is a way for components to adapt to the "context" they're being rendered in.

An example of how this is used is the [`Card` component](https://github.com/WordPress/gutenberg/blob/trunk/packages/components/src/card/card/component.js#L44-L54) — all of its subcomponents (e.g. `CardBody`, `CardHeader`...) will [use, by default, the same value for the `size` as the parent `Card` component](https://github.com/WordPress/gutenberg/blob/trunk/packages/components/src/card/card-body/hook.js#L23) — which results in all the components having all the correct spacing "auto-magically".

The Context system provides an API for components to:
- connect to the Context via `contextConnect`
- read the "computed" values from the context via `useContextSystem`

```jsx
function Confirm({ children }) {
  const [isOpen, setIsOpen] = useState(false);
  const [message, setMessage] = useState("Are you sure?");
  const listenersRef = useRef(new Set());

  const confirm = useCallback((message) => {
    setMessage(message);
    setIsOpen(true);
    return new Promise((resolve) => listenersRef.current.add(resolve));
  }, []);

  return (
    <ConfirmProvider value={confirm}>{children}</ConfirmProvider>
    <ConfirmDialog
      isOpen={isOpen}
      setIsOpen={setIsOpen}
      onConfirm={() => {
        listenersRef.current.forEach((listener) => listener(true));
      }
      onCancel={() => {
        listenersRef.current.forEach((listener) => listener(false));
      }
    >
      {message}
    </ConfirmDialog>
  );
}

function App() {
  return (
    <Confirm>
      ...
    </Confirm>
  );
}
```

### fullofcaffeine on 2021-09-10T01:45:18Z

I got rid of the imperative approach in favor of a naive, inline declarative approach. I still need to rename it to `ConfirmDialog`, still WIP, subject to changes as the discussion develops.

It's mostly self-contained and you could use it without much controlling code from the parent. It knows how to show/hide itself, but can also be controlled by binding the `isOpen` prop to some external parent state. The rationale is that it should be simple to use without much-supporting code, but easily controllable by its parent if needed. For example, you could add it as part of a component like this:

```js
<Confirm message='Are you sure?' onConfirm={ confirmSomething } />
```

And that's all you need for it to show to automatically once the parent component is mounted. 

A more complex example can be found [here](https://github.com/WordPress/gutenberg/pull/34153/files#diff-9db57b9cdf51b69cdf06f8beb7783bafd7bff211e30853630a84d33c73f59377R83-R91), which replaces the native `confirm` in the `PostVisibility` component with `Confirm` (the `PostVisibility` changes will be eventually removed from this PR). Here's a video:


https://user-images.githubusercontent.com/81248/132787445-65c1887e-c977-44aa-ad94-058f489bef3c.mp4


Some observations:

1. Having the component rendered inline, as a child of the component that's going to use it, is as simple as it gets and is closer to the imperative usage. No additional code is needed, apart from adding it in the component that's going to use it and setting up the callbacks. The `Portal` will make sure it's rendered at the root of the `body` element. The high `z-index` will also make sure it's rendered on top of everything else (see video).
2.  It's simple to use, but not as elegant and DRY as the singleton/context approach you've presented @diegohaz. Also, while the actual DOM element is added in the `body`, one might argue that the location of the React component in the React tree might be semantically wrong or at the very least, confusing. In my example, it's added as a child of the `PostVisibility` component. Might not be a huge deal, but it's worth mentioning.
3. Also, while in theory, it would handle multiple instances shown at the same time (one rendered in front of the other), it doesn't work well because of the `useFocusOutside` hook used in the `Modal` component. As soon as another `Confirm` is created, the previous dispatches an `onBlur` event, and the `onRequestClose` event is called, and the previous modal will be closed. I think this provides a great argument in favor of the wrapper/singleton approach @diegohaz described. With the native `confirm` we didn't have this problem because it's sync, and there's no way another `confirm` can be triggered while you already have a confirm dialog active, but this can be a problem for the async version. In theory, another `Confirm` could be triggered, and we need a way to "queue" them so no input is lost. I can see your singleton pseudo-imperative approach handles multiple calls (by keeping a collection of callbacks to call), in sequence if needed.
4. UX and styling and accessibility should be reviewed/discussed, there are some hints from a PR @Mamaduka linked, by @glendaviesnz. I'll read through it tomorrow.

The idea is to keep this PR restricted to the `ConfirmDialog` component, discuss its API, wrap it up, and then work on implementing a singleton, top-level `Confirm` that can be tapped through a `Context`, like @diegohaz exemplified [here](https://github.com/WordPress/gutenberg/pull/34153#issuecomment-908342367) in a follow-up PR. Let me know if you think that's a good plan, and let me know your thoughts about its current implementation.

> I guess we need to understand better the differences between "dialog" and "modal" (I'd probably add "alert" too), and see which one applies better in this case

"Dialog" is the element type. "Modal" is a state of a dialog, which means the document should enter a new "mode" where all elements outside are inaccessible. In practice, most dialogs (including the ones generated by the system, like confirm, alert, select popups etc.) have the "modal" state. There's still no consensus on how a non-modal dialog should behave, but people usually implement them as popovers.

I'd be okay with just `Confirm`. But I'd say `ConfirmDialog` is a better name here. `window.alert` also opens a dialog, but it has a specific role of [alertdialog](https://www.w3.org/TR/wai-aria-1.2/#alertdialog). If we create such a component in the future, we should probably name it `AlertDialog`. So, to keep consistency, I'd go for `ConfirmDialog` here.

+# `ConfirmDialog`
+
+<div class="callout callout-alert">
+This feature is still experimental. "Experimental" means this is an early implementation subject to drastic and breaking changes.
+</div>
+
+`ConfirmDialog` displays a confirmation dialog as a `Modal`, with `OK` and `Cancel` buttons. It's confirmed by clicking `OK` or by pressing the `Enter` key. It's cancelled by clicking `Cancel` or by pressing the `ESC` key or clicking outside the dialog focus (i.e, the overlay).
+
+It's built on top of `Modal`, so you can override any of the `Modal` props if you'd like. This also means that it's added as a child of the `body` element in the DOM tree through a React `Portal`, regardless of where it's declared in the React tree.
+
+## Usage
+
+`ConfirmDialog` has two main implicit modes: controlled and uncontrolled.
+
+### Uncontrolled mode
+
+Allows the component to be used standalone, just by declaring it as part of another React's component render method:
+  * It will be automatically open (displayed) upon mounting;
+  * It will automatically close itself when the `x`, `Cancel`, `Confirm` or overlay is clicked;
+  * `onCancel` is not mandatory but can be passed. Even if passed, the dialog will still be able to close itself.
+
+Activating this mode is as simple as omitting the `isOpen` prop. The only mandatory prop, in this case, is the `onConfirm` callback.
+
+```jsx
+import {
+  __experimentalConfirmDialog as ConfirmDialog
+} from '@wordpress/components';
+
+function Example() {
+  return (
+    <ConfirmDialog onConfirm={ () => console.debug(' Confirmed! ') }>
+  )
+}
+```
+
+### Controlled mode
+
+Let the parent component control when the dialog is open/closed. It's activated when a boolean value is passed to `isOpen`:
+  * It will not be automatically closed. You need to let it know when to open/close by updating the value of the `isOpen` prop;
+  * Both `onConfirm` and the `onCancel` callbacks are mandatory props in this mode;
+  * You'll want to update the state that controls `isOpen` by updating it from the `onCancel` and `onConfirm` callbacks.
+
+
+```jsx
+import {
+  __experimentalConfirmDialog as ConfirmDialog
+} from '@wordpress/components';
+
+function Example() {
+  const [ isOpen, setIsOpen ] = useState( true );
+
+  const handleConfirm = () => {
+    console.debug( 'Confirmed!' );
+    setIsOpen( false );
+  }
+
+  const handleCancel = () => {
+    console.debug( 'Cancelled!' );
+    setIsOpen( false );
+  }
+
+  return (
+    <ConfirmDialog isOpen={ isOpen } onConfirm={ handleConfirm } onCancel={ handleCancel }>
+  )
+}
+```
+
+### Unsupported: Multiple instances
+
+Multiple `ConfirmDialog's is an edge case that's currently not officially supported by this component. At the moment, new instances will end up closing the last instance due to the way the `Modal` is implemented (more specifically, because of the use of the `onFocusOutside` to detect a blur in order to close it). This will end up automatically cancelling the previous instance, which might or might not be what you want.
+
+Suppose you need to handle multiple confirmations without discarding other instances. In that case, it might be better to have a singleton wrapper component that provides a context-based API to trigger the dialog, keeping track of multiple instances. Here's an [example](https://github.com/WordPress/gutenberg/pull/34153#issuecomment-908342367).

Sure! This union type was the way I found to tell TypeScript to type a bit differently depending on the type of `isOpen`. If it's `undefined` (uncontrolled), then it gets uses the type structure defined in `Props`, if `isOpen` is `boolean`, then it uses the one to the right of the union operator.

+	props: WordPressComponentProps< OwnProps, 'div', false >,
+	forwardedRef: Ref< any >

+	const {
+		isOpen,
+		message,
+		onConfirm,
+		onCancel = () => {},
+		...otherProps
+	} = useContextSystem( props, 'ConfirmDialog' );
+
+	const cx = useCx();
+	const wrapperClassName = cx( styles.wrapper );
+
+	const [ _isOpen, setIsOpen ] = useState< Boolean >();

+		// We only allow the dialog to close itself if `isOpen` is *not* set.
+		// If `isOpen` is set, then it (probably) means it's controlled by a
+		// parent component. In that case, `selfClose` might do more harm than
+		// good, so we disable it.
+
+		const isIsOpenSet = typeof isOpen === 'boolean';
+		setIsOpen( isIsOpenSet ? isOpen : true );
+		setSelfClose( ! isIsOpenSet );
+	}, [ isOpen ] );
+
+	// @todo improve type, should handle keyboard and mousevent
+	const handleEvent = ( callback: ( event: SyntheticEvent ) => void ) => (
+		event: SyntheticEvent
+	) => {
+		callback( event );
+		if ( _selfClose ) {
+			setIsOpen( false );
+		}
+	};
+
+	const handleEnter = ( event: KeyboardEvent< HTMLDivElement > ) => {
+		if ( event.key === 'Enter' ) {
+			handleEvent( onConfirm )( event );
+		}
+	};
+
+	return (
+		<>
+			{ _isOpen && (
+				<Modal
+					title={ message }
+					overlayClassName={ wrapperClassName }
+					onRequestClose={ handleEvent( onCancel ) }
+					onKeyDown={ handleEnter }

+						>

+						</Button>

+# `ConfirmDialog`
+
+<div class="callout callout-alert">
+This feature is still experimental. "Experimental" means this is an early implementation subject to drastic and breaking changes.
+</div>
+
+`ConfirmDialog` displays a confirmation dialog as a `Modal`, with `OK` and `Cancel` buttons. It's confirmed by clicking `OK` or by pressing the `Enter` key. It's cancelled by clicking `Cancel` or by pressing the `ESC` key or clicking outside the dialog focus (i.e, the overlay).
+
+It's built on top of `Modal`, so you can override any of the `Modal` props if you'd like. This also means that it's added as a child of the `body` element in the DOM tree through a React `Portal`, regardless of where it's declared in the React tree.
+
+## Usage
+
+`ConfirmDialog` has two main implicit modes: controlled and uncontrolled.
+
+### Uncontrolled mode
+
+Allows the component to be used standalone, just by declaring it as part of another React's component render method:
+  * It will be automatically open (displayed) upon mounting;
+  * It will automatically close itself when the `x`, `Cancel`, `Confirm` or overlay is clicked;
+  * `onCancel` is not mandatory but can be passed. Even if passed, the dialog will still be able to close itself.
+
+Activating this mode is as simple as omitting the `isOpen` prop. The only mandatory prop, in this case, is the `onConfirm` callback.
+
+```jsx
+import {
+  __experimentalConfirmDialog as ConfirmDialog
+} from '@wordpress/components';
+
+function Example() {
+  return (
+    <ConfirmDialog onConfirm={ () => console.debug(' Confirmed! ') }>
+  )
+}
+```
+
+### Controlled mode
+
+Let the parent component control when the dialog is open/closed. It's activated when a boolean value is passed to `isOpen`:
+  * It will not be automatically closed. You need to let it know when to open/close by updating the value of the `isOpen` prop;
+  * Both `onConfirm` and the `onCancel` callbacks are mandatory props in this mode;
+  * You'll want to update the state that controls `isOpen` by updating it from the `onCancel` and `onConfirm` callbacks.
+
+
+```jsx
+import {
+  __experimentalConfirmDialog as ConfirmDialog
+} from '@wordpress/components';
+
+function Example() {
+  const [ isOpen, setIsOpen ] = useState( true );
+
+  const handleConfirm = () => {
+    console.debug( 'Confirmed!' );
+    setIsOpen( false );
+  }
+
+  const handleCancel = () => {
+    console.debug( 'Cancelled!' );
+    setIsOpen( false );
+  }
+
+  return (
+    <ConfirmDialog isOpen={ isOpen } onConfirm={ handleConfirm } onCancel={ handleCancel }>
+  )
+}
+```
+
+### Unsupported: Multiple instances
+
+Multiple `ConfirmDialog's is an edge case that's currently not officially supported by this component. At the moment, new instances will end up closing the last instance due to the way the `Modal` is implemented (more specifically, because of the use of the `onFocusOutside` to detect a blur in order to close it). This will end up automatically cancelling the previous instance, which might or might not be what you want.
+
+Suppose you need to handle multiple confirmations without discarding other instances. In that case, it might be better to have a singleton wrapper component that provides a context-based API to trigger the dialog, keeping track of multiple instances. Here's an [example](https://github.com/WordPress/gutenberg/pull/34153#issuecomment-908342367).
+
+### Props
+
+### `isOpen`: `boolean`
+
+Defines if the dialog is open (displayed) or closed (not rendered/displayed). It also implicitly toggles the controlled mode if set or the uncontrolled mode if it's not set.
+
+### `onConfirm`: `( event: SyntheticEvent ) => void`
+
+- Required: Yes
+
+The callback that's called when the user confirms. A confirmation can happen when the `OK` button is clicked or when `Enter` is pressed.
+
+### `onCancel`: `(event: SyntheticEvent ) => void`
+
+- Required: Yes if `isOpen` is set, No if `isOpen` is not set
