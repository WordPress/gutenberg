## Body

## What?
Follow up to #66806.

Migrates `View` away from Emotion while preserving polymorphic `as` behavior, refs, valid DOM/SVG prop forwarding, and legacy `css` prop consumption.

## Why?
`View` is a core dependency for many components, so this validates a high-risk part of the broader Emotion migration without changing public rendered markup or `components-*` class names.

## How?
- Adds an internal `PolymorphicElement` utility for `as`, ref forwarding, and intrinsic prop filtering.
- Updates `View` to render through that utility instead of `@emotion/styled`.
- Preserves source-order cascade where affected components still compose Emotion styles through `useCx`.

<details>
<summary>Implementation notes</summary>

- The intrinsic prop allowlists are derived from `@emotion/is-prop-valid`, but split by element type so SVG-only props are filtered from HTML elements.
- The legacy `css` prop is consumed by `View` so it does not leak to the DOM after removing `styled.div`.
- Some snapshots change because Emotion-generated styles are merged differently or removed from `View`-rendered elements.

</details>

> So, given that we have at least 3–5 components here that would have regressed without the style composition changes, I think that shows that this is definitely a breaking change. Not just for `View`, but possibly even for higher-level components that pass its `className` prop down to a `View` (if consumers were doing similar things with their own Emotion-generated styles).

It can be a breaking change when:

- component A is refactored away Emotion;
- a consumer uses Emotion and passes multiple Emotion fragments to `cx(...)` and then to component A,  and those fragments can set the same CSS property or same nested selector/property

Which also means that technically the `Divider`, `Surface` and `Truncate` changes could also be considered breaking?

Should we publish a deprecation and announce that the change will be carried over in two WordPress releases (7.3) ?

```diff
+function isValidIntrinsicElementProp( prop: string, element: string ) {
+	if (
+		prop.startsWith( 'data-' ) ||
+		prop.startsWith( 'aria-' ) ||
+		( prop.charCodeAt( 0 ) === 111 &&
+			prop.charCodeAt( 1 ) === 110 &&
+			prop.charCodeAt( 2 ) < 91 )
+	) {
+		return true;
+	}
+
+	if ( knownIntrinsicElementProps.has( prop ) ) {
+		return true;
+	}
+
+	const ownerDocument = globalThis.document;
+	if ( ownerDocument ) {
+		return prop in ownerDocument.createElement( element );
+	}
+
+	return prop === prop.toLowerCase();
+}
```

`isValidIntrinsicElementProp` creates a new DOM element for every prop check (`ownerDocument.createElement(element)`), which can be a hot path because `View` is widely used and will filter many props per render. Cache a single element instance per intrinsic tag so the validation is O(1) without repeated allocations.
