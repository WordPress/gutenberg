Just wanted to add that another approach is to leave those function props as `undefined` by default, and use the optional chaining syntax when invoking them, e.g.

```js
const handHover = () => {
  // do stuff

  onHover?.();
}
```

This has the the advantage of relying solely on native APIs/syntax (plus it avoids initialising those values to their default value). But this is more of a personal preference / micro-optimisation, so we can keep the code as-is.

There wasn't anything _wrong_ in your code — you were just refactoring the component from class to function — my suggestion here is more of an improvement on top of your changes. I believe the code is cleaner (and potentially causes less re-renders)

Here's the reasoning that brought me to suggest `useRefEffect`:

- While reviewing your PR, I was having a look at the `list` state, and noticed that it was used to hold a `ref`.
- Now, we could have used `useRef` instead, but then I noticed that `list` was used as a dependency of the `useEffect` hook — switching to `useRef` would meant that changes to `list` wouldn't trigger the `useEffect` hook.
- The proper way to refactor the code, then, would be to rewrite `list` to use `useCallback` to hold the `ref`. The code in `useEffect` (and its dependencies) could have moved to the body of `useCallback` too
- Finally, I realised that the pattern that I just described is implemented in a custom hook called [`useRefEffect`](https://github.com/WordPress/gutenberg/blob/trunk/packages/compose/src/hooks/use-ref-effect/index.ts)
