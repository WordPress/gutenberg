## Body

## What

Adds a `size` category to the dimension token family with eight design tokens for element sizing:

| Token | Value | Description |
|-------|-------|-------------|
| `--wpds-dimension-size-5xs` | 4px | Notification indicators |
| `--wpds-dimension-size-4xs` | 8px | Visual size for small interactive elements like resize handles |
| `--wpds-dimension-size-3xs` | 12px | Small markers |
| `--wpds-dimension-size-2xs` | 16px | For small controls like checkboxes and radios, or small decorative icons |
| `--wpds-dimension-size-xs`  | 20px | For medium sized icons |
| `--wpds-dimension-size-sm`  | 24px | For icons and small buttons |
| `--wpds-dimension-size-md`  | 32px | For medium-sized buttons and inputs |
| `--wpds-dimension-size-lg`  | 40px | Default size for buttons and inputs |

## Why

Components like buttons, checkboxes, icons, tabs, and other interactive controls currently use hardcoded pixel values for sizing. A shared set of size tokens provides a consistent, predictable scale that can be referenced across components, reducing ad hoc values and making it easier to maintain visual consistency.

## How

- Added a `size` group to `tokens/dimension.json` with `5xs` through `lg` entries, each referencing an existing space primitive (`space.10` through `space.80`) so sizes align with the base spacing scale (4px–40px), including a 20px step at `xs` via `space.50`.
- Added an `ElementSize` TypeScript type in `terrazzo.config.ts` so the scale is available as a union type (`'5xs' | '4xs' | '3xs' | '2xs' | 'xs' | 'sm' | 'md' | 'lg'`).
- Rebuilt prebuilt outputs (CSS custom properties, JS token lists, fallback values, TypeScript types, and docs).

@jasmussen I agree, but I think that’s a separate issue and one we can probably address by making the size ↔ value mapping feel more logical. For example, if we centre around the idea that `md` represents the default size for controls like buttons and inputs, then something like this could make sense:

```text
4xs - 4px
3xs - 8px
2xs - 12px
xs  - 16px
sm  - 24px
md  - 32px
lg  - 40px
```

That works if the mental model is control-based, but that won’t necessarily be universal. For example if the reference point is icons, then `md = 32px` will feel wrong.

In that case, maybe there’s an argument for aligning `md` to the most commonly referenced size instead. At a guess that would be something like:

```text
3xs - 4px
2xs - 8px
xs  - 12px
sm  - 16px
md  - 24px
lg  - 32px
xl  - 40px
```

The challenge is that different UI primitives have different natural defaults, so it’s always going to be difficult to make sizing feel universally ergonomic across all contexts. Documentation can help establish expectations, but the naming itself still needs to carry meaning.

The important point, in my view, is to provide a sanctioned set of semantic sizing tokens for elements. The exact mapping is always going to involve trade-offs, unless we break things down into additional categories. E.g. instead of a single `dimension/size` scale, we could have multiple; `dimension/size/control`, `dimension/size/avatars`, `dimension/size/chips`, but that would increase the token surface area _significantly_.

FWIW the previous convention is effectively what already exists as primitive tokens:

https://github.com/WordPress/gutenberg/blob/47ae633fd3b6e597cbb7171eee3d8ad77980f55e/packages/theme/tokens/dimension.json#L5-L46

These aren’t published because they don’t carry semantic meaning on their own.

### jameskoster on 2026-05-27T11:11:51Z

URL: https://github.com/WordPress/gutenberg/pull/76545#issuecomment-4553988844

I was chatting with @ciampo about this yesterday. I still think that however we approach it is going to result in trade-offs. For instance one angle would be to say that ‘medium’ always equals a specific value (let’s say 32px) regardless of the scale. This would ensure coherence and predictability between scales like size, gap, padding. However it falls apart when we consider scales like surface-width which do not go that low, or typography where the idea of size shifts down compared to other scales. The other drawback is that the t-shirt sizes just end up being a proxy for the primitives which kind of defeats the purpose—they’re supposed to carry meaning.

I think another important point is that generally speaking end users will not be consuming these tokens directly. For the most part they’re intended to be used by the system. So as long as we have good documentation and examples then users should be able to infer any nuance. 

With all that said, I think the most promising idea so far is to treat each scale independently and maybe centre the size/value mapping around the idea of medium being the most common/default value. Almost saying; if you’re unsure what size to use, use medium. To put that into practice:

```text
GAP
Medium = 16px (the gap between form fields, paragraphs of body text)

PADDING
Medium = 24px (card padding)

FONT-SIZE
Medium = 13px (body text)

LINE-HEIGHT
Medium = 20px (body text)

SURFACE-WIDTH
Medium = 720px (card max-width)

ELEMENT-SIZE
Medium = 32px (Most icon buttons, ‘compact’ controls)
```

This way there is at least some logical relationship we can document, even if not all scales include the same sizes, or all sizes map to the same values.
