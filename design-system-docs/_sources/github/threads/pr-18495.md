## Description
<!-- Please describe what you have changed or added -->
Added a `Text` mixin and component to `@wordpress/components` which provides typography styles in-line with the [`wp-admin-iterations`](https://www.figma.com/file/7xhcuCZhQKqgRsgLTof3AY/WP-Admin-Iterations?node-id=59%3A3149) experiment.

This addition provides a `text` mixin (e.g. `text({ variant: 'body.small' })`) that can be consumed in other components which are also using `emotion` (probably focussed more on internal usage) in addition to a `Text` component (e.g. `<Text variant="body.small">`).

This component is usable on web AND mobile, including styles.

To keep this PR small and easily reviewable I haven't included the following additions that I'll attempt to add in a future PR:
- additional props for the `Text` component e.g. `color`, `textAlign`,  `margin`, `padding` etc etc
- start to compose the `text` mixin into other components in order to improve the consistency of typography across the components

Related PR: #18244

### jameslnewell on 2019-11-21T20:58:13Z

URL: https://github.com/WordPress/gutenberg/pull/18495#issuecomment-557268944

> How are we planning to use this component?

I'd like to see this component/mixin used anywhere there is text - both within `@wordpress/components` and the consuming application. Within `@wordpress/components` a good example would be the `BaseControl`'s label and help.

The goal of using the component/mixin everywhere would be:

- to keep typography styles consistent across `gutenberg` and any other projects consuming `@wordpress/components`
- to make it easy to update typography styles across :allthethings: from one place when the styles change versus updating all the hard coded rules scattered around the place
- to encapsulate all styling within each component so they don't rely on a reset and can work in any application

> Are we planning a Refactor to existing components?

Eventually yes, I'd like to see all existing components refactored to use the component/mixin. However, for now, while we're not 💯sold on CSS-in-JS I'd limit its usage to any new components that are built in CSS-in-JS or any existing components that are refactored to CSS-in-JS (for some other purpose).

> Should we do it in one PR or iteratively?

For now, continuing on from the above answer, my gut feeling would be to just update the current CSS-in-JS components for now.

> When working on several components, how do we choose whether to use this component or just a regular div or p or whatever?

If the component will contain text as an immediate child then it likely makes sense to use this component e.g. for `BaseControl`'s label and help components, in place of a h1 (`<Text variant="title.large" as="h1">...</Text>`).

For more complex cases where a component has the visual appearance multiple things the mixin probably makes more sense e.g. 

```jsx
const HeroTitle = styled.h1`
  ${ text( {variant: 'title.large' } ) }
  ${ otherThing1() }
  ${ otherThing2() }
`;
```

> Do we foresee any performance impact if we start using this component everywhere?

There is always a cost to an additional wrapping component and if there are any existing performance issues due to large/deep component trees or unnecessary renders this might further complicate the problem. However, there are likely more effective solutions to those problems than avoiding an additional wrapping component in a few places. Otherwise, I wouldn't expect the impact to be noticeable. 

I can create a perf test if you'd like.
