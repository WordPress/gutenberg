### jeryj on 2025-08-25T19:51:08Z

URL: https://github.com/WordPress/gutenberg/pull/71252#issuecomment-3221541984

@aduth Went digging. Here's what I found:

This concept was first added in 2017 in https://github.com/WordPress/gutenberg/pull/3235. There is no specific mention or explanation of [`componentWillUnmount` cancelling the blur check](https://github.com/WordPress/gutenberg/pull/3235/files#diff-abf08faa9d622650de4925d5d2664ecaa7626d9a9bc86aa65ae071f60c704c02R16-R18). It's mentioned that the HOC is [built upon this closed PR's concept for fixing a blur event bug ](https://github.com/WordPress/gutenberg/pull/2974/)within the Clipboard Button component. The clipboard component _does_ have an[ `componentWillUnmount` that destroys the clipboard contents](https://github.com/WordPress/gutenberg/pull/2974/files#diff-47d2ff2409d037d3d54056d9ba6c3945606af986fa6f7249f1d54cd120586feaL28-L31) (Note linked code is collapesed). It feels like a stretch, but maybe it was scaffolded off the clipboard component, and it didn't cause any obvious issue, so it was left in?

There is no mention of needing it to fix a specific bug. It has just been there since the beginning. Then, [when it was changed to a hook, it was added](https://github.com/WordPress/gutenberg/pull/27369/files#diff-9732f79a944181759774e91a627dc5657483415a8f7dd2a703f16900cec84348R107-R112) because they were rewriting the HOC. [The philosophy to not make changes unless necessary is clear ](https://github.com/WordPress/gutenberg/pull/27369#discussion_r537237292), so the basis for the unmount goes back to the original PR. There is [some related conversation about why the cancelling is happening](https://github.com/WordPress/gutenberg/pull/27369#discussion_r539054687), but it's more for when the callback becomes null rather than the unmounting.

So, I don't see any specific conversation around why specifically it was added or what it fixes. If I were arguing for its inclusion, I would say it's because we shouldn't leave a dangling timeout without being cleaned up. This seems potentially valid?

If so, then a possible fix here isn't to remove the unmount, but to cancel the timeout and then immediately execute the callback:

```
// Cancel blur checks on unmount.
useEffect( () => {
	return () => {
	    cancelBlurCheck();
	    currentOnFocusOutsideRef.current();
	 }   
}, [] );
```

The issues with doing that would be:
- What event do we return for `currentOnFocusOutsideRef.current( event );`?
- `currentOnFocusOutsideRef.current( event );` would run immediately instead of after the next tick. That [causes issues since onClose could run before focus has resolved](https://github.com/WordPress/gutenberg/pull/71256#discussion_r2291104628).

Long story short: Since the unmount cancelling the timeout is causing a bug for us, and I don't see a clear reason why it was added, I feel comfortable with removing the unmount hook if we don't see it causing any new problems.

> What do you think? Is this taking things too far?

I think it may be riskier, as the normal flow and unmount flow would be separate. For example:

- `queueMicrotask` might not run at the same time in the cycle as `setTimeout( () => {}, 0 );`
