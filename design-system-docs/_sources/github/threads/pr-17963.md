## Description
![Screen Shot 2019-10-15 at 4 42 34 PM](https://user-images.githubusercontent.com/2322354/66868232-f6575080-ef6a-11e9-8df5-c856c6ede635.png)

This update adds a new `<Card />` component to `@wordpress/components`, as well as a collection of flexible sub-components that can be used to composed various user interfaces. The initial sub-components include:

* `<CardBody />`
* `<CardDivider />`
* `<CardFooter />`
* `<CardMedia />`

### ✨ Visual Design

The `<Card />` component's designs are very minimal. The `border-radius`, `border-color`, and `padding` are based on the aesthetics and values found within `@wordpress/components` and Gutenberg.

### 🤔 Component API Design

`<Card />` drew it's component **API** (and it's composition) from other frameworks/libraries like [Bootstrap](https://getbootstrap.com/docs/4.0/components/card/) and [Material UI](https://material-ui.com/components/cards/).

An example for how a `<Card />` UI my be composed looks something like this:

```jsx
import {
	Card,
	CardBody,
	CardDivider,
	CardFooter,
	CardHeader,
	CardMedia
} from '@wordpress/components';

const Example = () => (
	<Card>
		<CardHeader>
			...
		</CardHeader>
		<CardBody>
			...
		<CardBody>
		<CardDivider />
		<CardBody>
			...
		<CardBody>
		<CardMedia>
			<img src="..." />
		</CardMedia>
		<CardHeader>
			...
		</CardHeader>
	</Card>
);
```

## Types of changes

### 💅 Styled Components

This is new and experimental! For the `<Card />` styles (and it's sub-components), I introduced and used [styled-components](https://www.styled-components.com) to take care of the CSS.

I've seen a couple of PRs attempting this as well:
https://github.com/WordPress/gutenberg/pull/17673
https://github.com/WordPress/gutenberg/pull/17614

The benefits of a CSS-in-JS solution are many. Those PRs do a fantastic job at walking through several key benefits - **especially** for native mobile.

I think it's best feature is... components will be styled and working out-of-the-box. If you build a React component with styled components, you can `import` the component perfectly styled straight from `node_modules`. No fussing with Webpack, Grunt, compilers or scripts. It provides for a wonderful developer experience. Not only that, styled components will provide features like [theming](https://www.styled-components.com/docs/advanced#theming). This will make it much easier for folks to consume `@wordpress/components` to build their own interfaces - for their own blocks, plugins, or interfaces outside of Gutenberg.

An incredible example of this experience can be found in the [Material UI React library](https://github.com/mui-org/material-ui). All of the components come pre-styled and can be themed (Note: They use an alternate CSS-in-JS library, not styled components).

#### 🌲 Preserving standard CSS styling

This is 💯 important. To do this, I added a standard CSS className to the various components (e.g. `components-card-header`), just like the rest of `@wordpress/components`. Although these classNames aren't responsible for direct styling, they enable:

* Style overrides via standard CSS selector targeting
* A *way* better sense of `html` composition when debugging (e.g. Inspect Element)
* A way to target selectors via Jest/Enzyme

#### 🎨 Color Utils

Since I ventured into CSS-in-JS for the pull request, I needed a way to use the same colour values we have from `.scss` but for `.js` code. To do this, I built a `color()` utility, which lives within the new `components/utils` directory.

It can be used like this:

```js
color( 'blue.wordpress.700' );
// #00669b
```

The `.` notation represents the nested colour values I have stored in the constant `color.values.js` map (`Object`).

### koke on 2019-10-17T14:58:54Z

URL: https://github.com/WordPress/gutenberg/pull/17963#issuecomment-543215665

I really like this initiative and how things are looking. I have some concerns about the API design.

First, I think it would be beneficial to define better what a `Card` is. I think the current description in the [README](https://github.com/WordPress/gutenberg/blob/bfde12278c7e773d7011e48b75d7785e9fd6c5b0/packages/components/src/card/README.md) is too generic:

> Card provides a flexible and extensible content container

As a developer, if I don't know what a card is already, it's not easy to understand when I would use one. I like the definition in [Material](https://material.io/develop/ios/components/cards/):

> Cards contain content and actions about a single subject

Similarly on [StackOverflow's system](https://stackoverflow.design/product/components/cards):

> Cards are used to group similar concepts and tasks together to make information easier to scan, read, and act on

This implementation of Card seems to fit those descriptions. The current styling is very lightweight, but it clearly groups related things together. 

----

When I look at how to use this component, there are some things that caught my attention. I come from mobile development, and I'll warn you I might have some biases about what APIs should look like for that, but I believe these suggestions would be more universal.

Having to declare the inner components seems problematic. It might be the obsessive programmer in me, but the fact that you can declare multiple `CardBody` inside a card, or put a `CardFooter` before a `CardHeader` doesn't seem right. We have been inserting dividers manually in the [react native version](https://github.com/wordpress-mobile/gutenberg-mobile), but I believe we can do better.

I've been playing around with the code to get a feel for what I'd expect the API to be, and I re-did some of the stories:

```jsx
export const headerAndFooter = () => {
	return (
		<Card
			header={ <CheckboxControl label="Some control" /> }
			footer="Caption"
			footerShady={ true }
		>
			<DummyImage />
		</Card>
	);
};
```

Header and footer are optional things, but we know that we want at most one of each, that the header goes before the body, and the footer goes at the end. Instead of leaving it up to the developer, we can ensure a maximum of one by passing the header and footer via props. This also means that whatever the component children are, that goes into the body.

My changes so far to make that work: https://gist.github.com/koke/33cdd87a0c23d50402b777afa01a2afc

We still have to solve the divider and media components.

For dividers, I think we could add a `CardList` or `CardGroup` component that automatically inserts dividers between its children.

For media, I think the challenge is that we're adding padding to the card body instead of the children, but we still want to have some things that are full width. I'm no CSS expert, so I'll leave that one unanswered for now, but it feels like it should be solvable without adding extra markup from the outside. But we can also leverage [React.Children.map](https://reactjs.org/docs/react-api.html#reactchildrenmap) to add wrappers for each child element if necessary.

### ItsJonQ on 2019-10-24T14:01:04Z

URL: https://github.com/WordPress/gutenberg/pull/17963#issuecomment-545932081

@youknowriad Oh sure! Apologies. That makes sense :)

With regular CSS, I'm guessing we would like to modify certain styles in a `rtl` situation.
That flag needs to be identified somehow.

Usually it's with `<html dir="rlt" />`

Or maybe something like `<body class="rtl">`

With that, you can modify (regular) CSS like so:

```
.button { ... }

.rtl .button { ... }

html[dir="rtl"] .button { ... }
```

You can take the same approach with CSS-in-JS.

They have a handy feature in their [ampersand syntax](https://www.styled-components.com/docs/basics#pseudoelements-pseudoselectors-and-nesting).

So you can do something like this:


```
const Button = styled.button`
	...

	.rtl &,
	html[dir="rtl"] & {
		...
	}
`
```

Which will compile to:

```
.sc-12ad91 { ... }

.rtl .sc-12ad91 { ... }

html[dir="rtl"] .sc-12ad91 { ... }
```

> we need some dev education for people to be aware of these

💯 The concepts of variables and mixins are the same as SASS and other preprocessors but the syntax is definitely different. 

A design system docs website should document the mixins just like component. 

> Is this a common pattern in CSS in JS? Is there any prior art out there?

Yep, mixins are pretty standard...

- [Official `styled-components` tips and tricks](https://github.com/styled-components/styled-components/blob/master/packages/styled-components/docs/tips-and-tricks.md#using-javascript-to-our-advantage)
-  [That's what `space`, `layout`, `typography`, `color` in `styled-system` are](https://github.com/styled-system/styled-system#usage)
- There are [numerous](https://www.npmjs.com/package/styled-tools) [other](https://www.npmjs.com/package/styled-map) [packages](https://www.npmjs.com/package/styled-components-spacing#using-the-mixins) using mixins

I haven't seen mixins used for RTL before (but I haven't really seen enough people supporting RTL in general).

<details><summary>...</summary>

Mixins can be used to apply fixed styles to a component or used to create a reusable component which is stylable via props.

```jsx

const sizes = {small: '12px', large: '16px'};

const text =({size, align}) => css`
  font-size: ${sizes[size]};
  text-align: ${align};
`;

// we've created the component with a specific set of styles that can't be modified
const AFixedTextComponent = styled.p`
  ${text({size: 'large', align: 'center'})
`

// we're not calling `text` this time so `styled-components` will call it with any props passed to the component
const Text = styled.p`
  ${text}
`;

<Text size="large" align="center">Blah</Text>
```
