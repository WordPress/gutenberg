### mirka on 2024-01-13T06:06:56Z

URL: https://github.com/WordPress/gutenberg/issues/51102#issuecomment-1890336023

It looks like it had a default since the [beginning](https://github.com/WordPress/gutenberg/blame/trunk/packages/components/src/custom-gradient-picker/constants.ts#L6-L7).

I'd assume that it's this way because a gradient needs at least two color stops. If there are no stops to begin with, when the user adds the first stop it would be an invalid gradient. We'd have to design new behaviors to deal with that. Your suggestion of adding "a white with zero opacity" stop by default is one possibility, but then it may be unclear to the user that there is another color stop there, compared to a more obvious one like blue or violet.

I think it's mainly a UX design matter, so we'll need @WordPress/gutenberg-design feedback on this one.

### jameskoster on 2024-01-15T11:02:23Z

URL: https://github.com/WordPress/gutenberg/issues/51102#issuecomment-1891915603

This feels a bit inconsequential to me. For a custom gradient you're always going to change the values. One argument for the current setup is that the control feels more intuitive because the gradient is immediately recognisable. 

I do agree that with those default values the UX feels a bit odd – after switching to gradient, the control clearly shows the selected values, but they're not reflected on the canvas. I think I'd expect the tabs to behave like radios, but that's a totally separate discussion.
