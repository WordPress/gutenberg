## What?

Fixes an issue with `DateTimePicker` after #73444 where `Date` or `number` or `string` (with timezone) values passed as `currentDate` would be treated inconsistently from timezoneless strings, potentially resulting in mismatches between displayed and changed values similar to what was seen previously in #67480.

Related to: #67480
Follow-up to #73444
Fixes #73981

## Why?

The intent of the changes with #73444 were to normalize internal handling of dates within the component to use UTC time, but the changes only applied to values passed as timezoneless strings. In current Gutenberg usage, this is primarily how the component is used, since this is how WordPress represents dates.

Since the component internally assumes UTC times, this behavior should also extend to values passed in other formats (date objects, timestamps).

## How?

Updates `inputToDate` to consistently coerce all input values to UTC time.

## Testing Instructions

Verify included tests pass:

- `npm run test:unit packages/components/src/date-time/date-time/test/index.tsx`
- `npm run test:unit packages/components/src/date-time/test/utils.test.ts`

I was able to identify one Gutenberg usage where this bug previously existed, in [the initialization of the "Date" block](https://github.com/WordPress/gutenberg/blob/90c242a3020dc2ed8865cff38e5a33d7aa318fbd/packages/block-library/src/post-date/edit.js#L77).

To verify:

1. Set your local system timezone to a different date from the site's timezone (see instructions in #73444)
2. Go to "Posts" > "Add Post"
3. Insert a "Date" block
4. In the block toolbar, click "Change Date"
5. Verify that the initial date is accurately displayed as the current time on the site

### aduth on 2025-12-17T14:33:41Z

URL: https://github.com/WordPress/gutenberg/pull/73887#issuecomment-3665634735

After some more testing and reports, I discovered that there were a lot more issues with the implementation that needed to be solved. This required more extensive changes than initially expected, though I tried to keep the surface area as small as possible. In some cases, it reverts to some logic that had existed prior to #73444 (e.g. using `dateI18n` instead of `gmdateI18n` for date display).

A lot of the problems stem back to the fact that we're juggling three different timezones representations: the browser's local timezone (what's used with `new Date()`), UTC (useful as a normalization format), and the site's configured timezone.

One of the challenges is in how we interpret the different types of values. WordPress primarily uses timezoneless strings which map to the site's configured timezones, but the component also supports receiving `Date` values which are likely to be initialized using the browser's local timezone.

Here's how I think the values should be interpreted:

Input type | Example | Interpreted as | Displayed as
---|---|---|---
Timezoneless string | `"2025-11-15T20:00:00"` | Represents 20:00 in site timezone | Shows Nov 15, 20:00 regardless of browser timezone
Date object | `new Date(Date.UTC(2025, 10, 16, 1, 0, 0))` | UTC instant (Nov 16 01:00 UTC) | Converted to site timezone for display (Nov 15 20:00 if site is UTC-5)
Timestamp | `1731718800000` | UTC instant | Converted to site timezone for display
Default | `undefined` | Defaults to current time | Interpreted as current time in site timezone

Recapping all of what's been fixed in the recent changes:

- Date/time drift on round-trips: Values could shift when passed through `onChange` and back to the component. For example, components which pass `Date` values would likely be converting the received `onChange` string value back to a `Date` object.
- "Today" highlighting: This was based on browser timezone instead of site timezone
- Event indicators (#73981): These were associated with calendar days based on browser timezone instead of site timezone
- `undefined` input handling: Similarly used browser's current time instead of site's current time, which could cause the wrong day to be highlighted as "Today"
- `@wordpress/date`'s handling of `0` numeric timezone: These functions were checking truthiness to indicate the presence of a timezone argument (wrong behavior for `0` values, which are falsey but should be interpreted as present)
