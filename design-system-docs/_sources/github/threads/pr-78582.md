## Body

## What?

Fixes a race condition in `IsolatedSandBox` that caused the Custom HTML block preview iframe to remain at zero height after adding or reloading content in the editor.

Fixes #78576.

## Why?

After WordPress 7.0, the Custom HTML block preview uses `IsolatedSandBox` (via #77212) instead of a same-origin sandbox. The preview iframe relies on `postMessage` resize events to set its height. On first mount or when reopening a post, the initial resize message could be sent before the parent window's message listener was attached, leaving the iframe at `height={0}` and making the block appear blank in the editor.

## How?

- Schedule delayed resize messages inside the sandbox iframe so the parent listener receives them even when `srcdoc` loads synchronously.
- Attach load listeners to nested iframes so preview height updates when embedded iframe content finishes loading.
- Switch `IsolatedSandBox` to `useLayoutEffect` and re-sync the message listener whenever `srcDoc` changes.

## Testing Instructions

1. Create a new post and insert a **Custom HTML** block.
2. Click **Edit HTML**, add `<p>Hello World</p>`, click **Update**.
3. Confirm the preview renders immediately without refreshing.
4. Save the post, close the editor, and reopen the post.
5. Confirm the Custom HTML preview is visible on first load.
6. Add HTML containing a nested iframe (e.g. `<iframe src="https://example.com" width="400" height="300"></iframe>`).
7. Confirm the preview area sizes correctly (note: some third-party embeds may still not fully render in the isolated sandbox due to referrer restrictions from #77212 — this is expected and separate from this fix).

### Regression checks

- Verify oEmbed previews (YouTube, etc.) still work in the Embed block.
- Verify Cover block background video preview still works.
- Confirm Custom HTML block XSS isolation from #77212 is preserved (scripts cannot access parent cookies).

### alecgeatches on 2026-05-22T18:44:31Z

URL: https://github.com/WordPress/gutenberg/pull/78582#issuecomment-4521837970

Thanks for this fix! I agree with @aduth above, syncing resizes through two-way `postMessage` feels like a better solution than a wait-and-hope. Side note, I didn't even realize `postMessage` was possible without `allow-same-origin`, but [MDN (and existing code) says it's fine](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe#scripting):

> Script access to a frame's content is subject to the [same-origin policy](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy). Scripts cannot access most properties in other `window` objects if the script was loaded from a different origin, including scripts inside a frame accessing the frame's parent. Cross-origin communication can be achieved using [`Window.postMessage()`](https://developer.mozilla.org/en-US/docs/Web/API/Window/postMessage)

So `allow-same-origin` protects from DOM and cookie access, but it seems like it can still be used for two-way communication between the iframe and the page. I think it could work like:

1. `iframe` adds a message listener for a `'ready'` state from the editor. When that's received, send a message to apply a resize.
2. `iframe` also sends a resize message when first loaded in case the iframe missed the `'ready'` state during load as a backup.

On the editor side,

1. Send a `'ready'` state to the iframe when after it's mounted. It should be ready to resize at that point from the setup above.

The rest of the logic should work the same as before, I think.

Thanks @aduth  and @alecgeatches  for the feedback! I've replaced the delayed retry approach with a two-way postMessage handshake:

Parent sends { action: 'ready' } after the resize listener is attached

Iframe also sends an initial resize on load as a backup if it missed the ready message during synchronous srcdoc loading
