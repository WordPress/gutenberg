## Description
Because `compose` was untyped, we had originally duplicated the `useIsomorphicLayoutEffect` and `useInstanceId` hooks into the `components` package. This PR removes that duplication. It also upgrades the lodash type definitions used so we can use the `DebouncedFunc` utility type.

I also had to change the way that `flowRight` is imported because otherwise I was getting this error:

> Module '"../../node_modules/@types/lodash/common/util"' has no exported member 'flowRight'.

I have no idea how to solve this, it seems to be some kind of issue with the lodash type definitions. I don't know exactly what the implications are of how I changed it but it fixes that warning.

Maybe @jsnajdr @sirreal or @diegohaz one of y'all have any experience with the lodash definitions and why we can't import the `flowRight` from there to get a proper definition from it? To be clear, it seems that flowRight has a definition it's just not exported in the way we're using it. Maybe this is because we're not using `lodash-es`? 🤷

## Analysis

The issue is with the generated declarations. Our `compose` package compiles just fine. It produces a declaration like this:

```d.ts
export default compose;
import { flowRight as compose } from "lodash/common/util";
```

It's when `components` parses `compose` types that it encounters this import and fails with the error message. It can be reproduced in Gutenberg by building the components types: `npm run build:package-types packages/components`.

Even better, a [minimal reproduction is trivial in the TypeScript playground](https://www.typescriptlang.org/play?filetype=js#code/PTAEBUAsEsGdQMYHsAmBTAUNAtgByQE4AuoA3qAGYA2SA7gErQDmkJAhvMnkrGqAL6UCSbKADkNFB0hiMaAB75iodBTYBXKiS75eGDCFD00sTUXjQAdqDbWcSkldBFIfNNmhEiaFCrQIqNgI2Imgka1gcaECCZyRnGFgALixuZXJqOkYWdk4RXTQAUQ8vHwEhEVAAIklpYC5scOB1UKoqgG4gA)!

Interestingly, this only happens when compiling JavaScript source, _not TypeScript_. [The same playground with TypeScript source emits a correct declaration](https://www.typescriptlang.org/play?ssl=6&ssc=53&pln=6&pc=54&filetype=ts#code/PTAEBUAsEsGdQMYHsAmBTAUNAtgByQE4AuoA3qAGYA2SA7gErQDmkJAhvMnkrGqAL6UCSbKADkNFB0hiMaAB75iodBTYBXKiS75eGDCFD00sTUXjQAdqDbWcSkldBFIfNNmhEiaFCrQIqNgI2Imgka1gcaECCZyRnGFgALixuZXJqOkYWdk4RXTQAUQ8vHwEhEVAAIklpKoBuIA):

```d.ts
import { flowRight as compose } from 'lodash';
export default compose;
```

## Workarounds

Given that the bug only manifests in JavaScript sources, a trivial workaround should be to rename this file to end in `.ts` and the problem should be solved.

Alternatively, with a true [ECMAScript modules re-export the problem does not seem to manifest](https://www.typescriptlang.org/play?filetype=js#code/KYDwDg9gTgLgBAbzgMwDYQO4CUCWBzAC3gEMBnOAE2GWIFdV4BfFKCAWzgHJ0KyDOgA). We should check how this impacts generated docs, but this can be rewritten as `export { flowRight as default } from 'lodash'`.

## Further analysis

It's not entirely clear why this happens. [`flowRight` _is_ defined in `lodash/common/util`](https://github.com/DefinitelyTyped/DefinitelyTyped/blob/698efc50d7eb92c0152e4459cec9c909a7068ebd/types/lodash/common/util.d.ts#L282), but it isn't exported. It's just attached to the LoDashStatic interface. [This is "included" in lodash types via declaration triple-slash reference.](https://github.com/DefinitelyTyped/DefinitelyTyped/blob/698efc50d7eb92c0152e4459cec9c909a7068ebd/types/lodash/index.d.ts#L25)

The fact that only JavaScript compilation causes this to manifest suggests it may be a bug in the TypeScript compiler.

> while I like the idea of not just re-exporting something from lodash, the types are a huge pain to write for these functions.

I writing many overrides for 1..N number of arguments still the only option? Or can some recent TypeScript define types recursively, like:

```ts
type compose( f: ( a: A ) => B, ...rest ) = ( b: Param< compose( ...rest ) > ) => B
type compose( f: ( a: A ) => B ) = ( a: A ) => B
```
? That would be awesome 🙂 

An advantage of home-grown `compose` is that for our use-case, i.e., composing one-parameter HOCs, it's literally an one-liner:
```js
( ...fns ) => ( a ) => fns.reduceRight( ( r, fn ) => fn( r ), a );
```

On the other hand, the Lodash implemenation is a bit of a monster. It supports multiple arguments for the first function in the chain, and also Lodash lazy wrappers (https://lodash.com/docs/4.17.15#lodash). We don't use that at all.
