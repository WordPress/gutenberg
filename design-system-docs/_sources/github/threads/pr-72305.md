## Body

## What?

Adds a `@wordpress/theme` package to handle theming concerns of the WordPress design system.

### Punted to follow-up

- Add unit tests to verify the output of `ThemeProvider`. I omitted them for now (d377c0ce4958784b85da7049ba436d71736d89bb), because we cannot do these snapshot tests effectively without upgrading the repo to Jest 30. (jsdom < 26 will strip out CSS variables from the output.)
- Add Storybook stories. I omitted them for now (d0d0242774cbc7e74b034943cede99cc376a8ecd) because we need to set up a theme switcher in the top toolbar, and I need to figure out what to do with the existing experimental theme switcher.
- Implement linting for invalid theme variables.
- `design-tokens.js` and `design-tokens.ts` can probably be consolidated into a single JS file.
- Probably move the styles in the stylesheet to an inline `style` attribute.

## Why?

This package of design tokens will be the foundation to our design system, and is a requirement for our new UI components package.

## Code Review Instructions

Most of the core code has been reviewed before. I've highlighted any notable changes in the inline comments.

Structural decisions to discuss:

- The original folder structure made it hard to understand which files are generated in the prebuild. I've tried to clarify a bit by moving as many generated files as possible to the `src/prebuild` folder. The only exceptions are `tokens/color.json` and `docs`.
- The original folder structure made it unclear whether any of the code in the `scripts` folder is also used at runtime. I tried renaming it to `bin` to make it clearer that they're only used at compile time.

## Testing Instructions

See the output of the builds and confirm that CSS modules are being processed as expected. You can also try importing the `ThemeProvider` component into the app or a Storybook story to see how it handles CSS modules. (Note that the stylesheet will need to be imported separately.)

### jsnajdr on 2025-10-20T07:36:36Z

URL: https://github.com/WordPress/gutenberg/pull/72305#issuecomment-3420924235

We discussed in which folders we should put various files generated by build scripts. After a closer look I see there are three types of artifacts and three stages of build.

**First step:** the DTCG tokens in `tokens/*.json` files. One of them, `colors.json`, is partially generated by the `generate-primitive-tokens` script. The `semantic` tokens are handcoded, the `primitive` tokens are generated by an algorithm from two seed colors. Which correspond to the "WordPress Light" theme.

These DTCG tokens are not currently exported from the `theme` package, but they should be. It's information in a standardized format that could be useful for many tools.

**Second step:** generate various files from the DTCG info, using the Terrazzo tool:
- `build/css/design-tokens.css` is used by the `<Root>` component in the `boot` package to provide default `:root` values for token CSS variables. These styles are fully overrided by a `ThemeProvider` instance.
- `build/js/design-tokens.js` and `src/design-tokens.ts` exports a JSON object with info about semantic tokens (no primitives there). Used by the `no-unknown-ds-tokens` ESLint and Stylelint rules to read a list of known tokens, and by the `ThemeProvider` to generate styles for semantic tokens.
- `build/json/figma.json` contains all tokens (semantic and primitive) for the Figma plugin.
- `docs/ds-tokens.md` lists all token names and descriptions in a Markdown table.

In this step I propose two changes:
1. Unify the two `.js`/`.ts` files into one, and maybe rename it to a `.json`.
2. We commit all Terrazzo-produced files to Git. For that, avoid writing them to the `build` directory which is git-ignored and perishable. I wouldn't mind writing them simply to `src`.

**Third step:** Transpile all source files with the standard tooling, producing `build`, `build-module` and `build-style` directories. This could newly also transpile the `design-tokens.ts` (if we don't rename it to `.json` for some reason) into `design-tokens.js`. Instead of Terrazzo producing two files.

The `design-tokens.js` file also doesn't need a separate entry in the `exports` field in `package.json`. It could be just another export in the index, besides existing `ThemeProvider` and `useThemeProviderStyles`.
