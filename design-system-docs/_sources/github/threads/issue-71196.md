# Issue #71196: Design System: Support for admin redesign

- URL: https://github.com/WordPress/gutenberg/issues/71196
- Author: aduth
- Created: 2025-08-13T15:48:44Z
- Updated: 2026-01-07T18:22:03Z

## Body

To support the [Phase 3 admin redesign initiative](https://github.com/WordPress/gutenberg/issues/53322), we need a flexible, themeable, and accessible design system that can power a redesigned admin experience. It should serve as the foundation for the default admin interface while also enabling customization through user preferences and plugin extensibility. This issue outlines high-level requirements and current limitations, which will be used to guide more focused discussions.

This overview builds on and supports previous discussions:

* #70913
* #53322  
* #42388
* ["Admin Design" Make/Core post](https://make.wordpress.org/core/2023/07/12/admin-design/)  
* ["Admin Design Kickoff" Make/Core post](https://make.wordpress.org/design/2023/08/10/admin-design-kickoff/)

The redesign presents an opportunity to formalize design primitives, close functional gaps, and provide plugin authors with a themeable, scalable, and accessible set of tools for building admin workflows.

## Current limitations

The following limitations describe where we may encounter friction in using existing implementations to meet the needs of a redesign:

* **Limited theming support:** Current capabilities make it difficult to support the full range of redesign requirements, such as flexible color schemes, adjustable density, and user-customizable accents.  
* **Inconsistencies in APIs, styling, and composition:** Components follow different patterns and approaches, making it harder to ensure consistent usage and meet common needs.  
* **Limited composability and bloated abstractions:** Some components are hard to adapt or extend because they weren’t designed with composable patterns in mind, while others have grown overly complex due to scope creep and a lack of lower-level building blocks.  
* **Monolithic package structure:** The current structure makes it difficult to use only a subset of components, which can impact performance and bundling flexibility for different projects.  
* **Global dependency (`wp.components`):** Tightly coupling all components into a single shared dependency locks in historical decisions and limits how we can make decisions affecting individual components or the broader framework.  
* **Single-version limitation:** There’s no way to run multiple versions of components side-by-side, preventing plugins that support older WordPress releases from benefiting from newer component features.  
* **CSS conflicts and style isolation:** Lack of encapsulation increases the risk of overrides and inconsistencies, which can lead to visual inconsistencies and unpredictable results.  
* **Locked to specific implementation details:** Current reliance on CSS-in-JS introduces runtime performance costs, and this cannot be easily removed.  
* **Editor-focused design:** Components were primarily created to support the block and site editors, which can limit their suitability for the broader variety of admin screens.  
* **Maintenance cost:** Managing low-level implementation details consumes significant time, leaving less capacity for decisions and improvements that have a higher impact on the user and developer experience.

## High-level requirements

These are the broad capabilities the design system should support to meet the goals of the admin redesign project:

* **Theming**: Support for consistent, flexible color theming, adjustable density, and other appearance customizations. Allow room for expressive user personalization and plugin branding while preserving cohesion and accessibility.  
* **Tokens**: A foundational set of design tokens (e.g., color, spacing, typography) for consistency and extensibility across components and interfaces.  
* **Layers of abstraction**: Both low-level primitives and higher-level components to balance flexibility and ease of use for different types of interfaces.  
* **UI component library**: A cohesive set of components that align with modern conventions, optimized for common workflows in the WordPress admin.  
* **Accessibility**: Conformance with [WordPress accessibility coding standards](https://developer.wordpress.org/coding-standards/wordpress-coding-standards/accessibility/), including support for semantic markup, keyboard navigation, adequate color contrast, and other best practices for inclusive design.  
* **Responsiveness**: Components or tools that support the ability for interfaces to adapt gracefully to different viewports and contexts.

### aduth on 2026-01-02T16:41:58Z

URL: https://github.com/WordPress/gutenberg/issues/71196#issuecomment-3705750680

@fabiankaegy Good questions! There have been a few similar comments around this recently as components have been proposed, and while there is some documentation on the differences from `@wordpress/components` in [the `@wordpress/ui` README](https://github.com/WordPress/gutenberg/blob/trunk/packages/ui/README.md), I think we should specifically document the future intentions with the existing components and what impact the new package will have on that. It's also worth stating that with the new package still being early, a lot of this could change and be moulded over time as we take learnings from the proposed implementations.

On the point of duplication, I'm personally considering the `@wordpress/ui` package in the light of modularity and design system consistency, as opposed to a "components 2.0 do-over". This can be a more narrow scope, while granting that there are parts of the existing components that we also want in the design system. Conversely, there are parts of `@wordpress/components` that don't make sense: site bindings, domain-specific (e.g. editor) components, etc. 

In this framing, how I might consider future maintenance would be that many of the `@wordpress/components` implementations that also fall within the scope of `@wordpress/ui` could be updated to _compose from_ parts of `@wordpress/ui`, so that there's only a single implementation for those shared behaviors. This would allow us to avoid disruption for current usage, maintaining existing component APIs by internally mapping to the underlying design system components.

From a user's perspective, we should expect to maintain alignment between visual appearance of components, to avoid a situation where the interface becomes a disjointed mess depending on which components are used. If there are situations where a new component's development would motivate some design change, I'd expect that change would be applied to existing components as well to ensure symmetry.

Together, my expectation is that this approach would avoid disruption to downstream consumers without an excessive maintenance burden on ourselves. Existing component usage will continue to be supported per backwards-compatibility commitments without fear that the components would appear out of place with new implementations, while new low-level, modular design system components can unlock more flexible component combinations for both downstream consumers and our own component implementations.

### aduth on 2026-01-07T18:22:03Z

URL: https://github.com/WordPress/gutenberg/issues/71196#issuecomment-3720158342

Another angle with embracing package versioning and its effect on maintenance and duplication: Relying on versioning isn't just about allowing for breaking changes, but also for getting features into the hands of consumers sooner. Our current approach with WordPress scripts imposes a lot of fear around maintenance and backwards-compatibility that has led to widespread adoption of [private APIs](https://github.com/WordPress/gutenberg/blob/trunk/packages/private-apis/README.md) which make features completely inaccessible to external consumers. And those features often stay private longer than necessary (frankly, there's nothing stopping them from staying private _forever_). Versioning should allow maintainers to operate with a little less fear and more confidence to ship features sooner to be publicly-available for use.

As a concrete example, consider [the `Badge` component](https://wordpress.github.io/gutenberg/?path=/docs/components-badge--docs), which has already been highlighted as a component we've [duplicated into `@wordpress/ui`](https://wordpress.github.io/gutenberg/?path=/docs/design-system-components-badge--docs). The existing Badge component was [introduced over a year ago](https://github.com/WordPress/gutenberg/pull/66555) and is still a private API, meaning that it's completely inaccessible for third-party usage. The `@wordpress/ui` `Badge` can be used today.  On the maintenance and duplication front, being that it's a private API means that we could remove it altogether in favor of `@wordpress/ui` `Badge` as long as we update internal usage.

This doesn't apply for every component, but my impression is that we could largely move away from private APIs and clean up existing private APIs as part of this effort.
