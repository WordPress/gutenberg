## Body

## What?

Closes #79051

Bumps `@ariakit/react` from `^0.4.21` to `^0.4.29` in `@wordpress/components` and `@wordpress/dataviews` (keeping the ranges aligned, as in #77954), and adopts the upstream `Tabs` focus fix that this range ships — removing the now-unnecessary Gutenberg workarounds.

## Why?

#77954 parked the upgrade at `^0.4.21` because a patch in this range changed how controlled `Tabs` handle focus, breaking 4 unit tests.

That change is **intentional**: it's the canonical fix for [ariakit/ariakit#4213](https://github.com/ariakit/ariakit/issues/4213) (which I originally reported). Upstream now **moves focus to the newly selected tab** on a controlled `selectedId` change, instead of preventing `activeId` from updating. So the chain of Gutenberg workarounds that kept focus and `activeId` in sync is no longer needed.

<details>
<summary>More detail</summary>

The fix shipped in [ariakit/ariakit#6068](https://github.com/ariakit/ariakit/pull/6068), documented in the `0.4.29` changelog:

> Fixed `Tab` to move focus to the selected tab after a controlled `selectedId` update while a tab has DOM focus.

The removed workarounds (#56658 → #57696 → #58625) existed to fix the exact desync that #4213 now addresses upstream.

</details>

## How?

- Bumped `@ariakit/react` to `^0.4.29` and updated the lockfile.
- Removed the controlled-mode focus workarounds (the `requestAnimationFrame` re-sync in `Tabs` and the `onBlur` re-sync in `Tabs.TabList`).
- Updated the 4 controlled-selection unit tests to expect focus to follow the selection.
- Refreshed 4 `ToggleGroupControl` snapshots for an auto-generated `name` attribute on `Radio` (see changelog review).

## Changelog review (0.4.22 → 0.4.29)

I reviewed every CHANGELOG entry in the range against our actual usage. Only two changes produce observable output, both handled here:

- **`0.4.29`** — `Tab` focus follows controlled selection.
- **`0.4.26`** — `Radio` auto-generates a `name` from the `RadioGroup` `id`, adding a `name` attribute to `ToggleGroupControl` radios (snapshot-only).

Everything else is either a bug fix that improves a primitive we use or doesn't touch one. CI backs this up: the full unit + e2e suites pass with only the two changes above.

### Review thread 2

#### ciampo on 2026-06-09T14:44:00Z

URL: https://github.com/WordPress/gutenberg/pull/79055#discussion_r3381549574
Path: packages/components/src/tabs/test/index.tsx

The tweaks in unit tests describe the behaviour change. The upstream `ariakit` changes fix the same "out of sync" bug between focused element and `activeId` that the custom workaround (removed in this PR) also fixed, but with an opposite approach:

- the custom workaround (that is being removed in this PR) fixed the desync by pinning `activeId` back to the focused tab. In other words, focus stays on beta, selection moves to gamma. Focus and selection are decoupled.
- the upstream fix (which is being adopted in this PR) moves the DOM focus to the selected tab. In other words, focus moves to Gamma, matching selection. Focus and selection are coupled

Our previous approach respected user focus (in exchange for focus and selection going out of sync), while ariakit prioritizes matching focus with selection.

I don't think one approach is clearly better than another, they are just different compromises. With the new approach, the only "awkward" scenario is when `selectOnMove: false`: I believe the APG suggests keeping focus decoupled from selection, but in practice the change is small: focus is moved only when a tab already has dom focus and the value changes programmatically.
