## Body

Depends on: https://github.com/WordPress/gutenberg/pull/61062.

This is a follow-up to https://github.com/WordPress/gutenberg/pull/61062. See this comment for more details on how the work has been split: https://github.com/WordPress/gutenberg/pull/61062#issuecomment-2130015327. You can also read the discussion there to better understand how we arrived at this solution. You can also check the edit history to see the original description for this PR.

## What?

Better align the default width behavior with the [original component specs ](https://github.com/WordPress/gutenberg/pull/61976#issuecomment-2134537064)and make it easier to override it.

This PR also adds a new story to illustrate a custom width and updates the docs/jsdoc.

## Why?

This progress bar was designed to be of a fixed width, so we should keep it. Existing consumers already expect it, too. However, if there are any scenarios where a custom width size/behavior is required, we should provide the means to do so. 

## How?

* Keep the default width of `160px` for the progress bar. It's meant to have a fixed size, [see this comment](https://github.com/WordPress/gutenberg/pull/61976#issuecomment-2134537064);
* Stop using `max-width` to set it. It's not meant to adapt to the parent size, by default;
* Instead, use the `:where` pseud-element (which has zero specificity) to set a default width. This makes it trivial for consumers to override the width with a custom CSS class, if they wish.


## Testing Instructions

1. All tests should pass;
2. Check the storybook stories for the `ProgressBar`.
3. The component should be rendered the same in existing consumers.

### mirka on 2024-05-27T13:36:14Z

URL: https://github.com/WordPress/gutenberg/pull/61976#issuecomment-2133503282

> I think we should rely on the `classname`

The concern I have with the "just override with classname" approach with things like width, is that it's non-obvious _which properties exactly_ need to be overridden. Is it `width`, `max-width`, or both? Plus, as a package we always emphasize that we do not guarantee these styling implementation details to not change. So it's inherently an unstable approach that we'd have to recommend to consumers. Maybe I'm being too idealistic, but it doesn't look clean to me.

For me, it's either:

1. Have a default width for consistency, but provide a way to _safely_ change it. (Which a prop like `hasUnconstrainedWidth` achieves)
2. Have no width constraints.

Though I understand that there are no clear winners here. Both have downsides.

Also for what it's worth, I just realized that the native `<progress>` element has a default width of 160px in Chrome and Firefox, so that makes me feel a bit better about us having the same default width as that.

### DaniGuardiola on 2024-05-27T16:03:30Z

URL: https://github.com/WordPress/gutenberg/pull/61976#issuecomment-2133772585

My humble opinion is that I don't really see this potential consistency issue as important enough to grant a default fixed size plus this prop API.

Doing a fixed size comes with important trade-offs, and in this case having such a prop just to be able to change the size feels very wrong to me. In some components with content (such as buttons) it makes sense for a default sizing strategy to be `fit-content` ([example from a design system I built in the past](https://atlas.guide.co/?path=/story/components-button--width-examples)).

However, in most cases, the width I would expect by default is always 100%, because that's how block elements behave by default. Even if it isn't 100%, I would at least expect to be able to style them with CSS, directly. Having to pass a prop feels cumbersome, and also comes with a discoverability issue.

I think this is a case of YAGNI, and would strongly suggest not having a default fixed size at all.

Regarding HTML `<progress>`, while it's a very valid reference, I don't think it really matters that much. Take text inputs, for instance. They also come with a fixed size, yet we apply 100% size by default. Not only that, but they have `display: inline-block` by default, which we don't do at all (we do `block` instead). In fact, `<progress>` also does `inline-block`!

If lack of sizing consistency ever becomes a problem worth addressing, I'm sure we'll be able to find a satisfactory solution then. Until then, I'd suggest not committing to this kind of API. I think simpler and more consistent (with other components) should win this one. My two cents!
