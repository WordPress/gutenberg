## Still work in progress! Creating this PR early as a draft.

👋 Hi there! I'm my journey to help improve `@wordpress/components`, I've started working on adding common components (and primitives) that I feel like are missing in the current library. Common components that one would typically find in other libraries/frameworks, like Bootstrap, Material UI, etc...

One of them is some sort of top/action/page header. Something responsible for indicating context, and containing a handful of actions (links, buttons, maybe tab bars).

### Examples

From looking at different libraries, it looks like there are a couple of use cases:

* A dedicated top nav bar (e.g. [Bootstrap](https://getbootstrap.com/docs/4.0/components/navbar/))
* A dedicated page header bar (e.g. [Shopify Polaris](https://polaris.shopify.com/components/structure/page) . [Salesforce Lightning](https://lightningdesignsystem.com/components/page-headers/))
* A bar that (kinda) combines both (e.g. [Material](https://material.io/components/app-bars-top/#anatomy))

### What this is not

I don't think this component should be used as the main top navbar - something with nav links. Example, [Bootstrap's nav bar](https://getbootstrap.com/docs/4.0/components/navbar/).

### Where this can be used

It may be used to organize the actions at the top of Gutenberg's header bar area.
Also, it would be a handy component for folks to use in custom Gutenberg block creation, or for general purpose use outside of Gutenberg.

## Same, but different

In working through these components, I think I'm noticing 2 use cases:

* One with a title/subtitle
* One without

Even though they're almost identical in what they do (render stuff, in a white box, with somethings on the left and right), the **understanding of their purpose within the context of UI is different**.

From a (React component) code perspective...

I think we need to create something smaller. e.g. `Toolbar` or `ActionBar`.
Something more generally that can be refined/customized to construct something like `PageHeader`.

We took this approach with `Tooltip`!

`Tooltip` and `Popover` are basically identical in function. But there are subtle difference that distinguish where you'd use them. Therefore, you have a component for both.

But, under the hood, `Tooltip` is powered by `Popover`! 

I think the same approach can work here as well 👍

### MichaelArestad on 2019-10-29T17:57:30Z

URL: https://github.com/WordPress/gutenberg/pull/18141#issuecomment-547552644

I think, from a programmatic standpoint, both the Gutenberg Toolbar and the PageHeader component have much in common. The question is whether they should or should not be the same component.

I believe a component should be focused in purpose and simple to implement.

In the context of these two design patterns, their purposes and needs differ enough to warrant each being their own separate component. Perhaps they could be built behind the scenes sharing some code, but to someone implementing either in their design, they should be separate.

There are secondary benefits for them being separate components. As separate components, they will be more flexible to iterate as there are fewer possible prop-based variants in each. This reduces the complexity of designing and developing them down the road.

The Toolbar can be optimized to be a toolbar without concern for PageHeader needs. The PageHeader can be optimized to be a page header without concern for Toolbar needs.

### afercia on 2019-10-31T13:02:45Z

URL: https://github.com/WordPress/gutenberg/pull/18141#issuecomment-548363422

> Do PageHeaders always need a title? 

I can answer this one 🙂 
Any page needs a visible main H1 heading.

In the WordPress admin there's been a lot of work in the last releases to rebuild a decent headings hierarchy that went lost over the years. Today, most of the pages have a main H1 and a good headings hierarchy after the main heading.

In Gutenberg, there was a lengthy discussion about a visible main H1. Due to lack of consensus, all that the accessibility team was able to get was a _visually hidden_ H1. Which is still not ideal, in the accessibility team's opinion. Headings should be visible.

The main heading answers a fundamental question for users: Where am I? What can I do here?
Visible headings benefit all users. Also, all the Ui sections must be identified by headings.

References:

**Headings**
Headings communicate the organization of the content on the page. Web browsers, plug-ins, and assistive technologies can use them to provide in-page navigation.
https://www.w3.org/WAI/tutorials/page-structure/headings/

**Page Regions**
Mark up different regions of web pages and applications, so that they can be identified by web browsers and assistive technologies.
https://www.w3.org/WAI/tutorials/page-structure/regions/

A main H1 is of fundamental importance at the point a `PageHeader` component should make it required.
