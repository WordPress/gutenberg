# Issue #73015: Components: Validated form components should cancel browser invalid handling

## Body

## What problem does this address?

Validated form components use [browser-native form validation](https://html.spec.whatwg.org/multipage/form-control-infrastructure.html#constraints) behavior to control and intercept form validation to show visible error messages.

However, they don't currently work very well when external application logic programatically invokes validation, such as through [`HTMLFormElement#reportValidity`](https://developer.mozilla.org/en-US/docs/Web/API/HTMLFormElement/reportValidity). Use-cases include external revisions to a form field's value such as asynchronous validation or mirrored input values.

**Steps to reproduce:**

1. Go to https://wordpress.github.io/gutenberg/?path=/docs/components-validatedtextcontrol--docs
2. Enter "error" into the field
3. Right-click the field and "Inspect element" to inspect the input in your browser DevTools
4. In your DevTools console, enter `$0.reportValidity()`

The above steps result in both the custom visual error label and the browser-native error popup appearing:

<img width="325" height="192" alt="Image" src="https://github.com/user-attachments/assets/c7adac70-28c7-4427-b954-702d859d89fa" />

## What is your proposed solution?

It may be as simple as calling `event.preventDefault()` on [the handled '`invalid'` event](https://github.com/WordPress/gutenberg/blob/03e3101bd7e1a06067c5275ad5a4cf3873603c54/packages/components/src/validated-form-controls/control-with-error.tsx#L109-L112).

Via [MDN](https://developer.mozilla.org/en-US/docs/Web/API/HTMLFormElement/reportValidity) (emphasis mine):

>The reportValidity() method of the [HTMLFormElement](https://developer.mozilla.org/en-US/docs/Web/API/HTMLFormElement) interface performs the same validity checking steps as the [checkValidity()](https://developer.mozilla.org/en-US/docs/Web/API/HTMLFormElement/checkValidity) method. In addition, for each [invalid](https://developer.mozilla.org/en-US/docs/Web/API/HTMLInputElement/invalid_event) event that was fired **and not canceled**, the browser displays the problem to the user.

This is kind of by design. Also it will occur more frequently than "when external application logic programatically invokes validation", because it will be invoked when the user tries to submit the enclosing form.

There was some initial discussion with designers as to whether we were ok with the native popovers. I remember trying to figure out a way to suppress the popover only (but keep the other behaviors like scroll to and focus), but I don't think I found any. It's an interesting trade-off, because the popover actually provides a very convenient and obvious alert to the problem (better than just our custom red message), when the user's attention is not necessarily near the invalid inputs. It's just that we don't have control over the popover's visual design.

Even if we do figure out a way to suppress the native popovers, I think we may need to design and implement some other way to bring attention to the invalid field, which will likely also be a popover given the diversity of UI designs it needs to support.

That's the context of how we decided to go with the native behavior for our first iteration. We can go full custom if we're ready to commit the added effort.

### mirka on 2025-11-10T23:13:34Z

> What about them is insufficient as-is?

I think the point is that the native popovers are a "last resort" alert mechanism here. The user is basically given softer warning cues _before_ clicking on the submit button, whether that be "required/optional" indicators on the field labels, or the red error messages that have already appeared while filling out the form. In the majority case, the native popovers won't ever be seen if the user has noticed these cues and corrected the validation errors before attempting to submit.

Whether the user simply glossed over the cues, or if there are other ability issues (e.g. color blindness, forced-colors mode, cannot interpret the tiny warning icon), we don't know. But given that the cues already failed to catch their attention on the way down to the submit button, that probably justifies an escalation to a stronger, different form of alert.

> As a user seeing something like in the screenshot, I'd also be confused / distressed about seeing an alert indicator under the popup, but the error text being obscured

This is understandable. Maybe there are ways to increase the prominence of the errors without resorting to an obscuring popover.

> I'm not sure what added effort this entails

Aside from the design effort, at the very least we'll need to add logic for the "focus on first invalid field" functionality. Basically add a `submit` event listener on the enclosing form to find the first invalid control in `form.elements`. This would either need to be done by the control components themselves (where they each add a listener to `elementRef.current.form` that works in an idempotent way), or through a designated `Form` component.

Part of the complexity I've noticed is that not all control UI designs have an inherent focus ring we can easily repurpose for an error indicator. These can require case-by-case design assessment on whether simply changing the existing focus ring red has sufficient prominence, and that it doesn't "look weird", especially against any theme accent colors used. For example checkbox groups, radio groups, sliders, and probably other custom composed controls that we haven't added validation to yet.

I'm hoping we can land on a universal design that works for any control UI without requiring extra design decisions or implementation per component. I have to give it to the native implementation in this regard — the popovers will just work universally, no interference with existing colors or layout. I think this consideration will become increasingly relevant once consumers start adding validation to their [own custom components](https://github.com/WordPress/gutenberg/pull/72048#discussion_r2467182622).

### mirka on 2025-11-14T19:14:29Z

URL: https://github.com/WordPress/gutenberg/issues/73015#issuecomment-3534203612

I guess we can start by hiding the native popovers, and see how it goes? We can always escalate from there, or revert or whatever.

I played around a bit in a sandbox with plain elements, and if things are really as simple as they seem, it might even be as easy as:

```js
// Do this inside the 'invalid' event listener

  e.preventDefault();

  if (!e.target.form) {
    e.target.focus();
    return;
  }
  
  const firstErrorInForm = Array.from(e.target.form.elements).find(el => !el.validity.valid);
  
  if (firstErrorInForm === e.target) {
    e.target.focus();
  }
```

We may find some quirks and edge cases in actual implementation that doesn't allow it to be that simple, but we can assess then whether it's worth the trouble.
