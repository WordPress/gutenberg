## HALP!

Spot where I'm currently stuck:

When typing the `onChange` methods for `ColorListPicker` and its subcomponent `ColorOption` I have a conflict I can't quite shake.
- `ColorListPicker`'s `value` prop is typed as `Array< string >`, and its `onChange` method expects an `Array< string >` arg.
- `ColorOption`'s `onChange` accepts a single `string` value. It copies the `value` array mentioned above and appends the new string to it. That new array is passed to `ColorListPicker`'s `onChange`. This is fine, it's still an array of strings.
- `ColorOption`'s onChange is forwarded on to `ColorPalette`. Unfortunately, `ColorPalette`'s `onChange` wants the string we're passing to be optional - meaning we have a conflict between `string` and a potential `undefined`.

Potential solution:
I'm wondering if the problem isn't with that optional argument in `ColorPalette`, and if it shouldn't, in fact, be a required `string | undefined` argument. [Further down the line in `ColorPalette`](https://github.com/WordPress/gutenberg/blob/0b1998cf997d866bc1eca182fedb1abb42e337fd/packages/components/src/color-palette/index.tsx#L231), `clearColor` is written to explicitly pass `undefined` to `onChange`, so we need to account for that flow. If we replace `undefined` with an empty string, and make the first `onChange` arg required, everything lines up nicely.

This also feels like the right move to me, because the first argument isn't actually optional - there's a second argument (`index`) to `onChange`,  and the order matters, so you really can't just leave `newColor` out. You'd need to pass _something_ there, to avoid colliding with `index`.

I began working on a PR to demo this change, but it had a bit of a domino effect that spills over to other components, so I put a pin in that for now. I'm happy to chase it further if this feels like the right road to travel!
