# Issue #71153: Add `duration` prop to Snackbar component

- URL: https://github.com/WordPress/gutenberg/issues/71153
- Author: badasswp
- Created: 2025-08-10T04:08:43Z
- Updated: 2025-10-22T14:46:16Z
- Comments: 8 of 8

## Body

## What problem does this address?

At the moment, the `Snackbar` component's **NOTICE_TIMEOUT** appears to be hard-coded which doesn't leave much room for users to be able to dictate how long it should be visible on the screen.

## What is your proposed solution?

I suggest we add a `duration` prop, that gives users this flexibility they need so that they can adjust this as they choose.

### jasmussen on 2025-08-15T10:30:40Z

URL: https://github.com/WordPress/gutenberg/issues/71153#issuecomment-3191209539

Thanks for the ping. I'm immediately drawn to question: what's the use case? There is an option already to add an [explicit dismiss property](https://wordpress.github.io/gutenberg/?path=/docs/components-snackbar--docs), so the snackbar only disappears when dismissed, so assuming the motivation for extending the duration is to ensure users engage with it, that is arguably better handled with that prop.

At present, the snackbar lingers for a long time, I believe a full ten seconds. I personally think that's way too long, and even reducing that to 8 seconds would be a win, it certainly seems to linger much longer that the industry standard which appears to be around 5-6 seconds. To that end, I'd personally support a PR that reduced this time for all snackbars. 

The risk with introducing a prop, whether it's to allow an arbitrary number, or even choose between presets "short" and "long", is that it won't be clear to users why one snackbar exists for a long time, and another one disappears immediately.

@badasswp To be clear, we're being cautious because we want to protect the _end user_ from arbitrary choices of any given WP ecosystem developer. Custom durations would be totally reasonable if this were a general-purpose UI library to be used in isolated web apps, but given the nature of `@wordpress/components`, part of our responsibility is to restrict certain types of customizability in order to maintain cohesion throughout the WP ecosystem. Hope that makes sense!
