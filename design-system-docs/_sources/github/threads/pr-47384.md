## What?
<!-- In a few words, what is the PR actually doing? -->

As a follow-up to #46315, this PR further cleans up some of the logic around single vs multiple origin color palettes.

## Why?
<!-- Why is this PR necessary? What problem is it solving? Reference any existing previous issue(s) or PR(s), but please add a short summary here, too -->

Code quality (re-use same checks in different components, add comments, tighten up types)

## How?
<!-- How is your PR addressing the issue at hand? What are the implementation details? -->

Here's the main set of changes applies in this PR:

- moved `ColorPalette` utilities to a separate `utils` file
- rewrote slightly the "multiple origins" check for added clarity (and added the array `lenght` check)
- removed a check in `ColorPalette` that isn't necessary anymore since the removal of the `__experimentalHasMultipleOrigins` prop in #46315
- reuse the `ColorPalette` logic in `BorderControl` instead of custom check (which allows to simplify some types and checks too!)
- add similar logic for `GradientPicker` too

You can review this PR commit-by-commit too
