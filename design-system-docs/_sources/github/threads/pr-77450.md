See [#76837](https://github.com/WordPress/gutenberg/pull/76837) — extracted `@wordpress/components` **Menu** work.

Related context: [mui/base-ui#4640](https://github.com/mui/base-ui/issues/4640) — describes a scroll-lock handoff bug when opening another modal overlay while an Ariakit `Menu` is still closing; one mitigation is moving panel motion off the Ariakit root so scroll-lock cleanup is not delayed by leave transitions on that element.

## What?

Restructures `Menu.Popover` DOM: Ariakit **`Menu`** uses a **`render`** callback so merged props land on an inner **`MenuSurface`**, wrapped by an outer **`MenuMotionRoot`**. Panel motion stays **transition-based like `trunk`** (slide + fade with **enter and exit**), driven by **`data-enter`** / **`data-side`** on the inner surface.

## Why?

Separates the Ariakit root (positioning, z-index, Windows High Contrast outline) from the visual panel (grid, chrome, `variant`, overflow) while keeping **the same motion behavior as `trunk`**. The split also aligns with the kind of DOM layering discussed in [mui/base-ui#4640](https://github.com/mui/base-ui/issues/4640) for healthier scroll-lock behavior across stacked overlays.

> [!NOTE]
> **Close timing:** with motion applied on **`MenuMotionRoot`** (outside the Ariakit **`Menu`** element that coordinates scroll lock), **Ariakit may not wait for the close CSS transition to finish** before unmounting or running scroll-lock teardown. The exit animation can still play on the wrapper, but teardown timing may differ from a single-element `trunk` menu—pay extra attention when opening another modal overlay while a menu is closing (see [mui/base-ui#4640](https://github.com/mui/base-ui/issues/4640)).

## How?

- **`popover.tsx`**: `render` returns `<MenuMotionRoot><MenuSurface { ...htmlProps } variant /></MenuMotionRoot>`; popover `children` still reach the surface through Ariakit’s merged props.
- **`styles.ts`**: **`Menu`** — thin shell styles only. **`MenuSurface`** — layout, elevation, `overflow`, `variant`. **`MenuMotionRoot`** — `trunk`-equivalent transition rules under `@media not (prefers-reduced-motion)`, expressed with **`:has(> ${MenuSurface}[…])`** because `data-*` attributes live on the inner node.

<details>
<summary>Implementation notes (optional)</summary>

- Submenus: motion rules are gated with `:not(:has(> ${MenuSurface}[data-submenu]))`, matching trunk’s `&:not([data-submenu])` intent.
- Timing and easing still use `DROPDOWN_MOTION_CSS` from the shared dropdown motion tokens.

</details>

## Testing Instructions

1. From the repo root, run `npm run storybook:dev` (or your usual Storybook workflow) with dependencies installed.
2. Open **`Menu`** stories under `@wordpress/components`.
3. **Root menu**, system **without** reduced motion: open from trigger — slide/fade **in** should feel like **`trunk`**.
4. **Close paths**: dismiss via click-outside, Escape, and activating an item — confirm **exit** transition still runs (not limited to open-only motion).
5. **Reduced motion**: enable the system preference — non-essential motion should be skipped.
6. **Submenu**: open a nested menu — it should **not** use the root dropdown motion styling.

### Testing Instructions for Keyboard

1. Tab to a menu trigger; open with **Enter** or **Space**.
2. Use **arrow keys** to move; open a submenu with **ArrowRight** (LTR); **Escape** to close.
3. Confirm focus return matches **`trunk`** expectations.

The new keyframe-based open animation no longer sets `will-change: transform, opacity` on the animated element. This is a minor performance regression vs. the previous transition implementation and is inconsistent with other Ariakit popovers in this package (e.g. `SelectPopover`). Consider adding `will-change: transform, opacity` to the `MenuMotionRoot` rules that apply the animation so the compositor can optimize during the open animation.
