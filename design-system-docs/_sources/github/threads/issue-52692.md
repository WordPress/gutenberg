# Issue #52692: Remove dependencies to `block-editor` package in native files within the `components` package

- URL: https://github.com/WordPress/gutenberg/issues/52692
- Author: fluiddot
- Created: 2023-07-17T14:58:38Z
- Updated: 2026-06-10T06:32:01Z
- Comments: 4 of 4

## Body

## Description
<!-- Please write a brief description of the bug. -->

The following native files (i.e. `*.native.js`) are importing the `@wordpress/block-editor` package, however, this package is not included in the `package.json` of the `@wordpress/components` package. We should remove these dependencies as their importation could result in `undefined`, and to avoid circular dependencies since `@wordpress/block-editor` imports `@wordpress/components` package

- [x] [`font-size-picker/index.native.js`](https://github.com/WordPress/gutenberg/blob/trunk/packages/components/src/font-size-picker/index.native.js)
- [x] [`mobile/global-styles-context/utils.native.js`](https://github.com/WordPress/gutenberg/blob/trunk/packages/components/src/mobile/global-styles-context/utils.native.js)
- [x] [`mobile/inserter-button/index.native.js`](https://github.com/WordPress/gutenberg/blob/trunk/packages/components/src/mobile/inserter-button/index.native.js)
- [x] [`mobile/link-settings/image-link-destinations-screen.native.js`](https://github.com/WordPress/gutenberg/blob/trunk/packages/components/src/mobile/link-settings/image-link-destinations-screen.native.js)

> @fluiddot I'm curious if you feel we should just update these `block-editor` imports to their relative paths as was done [here](https://github.com/WordPress/gutenberg/pull/56061/files#diff-3cd7fb1cc5bdfd84c10f2aab1bcbb1535af16124ad86c1ad3b4f3c83ec3f64a3R4), or if you have an example of a better import path to remove the `block-editor` dependency.

I think it depends on each case. In general, I feel that most of the above-referenced components/tools under the `components` package could be under the `block-editor` package.

I noticed that the following items are only imported in the `block-editor` package, so makes sense to relocate them there:

- [mobile/inserter-button/index.native.js](https://github.com/WordPress/gutenberg/blob/trunk/packages/components/src/mobile/inserter-button/index.native.js): [Here is the import reference](https://github.com/search?q=repo%3AWordPress%2Fgutenberg+path%3A*.native.js+InserterButton&type=code)
- [mobile/link-settings/image-link-destinations-screen.native.js](https://github.com/WordPress/gutenberg/blob/trunk/packages/components/src/mobile/link-settings/image-link-destinations-screen.native.js): [Here is the import reference](https://github.com/search?q=repo%3AWordPress%2Fgutenberg%20ImageLinkDestinationsScreen&type=code)

The other two would need a deeper analysis:

- [font-size-picker/index.native.js](https://github.com/WordPress/gutenberg/blob/trunk/packages/components/src/font-size-picker/index.native.js): The web version is also located in `components` package, so looks like it makes sense to keep it in its current location. However, we should update [this import of `getPxFromCssUnit`](https://github.com/WordPress/gutenberg/blob/12f286c4605db3ee2a3640eefb52d3fa894bc766/packages/components/src/font-size-picker/index.native.js#L14). The utility function `getPxFromCssUnit`, along the rest located in [`packages/block-editor/src/utils/parse-css-unit-to-px.js`](https://github.com/WordPress/gutenberg/blob/trunk/packages/block-editor/src/utils/parse-css-unit-to-px.js) seem could be located in the `components` package as seem to provide a generic functionality (i.e. not strictly related to the block editor).

- [mobile/global-styles-context/utils.native.js](https://github.com/WordPress/gutenberg/blob/trunk/packages/components/src/mobile/global-styles-context/utils.native.js): This item is to me the more complex one to resolve, as [it imports several items from the `block-editor` package](https://github.com/WordPress/gutenberg/blob/de3c98e1bc335b5d727b9b5f4a8f08f02cfee445/packages/components/src/mobile/global-styles-context/utils.native.js#L11-L16). I see two options here:
    - Move `global-styles-context` to `block-editor` package. We could consider the global styles as block-editor-specific, although this might introduce new circular dependencies.
    - Analyze the usage of the imported functionality from the `block-editor` package in `global-styles-context`. Identify if any should be located in the `components` package, or if the values provided by them could be passed directly as function arguments.
