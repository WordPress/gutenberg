# Issue #15799: Disabled component allows keyboard interaction on links

- URL: https://github.com/WordPress/gutenberg/issues/15799

- Updated: 2019-05-29T16:27:40Z

## Body

**Describe the bug**

In a custom block, I'm using [the `Disabled` component](https://github.com/WordPress/gutenberg/tree/master/packages/components/src/disabled) around a `ServerSideRender`ed list, much like [the Latest Comments block](https://github.com/WordPress/gutenberg/blob/514e61298d5c056ef6ec4d3859b959dc46735dec/packages/block-library/src/latest-comments/edit.js#L92-L97), when I noticed you can tab to the links that are rendered. Since you can't mouse-click on the links, it seems like keyboard activation should also be prevented.

**To reproduce**
Steps to reproduce the behavior:

1. Add a Latest Comments block
2. You can't click on the rendered links
3. Tab through the toolbar to the block contents
4. You'll see your focus move from the links in the Latest Comments content
5. If you hit enter, you leave the editor and go to that link

**Expected behavior**

Perhaps [removing the href on links](https://css-tricks.com/how-to-disable-links/#article-header-id-1) contained in `Disabled` would work? That seems to match with the spec for `a`:

> If the a element has no href attribute, then the element represents a placeholder for where a link might otherwise have been placed
> – [HTML Living Standard for `a`](https://html.spec.whatwg.org/multipage/text-level-semantics.html#the-a-element)

A quick test of `a` with no href in Safari + VoiceOver seems to work okay, but might not be very clear– there's no indication that the item is anything other than text, it does not communicate that "placeholder link" status. Some accessibility team feedback would probably be good here.

**Desktop (please complete the following information):**
 - OS: Mac
 - Browser: Chrome & Safari
 - Gutenberg: master @ 514e61298d5c056ef6ec4d3859b959dc46735dec

Thanks @ryelle for labelling this issue for accessibility feedback. Seems to me this is an interesting case. I'd like to split a few considerations in two groups:

## From a code perspective 

While the documentation of the `Disabled` component initially refers to "descendant tabbable elements", it makes then clear that this component is meant to be used for **form inputs**.

Looking at the code, this is exactly what it does:

https://github.com/WordPress/gutenberg/blob/0e46e9ef92d27aa4af849c482c81216b9c579410/packages/components/src/disabled/index.js#L66-L80

- adds a `disabled` attribute to all the form controls, see `DISABLED_ELIGIBLE_NODE_NAMES`
- if one of the focusable elements has a tabindex attribute, it removes it (I guess this is meant for non-natively focusable elements with a negative `-1` tabindex)
- removes `contenteditable` 

Basically the JS part doesn't do anything related to _links_. 

Actually, the Latest Comments content is not clickable because of the CSS part. It adds a CSS generated element that overlays all the block content, plus a couple `pointer-events: none` properties thus making the whole block not clickable.

At this point, I'm not sure why `Disabled` is used for Latest Comments to start with, when all that's needed is a few lines of CSS that could be added directly to the Latest Comments component.

Basically, seems to me `Disabled` is used incorrectly and its usage goes against its documentation.

Also, I'm not sure I understand why `Disabled` is used for the Latest Comments block and it's not for Latests Posts, Archives, etc. 

## Usability and Accessibility

The fact the block content can't be clicked with a pointing device but it can still be navigated through (and activated) when using a keyboard is definitely not ideal. I don't see a reason why the interaction with the wrapped component content should be different for users depending on the device / assistive technology they use.

Also, links can't be really "disabled". One option would be omitting the `href` attribute as @ryelle mentioned. However, I'm not sure interaction with links should be prevented in the first place.

These are links: they're supposed to behave like links also in a preview/edit context. Thinking also at the long term goal of inline-editing, I wouldn't recommend to try to prevent interaction with links.
