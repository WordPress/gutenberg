# Issue #49110: Improve CustomSelectControl's usability around max height

- URL: https://github.com/WordPress/gutenberg/issues/49110
- Author: cbirdsong
- Created: 2023-03-15T18:58:01Z
- Updated: 2025-02-11T22:29:26Z
- Comments: 5 of 5

## Body

Gutenberg's CustomSelectControl (the reimplementation of the standard `<select>` control) has a maximum height due to an issue reported in #19751, but this ends up making it require scrolling when it shouldn't really be necessary:

https://user-images.githubusercontent.com/1672206/225408652-d7e273ed-dd91-4c2e-a093-609040d256ff.mp4

There are two complementary ways this could be addressed.

**1) Adjust the max height based on media queries**. Right now, it's just a flat 400px. Increasing it based on `@media (min-height: whatever)` is not a silver bullet, but it would help on large displays and/or portrait-oriented displays.[^calc] 

**2) Make the design more compact.** By default, CustomSelectControl only shows 7 or 8 items[^margin], which is far fewer than `<select>` while taking up far more vertical space:

[![SelectControl](https://user-images.githubusercontent.com/1672206/225408311-46b45471-09cf-4067-96ab-a2134339930e.png)](https://wordpress.github.io/gutenberg/?path=/story/components-selectcontrol--default&args=options[0].value:default;options[0].label:Default;options[0].disabled:!undefined;options[1].value:0;options[1].label:0;options[2].value:1;options[2].label:1;options[3].value:2;options[3].label:2;options[4].value:3;options[4].label:3;options[5].value:4;options[5].label:4;options[6].value:5;options[6].label:5;options[7].value:6;options[7].label:6;options[8].value:7;options[8].label:7;options[9].value:8;options[9].label:8;options[10].value:9;options[10].label:9&globals=marginChecker:show;maxWidthWrapper:wordpress-sidebar) [![CustomSelectControl](https://user-images.githubusercontent.com/1672206/225408297-263ede93-91c6-4da1-8359-2d8e3071723d.png)](https://wordpress.github.io/gutenberg/?path=/story/components-customselectcontrol--default&args=options[0].key:default;options[0].name:Default;options[0].style:!undefined;options[1].key:0;options[1].name:0;options[1].style:!undefined;options[1].className:!undefined;options[2].key:1;options[2].name:1;options[2].style:!undefined;options[3].key:2;options[3].name:2;options[3].style:!undefined;options[4].key:3;options[4].name:3;options[5].key:4;options[5].name:4;options[6].key:5;options[6].name:5;options[7].key:6;options[7].name:6;options[8].key:7;options[8].name:7;options[9].key:8;options[9].name:8;options[10].key:9;options[10].name:9;size:__unstable-large&globals=marginChecker:show;maxWidthWrapper:wordpress-sidebar)

The amount of padding and margin[^margin] can definitely be reduced while keeping the control usable[^touch] and legible.

## Issue comments

### ciampo on 2024-07-10T14:25:07Z

URL: https://github.com/WordPress/gutenberg/issues/49110#issuecomment-2220659495

Thank you for the report! 

While we're not going to be able to drop the `400px` `max-height` for the current version of the component, we're about to merge an improvement that allows the `max-height` to be _less than_ 400px in case the popover meets the viewport edge.

As we're starting to gather feedback for a hypothetical new version of `CustomSelectControl`, I'd like us to consider allowing consumers of the component to set `min-height` and `max-height` for the select popover (either via react props, or CSS rules). cc @WordPress/gutenberg-components

I hope you'll consider making the sizing/spacing dynamic using `@media (pointer: coarse)`/`@media (pointer: fine)`. That could make it a lot more usable for mouse users while still preserving usability for touch.

### ciampo on 2024-07-11T07:23:07Z

> consider making the sizing/spacing dynamic using `@media (pointer: coarse)`/`@media (pointer: fine)`

That's a great point, and definitely something that we could/should take into account at a broader design level (cc @WordPress/gutenberg-design ).

Regarding `CustomSelectControl` specifically, I'm not sure how much of an impact that would make on the component, since its main purpose will be to allow custom option item designs provided by the consumers of the component.

If a consumer doesn't need a custom item design and/or wants a more compact select popover look, `SelectControl` is a good alternative.
