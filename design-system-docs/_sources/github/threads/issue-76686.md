# Issue #76686: eslint rule `no-unknown-ds-tokens` is mixing concerns

- URL: https://github.com/WordPress/gutenberg/issues/76686
- Author: anomiex
- Created: 2026-03-19T15:42:44Z
- Updated: 2026-04-23T11:32:29Z
- Comments: 4 of 4

## Body

By name and original description, the eslint rule `no-unknown-ds-tokens` is supposed to flag *unknown* ds tokens.

#76210 added something else: it will now also flag *known* token strings that aren't wrapped in `var()`, [even in contexts where that would be incorrect](https://github.com/Automattic/jetpack/pull/47684/changes/990de817c16a9bff11bd18414af76a34d13f6498).

Since both checks are in the same rule, it's not possible to ignore any false positives for the `var()` check without also ignoring the possibility that the token may be (or become) unknown in the future. It would be better for these to be separate rules so that one can be ignored without also ignoring the other.

Thanks for reporting. Help me understand what exactly you're trying to accomplish, so we can figure out the best course of action here.

Looking at the example you provided, this is a violation of the [`no-setting-ds-tokens`](https://github.com/WordPress/gutenberg/blob/trunk/packages/eslint-plugin/docs/rules/no-setting-ds-tokens.md) guideline, regardless of whether it's caught by this or that lint rule:

```jsx
<style>
	{
		// eslint-disable-next-line @wordpress/no-unknown-ds-tokens -- Seems to be thinking this is a use, not a redefinition.
		`
		:root {
			--wpds-color-bg-interactive-brand-weak: ${ sanitizedAccentColor };
		}
	`
	}
</style>
```

We don't allow this because it's unsafe — there are many tokens that need to change based on the accent color, and arbitrarily overriding one token manually isn't going to do the trick. The intended way to customize theme colors is to use `ThemeProvider`. Have you tried this yet, or is there any reason it's not possible here?
