Here's a minimal reproduction case for the floating point errors if you're curious 🙂 Run this:
```
node -p 'const n=(0.955/1.055)**2.4;const b=Buffer.allocUnsafe(8);b.writeDoubleBE(n);[process.version,n,b.toString("hex")]'
```
It will compute the `(0.955/1.055)**2.4` expression, and after printing Node version, prints the result as a decimal and also as a raw binary/hex IEEE number. The results with different Node versions are:
```
[ 'v20.19.6', 0.787412289395617,  '3fe9327b41ed8674' ]
[ 'v24.12.0', 0.7874122893956171, '3fe9327b41ed8675' ]
```
The result is different in the last (16th) decimal place, and in the raw form, in the least significant bit.

If you don't do the `**2.4` operation, the results are the same for both versions. That means that the newer Node.js (or more precisely newer V8 engine) implements the `Math.pow` operation differently.

This operation is done when converting a `rgb(90% 90% 90%)` color to OKLCH. Then the first step is converting the 0.9 RGB value to linear SRGB. And that involves the `**2.4` operation (removing the gamma correction). The one-bit difference is sufficient to change the final result when serializing the color to hex. `0.5` and `0.49999999` round to `1` and `0`, respectively.

This is the color.js code with which I started:
```js
const color = 'rgb(90% 90% 90%)';
const oklch = to( color, OKLCH );
const srgb = to( oklch, sRGB );
const hex = serialize( srgb, { format: 'hex' } );
console.log( hex );
```
The result is either `#e6e6e6` or `#e6e5e6`.

Interesting that the original Node/Chromium bug you mention also involves the srgb-linear expression `((c + 0.055) / 1.055) ** 2.4` 🙂 Looks like it's the most popular usage of the `Math.pow` operation.

However, it seems that it was Node 20/22 that returned the wrong value and that Node 24 returns the correct one. So there's no bug to report.
- Node 20: 0.787412289395617
- Node 24: 0.7874122893956171
- Chrome 143: 0.7874122893956171
- Firefox 148: 0.7874122893956171
- Wolfram Mathematica: 0.7874122893956171

See, everyone says it ends with `171`.

However, trying to calculate the value with an extra precision, using a specialized library, yields:
```
0.78741228939561703910723453738342362810...
```
The crucial part is the `...17039...` sequence, which suggest that it should be rounded to `...170` rather than to `...171`. But the real IEEE rounding is probably not so straightforward, there's also the binary representation which might round differently.

@ciampo I updated the hex formatting so that it's the same on all Node.js versions. Then the test snapshots are also always the same. That makes this PR ready.

The trick is to patch the `getColorString` function so that it does two serializations. First it serializes to the `rgb(r g b)` form, using the default precision, which is 5. This rounds the 0.8999999999 numbers to 0.9. The second step is `hex` serialization. That re-parses the `rgb` string and serializes it again as `hex`. This is now stable because the floating point differences were "ironed out" in the previous rounding step.

And the second part of the trick is to use `getColorString` consistently in the codebase, removing all instances of `serialize({format:'hex'})`.

As a drive-by fix, I'm removing the `inGamut: true` option because in the color ramps we are always working with colors that were already ran through `clampToGamut`.
