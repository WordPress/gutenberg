## Body

## What?

Updates unit tests to shim `Element#getClientRects` across all tests to return a reasonably-realistic emulated value based on expected layout boxes for the element.

Related: https://github.com/WordPress/gutenberg/pull/79295#issuecomment-4744590452

## Why?

Unit tests that expect a browser environment should emulate the browser environment as realistically as possible, so that the tests can be trusted to protect against regressions and match the expected user experience.

In practice, the absence of this behavior has been a recurring paint point:

- Focusable utilities [consider `getClientRects`](https://github.com/WordPress/gutenberg/blob/8a6ce6862b98d5d6d659cc0885b6aed80431495e/packages/dom/src/focusable.js#L60) when looking for focusable elements, so the absence of this shim produces results that don't match actual browser behavior.
- As evidenced by the removed code in this branch, we've had to apply this shim in a number of tests already due to these exact types of behavioral differences.

By managing this centrally, we can avoid developer confusion when encountering unexpected behavior in tests, and ensure that the tests are more accurate to the expected user experience.

## How?

Modifies `test/unit/config/global-mocks.js` to patch `Element#getClientRects` with an implementation that returns a basic `rect` object shape if the element is expected to have its own layout box. `global-mocks.js` already contains many other mocks which similarly seek to improve the realism of tests.

A few tests had to be modified after the patch was added, which I've committed individually with extended commit descriptions explaining what's happening:

- In 0af1e05d41f4a96788a9e7df113515f6a795181e, widget dashboard tests were updated to work through a `userEvent.setup` instance because "With the getClientRects shim, Ariakit will detect focusable elements outside the opened menu and try to disable them by overriding `Element#focus`, which the global `userEvent` makes non-writable. This is the exact reason we have the patch in global-mocks.js, but the patch only applies to instances of userEvent that are initialized through userEvent.setup, the solution proposed here"
- In 8d700923fb563472c1333e7433d07975ada07733, LinkControl tests were updated to accurately assert correct focus target because "The global getClientRects shim makes the behavior in these tests more accurate, where the link itself is what receives focus at the first focusable element, not the container itself. This updated assertion matches the true behavior a user will experience in the browser."
- In e0d12e598fbe39c7e22aedb86ab78d547185ece6, the test was patched to make `requestAnimationFrame` behavior more like how it does in a browser. The inline code for `withAnimationFramesBeforeTimers` explains what's happening here, and there's a legitimate race condition that could affect runtime usage. A separate pull request is being opened to improve this, at which point we could remove `withAnimationFramesBeforeTimers`.

For example, Menu tests have >4000 calls to `getComputedStyles` through userEvent `toBeVisible` and Ariakit helpers, and the shim here had added about 800 extra. There are trade-offs to this, explained in the included code comment, but probably fine enough for our tests. I also temporarily reverted the `waitFor` change in 0a4bd354512aed82ad6ac2fa62f77017ec4d1d61 to see if it has an impact, but my impression is that `waitFor` is an actual improvement to the test regardless of performance and test passing or failing.

### jsnajdr on 2026-06-24T10:13:57Z

URL: https://github.com/WordPress/gutenberg/pull/79353#issuecomment-4788175216

> the general performance problem of `getComputedStyle`

JSDOM used to have zero support for CSS, and in more recent versions it was gradually added. Today it has a more-or-less complete CSSOM implementation. It does CSS parsing and validation, and calculates the effective styles. It does this correctly, but is not very fast and optimized. That would need a very significant amount of work. And it also doesn't do the actual layout, needed for `getClientRects` to return correct values.

The various layout and timing quirks and hotfixes that this PR does are not long term sustainable. At some point we need to give up, accept that only a real browser will do everything correctly, and switch to e2e tests 🙂 Nowadays the available e2e tooling is really beautiful and pleasant to use; it used to be much worse not so long time ago.
