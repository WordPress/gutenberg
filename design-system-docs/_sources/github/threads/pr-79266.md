<!-- In a few words, what is the PR actually doing? -->

Adds inline color-palette editing to the block inspector's color picker. While editing a page/post you can now manage palette colors directly from the color control instead of switching to global styles. There a different capabilities depending on the palette:

- Custom colors: Allows to add, rename, change color, and delete.
- Theme / default colors: recolor only (allows only value editing. Names/slugs stay fixed, matching what GS allows today).

All edits persist to the user's global styles entity with optimistic updates and snackbar feedback, and preview live on the canvas as you drag.

In terms of UX, after trying a few different directions I found that the way it could work best would be by not moving too far from the design language we have now for the palette and adding a few buttons and states.

Regarding implementation, the direction I took was to have this behind a private prop (as we have some other preceding examples). 

The way it works is the following:

- We're adding actions next to the color name (below the square that triggers the picker). We have Edit/Delete and when clicked, the area transforms into a form. Once you open the color picker it will edit the color value, and there's also an input to change the name (if it is a custom color, not available for theme or core colors). Hitting save will save the changes and will trigger a snackbar so that we can give immediate feedback
- Saving new custom colors: Once you pick a color that's not part of any palette, next to the color name there'll be a "+" button to save it. Clicking that button will open the form, so that you can set the color name and adjust the color if necessary. There's also a round `+` button in the Custom color palette so you can add them from there. These two affordances are there, because the latter may not be reachable depending of the context (if there are too many custom colors, or if the popover is opened in a way that's trimming some content and only showing the top)

**A few notes:**

- Sorry for the size of the PR, but it was really difficult to decouple things.
- Included a fix for bug I've found with the color picker when the colors were changing fast. It became noticeable while debugging in Firefox. I've commited that separately in case we want to take it out of the PR and take care of it independently.
- There's an issue (preceding these changes) when changing custom color names, the value is lost. It was [reported here](https://github.com/WordPress/gutenberg/issues/50232), and maybe having the inline editing is exposing it more. We should try to fix that one.
- Color previewing is applied as a single css variable style override on the canvas, not as a global-styles entity edit per pointer move. This avoids re-merging the config, regenerating
the full block stylesheet.
- Also updated the contrast checker. It now subscribes to style overrides, so its warning updates during preview for saved colors.
- Added a small local `setImmutably` copy in `@wordpress/editor` because no package exports a public one (block-editor and global-styles-engine both keep theirs internal)

## Why?
<!-- Why is this PR necessary? What problem is it solving? Reference any existing previous issue(s) or PR(s), but please add a short summary here, too -->

Managing colors when editing content was really a pain. If you are testing out colors for the website you are building you want to be able to save them to your palette in the same context, without the need to go to global styles or writing an hex code to later save in a different screen.

The idea was to have this only for custom colors. While demoing it to @Mamaduka and @richtabor at WCEU they suggested that it'd be also interesting to have this same functionality for theme colors.

## How?
<!-- How is your PR addressing the issue at hand? What are the implementation details? -->

`ColorPalette` receives an editing config keyed by each palette `slug`:

| capability | operations |
|---|---|
| `full`  | add / rename / recolor / delete (custom) |
| `value` | recolor only (theme, default) |

When there's no value (slug), then it's read only.

Per the repo's guidance, the editing config is passed via a private prop (the same pattern as `globalStylesDataKey`, etc)
obtained through `unlock()`. It does not appear in the public props type.

if the capabilities are there, then the palette will show up different UIs for the different use cases.

### aduth on 2026-06-17T19:23:38Z

URL: https://github.com/WordPress/gutenberg/pull/79266#issuecomment-4734370691

Watching the video, I wonder about the accessibility of the proposed experience and particularly the focus order and focus shifting. It looks like clicking the "Add" button at the bottom of the panel shifts focus back up to the input field for the name, but it's placed _after_ the field that the user is expected to interact with to choose the color. So the process of adding a color involves moving focus backwards, and the user being aware that they have to then select a value in a preceding field (which may not be obvious to screen reader users, for example).

I wonder if this should be more like how the custom color selector works in the Site Editor, which is still "inline". And we'd have the benefit of reusing existing components and user familiarity.

### juanfra on 2026-06-18T08:27:31Z

URL: https://github.com/WordPress/gutenberg/pull/79266#issuecomment-4739670217

Thanks for looking into this @aduth! Fair point about the focus order.

The idea of the editing zone is to keep the user in the same color picking flow with a familiar UI, instead of the friction of sending them somewhere else to manage colors and come back. On close (save or cancel) focus returns to where it was.

You're right that for SR users the order of landing on the name field can be confusing, especially when no color is chosen yet. I'll iterate on that and adjust the focus for these cases.

Regarding reusing the PaletteEdit: I personally don't think it fits here. In a popover it doesn't scale. The list of custom colors pushes the rest down, and the experience can be quite messy if there are quite some colors. It also adds a second way to pick colors (the circle options, which are a way to "select" a pre-saved color in that context) next to the square swatch on top, which is more confusing than familiar in this context.

> I'm not sure I follow the UX behind the changes at 0:42 in the video of the PR description — what's the logic that decides that the color being edited is the same as the above paragraph, or becomes "detached" only for the current paragraph?

The logic is that if you click on the pencil icon, you're editing the saved color. If you haven't clicked the pencil, then you're not in editing mode and it follows the same logic as we have right now. It changes to an "on the fly-custom" value, which now has the "+" icon to save to the custom palette. 

> I also share the same gut feeling about parts of the UI appearing / disappearing, it could be quite confusing for the end users. Have we explored a separate dialog?

The are a few problems with dialogs. One is that it'll be adding an overlay that will make difficult to actually preview the color that you're trying out. Another is that it'll force you to "leave" the color picking context, and it is a pattern that we don't have in the editor. Finally, it'll also get complicated with contrast checking, you could be coming and going between dialog and actual picker.

I've iterated on different directions, and this one felt the most natural in the context of being in the flow of editing and creating content. I think the strength here is that people are familiar with how the picker works, and the proposal doesn't move far from that. But maybe there's other directions we'd like to explore.

From the tests I performed (I asked a few people to try it out), users were smoothly managing their colors, it felt natural to them. And the feedback was that it was great to be able to manage colors without being forced to exit the flow.
