# Issue #77039: UI: Add Breadcrumb component (adapted from admin-ui)

## Body

## What problem does this address?

Currently, `@wordpress/admin-ui` implements a `Breadcrumb` component that is tightly coupled to the `@wordpress/route` router. This limits its reusability (such as in projects that _don't_ use `@wordpress/route`, or use-cases detached from routing) and makes the `admin-ui` package responsible for maintaining a lot of underlying UI implementation details.

## What is your proposed solution?

`@wordpress/ui` should implement a `Breadcrumb` component that is agnostic to application concerns like routing.

It is common for component libraries / design systems to provide breadcrumbs behavior:

- https://chakra-ui.com/docs/components/breadcrumb
- https://mui.com/material-ui/react-breadcrumbs/
- https://coss.com/ui/docs/components/breadcrumb
- https://ui.shadcn.com/docs/components/radix/breadcrumb

Implementation details:

- It should be a pure UI primitive, using standard HTML elements or composing other low-level `@wordpress/ui` components
- Items are rendered as `<a href>` by default, though render behavior can be controlled through `render` prop (standard component behavior described in README.md)
- This shouldn't just be a straight port of the existing implementation. Consider improvements to accessibility and semantics (e.g. `aria-current="page"`).
   - Also adapting to [compound components](https://github.com/WordPress/gutenberg/blob/trunk/packages/ui/CONTRIBUTING.md#compound-components) as appropriate
- Does not render header elements (although, again, render element may be customized through `render` prop)
- Should handle truncation (see discussion in #76709)
- `@wordpress/admin-ui`'s breadcrumb implementation should be refactored to use this component, though also keep in mind other related changes planned in #77040

**Needs Design:**

- While the design proposals in #76709 work well in larger viewports, it's not clear how best to handle longer breadcrumbs at smaller viewport sizes (e.g. collapsing or truncating items). There's some discussion in #76709, but the designs of the complete user flow (including _expanding_ truncated content) are incomplete.

Hey @abd-RAHEEM , glad you're interested in helping push this along!

Before jumping into implementation, I think it might be good to get some design alignment on some of the finer details of the component, especially the truncation behavior. A lot of the discussion in #76709 revolved around how the text should be truncated, but (a) I don't know that there was a firm decision there, and (b) we haven't really talked much about what should happen with the truncated content. For example, should we show the truncated items in a menu / popover after clicking the "..." ellipsis? There might be a dependency on related components like what's being added in #76438 . It's also not clear if that truncation happens automatically based on text overflow, or if we'll want to handle it with designated breakpoints (possible dependency on #73361).

I'm going to add a "Needs Design" label so that we can try to get some more clear design direction on some of these decisions.

In the meantime, I'd be interested to get your thoughts on this or other requirements we might need for the implementation, or an API design proposal for the component. Maybe we can learn something from how other component libraries implement these components.
