# PR #77746: ui: Restore overlay borders and tokenize backdrop on `Dialog`/`AlertDialog`/`Drawer`

## Body

## What

Follow-up to #77691. Three related visual tweaks to the overlay popups:

1. **Always show the hairline border** on `Dialog`, `AlertDialog`, `Drawer`, `Popover`, and `Modal` (`@wordpress/components`) — including when a backdrop is rendered. Previously #77691 hid the border in modal mode because the popup edge looked fuzzy against the dark backdrop. `Modal` had no border at all; one is added to match.
2. **Tokenize the backdrop**. Replace the hardcoded `rgba(0, 0, 0, …)` / `rgb(0, 0, 0)` backgrounds with `--wpds-color-bg-surface-neutral-weak`, and bump opacity from 35% (or 15% on `Popover`) → 75% so the lighter token retains comparable presence. Applied across `Dialog`, `Drawer`, `Popover`, and `Modal`.
3. **Inset `Drawer`'s popup by 4px** from every anchored viewport edge and round all four corners, so the now-always-on hairline border doesn't butt directly against the viewport edge.

`AlertDialog` inherits the first two changes via composition (its `Popup` already uses `dialogStyles.backdrop` / `dialogStyles.popup`), so it picks them up without a code change.

## Why

In #77691 we landed an a11y fix that gave every overlay a visible border in forced-colors mode. To accommodate, we suppressed the regular-mode border whenever a backdrop was rendered, because the popup edge looked clipped/fuzzy against the dark scrim ([#77691 (comment)](https://github.com/WordPress/gutenberg/pull/77691#discussion_r…)). The cause was contrast: a near-black scrim made the token-colored stroke read as a thin cut.

Switching the backdrop to a neutral surface token instead of pure black removes the contrast issue at its source, lets the popup keep its border in every mode, and brings overlay scrim color into the design system. A small 4px inset on `Drawer` does the same thing for the viewport-edge case (where the border was being clipped by the screen edge instead of by the scrim). Extending the same border + tokenized scrim to `Popover`'s backdrop variant and to the legacy `Modal` keeps the full overlay family visually consistent.

## Behavior

| Component                          | regular (no backdrop) | regular (backdrop)        | forced-colors (any)            |
| ---------------------------------- | --------------------- | ------------------------- | ------------------------------ |
| Dialog (non-modal)                 | token border          | —                         | `CanvasText` border (UA-substituted) |
| Dialog (modal, default)            | —                     | **token border** (was: —) | `CanvasText` border (UA-substituted) |
| Drawer (non-modal)                 | token border          | —                         | `CanvasText` border (UA-substituted) |
| Drawer (modal, default)            | —                     | **token border** (was: —) | `CanvasText` border (UA-substituted) |
| AlertDialog (always modal)         | —                     | **token border** (was: —) | `CanvasText` border (UA-substituted) |
| Popover (no backdrop)              | token border          | —                         | `CanvasText` border (UA-substituted) |
| Popover (`backdrop` prop)          | —                     | **token border** (was: —) | `CanvasText` border (UA-substituted) |
| Modal (`@wordpress/components`)    | —                     | **token border** (was: none) | `CanvasText` border (UA-substituted) |

`Select` and `Tooltip` are untouched — they were already correct after #77691.

## Implementation notes

- `Dialog`'s backdrop now drives its alpha through the `opacity` property (matching `Drawer`'s existing pattern). The previous `&[data-open] { opacity: 1 }` rule becomes redundant — Base UI only sets `data-starting-style` / `data-ending-style` during transitions, so the resting state is the default `opacity: 0.75`, and the existing `transition: opacity` interpolates 0 ↔ 0.75.
- The `.backdrop ~ * .popup { border-color: transparent }` rule is removed in `Dialog`, `Drawer`, and `Popover`.
- The explicit `@media (forced-colors: active) { .popup { border-color: CanvasText } }` blocks are removed entirely from `Dialog`, `Drawer`, and `Popover`. The popup already declares a colored token border, so the UA substitutes a system color (typically `CanvasText`) automatically in forced-colors mode — same pattern documented in `overlay-chrome.module.css` for the scroll separator. This removes the last special-case block from the popup CSS.
- `Drawer` introduces `--popup-inset: var(--wpds-dimension-padding-xs)` (4px), applied to every anchored side per direction. Per-direction `border-*-radius` declarations are removed in favor of a single `border-radius: var(--wpds-border-radius-lg)` on `.popup`. Swipe-out transforms are extended to `translate(±100% ± var(--popup-inset))` so the popup still slides fully off-screen from its inset resting position.
- `max-width` / `max-height` calcs on `Drawer` remain `100vw - var(--viewport-inset)` — they're a generous safety bound and the trailing-edge gap stays comfortably within the viewport even with the new 4px inset.
- `Modal` (`@wordpress/components`) bakes the 75% alpha into the backdrop color via `color-mix(in srgb, var(--wpds-color-bg-surface-neutral-weak), transparent 25%)` rather than the `opacity` property, because the existing `animation__fade-in` mixin uses `animation-fill-mode: forwards` and would override a static `opacity: 0.75`. The new border on `.components-modal__frame` matches `Dialog`'s declaration (`var(--wpds-border-width-xs) solid var(--wpds-color-stroke-surface-neutral)`); `@include reset` already applies `box-sizing: border-box`, so the 1px is absorbed into existing dimensions and does not shift layout.

## Testing instructions

1. `npm run start`, then open the Storybook for `Dialog`, `AlertDialog`, `Drawer`, `Popover`, and `Modal`.
2. **Modal backdrop**: open each component's modal/backdrop story (`Dialog` default, `AlertDialog`, `Drawer` default, `Popover` "Backdrop" story, `Modal` default). The backdrop should now read as a soft light wash rather than a near-black scrim, and the popup should have a visible 1px hairline border around all four edges.
3. **Non-modal**: open the non-modal `Dialog`/`Drawer` stories and the default (no-backdrop) `Popover` story. These were already showing the border in #77691 — confirm no regression (still token border, no backdrop).
4. **Drawer edge**: open the `Drawer` stories for each of the four directions (left/right/up/down). The popup should sit ~4px off the anchored viewport edge with all four corners rounded, and there should be a continuous border around the perimeter (no clipped/cut-off edge against the viewport).
5. **Drawer swipe**: swipe-dismiss a `Drawer` from each direction. The popup should still slide fully off-screen with no sliver remaining at the anchored edge.
6. **Forced-colors / High Contrast**: re-open every story with Windows High Contrast mode (or Edge "Force colors"). Every popup should still show a `CanvasText` border around its edge — now via UA color substitution rather than an explicit forced-colors override.
7. **Reduced motion**: enable `prefers-reduced-motion` and confirm the backdrop snaps in/out without the opacity transition (`Dialog`/`Drawer`/`Popover`); `Modal`'s fade-in mixin is already gated on `not (prefers-reduced-motion)`, so its backdrop should also snap in.

### jasmussen on 2026-05-20T06:42:32Z

Thanks for the ping. I don't personally love the border on a purely visual level; it adds a little bit of visual noise in an otherwise very clean context. I'm also not quite sure I understand precisely why we need a border: it doesn't meet any contrast ratios and thus doesn't seem to technically improve anything that isn't already handled, if more subtly, by the drop shadow. It looks to me purely as a style change, one that I'm not completely convinced about.

However that's purely a personal opinion, and I don't feel strongly about it. I don't want to block _any_ of this work from moving forward, so consider that first paragraph mostly as a question.

I will also say if we do move forward, I think we should lean into it as a style change: seek out where this shares visual language with other elements in the component library and emphasise that. E.g. does this share some visual cues from the Card component? If yes, perhaps that means the borders should be the same? Conceptually we could think of this as simply an "elevated card" (that happens to have modal behavior). A final idea which would almost certainly be outside the bounds of this effort: I've seen some modals focus the modal _itself_ on mount, rather than the first tabbable (which almost inevitably means the close button). In those cases, the focus style is on the card itself. If we were to do this, it might translate cleanly to our other focusables: 1px border at rest, 1.5px theme color on focus. It might still have focus-visible handling, but it would be nice when keyboarding through.

Is that helpful? Let me know any nuance I'm missing.
