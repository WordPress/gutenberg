## Body

## What

Adds a `cornerRadius` theme aspect to `ThemeProvider`, letting consumers pick a roundness preset for a subtree: `none`, `subtle`, `moderate`, or `pronounced`.

Preset values are authored as Terrazzo modes on the border-radius primitives and emitted as prebuilt CSS. `ThemeProvider` always sets `data-wpds-corner-radius` on its scoping div (defaulting to `subtle`); the cascade updates `--wpds-border-radius-*` for all `@wordpress/ui` components in that subtree.

Also includes a corner-radius control in the Design System Theme Storybook toolbar and a preset `<select>` in the Example Application story.

## Why

Corner radius is a meaningful theme personality axis (sharp vs. soft UI), but today the border-radius scale is static. Color and cursor are already configurable via `ThemeProvider`; radius can follow the same pattern so apps can tune roundness without overriding tokens manually.

Using build-time token modes (not runtime CSS injection) keeps this simple, performant, and composable: multiple `ThemeProvider` instances on a page can use different presets, and nested providers inherit/override via the cascade. Portalled UI (dialogs, tooltips, menus) is expected to render its own dedicated `ThemeProvider`, which carries the preset to the portalled subtree rather than relying on the root provider's preset leaking through `:root`.

Early exploration used uniform multipliers per preset (e.g. 2× / 3× across all primitives). That felt **lop-sided in practice**: absolute jumps grow with token size, so cards and dialogs (`--wpds-border-radius-lg`) changed dramatically while buttons and inputs (`--wpds-border-radius-sm`) barely moved. The preset values are **hand-tuned** per primitive instead. At higher presets the per-size scale intentionally **compresses toward a shared radius** — small controls round up substantially while large surfaces are held back — so a `pronounced` theme reads as strongly rounded controls on calmly rounded cards and shells, rather than ballooning every corner.

A **runtime taper formula** (e.g. per-token multiplier curves or a `multiplier` escape hatch) was considered but deferred — with four presets across five primitives (~20 explicit values), explicit mode values are easier to reason about, validate in Storybook, and ship without a second code path.

The scale started at six presets and was **reduced to four** after feedback that six was too many for an initial offering and that some adjacent names were ambiguous.

Preset names use a **roundness-amount scale** (`subtle` → `pronounced`) rather than t-shirt sizes or shape words (`sharp`, `pill`, etc.). That avoids colliding with the underlying `--wpds-border-radius-*` token sizes (`xs`–`xl`) and avoids overpromising a specific corner shape on larger surfaces (e.g. a card in the default preset is gently rounded, not literally "sharp"). `none` is kept as the one literal, unambiguous value.

## How

- **`border.json`**: Each of the five `radius` primitives (`xs`, `sm`, `md`, `lg`, `xl`) defines `$extensions.mode` overrides for all four presets (`corner-radius-none`, `-subtle`, `-moderate`, `-pronounced`). The `xl` primitive (page and app shell surfaces) is the newest addition and is brought into the preset system here so shells scale alongside the other steps. `subtle` is the default and matches the static base values, but is authored explicitly like the others (no longer a no-op baseline). The `tokens/modes/*.json` files and prebuilt CSS are generated from these.
- **`terrazzo.config.ts`**: Added a `modeSelectors` entry per preset, each gated on its `[data-wpds-corner-radius="…"]` attribute.
- **`ThemeProvider`**: New `cornerRadius` prop (a `CornerRadiusPreset` string); resolves with inheritance (default `subtle`) and always writes `data-wpds-corner-radius` (including `subtle`).
- **`useThemeProviderStyles`**: Resolves the preset into `resolvedSettings`; no runtime `--wpds-border-radius-*` emission.
- **Storybook**: Design System Theme toolbar control for corner radius; preset `<select>` in the Example Application demo, whose "General" card now includes `InputControl`, `SelectControl`, and a Save `Button` so the radius change is demonstrable across input and control sizes alongside cards; falsy toolbar globals coerced to `undefined` so invalid values like `''` are not passed through.
- **Docs**: README + CHANGELOG updated; `CornerRadiusPreset` exported from `@wordpress/theme`.

### Preset scale

| Preset | xs | sm | md | lg | xl |
|--------|----|----|-----|-----|-----|
| none   | 0  | 0  | 0   | 0   | 0   |
| subtle (default) | 1 | 2 | 4 | 8 | 12 |
| moderate | 6 | 8 | 12 | 16 | 20 |
| pronounced | 18 | 20 | 22 | 24 | 26 |

`subtle` mirrors the existing static radii. Toward `pronounced`, the smaller primitives climb steeply (e.g. `xs` 1 → 18) while the larger surfaces grow more gently (`lg` 8 → 24, `xl` 12 → 26), so compact controls become strongly rounded while cards and shells stay tastefully — not excessively — round.
