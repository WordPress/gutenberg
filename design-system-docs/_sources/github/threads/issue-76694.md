# Issue #76694: Input validation error on link control not explicitly connected to input field

- URL: https://github.com/WordPress/gutenberg/issues/76694
- Author: joedolson
- Created: 2026-03-19T18:14:50Z
- Updated: 2026-03-26T10:46:52Z
- Comments: 3 of 3

## Body

### Description

Error messages need to have an explicit connection to the field that generated the error. The input validation on the link control displays a message which is announced using `aria-live`, but is not connected to the input. While this will serve in most cases, it will be a problem if the user misses the announcement for any reason (it's overridden by another message, just missed because of distraction, etc.). It won't be announced if the user navigates away from the field (e.g., to the submit button), and then navigates back.

Two suggestions:

1) Explicitly connect the two fields by using `aria-describedby` with the ID attribute of the error message.
2) Announce the message through `a11y.speak()` instead of adding a new `aria-live` region specifically for that message.

### Step-by-step reproduction instructions

1. Add a paragraph with text.
2. Select text and add a Link
3. Enter a non-URL string like 'test' in the field and click 'Submit' or press the 'Enter' key.
4. Note the appended text with the invalid URL error message with no ID connection to the input.

Thanks for testing this 🙏

The thing I was worried about here is redundancy in certain AT/browser combinations, because we do in fact associate the error message with the field, through the [validity APIs](https://developer.mozilla.org/en-US/docs/Web/API/ValidityState). The visible error message is actually just showing whatever the [input element's `validationMessage`](https://developer.mozilla.org/en-US/docs/Web/API/HTMLInputElement/validationMessage)  holds. And if I understand correctly, some environments do read out this message on focus, or could start reading it out at any given version. If that's true, would the risk of a double announcement (one from the validity APIs, one from the aria description) in some environments be acceptable here in your opinion?

I tried to find a balance between "stick with browser APIs" and "acknowledge limitations of AT behavior consistency", but would appreciate some guidance on this point.

### joedolson on 2026-03-19T22:12:20Z

URL: https://github.com/WordPress/gutenberg/issues/76694#issuecomment-4093620638

The `validationMessage` value isn't communicated directly to users in the accessibility API. The standard practice would be to inject that value into a field that will be read. I'm not aware of anything that currently reads it directly; but the full matrix of tests for that is pretty substantial, so I could be missing something. 

On the whole, I'd consider the risk of a double message to be less of a concern than the risk of somebody missing the error. Screen reader users are able to stop messages at any point during the speaking; so they will only hear as much as they need.
