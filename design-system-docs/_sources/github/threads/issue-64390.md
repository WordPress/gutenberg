## Body

Extracted from https://github.com/WordPress/gutenberg/pull/64267#discussion_r1710061434

[`TimePicker`](https://wordpress.github.io/gutenberg/?path=/docs/components-timepicker--docs) was originally designed with a fairly narrow scope; the date picking UI in the page inspector:

<img width="378" alt="Screenshot 2024-08-09 at 09 56 49" src="https://github.com/user-attachments/assets/5a1853c2-508e-441a-9674-76dbb2e10988">

In this context (popover) there is room enough for a more elaborate UI with multiple controls. However in a more traditional form setting this design is convoluted and overly prominent. Let's explore a more lightweight design, applicable either as a variant or a full redesign. 

Inspiration can be taken from the [`datetime-local` input type](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/input/datetime-local) which condenses everything into a single text field with a built-in calendar/time selection popover: 

<img width="363" alt="Screenshot 2024-08-09 at 09 59 11" src="https://github.com/user-attachments/assets/c7b65faf-7e44-4d93-a8e2-d99f2c8ae630">

While I agree that TimePicker feels heavy, the separate controls also ensure accessibility. Calendar and time controls are two of the most difficult UIs to make accessible.

The native datetime-location input type allow selection of each date/time segment:

<img width="363" alt="356532746-c7b65faf-7e44-4d93-a8e2-d99f2c8ae630" src="https://github.com/user-attachments/assets/91572134-044b-40aa-a8e9-6e2e4046a1ab">

### jameskoster on 2024-08-12T12:34:53Z

URL: https://github.com/WordPress/gutenberg/issues/64390#issuecomment-2283854555

@christopherabalos absolutely, 100%! I think the first step here is to assess the accessibility of the `datetime-location` input type, and how much of that should be embodied 1:1 in the updated design. 

From there it'll mostly be a case of applying the wp design language to the visuals, as @seifeldinio did above. 

It's worth keeping date _range_ picking in mind as well (https://github.com/WordPress/gutenberg/issues/60971 as pointed out above), with additional shortcuts for things like "Last week", "Month to date", etc. This will be useful for filtering data views (e.g. to show pages published in the last month).

### mirka on 2024-08-30T16:57:52Z

URL: https://github.com/WordPress/gutenberg/issues/64390#issuecomment-2321977162

Might be stupid question, but what is stopping us from just using the native `<input type="datetime-local">` (or `<InputControl type="datetime-local">`)?  Especially when we want to shift to this "popover" style. A [recent accessibility test](https://www.digitala11y.com/input-type-date-the-accessibility-of-html-date-picker/) said that "its overall experience surpasses any other custom date picker I’ve encountered on various booking platforms". And we get a ton of stuff for free, like mobile support.

Even for the date range picker case, I find it likely that the easiest way to build that accessibly is to use two native `datetime-local` inputs, rather than going for a custom or library solution.
