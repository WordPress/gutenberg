## Body

## What?

Part of the ESLint v10 upgrade effort — see #76506.

Upgrades ESLint from v8 to v10 and migrates the entire codebase to flat config format. Also updates `@wordpress/eslint-plugin` and `@wordpress/scripts` to support the new config format while maintaining backward compatibility for existing consumers.

## Why?

ESLint v8 reached end of life. v9 introduced flat config as the default, and v10 removes the legacy eslintrc format entirely. This upgrade ensures Gutenberg stays on a supported ESLint version and benefits from the latest rule improvements across all plugins.

## How?

This is a multi-layered migration:

### 1. Dependency upgrades (`package.json`)
- ESLint v8 → v10
- All ESLint plugins upgraded to v10-compatible versions (e.g., `eslint-plugin-import` → `eslint-plugin-import-x`, `@typescript-eslint/*` v6 → v8)
- Added `globals` and `typescript-eslint` as devDependencies (replacing the old `env` and parser config patterns)
- Added `eslint-formatter-compact` (compact formatter was removed from ESLint core in v10)

### 2. `@wordpress/eslint-plugin` flat config conversion
- All config files under `packages/eslint-plugin/configs/` rewritten to export flat config arrays instead of eslintrc objects
- Added `babel-parser-compat.js` — a compatibility wrapper that adapts `@babel/eslint-parser` for flat config's `languageOptions.parser` format
- Used `fixupPluginRules` from `@eslint/compat` for plugins that haven't yet migrated to flat config natively (`eslint-plugin-import`, `eslint-plugin-react`)
- Added `dedupePlugins` utility in `index.js` to prevent ESLint v10's "Cannot redefine plugin" error when consumers spread config arrays that share plugin namespaces
- Widened peer dep to `"eslint": "^9.0.0 || ^10.0.0"` for transition period

### 3. eslintrc compatibility wrapper (`packages/eslint-plugin/eslintrc/`)
- New `@wordpress/eslint-plugin/eslintrc` entry point for ESLint v9 consumers still using `.eslintrc.*` files
- Converts flat config arrays back to eslintrc-compatible objects (rules, plugins, parser, parserOptions, settings, overrides)
- Maps internal parser names to resolvable package names (e.g., `@wordpress/babel-eslint-parser-compat` → `@babel/eslint-parser`)
- Maps flat config plugin namespaces to eslintrc plugin names (e.g., `@eslint-community/eslint-comments` → `@eslint-community/eslint-plugin-eslint-comments`)
- Prints deprecation warning on import

### 4. Root config migration
- `.eslintrc.js` → `eslint.config.mjs` using flat config format
- `.eslintrc.strict.js` → `eslint.config.strict.mjs`
- Removed `.eslintignore` (patterns moved to `ignores` in flat config)
- Package-level `.eslintrc.json` files replaced with `eslint-overrides.cjs` files loaded from the root config

### 5. `@wordpress/scripts` lint-js updates (`packages/scripts/`)
- `lint-js.js` updated to detect and use flat config (`eslint.config.*`) with fallback to eslintrc
- Default config changed from `.eslintrc.js` → `eslint.config.cjs`
- Removed old `config/.eslintrc.js` and `config/.eslintignore`, replaced with `config/eslint.config.cjs`

### 6. Pre-existing lint error fixes
- Fixed ~120 lint errors surfaced by upgraded plugin rules
- Removed unused catch block variables (ESLint v10 `no-unused-vars` `caughtErrors` defaults to `"all"`)
- Updated `eslint-comments/*` rule prefixes to `@eslint-community/eslint-comments/*`
- Added `// eslint-disable-next-line react-compiler/react-compiler` for known false positives on `ref.current` mutations in effects ([facebook/react#29196](https://github.com/facebook/react/issues/29196))
- Converted Playwright test assertions to web-first patterns (`toHaveAttribute`, `toHaveValue`, etc.)
- Fixed testing-library naming convention violations
- Fixed type-only imports

### 7. RuleTester compatibility
- Updated all `@wordpress/eslint-plugin` rule tests from `parserOptions` to `languageOptions` format
- Tests using `parser` string references converted to `languageOptions.parser` object references

### 8. CI fixes
- `bin/test-create-block.sh` updated to generate `eslint.config.cjs` instead of `.eslintrc.js`
- Added `example-*/` to global ignores for directories generated during CI build tests

```js
// eslint.config.mjs
import wordpress from '@wordpress/eslint-plugin';

export default [
  ...wordpress.configs.recommended,
  // your overrides
];
```


### Manual: eslintrc consumer (ESLint v9)

```js
// .eslintrc.js
const wordpress = require('@wordpress/eslint-plugin/eslintrc');

module.exports = wordpress.configs.recommended;
```

```bash
ESLINT_USE_FLAT_CONFIG=false npx eslint --print-config test.js
```

<summary>Click to expand</summary>

## 1. Breaking change

This update includes multiple, simultaneous breaking changes:

- The export format of `@wordpress/eslint-plugin` changed fundamentally (flat config array)
- In `@wordpress/scripts`, the old `config/.eslintrc.js` file is deleted, meaning that folks who were `extends: [require.resolve('@wordpress/scripts/config/.eslintrc')]` in their configs will now get an error
- Node.js minimum version bump: maybe this could be carried out separately?
- ESLint 8 comaptibility dropped at once, meaning that consumers don't have a grace period to update to the new config

Since it's tooling, I assume this can be fine, but let's discuss it explicitly — especially since migrating to the new ESLint config is not necessarily a straightforward task

## 2. Missing details about coordination

For a change of this impact, we should plan carefully the communication and timing around it: maybe a Make Core post, dev notes, ample time between the announcement and the release, and maybe some tooling (codemod, or even a AI agent prompt?) to help with the migration.

## 3. The ESLint 9 compat wrapper seems incomplete [Opus generated]

Opus flags some notable gaps:

### Missing `globals` conversion

The `flatToEslintrc()` function converts `languageOptions.parser` and `languageOptions.parserOptions`, but **does not convert `languageOptions.globals`**. Since the flat configs define globals like `window`, `document`, `wp`, `SCRIPT_DEBUG`, Node.js globals, and ES2015 globals via `languageOptions.globals`, the eslintrc wrapper will produce a config missing all global variable definitions. This will cause `no-undef` errors for every consumer using the compat wrapper.

### Deprecation warning on import — noisy

The wrapper unconditionally calls `console.warn()` at import time. This means every `lint-js` invocation will print a deprecation warning, which is unnecessarily noisy during CI runs and local development for projects that haven't migrated yet.

### Only supports ESLint v9, not v8

The wrapper only targets ESLint v9 in eslintrc mode (`ESLINT_USE_FLAT_CONFIG=false`). Since the peer dependency explicitly drops v8, consumers must first upgrade ESLint to v9 *before* they can use the compat wrapper — which itself is deprecated. This creates a two-step migration where both steps require config changes.

Maybe, as an additional intermediate steps, we could use the fact that ESLint 9 supports both flat and eslintrc?

## 4. The CHANGELOG entry feels inaccurate

The `@wordpress/eslint-plugin` CHANGELOG states 

> Replaced `eslint-plugin-import` with `eslint-plugin-import-x`.

but internally it still uses `eslint-plugin-import`? The PR description mentions the same thing.


## 5. `dedupePlugins` — fragile mutation pattern [Opus generated]

The `dedupePlugins` helper mutates the config array in-place to ensure all plugin namespaces point to the same object reference (required by ESLint v10's strict identity check). This is called both in `packages/eslint-plugin/index.js` and **duplicated** in `eslint.config.mjs`:

```js
function dedupePlugins(configs) {
    const seen = Object.create(null);
    for (const config of configs) {
        if (!config.plugins) continue;
        for (const name of Object.keys(config.plugins)) {
            if (name in seen) {
                config.plugins[name] = seen[name];
            } else {
                seen[name] = config.plugins[name];
            }
        }
    }
    return configs;
}
```

The duplication between `index.js` and the root config is concerning. If a consumer spreads multiple config presets (e.g., `recommended` + `test-unit`), the deduplication only happens within each preset but not across them. The root config paper-covers this with its own `dedupePlugins`, but external consumers will hit the "Cannot redefine plugin" error unless they also deduplicate. **This should be documented prominently.**


## 6 `babel-parser-compat.js` — monkey-patching scope manager internals [Opus generated]

The Babel parser wrapper patches `scopeManager.addGlobals` by reaching into internal APIs (`__defineGeneric`, `scopes[0].set`, `scopes[0].through`). This works but is inherently fragile:

```js
result.scopeManager.addGlobals = function addGlobals(names) {
    const globalScope = this.scopes[0];
    // ... uses __defineGeneric, .set, .variables, .through
};
```

The TODO referencing the upstream Babel issue is good, but there's no version guard — if the internal API changes in an `eslint-scope` patch, this will break silently.

## 7. `fixupPluginRules` usage for `eslint-plugin-react` and `eslint-plugin-import` [Opus generated]

Both plugins are wrapped with `fixupPluginRules` from `@eslint/compat` because they haven't migrated to ESLint v10's rule context API. This adds a compatibility shim that may mask subtle behavior differences. If either plugin releases a flat-config-native version, the wrapper should be removed — but there's no tracking mechanism for this.

## 8. `@eslint-community/eslint-plugin-eslint-comments`

Add `@eslint-community/eslint-plugin-eslint-comments` as a dependency of `@wordpress/eslint-plugin` if the plugin's configs reference `@eslint-community/eslint-comments/*` rules — currently it's only a root devDependency but the CHANGELOG implies the rule prefix change affects all consumers.
