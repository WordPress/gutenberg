# Issue #78406: Components: Popover closes when focus moves to a portaled descendant

- URL: https://github.com/WordPress/gutenberg/issues/78406
- Author: ciampo
- Created: 2026-05-18T15:22:03Z
- Updated: 2026-05-19T11:52:23Z
- Comments: 2 of 2

## Body

## Summary

`@wordpress/components` `Popover` closes whenever DOM focus moves to a **portaled descendant** that lives outside its DOM subtree. The Popover treats any focus move whose `relatedTarget` is outside the floating element as "focus left the Popover" — but a portaled child (e.g. a listbox, menu, or any sub-overlay rendered via `createPortal` to `document.body`) is *logically* inside the Popover even though DOM-wise it's a sibling under `<body>`.

This makes nested UIs that need to move real focus into a portaled popup unusable inside a `Popover`, and the same root cause applies to anything else built on top of `useFocusOutside`.

## Steps to reproduce

A specific instance that's easy to demo: the [Playground/WP Compat Overlay Slot](https://wordpress.github.io/gutenberg/?path=/story/playground-wp-compat-overlay-slot--inside-components-popover) story (`Inside Components Popover`).

1. Open the `@wordpress/ui` `Select` inside the `Popover`.
2. Hover any item.

**Expected:** the host `Popover` stays open.
**Actual:** the host `Popover` closes as soon as an item is hovered (because base-ui moves real DOM focus to the hovered option, which lives in a body-level portal).

The same kind of failure can be reproduced with any portaled descendant that moves focus — not just `@wordpress/ui` overlays.

<details>
<summary>Existing workarounds in the codebase</summary>

The same problem has been worked around ad-hoc in several places. Each of these is fundamentally the same issue:

- **`useFocusOutside` itself** already has an escape hatch via the `data-unstable-ignore-focus-outside-for-relatedtarget` attribute, explicitly documented as "for modals that don't exist in the React tree": [`packages/compose/src/hooks/use-focus-outside/index.ts` L137–L152](https://github.com/WordPress/gutenberg/blob/trunk/packages/compose/src/hooks/use-focus-outside/index.ts#L137-L152).
- **Inserter / Media tab** opts a button into that escape hatch so opening the Media Library modal doesn't close the inserter: [`packages/block-editor/src/components/inserter/media-tab/media-tab.js` L85–L93](https://github.com/WordPress/gutenberg/blob/trunk/packages/block-editor/src/components/inserter/media-tab/media-tab.js#L85-L93).
- **URL popover image input** maintains a custom `autocompleteRef` and overrides `onFocusOutside` because the autocomplete suggestions list is rendered in a separate portaled popover: [`packages/block-editor/src/components/url-popover/image-url-input-ui.js` L129–L146](https://github.com/WordPress/gutenberg/blob/trunk/packages/block-editor/src/components/url-popover/image-url-input-ui.js#L129-L146).
- **List View content popover** ships with a comment lamenting the same constraint — it avoids `bubblesVirtually` on the inner Slot specifically because otherwise opening a nested popover would close the outer one ("Is there a solution that has no trade-offs?"): [`packages/block-editor/src/components/inspector-controls/list-view-content-popover.js` L96–L101](https://github.com/WordPress/gutenberg/blob/trunk/packages/block-editor/src/components/inspector-controls/list-view-content-popover.js#L96-L101).
- **Collab sidebar note thread** checks `event.relatedTarget?.closest('.editor-collab-sidebar-panel__thread')` / `closest('[role="dialog"]')` to ignore focus moves into other notes or any portaled `[role="dialog"]`: [`packages/editor/src/components/collab-sidebar/note-thread.js` L100–L125](https://github.com/WordPress/gutenberg/blob/trunk/packages/editor/src/components/collab-sidebar/note-thread.js#L100-L125).

These are all individual symptoms of the same general gap, papered over with case-specific selectors / refs / attributes.
</details>

<details>
<summary>Root cause</summary>

- `Popover` closes via `useDialog` → `useFocusOutside`, which fires `onFocusOutside` whenever a `blur` event has a `relatedTarget` outside the wrapped DOM subtree.
- `useFocusOutside` only checks **DOM** containment, not the logical/React tree. Any descendant rendered via `createPortal` is outside the wrapped DOM subtree, so focus moves into it look identical to focus moves to truly unrelated UI.
- This bites whenever a portaled child takes real focus: hover-driven focus in floating-ui listboxes (`@wordpress/ui` `Select`, base-ui `Menu`, etc.), `.focus()` calls inside portaled sub-popovers, focus traps in nested portaled dialogs, the Media Library modal, autocomplete suggestion popovers, …

ARIA combobox patterns that keep DOM focus on the input (e.g. `@wordpress/ui` `Autocomplete`, which uses `aria-activedescendant`) don't trigger the bug — they don't actually move DOM focus.
</details>

<details>
<summary>Possible fixes</summary>

The underlying fix is to let consumers express **logical** containment so portaled descendants count as "still inside":

- **Generic, in `@wordpress/compose`/`useFocusOutside`** — accept a list of additional containers / a predicate to consider "inside", and have portals register themselves via React context. Most powerful, but the largest API change. Would let us eventually retire the `data-unstable-ignore-focus-outside-for-relatedtarget` escape hatch and remove the per-consumer workarounds listed above.
- **Per-consumer, in `Popover`** — accept opt-in "logical descendant" containers (refs / selectors) and ignore blur events whose `relatedTarget` is inside any of them.
- **Convention-based** — recognise specific marker attributes (e.g. `[data-wp-compat-overlay-slot]`) as "logically inside". Doesn't generalise, but it's a small, surgical fix for the most common instances.

#78407 implements the convention-based variant for the `@wordpress/ui` compat overlay slot — it unblocks the `Select`-inside-`Popover` scenario today, but does not solve the broader problem.
</details>
