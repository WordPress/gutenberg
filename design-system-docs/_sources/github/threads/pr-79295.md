## Body

## What?

Updates tests for the `@wordpress/components` `Menu` component to avoid relying on `setTimeout` "sleep"-ing measured in real-world half-seconds, and in doing so refactor toward `@testing-library/user-event` for interaction.

## Why?

- Performance: Locally, reduced test runtime from ~15s to ~\~5s (-66.6%)~ **~2.5s (-84%) after 3bb955adaa94c4c1d0feb8b256f126113abb0501**. This also extends to CI, which we can expect to complete in around the same 10 real-time seconds less.
- Consistency: Migrating toward `@testing-library/user-event` where possible for simulated user interactions avoids tying ourselves to a specific library implementation

## How?

- Use Jest fake timers to advance time where we're waiting for a delayed action
- Replace `@ariakit/test` interaction helpers with `@testing-library/user-event` where possible. Ariakit's test helpers have internal timers which must be either awaited or advanced manually, while `@testing-library/user-event` exposes an `advanceTimers` option to allow integration with features like Jest's fake timers

## Testing Instructions

`npm run test:unit packages/components/src/menu/test/index.tsx` should pass.

## Use of AI Tools

Used Cursor + "Auto" model (likely Composer) to research and implement, with manually-prompted iterations to generalize refactor across test cases within the file.

I dug into it further and it seems like it's a similar issue we've encountered elsewhere in test code where code that tests focusability considers element visibility using element rects. Comparing Ariakit and Testing Library, Ariakit applies this shim temporarily as part of its test helpers ([source](https://github.com/ariakit/ariakit/blob/9b8f1434d75abe714a8146e80aff9f4e9f58deae/packages/ariakit-test/src/shims.ts#L40-L51), recently revised in https://github.com/ariakit/ariakit/pull/6256). So we can migrate from Ariakit helpers to Testing Library, but in doing so we need to implement that shim ourselves, which I did in 3bb955adaa94c4c1d0feb8b256f126113abb0501.

Doing so halves the time of the tests yet again, down to ~2.5s in my testing (-84% from baseline). I'd be curious if we'd find similar gains in other tests throughout the package.

As for the mocking itself, a couple thoughts:

- To me, it would make sense to apply this kind of mock in [`test/unit/config/global-mocks.js`](https://github.com/WordPress/gutenberg/blob/trunk/test/unit/config/global-mocks.js) if we think it creates a "true"-er browser environment for tests
- Part of the relevance of mocking this comes from our [own `isVisible` utility](https://github.com/WordPress/gutenberg/blob/4429bf0841927c58c18da3e7f8e8981285c0332b/packages/dom/src/focusable.js#L60). This change is needed because the previous assertion here was not strictly correct for how this behaves in a real browser and instead relied on JSDOM's behavior in absence of "visible" elements. Because Ariakit only applies its `getClientRects` shim temporarily during interactions, the initial rendering here happens without the shim. And so Ariakit doesn't see any visible elements and falls back to the menu container. With the test-wide shim, Ariakit sees the visible elements and instead focuses the first menu item, which is what happens in a real browser ([example](https://wordpress.github.io/gutenberg/?path=/story/components-menu--default&args=defaultOpen:!true)).

This seems to be the exact kind of thing that the recent change https://github.com/ariakit/ariakit/pull/6256 was aimed at addressing too.
