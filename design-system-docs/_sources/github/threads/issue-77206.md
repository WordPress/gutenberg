# Issue #77206: Design System: Provide MCP server tooling for design system resources

## Body

Sub-issue of #77205 

## What problem does this address?

Today, working with AI agents to implement or ask questions in accordance with design system offerings (e.g. components, design tokens), agents often struggle to find the correct information.

Anecdotally, I've watched agents dive into [built output of `@wordpress/ui` root barrel file](https://unpkg.com/@wordpress/ui@0.10.0/build/index.cjs) to analyze exported members to understand what components are available from the package, which is both inefficient and provides an incomplete picture of the design system.

## What is your proposed solution?

Provide an MCP server (local or remote) with tools that allow an AI agent to efficiently get answers to questions about using the design system offerings: especially available components (including detailed examples and prop references) and tokens.

This should be quick and easy for someone to set up. Ideally a one-liner, including snippets for popular setups (e.g. Claude Code, Cursor, etc., see prior art below). No git clones, servers running in separate process, etc.

[MCP](https://modelcontextprotocol.io/docs/getting-started/intro) is a standardized protocol to bridge documentation sources of truth to AI agents.

This is separate-but-complementary from [Agent Skills](https://agentskills.io/home) ([#77209](https://github.com/WordPress/gutenberg/issues/77209)), which provide written instructions on how to accomplish a specific task or workflow. The scope of the MCP should cover _what exists_, not necessarily how to use it. Although there may be some overlap in the case of pattern guidance ([example](https://wordpress.github.io/gutenberg/?path=/docs/design-system-patterns-destructive-actions--docs)).

**Implementation notes:**

The two most obvious paths to implement are either a hosted MCP offering (likely built as a WordPress plugin interfacing with the [Abilities API](https://developer.wordpress.org/news/2025/11/introducing-the-wordpress-abilities-api/) and [mcp-adapter](https://github.com/WordPress/mcp-adapter)), or a local server (likely built and distributed as an npm package). This was raised in #77159, with a general leaning toward an npm package:

> I had explored an alternative approach leveraging [WordPress Abilities API](https://developer.wordpress.org/news/2025/11/introducing-the-wordpress-abilities-api/) + [mcp-adapter](https://github.com/WordPress/mcp-adapter) which, while an interesting example of "dog-fooding", may not be a great fit:
> 
> * It requires that we figure out a hosting arrangement for where this lives, presumably somewhere on wordpress.org
> * The bigger issue is that MCP servers using HTTP as a transport layer are _stateful_, and require session management. The existing WordPress tooling around MCP (i.e. [mcp-adapter](https://github.com/WordPress/mcp-adapter)) is optimized for authenticated users, and isn't a good fit for a public MCP server where we'd want to support anonymous access.
> * It's also overkill, since the proposed approach here doesn't do anything particularly special beyond fetching and transforming static assets

**Prior art:**

- [Chakra UI MCP Server](https://chakra-ui.com/docs/get-started/ai/mcp-server)

On the topic of whether we could just use [Storybook's MCP server](https://storybook.js.org/docs/ai/mcp/), my current sense is that we will want to use some of the same underlying infrastructure, especially [the Manifests feature](https://storybook.js.org/docs/ai/manifests), already enabled in #74626 for this exact purpose. But I don't know that the out-of-the-box Storybook MCP server is a good fit for a few reasons:

- It requires that we keep all relevant documentation that we want to be discoverable in Storybook.
   - That's technically possible, but constrains us. Today, we have documentation like [tokens reference](https://github.com/WordPress/gutenberg/blob/trunk/packages/theme/docs/tokens.md) that live outside Storybook (although maybe there's a strong case to be made that it should be available in Storybook as well/instead). More problematic is if we ever wanted to publish a standalone reference website for the design system independent of Storybook, the reference site content would be out of reach. The idea with maintaining our own MCP server tooling would be that it can aggregate from multiple sources.
- As mentioned in #77205, we have a lot of unrelated and legacy components that are documented in Storybook, and part of the goal of this effort would be to distill current best practices in working with the design system.
- The Storybook MCP [requires a hosted setup](https://storybook.js.org/docs/ai/mcp/sharing#self-hosting-with-storybookmcp), including all the trade-offs described in the original post about a hosted offering. It's also a Node.js-based server, while WordPress.org hosting is optimized for WordPress/PHP.
