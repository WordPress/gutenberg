# Issue #65519: Establish a consistent pattern for Range control and input field order

- URL: https://github.com/WordPress/gutenberg/issues/65519

- Updated: 2024-09-20T13:31:42Z

## Body

### Description

By default, the `RangeControl` component shows:
- A `range` input on the left.
- A `number` input on the right.

Screenshot of a couple examples in the editor UI:

![RangeControl](https://github.com/user-attachments/assets/cc7a4fb0-9619-4b00-8018-b9279fcd945b)

However, in many other cases the editor UI provides users with a design pattern that is 'reversed', as in: the input is on the left and the range control is on the right.

This is tipically done 'manually' in the editor by combining ab `UnitControl` + a `RangeControl` with `withInputField={ false }`. See for example the [HeightControl](https://github.com/WordPress/gutenberg/blob/5e37a1316d0a39bc880bf6efff9b9f26db381690/packages/block-editor/src/components/height-control/index.js).

A few example screenshots:

![UnitControl + RangeControl](https://github.com/user-attachments/assets/8a05994c-a776-4434-8753-df831ccc89b1)


Regardless of whether these UIs are made of a default component from the `components` package or are local implementations in the editor, my point is about consistency and providing users with a cohesive experience across the editor.

What is the value from a design perspective of providing users with an UI that _sometimes_ shows a range on the left plus an input on the right and _sometimes_ ci ve-versa? Is this an intentional design choice?
How this inconsistency helps users in any way?

To me, the UI should be consistent and predictable. The order should be always the same and this range + input pattern should be always consistent across the editor.

Cc @WordPress/gutenberg-design 

### Step-by-step reproduction instructions

- Add a Query Loop block.
- In the Inspector, observe the 'Posts per page' settings renders a range plus an input, in that order.
- Add a Group block
- In the Inspector > Styles tab, observe the 'Minimum height' setting renders an input plus a range, in that order.

### jameskoster on 2024-09-20T13:13:50Z

URL: https://github.com/WordPress/gutenberg/issues/65519#issuecomment-2363711502

Yes, there's a lot of untangling we might do here. 

> What is the value from a design perspective of providing users with an UI that sometimes shows a range on the left plus an input on the right and sometimes ci ve-versa?

My _guess_ at the reasoning is that some controls are more ergonomically manipulated via range, and others by text input, and the order is set accordingly. But I tend to agree, the inconsistency this creates feels like a trade-off.

More conceptually I'd question the rationale of including visible ranges and text inputs in the same control as frequently as we do. If the UI requires the presence of a text field alongside the range, that suggests to me that a range may not be the right choice in the first place. I appreciate the need to determine the actual value, but that's best handled within the range—it shouldn't require an additional input.

Likely related to the previous point; I find it a little strange to see so many range controls used for settings that are not actually range bound. I suppose the argument is that the range offers a quick way to select common options, kind of like presets, but that doesn't feel like a great fit semantically and there are probably better patterns to consider. The spacing preset controls work much better in this respect.

### afercia on 2024-09-20T13:31:41Z

> More conceptually I'd question the rationale of including visible ranges and text inputs in the same control as frequently as we do. If the UI requires the presence of a text field alongside the range, that suggests to me that a range may not be the right choice in the first place.

I'd tend to agree all the range control usages should be audited. There's two more problems related to the range control raised in other issues and PRs:
1. The range control is, by its own nature, meant to be used vor values _in a fixed range_. However, sometimes the editor UI uses range controls for values that accept arbitrary, out-of-range, potentially _infinite_ values. This is just using the wrong input type.
2. When using a mouse or other pointing devices, the slider of the range control needs sufficient horizontal space to enable users to _fine tune_ the value they want to set. This point is even more valid when the range of values is pretty large. However, often, the rnge control is placed in a very narrow space typically in a narrow sidebar. As such, the horizontal space is very limited.
