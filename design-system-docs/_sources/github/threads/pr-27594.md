## Body

This update adapts `FontSizePicker` from `@wordpress/components` with the new Component System setup.
It does this by adding the (current) external `@wp-g2` component system packages as dependencies and using them directly.

This strategy was something @gziolo had suggested here:
https://github.com/WordPress/gutenberg/issues/27484#issuecomment-738857333


## How has this been tested?

* `npm install`
* Run `npm run dev`
* Fire up local Gutenberg
* Edit or add a Paragraph block
* Adjust the font-size
* It should work like normal (and the controls may look slightly slightly different)

### jsnajdr on 2021-01-11T08:35:39Z

URL: https://github.com/WordPress/gutenberg/pull/27594#issuecomment-757720867

> The Components were originally constructed with useState/useReducer, but we ran into performance issues.

I understand now why `useReducer` would be significantly slower than `zustand`: any state update of the reducer is propagated to all its consumer components, and triggers their rerender. On the other hand, `zustand` supports selector that select only a slice of the state and trigger a React rerender only when that slice changes. That saves a lot of wasted rerenders.

However, that applies only when one store is shared by multiple components using a React context. That's what the [G2 performance test](https://github.com/ItsJonQ/g2/tree/master/packages/design-tools/src/__stories__/PerformanceTest) does and I can see why it gets much slower with vanilla `useReducer`.

Usages of `useSubState()` in the G2 components work very differently though. They manage only one component's local state, the store is never seen by any other component and the selector optimization doesn't save any rerenders. Plain `useState` or `useReducer` should work here equally well without any performance penalty. Hooks like `useAccordion`, `useColorPickerState` or `useTextInputState` could be implemented like this, without a 3rd party dependency.

Then there are usages with `createStore` and context. Like `useModalStore`, `useThemeStylesStore` or `useContextSystem`. These could theoretically make use of the selector optimization, but in practice they don't. These stores store only one atomic value (`theme`, `context`) and consumers use it in such a way that the rerender is triggered on any change. That's suboptimal particularly for the context system. `useContextSystem( props, 'Alert' )` and `useContextSystem( props, 'Accordion' )`, should never trigger cross-namespace updates, but they do.

So, the conclusion so far is that the performance test is testing something that G2 doesn't really do in practice and that `useReducer` should be equally fast in most cases.

Still, the selector optimization is valuable. It would certainly make `useContextSystem` faster, at least.

On the other hand, Redux and `@wordpress/data` support this optimization, too, and I don't see a fundamental reason why any of them should do it faster than the other. They all implement more or less the same thing.

For these usages, I think that a `@wordpress/data` store would be a suitable and well-performing replacement for `zustand`.

The anonymous unregistered data stores that @gziolo started working on in #26655 could also be useful here. You don't need to register a global singleton store like `core/components-context`. You can just create a data store, assign the return value ("store descriptor") to a variable, pass that variable around however you want to (module exports, context, ...), and use it to work with the store using the `useSelect( storeDesc )` and `useDispatch( storeDesc )` hook.
