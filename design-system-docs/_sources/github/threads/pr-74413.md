## Body

This fixes a mismatch in our package versions. On Dec 23 2024 @priethor published the `latest` version of Gutenberg packages in this action run: https://github.com/WordPress/gutenberg/actions/runs/20462309747/job/58797649853

But this action run didn't finish successfully. It succeeded actually publishing the packages to NPM, but then failed to commit to `trunk` the changes to `package.json` version fields and to changelogs. As a result, the git repo has no traces of packages being published. And there is a mismatch. For example, the latest `@wordpress/data` on NPM is 10.37.0, but in the git repo it's still 10.36.0.

Another bad consequence is that development `next` packages are published with the old version number, for example as `10.36.1-next.76cff8c98.0`, although an earlier `latest` package is already `10.37.0`.

This causes chaos for consumers like Jetpack (https://github.com/Automattic/jetpack/pull/46397) where specifying a version `^10.36.1-next.76cff8c98.0` doesn't match the specified `next` version, because the older `10.37.0` is a better semver match (!).

This PR updates the version numbers to be aligned with what is published on NPM. I extracted the version list from the GitHub action run log, there are 112 published packages.

The changelogs are still not up to date. For example, `packages/components/CHANGELOG.md` mentions as "unreleased" also changes that were published in 31.0.0. But that's much harder to fix because the changelog already contains a lot of newer entries. It will be fixed only after the next release.

> How do we prevent this from happening again?

Ideally the whole operation would be atomic. The script makes local changes, commits them, then publishes packages to NPM and pushes the new commits to GitHub. Either the NPM and GitHub operations both succeed or they both fail. But here the NPM publishing succeeded and then the GitHub push failed.

The push failed because there were conflicts in the `date` and `block-library` changelogs. Hector then fixed these two changelogs in #74202, but this fix was very incomplete. The versions in `package.json` files were not updated, and also the other, non-conflicting changelogs (like `components`) weren't updated either.

What's bad that the GitHub action run did these commits only locally, they were lost after the run ended. A better workflow would be:
- create a local branch, commit changes there
- push the local branch to the repo so that it's preserved
- do the NPM publishing
- if the NPM publishing fails, leave the branch alone, or maybe delete it, but don't merge it to `trunk`
- if the NPM publishing succeeds, merge the branch to `trunk`, as if you were doing a PR

Here the only failure mode is that after successful NPM publishing merging to `trunk` fails. I'm afraid that can'be fixed, i.e., made atomic. The best thing we can do is to have a branch pushed in the server repo, and then merge that branch manually, without any data loss. That's better than the current situation, where the changes got lost and we needed to recreate them, unreliably and with mistakes.

### manzoorwanijk on 2026-01-08T09:49:16Z

URL: https://github.com/WordPress/gutenberg/pull/74413#issuecomment-3723067426

Once the versions are updated or even merged to trunk, publishing should ideally be done from trunk. That is the approach used by tools like [Changesets](https://github.com/changesets/changesets/tree/main#readme).

Once set up,
- It expects (not mandatory) every PR to have a changelog entry for the affected packages
- Once the PR is merged, it creates a release PR with version bumps for the packages depending upon the type of change (Major, Minor, Patch). See https://github.com/statelyai/xstate/pull/5394.
- It keeps the release PR up to date after PRs are merged to trunk.
- It automatically adds props to the changelogs, linking them to the PR.
- Once we are ready, we just need to merge the release PR
- It then publishes the packages to npm. Like [this](https://github.com/statelyai/xstate/actions/runs/20680701766/job/59374496332).


If the CI errs, it's easy to publish them from trunk or re-run the CI job.

It works on the assumption that the trunk is always in the releasable state because it creates the release branch from the trunk.

There is a [large list of projects](https://github.com/changesets/changesets/tree/main?tab=readme-ov-file#cool-projects-already-using-changesets-for-versioning-and-changelogs) that use the tool.
