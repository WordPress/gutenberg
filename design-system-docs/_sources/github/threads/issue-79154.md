# Issue #79154: Design System: Add a dedicated Navigation component

- URL: https://github.com/WordPress/gutenberg/issues/79154
- Author: jameskoster
- Created: 2026-06-12T14:12:55Z
- Updated: 2026-06-12T14:12:55Z
- Comments: 0 of 0

## Body

## Summary

We're missing a dedicated **navigation menu** component in the design system. As a result, consumers are reaching for `Tabs` to build page-level / in-page navigation (e.g. switching between admin screens or filtered views within a screen). This is semantically inappropriate: `Tabs` are an ARIA `tablist` pattern for toggling between panels of content within a single view, not for navigating between locations/URLs.

This issue is initially intended to open a discussion about adding a navigation component, rather than to prescribe a final API or design.

## The problem

`Tabs` is being used as navigation in several places. For example, in the boot-backed admin screens, the "tabs" rendered under the page header don't switch panels — selecting one changes the route:

- `routes/post-list/stage.tsx` — All / Published / Draft / Pending / Private / Trash are navigational
- `routes/pattern-list/stage.tsx` — All / My patterns / Registered are navigational
- `routes/template-part-list/stage.tsx` — All / Headers / Footers / Sidebars / … are navigational
- `routes/template-list/stage-activation.tsx` and `stage-legacy.tsx` — template views are navigational

These are links/destinations, so they should be real navigation (an `<a>`-based pattern with proper active states), not a `tablist`. I've seen this same `Tabs`-as-navigation pattern crop up with other design system consumers too, so it seems worth solving at the system level rather than per-consumer.

### Why this matters

- **Semantics / accessibility**: `tablist` / `tab` / `tabpanel` roles communicate "panels within a view" to assistive tech. Navigation should expose links and a current-page state (`aria-current`), not tab selection.
- **Behavior**: tabs imply local content swapping; navigation implies a location change (history, deep-linking, right-click / open-in-new-tab, etc.).
- **Consistency**: without a sanctioned component, consumers are forced to invent, or use inappropriate componentry.

## Proposed direction

[Base UI ships a `NavigationMenu` component](https://base-ui.com/react/components/navigation-menu) that we could use as the headless foundation — consistent with how the rest of `@wordpress/ui` is built on Base UI. It provides a `<nav>` root, list/item/link parts, an `active` state on links, optional trigger+popup content for richer menus, nested submenus, and an `orientation` prop (`horizontal | vertical`).

## Open questions for discussion

1. **Which package owns it — `@wordpress/ui` or `@wordpress/admin-ui`?**
   `@wordpress/ui` is the generic, context-agnostic layer (where a primitive navigation component would naturally live, built on Base UI). `@wordpress/admin-ui` is the higher-level layer for admin page layout patterns (`Page`, `Breadcrumbs`, etc.) and might be where an opinionated, admin-specific navigation pattern belongs. Possibly both: a generic primitive in `ui`, composed into an admin-specific layout in `admin-ui`.

2. **Visual design.**
   It should be clearly distinct from `Tabs` so users can interpret the difference and not conflate the two interaction patterns — the component should read as "links/destinations" rather than "panels." Things to work through:
   - **Differentiation from Tabs**: what visual language signals navigation vs. tab selection (active indicator style, separators, weight, background, etc.)?
   - **Active / current-page treatment**: how the current location is styled, distinct from hover/focus.
   - **Per-item icons**: should items support a leading icon (some current `Tabs`-as-nav usages already do, e.g. the template views), and how do icon + label align?
   - **Density / size variants**: any need for compact vs. comfortable, or a "minimal" treatment like `Tabs.List` already has?

3. **Deep / nested navigation structures.**
   How do we support and display hierarchical navigation? Base UI's `NavigationMenu` supports trigger + popup content and nested submenus — do we want flyouts/popovers, inline expansion, or both? How deep should we reasonably support, and how does this relate to the existing sidebar navigation in boot?

4. **Orientation.**
   Do we need a vertical orientation in addition to horizontal? Base UI exposes an `orientation` prop, so it's low-cost to support — but we should decide whether vertical is in scope for v1 and what real use cases it serves (e.g. sidebars vs. horizontal page-header nav).

5. **Routing and active state.**
   Consistent with the rest of the design system, the component should stay router-agnostic: routing is composed in via Base UI's `render` prop (as `@wordpress/ui` `Link` + `@wordpress/route` `Link` already are in `admin-ui`'s `Breadcrumbs`), rather than depending on a router directly. The open question is the **active/current-page state**: Base UI's `NavigationMenu.Link` exposes an `active` prop (and `data-active`), but determining which item is active requires knowing the current route. Should that be left entirely to the consumer, or should `admin-ui` provide a route-aware wrapper that wires `active` from `@wordpress/route` automatically?

6. **Migration / guidance.**
   Once available, we'd want to migrate existing `Tabs`-as-navigation usages (the boot route stages above) and add ESLint guidance steering consumers toward the navigation component for link-based UIs, similar to the existing `use-recommended-components` rule that nudges toward `@wordpress/ui` `Tabs`.

7. **Responsive / overflow behavior.**
   How should horizontal navigation behave on narrow viewports — horizontal scrolling, a "more" overflow menu, wrapping, or collapsing into a drawer/disclosure? Base UI's `NavigationMenu` has a scrollable popup pattern, but top-level horizontal overflow is a separate concern.

8. **Scope.**
   Should this component stay focused purely on primary/section navigation, or also cover adjacent patterns like breadcrumbs (which `admin-ui` already has as a separate `Breadcrumbs` component)? Where's the boundary between this and existing navigation surfaces (e.g. boot's sidebar)?

9. **Naming.**
   What should it be called — `Navigation`, `NavMenu`, `NavigationMenu`, or something else? Worth aligning with both Base UI's naming and existing WordPress conventions.

10. **Anything else?**
   Other considerations, prior art, or constraints we should fold into the discussion.
