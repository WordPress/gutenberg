## Body

Add a 100 ms clear-to-fill delay and a FIFO polite-announcement queue to speak() in @wordpress/a11y.

Closes #79561

## Why?

speak() currently calls clear() and sets the live-region content in the same synchronous JavaScript tick. VoiceOver on Safari/macOS can batch those two DOM mutations into a single accessibility-tree snapshot, observe no net change, and stay silent — even for distinct, non-repeated strings. A settled blank state between the clear and the fill gives assistive technology a detectable mutation to act on.

A second problem: when speak() is called multiple times in rapid succession (e.g. during a save sequence or a search-result update), each call clears and immediately overwrites the live region. Every intermediate polite message is silently dropped. Adding the delay without a queue makes this worse, not better, a 100 ms timer from call N can fire after call N+1 has already cleared the region again.

See issue #79561 for the full rationale and supporting references.

## How?

New packages/a11y/src/shared/queue.ts. A FIFO queue for polite announcements with a drain loop:
- enqueuePolite(message) adds to the queue and starts draining if idle.
- Each drain cycle: clear the polite container → wait 100 ms → fill → wait 500 ms (reading window) → repeat until empty.

Refactored packages/a11y/src/shared/index.ts. `speak()` no longer calls the shared `clear()` (which cleared all regions at once):
- Polite path delegates to `enqueuePolite()`. The queue owns the clear and fill.
- Assertive path wriites to the container with no delay, the polite queue is undisturbed.

The public API - speak(message, ariaLive?) - is unchanged.

Testing Instructions

1. In a browser with VoiceOver active (Safari + macOS), open the Gutenberg editor.
2. Save a post and confirm VoiceOver announces "Post published." or equivalent.
3. Save again immediately and confirm the second announcement is also read aloud.
4. Open the browser console and run:
wp.a11y.speak('Step 1 complete');
wp.a11y.speak('Step 2 complete');
wp.a11y.speak('Step 3 complete');
4. Confirm all three are announced in order.
5. Run npm run test:unit packages/a11y - all tests should pass.

Testing Instructions for Keyboard

No UI changes in this PR. The fix is internal to the `speak()` function; keyboard navigation is unaffected.

If I understand the implementation correctly, with the 100ms delay the assertive path can announce stale urgent messages.

For example:

- call A schedules a fill at T+100
- call B happens at T+10
- A still writes at T+100 even though B is already the newer state and will not write until T+110.

If I'm not wrong, WAI-ARIA says assertive updates should be presented immediately and only used for imperative interruptions.

In that sense, for assertive announcements, I think latest-wins behavior is safer than preserving intermediate messages. Could we store the assertive timeout id and clear it before scheduling the next assertive fill?
