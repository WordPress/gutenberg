## What?
<!-- In a few words, what is the PR actually doing? -->
The `<ItemGroup>` component should only contain `<Item>` sub-components as it's intended to render a `list` with `listitems`. This quick PR aims to fix one incorrect usage.

It also contains a fix for the `Item` height new default of 40 pixels when it is rendered as a Button. This part is mainly for demoing a potential way to fix the size but I'm not sure it should be addressed this way. After crafting this PR I discovered the size issue is tracked in https://github.com/WordPress/gutenberg/issues/46741 and should be better addressed there. I'm glad to revert the size fix in this PR, just submitting as is so far, pending feedback.
Cc @WordPress/gutenberg-components

<!-- Why is this PR necessary? What problem is it solving? Reference any existing previous issue(s) or PR(s), but please add a short summary here, too -->

@tyxla thanks for your feedback.

> In this PR, I see the double border. On trunk, the item remains focused. I think keeping it focused makes sense.

The difference you are seeing in the focus indication comes from the fact that in this PR the `ItemGroup` is rendered as a button element and styled via `unstyledButton`, which uses [:focus-visible for the focus style](https://github.com/WordPress/gutenberg/blob/f6d8c69efa9ebd7c3dd1fdd02cddde779c970319/packages/components/src/item-group/styles.ts#L31-L42).

Instead, on trunk it's a Button component, which uses [:focus](https://github.com/WordPress/gutenberg/blob/f6d8c69efa9ebd7c3dd1fdd02cddde779c970319/packages/components/src/button/style.scss#L39-L44). 

`:focus-visible` is supposed to be shown only when using the keyboard, while `:focus` is shown also when using the mouse (as such, on trunk the focus indication is shown also when clicking with the mouse and persists when dragging and releasing the mouse outside of the button). 

It's an inconsistency in the focus indication between the Button component and ItemGroup as a button element which is outside of the scope of this issue. I think this has been implemented intentionally, but I'm not sure it's a good thinkg. I'll create a separate issue to consider making this behavior consistent.
