## Description
<!-- Please describe what you have changed or added -->
This pull request adds two things:

1. `getAuxiliaryColorArtefactWrapper` prop for the color picker component
2. Implement a serie of props for the gradient-picker that allows passing custom props to the color picker from the custom gradient UI

Reason for this being allowing client code to use a simpler version of the color & gradient pickers without completely re-implementing those from the plugin side. This will cause a lot of duplication on the plugin end and we'll also be forced to bundle [`react-colorful`](https://github.com/omgovich/react-colorful) twice to make that happen.
Reasoning for this is also described in the updated README.

> Why do you need a simpler version of the color picker? 

We need to be able to easily swap out the auxiliary color artefact part of the color picker. For example here's a quick usage of the render prop and its visual result:

1. Screenshot of the result (swap auxiliary color artefact with a simpler input to save space in restricted places or remove it at all): https://cln.sh/UIwIj3
2. Render prop usage:

```
<ColorPicker
    getAuxiliaryColorArtefactWrapper={() => {
        return <input value={color} />
    }}
    color={color}
    enableAlpha
    onChange={{}}
/>
```

> And what in particular do you consider extra?

The auxiliary color artefact itself, according to the above screenshot. 


----

API wise, I agree that the proposed render prop might not be the best solution and I'm happy to hear your advise hear on what other options we might have. Something based on filters/portals or React contexts might do a better job here.

Another requirement of ours is that we need to also be able to change the color picker from the gradient picker when we render it from our components, thus the need of all the props there. With all the props the usage is quite ugly:

```
<GradientPickerComponent
    value={value.gradient || ''}
    onChange={(val) => {
        onChange({
            ...value,
            gradient: val,
        })
    }}
    customGradientPickerProps={{
        customGradientBarProps: {
            controlPointsProps: {
                colorPickerProps: {
                    getAuxiliaryColorArtefactWrapper: () => {
                        return <input value={'#fff'} />
                    },
                },
            },
        },
    }}
/>
```

If we are to implement a solution for swapping out the auxiliary color artefact using a filter or with a context based solution we should be able to avoid all this messy prop drill. Again, happy to hear your ideas here and also update the PR with the implementation.

---

So, to conclude:

1. I won't be making a storybook screen with this new render prop until we settle upon an better API. When we have that, I'll provide an implementation of the API + a storybook screen to see it in action
2. With the correct API implementation, prop drill in the gradient component will become obsolete and it won't be needed anymore. I'll update the PR to remove all these props and a 2nd PR to cover the gradient won't be needed hopefully
3. I will add the relevant Changelog entries as soon as we settle upon an API that you like here.

I'm not really sure about the best way to allow this extensibility scenario, in the end, I think we will always face some customization cases that are not possible.

I think of two possible alternative ideas to achieve the UI show by @andreiglingeanu:

Alternative 1:
- Add a property to the color picker that allows showing input details by default (set the default show details to true) so we would get this:

- Then using CSS one can remove the show details button, the hex selection, and customize the input.
- Add a property to the gradient picker called color picker props that is passed to the color pickers.

Alternative 2:
- Add a property to the color picker that totally disables the additional UI.
- Then one can create a wrapper component that uses our component and the custom input field.
- Add a component property to the gradient picker called ColorPicker that would allow changing the color picker used by gradient picker allowing one to use a custom color component.


I don't have a strong preference for any one these options and I'm open to other alternatives.

### ciampo on 2022-01-11T11:33:23Z

URL: https://github.com/WordPress/gutenberg/pull/37599#issuecomment-1009874978

Alright, here's some thoughts.

> We need to be able to easily swap out the auxiliary color artefact part of the color picker.

I still don't understand what's the problem with the auxiliary controls that come by default with the `ColorPicker` — do they take too much space when expanded? Do you want to limit the user's ability to pick different color formats? Anything else?

Maybe we can just add some functionality to the `ColorPicker` itself, which would be a much smaller change? (cc @jasmussen who may be interested in this conversation)

---

Alternatively, I agree that Jorge's option no. 2 is the better one. We could:
- add a `hideAuxiliaryControls` boolean prop
- allow the `ColorPicker` to render `children`
- this way, you would be able to hide the auxiliary controls and then show whatever component you need as children of the ColorPicker

I went ahead and created a draft PR to illustrate this approach in #37864.

---

Regarding the Gradient Picker, I'm not sure we can avoid prop drilling. The main problem is how the gradient-related components are written and composed together, and consequently how the `ColorPicker` gets imported and used.

This seems to be the component's dependency graph:

```
GradientPicker
  CustomGradientPicker
    CustomGradientBar
      ControlPoints.InsertPoint
        ColorPicker
```

Exposing any props that targets `ColorPicker` would still need to _drill_ through 4 components, and I'm not sure if there's a way to avoid this from happening (which doesn't involve refactoring the whole set of components)
