## Body

## What problem does this address?

There have been several recent examples highlighting the need for a common primitive component that allows for (design) systems-based component layouts based on shared design standards for e.g. spacing, color, etc.

Related discussions: 

- https://github.com/WordPress/gutenberg/pull/72511#issuecomment-3442840811
- https://github.com/WordPress/gutenberg/issues/72336#issuecomment-3435843856

## What is your proposed solution?

Create a new `Box` component that integrates with the [new Theme package](https://github.com/WordPress/gutenberg/tree/trunk/packages/theme) to provide a way to render components styled using tokens provided through the theming context.

Prior art:

- https://chakra-ui.com/docs/components/box

Customization should potentially include:

- [x] Padding (implemented in #72984)
- [x] Background color (implemented in #72984)
- [x] Border color (implemented in #73530)
- [x] Border radius (implemented in #73530)
- [ ] Elevation
- [ ] Sizing (width, height)
- [x] Text color (implemented in #72984)

### aduth on 2026-01-14T21:23:47Z

URL: https://github.com/WordPress/gutenberg/issues/72784#issuecomment-3751776941

There was some recent discussion in https://github.com/WordPress/gutenberg/pull/73931#issuecomment-3660919463 about the value of component abstractions like `Box` or `Text`. In reflection, I'm not as convinced to the imminent value of `Box` as currently implemented. One of the original arguments I raised in #73931 was that this would provide useful guardrails for token usage, but we _also_ recognize that `Box` is a very low-level abstraction that ideally most people wouldn't need to be using directly anyways. And so if that leaves usage primarily for folks iterating on the design system, those people would already be well-positioned to understand correct usage of the tokens. There are also some trade-offs already acknowledged elsewhere, like mixing and matching different token types (e.g. `color` and `dimensions` in `Box`), excessive DOM element nesting, etc.

With that in mind, I'd propose:

- Removing the `Box` component implementation, updating existing usage (pretty limited) to use equivalent design tokens directly
- Continue introducing `Text` component, but only with support for `variant` or `preset` prop for convenience to opting into a preset of multiple token options. This should be a separate GitHub issue.
- Explore other means of sharing utilities, like React hooks. In particular, I was hoping to use [`Box`'s dimension variants support](https://github.com/WordPress/gutenberg/blob/30c040ca8415ec2319dce73fc81bbbbfb469f80f/packages/ui/src/box/box.tsx#L34-L61) in higher-level components like `Card` padding (like #72511 from which it was inspired). This could still be achieved using a React hook if needed.

This is also proposed in mind that it's easier to reintroduce the component later if there's demonstrated value, than it is to try to remove it later.
