# Issue #77628: Admin UI: Proposal — redesign `@wordpress/admin-ui` as a focused admin-page framework (2.0)

- URL: https://github.com/WordPress/gutenberg/issues/77628
- Author: ciampo
- Created: 2026-04-23T18:21:07Z
- Updated: 2026-06-04T17:28:53Z

## Body

## Summary

This proposal reframes `@wordpress/admin-ui` from a loose component library into a focused **admin page framework**: a small, opinionated surface that encodes WordPress's admin-page design spec as code, so consumers get correct semantics, accessibility, and visual rhythm for free — with no room to drift.

The redesign is a single major bump (`@wordpress/admin-ui@2.0`) that accepts breaking changes. After 2.0 the package exports exactly **one component — `<Page>` — plus one narrow styling subcomponent, `<Page.FullBleed>`.** Individual UI primitives move to `@wordpress/ui`; routing, chrome, and cross-tree communication move to consumers as plain props.

### Key decisions at a glance

- **One public component.** `<Page>` (with `<Page.FullBleed>` as a static property). No `Breadcrumbs`, no `NavigableRegion`, no `Page.Section`, no `PageChromeProvider`, no slot/fill, no exported type aliases.
- **Declarative data over JSX.** Header content (`badges`, `breadcrumbs`, `actions`) is typed data. Cardinality rules that can be expressed in the type system (e.g. "≤ 2 secondary actions") are **compile-time errors**, not runtime warnings. `PageActions` is role-shaped: `{ primary?, secondary?, overflow? }`.
- **Routing is the consumer's concern.** No `@wordpress/route` import. Breadcrumb items carry `href` and/or `onClick`; component-based routers plug in via a single `linkComponent` prop. Works for static links, event-based routers, and component-based routers (`@wordpress/route`, React Router, Next.js) with no admin-ui changes.
- **Chrome injection is a plain prop.** `createSlotFill` is dropped; the mobile sidebar toggle is forwarded through a `leading?: ReactNode` prop, with a one-line `AppPage` wrapper in `@wordpress/boot` replacing the current fill pattern.
- **Correct semantics by default.** `<main>` landmark, `<h1>` always present (auto-hidden via `<VisuallyHidden>` when breadcrumbs are shown, per [#76709](https://github.com/WordPress/gutenberg/issues/76709)), `aria-current="page"` on the last breadcrumb per WAI-ARIA APG, `visual` always treated as decorative (`aria-hidden`), actions wrapped in a labelled group with a spec-ordered primary / secondary / overflow layout.
- **CSS modules + design tokens.** Authored as CSS modules, 100% logical properties, all values sourced from `@wordpress/theme`. Drops `@wordpress/base-styles`.
- **Responsive header is internal.** Container-aware (`ResizeObserver`), not viewport-aware: actions overflow to an ellipsis menu, breadcrumbs collapse, the tagline truncates on scroll. No prop surface for it.
- **Explicit test contract.** Unit + integration + `jest-axe` + type tests (`tstyche`) cover the 10 a11y invariants and every branch of the `PageBreadcrumbItem` discriminated union.

## 1. Product vision

`@wordpress/admin-ui` is **not** a component library. It is an **admin page framework**: a small set of opinionated, high-level building blocks that encode WordPress's admin page design spec as code.

The mental model should be:

| Layer                  | Purpose                                                                                         | Flexibility | Example                      |
| ---------------------- | ----------------------------------------------------------------------------------------------- | ----------- | ---------------------------- |
| `@wordpress/theme`     | Design tokens (spacing, color, type, radius).                                                   | —           | `--wp-space-300`             |
| `@wordpress/ui`        | Low-level generic UI primitives (`Stack`, `Button`, `Badge`, `Text`, `Card.FullBleed`, etc.).   | High        | `<Text>`, `<Badge>`          |
| `@wordpress/admin-ui`  | Page-level composition that bakes in the admin spec.                                            | **Low**     | `<Page>`, `<Page.FullBleed>` |
| Consumers (boot, etc.) | Wire up routing, data, chrome.                                                                  | —           | `<Root>`, `<Outlet>`         |

Key principle: **admin-ui hides decisions, `@wordpress/ui` exposes them.** If a consumer wants full control over a breadcrumb rendering they reach for `@wordpress/ui`. If they want "the WordPress admin page header, done right", they reach for `@wordpress/admin-ui`.

This reframing drives every decision below.

## 2. Scope — what belongs, what does not

### 2.1 Does not belong

- **`Breadcrumbs`** → move to `@wordpress/ui` as a generic, container-aware, routing-agnostic primitive (see §5 and #77039). `admin-ui` accepts breadcrumbs as data, it does not _implement_ breadcrumbs.
- **`NavigableRegion`** → **drop from the admin-ui public API.** Needs a pre-2.0 decision: PR [#72106](https://github.com/WordPress/gutenberg/pull/72106) (Oct 2025) moved the component _out_ of `@wordpress/interface` into `@wordpress/admin-ui` and deleted the interface copy, so admin-ui's version is the canonical implementation. The four consumers — `edit-post/components/layout`, `edit-site/components/layout`, `edit-site/components/save-panel`, `interface/components/interface-skeleton` — import it from here. (The source comment referencing `@wordpress/editor` is stale.)

  Consequence: no "original" private API exists to migrate back to. Before `admin-ui@2.0` can drop the export, `NavigableRegion` needs a new home. Options (decision required — see §12 Q2):

  1. **Rehome to `@wordpress/interface`.** Natural owner given `interface-skeleton` is the heaviest user. No API change; callers update import paths.
  2. **Rehome to `@wordpress/components`** alongside `useNavigateRegions`. Architecturally clean — the region primitive and the cycling hook live together — but bloats a public package.
  3. **Keep in admin-ui, drop from public exports.** Export as a private API via `lock-unlock`. Contradicts the "admin-ui drops responsibility for individual UI components" principle (§1); included for completeness.

  Whichever option is chosen, `NavigableRegion` itself is **not modified** by this work; it moves as-is.
- **Slot/Fill infrastructure** → drop. `createSlotFill` is only used today for the mobile sidebar toggle, which is solvable with a plain prop plus a consumer-side wrapper component (§7). `createSlotFill` stays where it is (in `@wordpress/components`); it is not moved to `@wordpress/ui`.
- **Direct `@wordpress/route` dependency** → drop. Routing is a concern of the consumer (§5.3 and #77040).

### 2.2 Belongs

- **Page shell** (`<Page>`) — landmarks, heading hierarchy, header content, padded content area by default (§4.3).
- **Full-bleed escape** (`<Page.FullBleed>`) — opt-out wrapper that lets a specific content block span the full page width, bypassing the default inline padding (§4.3.a).

Everything else that a "package for admin pages" might plausibly own is explicitly _not_ in scope for 2.0: router integration is handled by breadcrumb data plus an optional `linkComponent` prop (§5.3), chrome injection is a plain prop (§4.5), and cross-tree communication is the consumer's concern (not admin-ui's). Patterns for list views or split/detail layouts may land in later minors without breaking changes — not part of the initial surface.

Anything that is not _specific to admin pages_ does not belong here.

## 3. API strategy — decision

Options considered:

| Strategy                                                             | Strength                                                     | Weakness for admin-ui                                                                                                |
| -------------------------------------------------------------------- | ------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------- |
| **Monolithic props** (current)                                       | Easiest to type.                                             | Prop soup (`title`, `subTitle`, `visual`, `badges`, `actions`, `breadcrumbs`, `headingLevel`, `hasPadding` …). And constraints that _should_ be enforced at compile time (e.g. "≤ 2 secondary actions") degrade to runtime warnings when the prop is a flat list. |
| **Compound components** (`<Page.Header>`, `<Page.Title>`, …)         | Ergonomic, composable.                                       | _Too_ permissive. Consumers can re-order, duplicate or omit parts, defeating the point of an inflexible spec.        |
| **Render/slot props with typed contracts**                           | Allows structured content plus runtime validation.           | Awkward when only one slot varies; boilerplate; types can't always express "string-or-one-of-a-set-of-ReactNodes".   |
| **Declarative data + a few named slots, no exposed compound parts** | Strongest fit with the product vision: opinionated, precise. | Slightly less "React-idiomatic". But we _want_ less idiom here — we want a spec. Data is easy to validate and lint. |

### Decision: **declarative configuration, with a minimal, named slot surface.**

- The shape of the header is **data**, not JSX. Where a cardinality rule can be expressed in the type system — e.g. "at most one primary action, at most two secondary actions" as a tuple union on `PageActions` (§4.3) — it is type-enforced, not runtime-validated. Runtime validation only covers what types can't, such as breadcrumb items that provide neither `href` nor `onClick`.
- **One narrow styling subcomponent** is publicly exposed: `<Page.FullBleed>` (§4.3.a). It is a _styling wrapper_, not a structural compound part, and earns the exception for the reasons spelled out below. No other compound sub-components (`<Page.Header>`, `<Page.Title>`, `<Page.Section>`, …) are exposed. Internally `<Page>` composes a private `<Header>`; that composition is not part of the API surface.
- Two tight escape hatches for content that cannot reasonably be data: `visual` (a decorative `ReactNode`) and `leading` (app-shell chrome, §4.5).
- Runtime validation (dev-only) catches the few things types can't: breadcrumb items missing both `href` and `onClick`, etc. Cardinality rules that _can_ be expressed in the type system (actions shape) are enforced at compile time — see §4.3.

This gives us the ergonomics of named fields + the safety of a schema.

## 4. Proposed public API

### 4.1 Exports (complete)

```ts
// packages/admin-ui/src/index.ts
export { Page } from './page';
// <Page.FullBleed> is attached as a static property of Page (see §4.3.a).
```

One component (plus `Page.FullBleed` as a static subcomponent). No `Breadcrumbs`, no `NavigableRegion`, no slot/fill, no `Page.Section`, no `PageContent`, no `PageChromeProvider` / `usePageChrome`, and no exported type aliases. Consumers that need a prop type use `React.ComponentProps<typeof Page>`; keeping named types out of the public surface shrinks the API we have to maintain and version.

Router integration is expressed as data on breadcrumb items, with an optional `linkComponent` prop for consumers who want their router's Link to render the markup (§5.3). Chrome injection is a plain prop on `<Page>` (§4.5). Padding is the default, with `<Page.FullBleed>` as the opt-out (§4.3.a).

### 4.2 `<Page>`

```tsx
<Page
    // Required semantic identity
    title="Pages"
    // Optional header content
    subtitle="Manage static site pages"
    visual={ <Icon icon={ pages } /> /* see §4.3, always decorative */ }
    badges={ [ { label: 'Beta', intent: 'informational' } ] }
    breadcrumbs={ [
        { label: 'Dashboard', href: '/' },
        { label: 'Content' },
    ] }
    actions={ {
        primary: { label: 'Add new', onClick: onAddNew },
        secondary: [
            { label: 'Import', onClick: onImport },
        ],
        overflow: [
            { label: 'Export all', onClick: onExport },
            { label: 'Delete all', onClick: onDeleteAll, isDestructive: true },
        ],
    } }
    // App-shell injection slot (§4.5)
    leading={ /* e.g. mobile sidebar toggle */ }
    // Optional: render breadcrumb links with a custom component, e.g. a router Link (§5.3)
    linkComponent={ RouteLink }
    // Ref to the <main> landmark (§6.1), plus standard HTML pass-through
    ref={ pageRef }
    className="my-route-page"
    id="pages-route"
>
    <h2>Recent</h2>
    <Summary />
    <Page.FullBleed>
        <DataViewsTable />
    </Page.FullBleed>
</Page>
```

`<Page>` is the only component that encodes admin-page semantics. There are no publicly exposed _structural_ compound sub-components — see §4.4 for why `<Page.Section>` was considered and dropped.

`<Page>` is `forwardRef`-ed to the `<main>` landmark (§6.1). It accepts `className`, `id`, and `ref` as standard pass-throughs; no other HTML attribute pass-through is supported so the component can evolve its internal markup without leaking.

### 4.3 Props, typed primitives, and runtime validation

Prop types of `<Page>` (shown for documentation; not exported):

```ts
type PageProps = {
    // Required
    title: string;

    // Optional text / layout — "subtitle" maps to the design spec's "Tagline" (short page summary)
    subtitle?: string;

    // Header slots
    visual?: React.ReactNode; // always decorative — see below
    leading?: React.ReactNode; // §4.5

    // Header data
    badges?: ReadonlyArray< PageBadge >;
    breadcrumbs?: ReadonlyArray< PageBreadcrumbItem >;
    actions?: PageActions;

    // Router integration (§5.3)
    linkComponent?: BreadcrumbLinkComponent;

    // Content
    children?: React.ReactNode;

    // Standard HTML pass-through
    className?: string;
    id?: string;
};

type PageBreadcrumbItem =
    // Link: may also attach an onClick for SPA interception (§5.3).
    | {
          label: string;
          href: string;
          onClick?: ( event: React.MouseEvent< HTMLElement > ) => void;
      }
    // Non-URL action (not a link — rendered as a <button>).
    | {
          label: string;
          onClick: ( event: React.MouseEvent< HTMLElement > ) => void;
      }
    // Current / non-interactive item.
    | { label: string };

type PageBadge = {
    label: string;
    intent?: 'informational' | 'success' | 'warning' | 'critical';
}; // non-interactive; for interactive status use `actions`

// Actions shape encodes the spec's roles (#76709):
//   - exactly 0 or 1 primary (always rendered right-aligned);
//   - 0, 1, or 2 secondary buttons (cap enforced by the tuple union below);
//   - any number of overflow actions, rendered as items inside an ellipsis menu admin-ui owns.
type PageActions = {
    primary?: PageAction;
    secondary?:
        | readonly [ PageAction ]
        | readonly [ PageAction, PageAction ];
    overflow?: ReadonlyArray< PageAction >;
};

// Shared shape for all three roles. The event target is `HTMLElement` because overflow
// items render as menu items, not `<button>`s. The final mapping onto @wordpress/ui's
// `<Button>` / menu-item surface (leading-icon vs. icon-only, disabled semantics) is
// a small integration task, not a shape decision for admin-ui.
type PageAction = {
    label: string;
    onClick: ( event: React.MouseEvent< HTMLElement > ) => void;
    icon?: React.ReactNode;
    isDisabled?: boolean;
    isDestructive?: boolean; // visual treatment; not a semantic confirmation flow
};

// Optional escape hatch for component-based routers (§5.3).
type BreadcrumbLinkComponent = React.ComponentType< {
    href: string;
    children: React.ReactNode;
    onClick?: ( event: React.MouseEvent< HTMLElement > ) => void;
    className?: string;
} >;
```

Observations:

- `title` is required. `<Page>` derives its accessible name from the `<h1>` via `aria-labelledby`; there is no `ariaLabel` prop.
- **No `hideTitle` prop.** The spec (#76709) defines the rule: "when breadcrumbs are shown, the page title should be hidden (but still present) to avoid visually duplicating page info". `<Page>` implements that rule automatically — if `breadcrumbs` is non-empty, the `<h1>` is wrapped in `<VisuallyHidden>` (kept in the DOM for `aria-labelledby`); otherwise it renders visibly. Consumers make no decision.
- `breadcrumbs` is **data**, not `<Breadcrumbs>` JSX. `<Page>` renders the primitive from `@wordpress/ui` internally. That is how routing becomes pluggable (§5.3).
- `actions` is **role-shaped**, not a flat list. `primary` is a single object (never multiple), `secondary` is a tuple capped at two elements by the type itself, and `overflow` is the ellipsis-menu bucket. The spec's rules (#76709 — 1 primary, ≤ 2 secondary, tertiary behind an ellipsis menu) are expressed at the type level and cannot be violated without a compile error; runtime validation has nothing to enforce on this front. Ordering is owned by admin-ui per the spec ("primary button is always positioned to the right"); consumers do not author order.
- `overflow` items are rendered as menu items inside an ellipsis-menu button admin-ui emits. Admin-ui owns the menu's ARIA (`aria-haspopup="menu"`, keyboard behavior, focus return). Consumers do not supply the menu or its trigger.
- `PageAction` is shared across all three roles. The final visual mapping onto `@wordpress/ui`'s `<Button>` / menu-item surface (leading-icon vs. icon-only, disabled semantics, destructive styling) is a small integration task; none of it changes the admin-ui prop shape.
- `visual` is a plain `React.ReactNode` and is **always decorative**: admin-ui renders it inside a wrapper with `aria-hidden="true"`. Informative imagery belongs in the content area with its own `alt` text, not in the page-title visual slot. This keeps the header's accessible name exactly the title. Consumers pass whatever they like — `<Icon icon={…} />`, an `<img alt="">`, an emoji, nothing.
- No free-form `headingLevel` prop. `<Page>` is always `h1`. Content-area headings are the consumer's responsibility and should use `h2` for top-level blocks (see §4.4 and §6).
- **No `density`, `size`, or `padding` props.** All considered and rejected as speculative: admin pages use one canonical density and layout from the design system, padding defaults to on with `<Page.FullBleed>` (§4.3.a) as the only escape. Any of these can be added later with an explicit, spec-backed value if a real need appears.
- **Responsive header behavior is internal**, not configurable. `<Page>` implements the spec's responsive rules (actions overflowing to the ellipsis menu, breadcrumb collapsing, tagline truncation on scroll, hamburger revealing at the mobile breakpoint) via `ResizeObserver` on the page header — container-aware, not viewport-aware. No prop opts in or out.

Runtime validation (dev-only):

```ts
if ( process.env.NODE_ENV !== 'production' ) {
    assertPagePropsValid( props );
}
```

Rules enforced:

- `breadcrumbs`: all but the last must have `href` or `onClick`.
- (Actions cardinality rules are type-enforced via `PageActions`, not runtime-validated.)

Errors are thrown in development; silent in production (see §13).

#### 4.3.a Padding: default + `<Page.FullBleed>` escape

`<Page>` applies the canonical admin-page inline padding by default — header and content use the same value from `@wordpress/theme`. No prop is required. Most admin pages want this and should not have to think about it.

For the specific case where a single content block needs to span the full page width (the canonical example is a DataViews-style list/table that aligns with the outer container), consumers wrap that block in `<Page.FullBleed>`:

```tsx
<Page title="Pages">
    <h2>Recent</h2>
    <Summary />

    <Page.FullBleed>
        <DataViewsTable />
    </Page.FullBleed>

    <Footer />
</Page>
```

- `<Page.FullBleed>` neutralizes the page's inline padding for its children — typically via negative inline margins sized from the same token the page uses, so the two cannot drift.
- Accepts all standard `<div>` props (`className`, `id`, `style`, `role`, `aria-*`, data attributes, `children`, …). `ref` is forwarded to the underlying `<div>`. No admin-ui-specific knobs (no size, no variant) — the only thing this component _does_ is neutralize the page's inline padding.

    ```ts
    type PageFullBleedProps = React.ComponentPropsWithRef< 'div' >;
    ```

- Valid only inside `<Page>` (nothing outside `<Page>` has a padding to neutralize). This is stated in the docs; no runtime dev warning is shipped in 2.0. If misuse shows up in practice, a warning can be added later without an API change.

Pattern precedent: `Card.FullBleed` in `@wordpress/ui` (`packages/ui/src/card/full-bleed.tsx`). Contributors already know the semantics.

Why no padding prop up front: the default is correct for most pages; a two-value prop forces every consumer to decide and encodes a bet about which cases exist. `<Page.FullBleed>` inverts the default at the exact content-tree location where the decision is made. Padded header + full-bleed table is a recognized admin UI pattern (Notion, Linear, GitHub settings, WP admin). If a whole-page full-bleed variant ever becomes a real need, we add a prop then with a spec-backed value.

On the compound-component trade-off: §3 rejects compound patterns as too permissive. `<Page.FullBleed>` earns the pattern anyway because it's a **styling wrapper**, not a structural component — one narrow, named affordance ("this block is full-bleed"), namespaced to telegraph the "only valid inside `<Page>`" constraint. `<Page.Section>` failed because it was both too weak (enforced little) and too opinionated (fixed title shape); `<Page.FullBleed>` is strong (neutralizes a specific rule) and opinionless about content.

### 4.4 No `<Page.Section>` — and why

A `<Page.Section>` component was considered and rejected. It would have:

1. Wrapped children in `<section aria-labelledby={generatedId}>`.
2. Generated the id and rendered an `<h2 id={generatedId}>{title}</h2>`.
3. Enforced `h2` for section headings.
4. Applied some vertical rhythm.

Each is weak in practice:

- **(1)–(2)** are three lines of consumer JSX; the `aria-labelledby` wiring is documented in the README.
- **(3)** is enforced by the API, not by the DOM — a consumer who puts `<h3>` inside still ships `<h3>`. Lint / axe catch this regardless.
- **(4)** is styling, cleaner on the page-content wrapper.
- **The title shape is inflexible.** Real admin-page sections combine title + description + action + status + icon in ways that vary by page type; a fixed shape is wrong for most, and a permissive shape starts replicating `<Page>`'s header at a smaller scale.

Consequence: admin-ui does not ship `<Page.Section>`. Content inside `<Page>` uses `<section aria-labelledby>` where appropriate, composed from `@wordpress/ui` primitives. Validated by a11y tests (§9, §10). If practice shows a common shape emerging, we revisit — not before.

### 4.5 `leading` — the one chrome injection point

App shells sometimes need to decorate every page's header with a piece of chrome that the page itself does not know about — the canonical example is `boot`'s mobile sidebar toggle. `<Page>` accommodates this with a single plain prop:

```tsx
leading?: React.ReactNode;
```

- Rendered in the header row, as the leading item before the visual / title cluster. This hypothesis mirrors where today's `SidebarToggleSlot` sits in `packages/admin-ui/src/page/header.tsx`, so existing integrations carry over without visual change.
- **Design feedback still required.** #76709 illustrates the hamburger appearing at a specific mobile breakpoint; the final position (in-row vs. on its own line above the breadcrumbs, size/alignment, responsive behavior) should be confirmed by design before we freeze the spec. Adjusting the internal render location is not a breaking change; the prop itself is stable.
- A plain `ReactNode`, not a render prop (nothing about the rendering is dynamic per-invocation) and not a slot/fill or context (both add DI infrastructure the package does not need).
- Admin-ui does not ship a provider for this. If a shell wants every page to receive the same node, it defines a one-line wrapper:

  ```tsx
  // boot:
  const AppPage = ( props ) => (
      <Page
          leading={ isMobileViewport ? <MobileSidebarToggle /> : undefined }
          { ...props }
      />
  );
  ```

  Routes render `<AppPage>` instead of `<Page>`. That wrapper is boot's concern, not admin-ui's.

### 4.6 No `PageChromeProvider` / context / slot-fill / render-prop functions

**Admin-ui ships no public DI infrastructure** — no slot/fill, no exported context, no provider, no hook, no render-prop functions. `leading` is a plain `ReactNode` prop (§4.5); router integration uses breadcrumb item data (`href`, `onClick`) plus an optional `linkComponent` component type (§5.3). The "one place, many pages" case is handled by a consumer wrapper component (§11 — e.g. boot's `AppPage`), not a provider.

## 5. Decoupling: components, routing, breadcrumbs

### 5.1 Drop `@wordpress/components`; consolidate on `@wordpress/ui`

Current admin-ui imports from `@wordpress/components` are replaced entirely:

| Current                                             | Replacement                                                                         |
| --------------------------------------------------- | ----------------------------------------------------------------------------------- |
| `__experimentalHeading` (inside the Breadcrumbs)    | Removed. `@wordpress/ui/Breadcrumb` no longer renders a heading (§5.2). `<Page>`'s own `<h1>` is a native heading, styled with `<Text render={ <h1 /> } />` from `@wordpress/ui`. |
| `__experimentalHStack` / `HStack`                   | `<Stack direction="row">` from `@wordpress/ui`.                                     |
| `createSlotFill` (sidebar toggle)                   | Plain `leading` prop on `<Page>` (§4.5).                                            |
| `SlotFillProvider` in consumers                     | No longer needed _for admin-ui_ (consumers may still use it for their own reasons). |
| Badge for `PageBadge`                               | `<Badge>` from `@wordpress/ui`.                                                     |

`@wordpress/ui` component catalog actually used by admin-ui 2.0 (verified against `packages/ui/src/index.ts`):

| Component        | Exists in `@wordpress/ui` today? | Used for                                        |
| ---------------- | -------------------------------- | ----------------------------------------------- |
| `Stack`          | yes                              | header layout                                   |
| `Text`           | yes (with `variant` + `render`)  | title, subtitle, section headings               |
| `Badge`          | yes                              | `PageBadge`                                     |
| `Button`         | yes                              | `PageAction`                                    |
| `Icon`           | yes                              | icons inside `visual` / action buttons          |
| `VisuallyHidden` | yes                              | hiding the `<h1>` when breadcrumbs are set      |
| `Breadcrumb`     | **no (#77039)**                  | new component, ships before admin-ui 2.0        |

`Card.FullBleed` exists in `@wordpress/ui` (`packages/ui/src/card/full-bleed.tsx`) and is _not_ consumed by admin-ui. It is referenced separately in §4.3.a as **pattern precedent** and naming/semantics source for `<Page.FullBleed>`. No runtime dependency.

After this, **admin-ui depends on `@wordpress/ui`, `@wordpress/theme`, `@wordpress/i18n`, `clsx` — and nothing else from the components ecosystem.** Where no `@wordpress/ui` component fits (e.g. custom layout rules for the header grid), we write plain CSS with **design tokens from `@wordpress/theme`**. No ad-hoc values.

All user-facing strings (accessible labels, dev-validation messages shown in UI) are marked for translation with `__()` / `_x()` from `@wordpress/i18n`. Nothing is hard-coded English.

### 5.2 Move Breadcrumbs to `@wordpress/ui` (container-aware, router-agnostic)

This is #77039. Concrete shape of the new `@wordpress/ui/Breadcrumb`:

- **Container-aware** via `ResizeObserver`. When the available inline size drops below a measured threshold, items collapse to an overflow menu (middle items first, keeping the root and the current). **Not** tied to viewport media queries.
- **Data-first, opt-in component rendering.** Items carry `href` and/or `onClick` directly. The component renders:
  - `href` only, no `linkComponent` → `<a href>` (static link).
  - `href` + `onClick`, no `linkComponent` → `<a href onClick>` (SPA link; consumer `preventDefault`s if they want to intercept).
  - `href` + `linkComponent` → renders the consumer's component, passing `{ href, children, onClick?, className? }`.
  - `onClick` only → `<button type="button" onClick>` (non-URL action). `linkComponent` does not apply to buttons.
  - Neither → non-interactive text with `aria-current="page"` (the current item).

  There is no provider and no function render-prop. The integration point is a single optional `linkComponent: React.ComponentType<…>` on the container (`<Page>` in admin-ui's case, `<Breadcrumb>` in `@wordpress/ui`).
- Accessibility: `<nav aria-label={ translated 'Breadcrumb' }>`, `<ol>`, `aria-current="page"` on the **last** item regardless of whether that item is a link, a button, or plain text (per [WAI-ARIA Authoring Practices – Breadcrumb](https://www.w3.org/WAI/ARIA/apg/patterns/breadcrumb/)). Proper collapsed-menu ARIA for the overflow state.
- **External breadcrumb links are out of scope.** Breadcrumbs represent the hierarchy of the current admin surface; they are assumed internal. `target`, `rel`, and `download` are not part of the contract. Consumers that need external links in navigation use regular `<a>` elements outside the breadcrumb component.
- **Does not** own the page `h1` (the current admin-ui Breadcrumbs does, which is wrong — it only makes sense because the component lives inside a Page header; the primitive must not make that assumption).

Admin-ui consumes this primitive internally for its `breadcrumbs` prop and renders the `h1` separately and unconditionally.

### 5.3 Decouple from `@wordpress/route` (#77040): data + `linkComponent`

`@wordpress/admin-ui` has **no** import from `@wordpress/route`. `<Page>` exposes two integration surfaces, both plain props:

1. **Breadcrumb item data** (`href`, `onClick`) — for the common case where the item is a static URL, an SPA link with click interception, or a non-URL action.
2. **`linkComponent?`** — a single optional React component type that admin-ui uses to render items with `href`. Lets consumers plug in their router's `<Link>` when they want the extras it provides (prefetching, active state, client-side routing semantics).

The fixed contract for `linkComponent`:

```tsx
type BreadcrumbLinkComponent = React.ComponentType< {
    href: string;
    children: React.ReactNode;
    onClick?: ( event: React.MouseEvent< HTMLElement > ) => void;
    className?: string;
} >;
```

`href` is always passed to `linkComponent` (admin-ui normalizes the shape regardless of what a given router's component uses internally). Routers whose Link uses a different prop name are adapted at the call site with a one-line component. No consumer ever imports from `@wordpress/ui` to wire routing.

How each router pattern integrates:

**Static `<a href>` (no JS routing).** Just set `href`, don't pass `linkComponent`:

```tsx
breadcrumbs={ [
    { label: 'Dashboard', href: '/wp-admin/' },
    { label: 'Pages', href: '/wp-admin/edit.php?post_type=page' },
    { label: 'Edit' },
] }
```

**Event-based / imperative router** (exposes `navigate(url)`, no Link component). Attach navigation in `onClick`; keep `href` so the link still works without JS and so middle/cmd-click still open the target via the browser default:

```tsx
breadcrumbs={ [
    {
        label: 'Dashboard',
        href: '/',
        onClick: ( event ) => {
            event.preventDefault();
            router.navigate( '/' );
        },
    },
    { label: 'Pages' },
] }
```

(Whether to defer to the browser on modifier / middle clicks is a consumer decision and out of scope for admin-ui. `<Page>` simply forwards the event.)

**Component-based router** (`@wordpress/route`, React Router, etc. — Link uses `to`). Define a one-line adapter in the shell and pass it once via `linkComponent`:

```tsx
import { Link } from '@wordpress/route';

const RouteLink = ( { href, children, ...rest } ) => (
    <Link to={ href } { ...rest }>{ children }</Link>
);

<Page breadcrumbs={ [ … ] } linkComponent={ RouteLink } />
```

(Routers with strictly-typed route tables — TanStack, React Router v6 type-safe mode — may require a typed cast in the adapter; that's a one-time shell concern, not a per-page one.)

**Component-based router whose Link already uses `href`** (Next.js et al.): pass the component directly.

### 5.4 Reducing repetition: the `AppPage` wrapper threads both props

Both `leading` (§4.5) and `linkComponent` are configured identically by the app shell — once, in a thin `AppPage` wrapper — so consumer route pages never touch either:

```tsx
// boot/app-page.tsx
import { Page } from '@wordpress/admin-ui';
import { Link } from '@wordpress/route';

const RouteLink = ( { href, children, ...rest } ) => (
    <Link to={ href } { ...rest }>{ children }</Link>
);

export const AppPage = ( props: React.ComponentProps< typeof Page > ) => (
    <Page
        leading={ isMobileViewport ? <MobileSidebarToggle /> : undefined }
        linkComponent={ RouteLink }
        { ...props }
    />
);
```

Route pages — including third-party plugins inside boot — render `<AppPage>` and get both shell chrome and router integration for free. Pages outside boot render `<Page>` and choose what (if anything) to pass; they will not participate in boot's chrome, which is the intended boundary.

### 5.5 Why `linkComponent` over a provider or function render-prop

Consumers don't import from sibling packages or configure providers to wire routing. Event-based routers and static links work out of the box; component-based routers plug in via a one-line adapter — a component type, not a render-prop function, so it composes with `React.memo`. Progressive enhancement comes for free: `href` is a real URL and works without JS; `onClick` is a pure enhancement.

This closes #77040 (no router code in admin-ui), keeps the consumer's dependency surface on admin-ui only, and supports event-based and component-based routers equally well.

## 6. Document hierarchy & semantics (non-negotiable)

> **Pending a11y review.** The defaults below are our proposal; before finalizing, the spec needs sign-off from WordPress a11y reviewers (e.g. Joe Dolson and the a11y team). The `<main>` vs. `useNavigateRegions` decision in §6.1 is the most likely item to warrant discussion.

`<Page>` is responsible for a correct, predictable document skeleton. This is the main reason the package exists.

Baseline output (labels shown in English for readability; all are translated with `__()` / `_x()` from `@wordpress/i18n`). The readable suffixes on `class="[hashed] …"` are there to help the reader identify each element — the actual output is hashed class names only, per §8.1:

```html
<main class="[hashed]" aria-labelledby="[generated-page-title-id]">
    <header class="[hashed]">
        <nav aria-label="Breadcrumb">...</nav>
        <div class="[hashed] header-row">
            <!-- `leading` renders as the leading item of the header row (hypothesis from §4.5; pending design sign-off on #76709). -->
            <div class="[hashed] leading">...</div>
            <div class="[hashed] visual" aria-hidden="true">...</div>
            <h1 id="[generated-page-title-id]">Pages</h1>
            <!-- Badges rendered adjacent to the title, not as part of it. Non-interactive. -->
        </div>
        <!-- Subtitle uses `<Text render={ <p /> } />` from @wordpress/ui (spec calls this the "Tagline"). The exact variant is chosen from the design tokens / spec — do not hard-code. -->
        <p class="[hashed] subtitle">Manage static site pages</p>
        <!--
          Actions group. Label is a generic, fixed, translated string.
          Order of children is fixed by admin-ui, not by the consumer:
          secondary buttons → (ellipsis menu, if `overflow` is non-empty) → primary button (right-aligned per #76709).
          The ellipsis button is labelled "More actions" (translated); opening it reveals a role="menu" with the overflow items.
        -->
        <div class="[hashed] actions" role="group" aria-label="Actions">
            <button>Import</button>
            <button aria-haspopup="menu" aria-expanded="false" aria-label="More actions">...</button>
            <button class="[hashed] primary">Add new</button>
        </div>
    </header>

    <!-- Consumer-authored content. Inline padding is the admin-page default; <Page.FullBleed> neutralizes it per-block. -->
    <div class="[hashed] content">
        <!-- Sections, if used, are <section aria-labelledby> with <h2>. -->
    </div>
</main>
```

Rules the component guarantees:

- The page landmark is `<main>`, not a generic `region`. There is exactly one `<main>` per rendered `<Page>`.
- The page title is always `<h1>`. When `breadcrumbs` is non-empty the `<h1>` is wrapped in `<VisuallyHidden>` (per #76709: "when breadcrumbs are shown, the page title should be hidden but still present"). It remains in the DOM so `aria-labelledby` and AT navigation still work; only the visible rendering is suppressed. No consumer-facing prop controls this.
- The visual element is **always decorative** — admin-ui wraps it with `aria-hidden="true"` unconditionally. Informative imagery belongs in the content area.
- Badges sit alongside the title but outside the `<h1>` (current behavior is sometimes inside the heading — confusing for AT) and are non-interactive.
- Actions are wrapped in a group labelled "Actions" (generic, fixed, translated).
- The header responds to its container size (`ResizeObserver`, not viewport media queries): actions overflow to the ellipsis menu, breadcrumbs collapse to a middle-truncated form, the tagline truncates on scroll, and the hamburger (`leading`) reveals at the mobile breakpoint per #76709. This is internal behavior; no prop configures it.

Rules documented for consumer-authored content (enforced by tests, not by a component):

- Top-level content blocks should be `<section aria-labelledby={id}>` with an `<h2 id={id}>`. From `@wordpress/ui`, `<Text render={ <h2 /> }>` (with the heading variant chosen from the design spec) is the canonical primitive.
- Heading order is monotonic: no `<h3>` without a preceding `<h2>`; no level skipping.
- Inline padding is the admin-page default, applied by `<Page>`. Blocks that need full width use `<Page.FullBleed>` (§4.3.a). Content-specific spacing inside the page uses `@wordpress/theme` tokens, not hard-coded values.

### 6.1 `<main>` vs. `useNavigateRegions` — explicit trade-off

`<Page>` renders a plain `<main>`. It does **not** add `role="region"` or `tabIndex="-1"`, and therefore does **not** participate in the `useNavigateRegions` (`@wordpress/components`) cycle by default.

Why:

- `useNavigateRegions` matches a hard-coded selector: `[role="region"][tabindex="-1"]`. It does not recognize native landmarks (`<main>`, `<nav>`, `<aside>`, …).
- Adding `role="region"` to `<main>` _overrides_ the implicit `main` role (author role wins), downgrading the landmark to a generic named region. We want to keep the strongest landmark.
- Nesting (`<main><section role="region" tabindex="-1">`) reintroduces the `NavigableRegion`-style wrapper we are deleting.
- `tabIndex="-1"` only matters for programmatic focus. Route-change focus management is a consumer concern, not a `<Page>` concern. `<Page>` forwards a `ref` to its `<main>` element so consumers that need to call `.focus()` on route changes can do so.

Consequence: the existing `NavigableRegion` instances in editor chrome (`interface-skeleton` emits them for header, sidebars, content, actions, footer; `edit-post` / `edit-site` / `save-panel` add more) keep cycling under Ctrl+\` / Alt+Shift+N,P. The cycle simply does not include the admin page itself. This matches the spirit of the hook — it's most useful for moving _within_ chrome, not for picking the page. (Wherever `NavigableRegion` is rehomed per §2.1 and §13 Q2, it continues to work unchanged.)

**Follow-up (separate task, `@wordpress/components`):** generalize `useNavigateRegions` to recognize native landmarks (`main`, `nav`, `aside`, labelled `section`, …) and handle focus on elements without a pre-set `tabindex` (either by setting it imperatively before `.focus()` or by using `{ preventScroll: true }` and tolerating the focus-outline story). This unlocks "use real landmarks" codebase-wide, not just in admin-ui, and removes the custom `NavigableRegion` idiom over time. Tracked separately from the admin-ui 2.0 work; a11y review should confirm the approach before we implement.

(If it turns out admin pages genuinely need to participate in the cycle before the `useNavigateRegions` generalization lands, the fix is implemented there — inside `@wordpress/components` — not by adding a prop to `<Page>`. This keeps admin-ui's API spec-backed rather than an accumulation of toggles.)

## 7. Retiring `createSlotFill` without replacing it with DI

Today: `Page.SidebarToggleFill` in `<Root>` teleports a button into `<SidebarToggleSlot>` via `@wordpress/components` slot/fill + `SlotFillProvider`. The replacement:

- `<Page>` exposes one plain `ReactNode` prop, `leading`, for header chrome (§4.5).
- The app shell (`boot`) defines a one-line `AppPage` wrapper that forwards state-driven chrome to `<Page>` as `leading`.
- Route components render `<AppPage>` instead of `<Page>`. A `PageChromeProvider` context was considered and rejected: an ancestor→descendant DI step is handled better _outside_ admin-ui, by a wrapper component in the shell.

After migration:

```tsx
// boot/app-page.tsx
export const AppPage = ( props ) => (
    <Page
        leading={ isMobileViewport ? <MobileSidebarToggle /> : undefined }
        { ...props }
    />
);

// route page
<AppPage title="…">…</AppPage>
```

(`Page.SidebarToggleFill` + `SlotFillProvider` go away on both sides.)

Benefits over slot/fill and context: no DI infrastructure shipped by admin-ui, no `SlotFillProvider` required by consumers for this feature, every integration point on `<Page>` is a plain prop with an obvious call stack (easier to reason about in tests, Storybook, SSR), and the shell is explicit about what it decorates pages with in exactly one place (`AppPage`).

Nesting `<Page>` (two landmarks on one screen) is **unsupported** — it violates the "exactly one `<main>`" invariant in §9. Route-level modals should render a `role="dialog"` with their own header, not another `<Page>`.

## 8. Styling & build

### 8.1 CSS modules, logical properties, tokens

- All styles are authored as **CSS modules** (`*.module.scss` or `*.module.css`), colocated with components. No global selectors like `.admin-ui-page` in the authored CSS; consumers get hashed class names and can't accidentally override internals. (Design-token references such as `var(--wp-space-300)` and semantic custom properties set at the Page root remain global — custom properties are intentionally global.)
- 100% **logical properties** (`padding-block`, `margin-inline-start`, `inset-inline-end`). This is already partially true and must be enforced via a stylelint rule (`@wordpress/stylelint-config`'s logical-props rule or equivalent).
- All spacing, color, type, radius values come from `@wordpress/theme` tokens. No hard-coded `24px`, no raw `#fff`. If a value is used that has no theme-token equivalent, file a gap on `@wordpress/theme` rather than inlining a literal.
- A few semantic CSS custom properties at the Page level (`--admin-ui-page-padding-inline`) so `<Page.FullBleed>` can reference the exact same value for its negative margin.
- `@wordpress/base-styles` dependency: removed. If a utility is needed, pull the token from `@wordpress/theme`; otherwise write the few lines of plain CSS.

Supersedes / subsumes #77032.

### 8.2 `package.json` hygiene

```json
{
    "name": "@wordpress/admin-ui",
    "sideEffects": [
        "**/*.css",

    "files": [
        "build",
```

- `./style` export is explicit. Stylesheet shipping becomes a documented choice instead of an implicit side effect.

- TypeScript strict, `noUncheckedIndexedAccess` enabled.
- No `any` in the admin-ui source (`NavigableRegion` is removed from admin-ui and, per §2.1, is not modified as part of this work).
- ESM-first; CJS kept while monorepo requires it.

## 9. Accessibility requirements (explicit contract)

Captured here as testable invariants:

1. Exactly one `<main>` per `<Page>` render.
2. Exactly one `<h1>` emitted by `<Page>` per render, carrying the accessible name from `title`. When `breadcrumbs` is non-empty, the `<h1>` is visually hidden (via `<VisuallyHidden>`) but remains in the DOM with the same accessible name. Consumer-authored `<h1>`s inside content are a consumer concern and are flagged by axe, not by `<Page>`.
3. `aria-current="page"` on the **last** breadcrumb item, regardless of how it is rendered (per WAI-ARIA APG).
4. The `visual` slot is always wrapped in `aria-hidden="true"` and rendered outside the heading.
5. Actions group has a fixed, translated accessible label ("Actions").
6. All interactive header elements have visible and programmatic names (enforced by axe in tests).
7. Color contrast tested against the current `@wordpress/theme` palette in light and dark.
8. Tab order follows DOM order: breadcrumbs → `leading` → header actions → content. (Per the §6 baseline HTML, `<nav aria-label="Breadcrumb">` is a sibling _above_ the title row, and `leading` sits inside the title row before the visual/title cluster.) The `<h1>` is non-interactive and is skipped, as expected.
9. Reduced-motion honored for any internal transitions (currently none; keep it that way).
10. Heading order inside `<Page>` content is monotonic (no skipped levels). Validated by axe in the integration tests against a representative content fixture; consumer-authored content is otherwise their responsibility.

Each item is backed by unit tests (§10).

## 10. Testing plan

The package ships with:

- **Unit tests (RTL + jest-axe)** — one test file per component, covering:
  - Invariants 1–10 from §9.
  - Dev-validation errors (correct messages, only thrown in dev).
  - `leading` renders in the header; absent when `undefined`. `visual` is always rendered inside an `aria-hidden` wrapper.
  - Default inline padding applies; `<Page.FullBleed>` neutralizes it for its subtree (box-model assertions).
  - Breadcrumb item shape matrix: `href` only → `<a href>`; `href + onClick` → `<a href onClick>` with `onClick` invoked and `preventDefault` available; `onClick` only → `<button>`; neither → non-interactive text. The last item always carries `aria-current="page"` regardless of interactivity.
  - `linkComponent` is used for items with `href` and not for `<button>`-rendered items; contract props are passed as declared.
  - Actions ordering: secondary → ellipsis trigger (when `overflow` non-empty) → primary in DOM order; primary is visually right-aligned.
  - Overflow menu: ellipsis trigger has `aria-haspopup="menu"` and translated name ("More actions"); opening reveals a `role="menu"` with `role="menuitem"` children; arrow keys, Escape, and focus-return on close all work.
  - Actions cardinality is compile-time enforced: three items to `secondary` fails the build (type tests).
- **Integration tests** — a small suite that mounts `<Page>` with representative content including `<section aria-labelledby>` blocks and a `<Page.FullBleed>` block, and:
  - Runs `axe` against it in every variant combination. Matrix axes: with/without `breadcrumbs` (drives the auto-hidden-title branch) × with/without `badges` × actions shape (none, primary only, secondary only, primary + 1 secondary, primary + 2 secondary, overflow only, primary + 2 secondary + overflow) × with/without `visual` × with/without `leading` × with/without `Page.FullBleed` × with/without `linkComponent` × LTR / RTL.
  - Asserts landmark uniqueness and heading order using `@testing-library/react`'s `getByRole('main')`, `getAllByRole('heading', { level: 1 })`, etc.
  - Asserts the breadcrumbs-drives-hidden-title rule at both ends: `breadcrumbs` non-empty → `<h1>` is in the DOM but has an accessible-but-not-visible presentation; `breadcrumbs` empty → `<h1>` is visible.
- **Storybook + visual regression** — a11y addon enabled, stories cover the matrix, and snapshots are wired into the existing Chromatic / Playwright pipeline. Stories live in `/stories` and are imported by docs.
- **Type tests** (`tstyche` or `@ts-expect-error` comments) — exhaustiveness of the `PageBreadcrumbItem` discriminated union, the `linkComponent` contract, and that disallowed combinations fail at compile time.

Route-change focus management is out of scope for admin-ui and not covered by this test matrix; consumer shells are responsible for it.

Coverage target: ~95% of `src/` statements, 100% of invariants in §9.

## 11. Migration plan (breaking changes welcome)

Since we are explicitly accepting breaking changes, we publish a single major (`@wordpress/admin-ui@2.0.0`) that lands the redesign wholesale. A soft-deprecation period is not worth the double maintenance cost for a package with few external consumers.

| ------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Breadcrumbs` removed.                                                                     | Pass `breadcrumbs` data to `<Page>`, or import `Breadcrumb` directly from `@wordpress/ui`.                                                                             |

The component itself is unchanged. |
| `Page.SidebarToggleFill` removed.                                                          | Define a thin `AppPage` wrapper in the shell that forwards chrome as `leading` to `<Page>` (§4.5). No provider, no slot/fill.                                          |
| `Page` prop `headingLevel` removed.                                                        | Title is always `<h1>`. Consumer-authored top-level content blocks are `<h2>`.                                                                                         |
| `hasPadding: boolean` removed.                                                             | Padding is on by default. Use `<Page.FullBleed>` to opt a single content block out (§4.3.a).                                                                           |
| `subTitle` → `subtitle` (casing consistency with WordPress conventions).                   | Rename prop.                                                                                                                                                           |
| `ariaLabel` removed; `<Page>` derives its accessible name from the `<h1>` via `aria-labelledby`. | Stop passing `ariaLabel`; `title` is now required.                                                                                                                |

| No `size`, `density`, or exported type aliases.                                            | One canonical layout / density; use `React.ComponentProps<typeof Page>` if a prop type is needed.                                                                      |

### 11.2 Rollout steps

1. **A11y review of the spec.** Before any code lands, share §6 (semantics), §9 (invariants), and §6.1 (the `<main>` / `useNavigateRegions` trade-off) with the WordPress a11y team (e.g. Joe Dolson) and collect sign-off or required adjustments. Freeze the contract after this step.
2. **Land `@wordpress/ui/Breadcrumb`** (#77039) with container-aware behavior, the data-first `{ href, onClick }` item shape, and an optional `linkComponent` prop for component-based routers (no provider, no function render-prop). Ship in a UI release.
3. **Rehome `NavigableRegion`** per the decision on §13 Q2 (options listed in §2.1). Because no "original private API" exists today (PR #72106 moved it _into_ admin-ui and deleted the interface copy), this is a prerequisite for step 4, not an incidental cleanup. The component itself is not modified — it moves as-is. The four consumer packages (`edit-post`, `edit-site` × 2, `interface`) update their imports.
4. **Land `admin-ui@2.0.0`** exporting only `<Page>` (with `Page.FullBleed`) — no `Breadcrumbs`, `NavigableRegion`, slot-fill, `Page.Section`, `PageContent`, or `PageChromeProvider`. Router integration is the optional `linkComponent` prop on `<Page>`.
5. **Migrate boot** to a thin `AppPage` wrapper (exported from boot) that forwards `leading` to `<Page>`; drop `<SlotFillProvider>` if not otherwise needed. Route pages inside boot — including third-party plugins — import `AppPage` from `@wordpress/boot`; pages outside boot import `Page` from `@wordpress/admin-ui`. Document this boundary explicitly in boot's README so plugin authors understand the split.
6. **Document breadcrumb → router integration** (§5.3) with concrete recipes for static links, event-based routers, and component-based routers (including `@wordpress/route`, React Router, and Next.js); optionally ship a `useBreadcrumbLink()` convenience helper in `@wordpress/route`.
7. **Update Storybook** stories and regenerate docs.
8. **Changelog**: write a dedicated _Breaking changes_ section with a migration table (§11.1 verbatim).

Separately tracked, not a prerequisite for 2.0:

- **Generalize `useNavigateRegions`** (in `@wordpress/components`) to recognize native landmarks (`<main>`, `<nav>`, `<aside>`, labelled `<section>`) and handle focus without requiring `tabindex="-1"` to already be set. Deliverable: an issue in `@wordpress/components` with the proposal in §6.1; implementation follows after a11y confirms the approach. When this lands, admin pages pick up navigate-regions participation with no change to `admin-ui`.

### 11.3 Risk checklist

- Any external consumer of `Breadcrumbs` / `NavigableRegion` from `admin-ui` (none visible in-repo outside the places listed). Cover with a forward-only migration note.
- Slot/Fill removal is invisible to end users; only `boot` is affected.
- `actions` shape restructure: in-repo consumers currently pass a flat array. Each call site has to regroup into `{ primary?, secondary?, overflow? }` — a manual edit, not a codemod (the input is too underspecified to infer role reliably). In-repo surface is small; no automation planned.
- `<main>` landmark uniqueness: audit any page that embeds another `<Page>` (shouldn't happen; nesting is unsupported per §7 and §9, but assert in tests).
- RTL: CSS-modules migration should not regress RTL. Add visual snapshots in RTL mode.

## 12. Open questions and follow-ups

### Open questions (to resolve before or during implementation)

Ordered roughly by how close they sit to blocking 2.0 — a11y sign-off and the `NavigableRegion` rehoming are gates; the rest can be decided during implementation.

1. **A11y sign-off on the spec.** §6 and §9 encode the accessibility contract; they need review by the WordPress a11y team (e.g. Joe Dolson) before 2.0 ships. Specifically to confirm: single `<main>` per page, `<h1>` present even when visually hidden (auto-hidden when breadcrumbs are set, per #76709), `aria-labelledby` wiring, decorative-visual handling, actions group label ("Actions"), `aria-current="page"` on the last breadcrumb item regardless of interactivity, and the default of _not_ making `<Page>` participate in `useNavigateRegions` (§6.1). **Gating.**

2. **Where does `NavigableRegion` live after admin-ui drops the export?** Options listed in §2.1: rehome to `@wordpress/interface` (natural owner), rehome to `@wordpress/components` (lives next to `useNavigateRegions`), or keep inside admin-ui as a non-public export via `lock-unlock`. The component itself is _not_ modified either way. **Gating** for step 4 of the rollout.

3. **Header `navigation` and `controls` slots (#76709).** The design spec lists two optional in-header elements not in this proposal: **navigation** (in-header horizontal nav with horizontal-scroll overflow) and **controls** (search / DataViews controls, which responsively stack with navigation). Decision for 2.0:

    - **Responsive header stacking ships in 2.0.** The rules governing overflow, collapsing, tagline truncation, and the mobile hamburger are internal `ResizeObserver`-driven behavior (§4.3 and §6). No prop surface.
    - **`navigation` slot does not ship in 2.0.** Design spec is retained as reference; the prop lands in a later minor when the first consumer needs it. Non-breaking addition.
    - **`controls` slot does not ship in 2.0.** Same reasoning. The spec couples its responsive behavior to `navigation`, so shipping one without the other would be inconsistent — both land together.

4. **Dev validation: throw or warn in production?** Default to "throw in dev, silent in production". If consumer apps want to fail loudly in production previews, surface that as a module-level flag on `admin-ui` (not a provider) — the package intentionally ships no provider (§4.6).

5. **Whole-page full-bleed variant?** Out of scope for 2.0. Default is padded, `<Page.FullBleed>` is per-block. If a real need appears for an entirely edge-to-edge page (including the header), add a `<Page>` prop with an explicit spec-backed value — not before. See §4.3.a.

6. **Convenience helper for router integration.** `useBreadcrumbLink()` helper shipped in `@wordpress/route` to remove boilerplate in consumer code — cheap, not strictly required. Decide during §11.2 step 6.

### Separately tracked follow-ups (not blocking 2.0)

- **Generalize `useNavigateRegions`** in `@wordpress/components` to recognize native landmarks (`<main>`, `<nav>`, `<aside>`, labelled `<section>`) and to handle focus on elements without a pre-set `tabindex`. Rationale and approach: §6.1. Owner: `@wordpress/components`. A11y team should review the selector + focus-management change before implementation. Once landed, admin pages automatically participate with no change to `admin-ui`.
- **`navigation` / `controls` slots on `<Page>`.** Deferred per Q3 above. Adding either is a non-breaking minor; revisit when a consumer needs them.
- **Split / detail layout patterns** — not part of 2.0; may land in later minors if a need materializes.
