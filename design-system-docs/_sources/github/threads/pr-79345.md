## Summary

**Draft / illustration, stacked on #78471.** This explores the counter-proposal raised in #78471 review by @ciampo and @mirka: instead of a dedicated `@wordpress/rich-text-control` package that hard-wires `@wordpress/rich-text`, host a **presentational shell** in `@wordpress/components` and **inject** the rich-text wiring from the consumer.

Because it is stacked on #78471, the diff reads as "convert approach A → B". It is **not** meant to merge as-is; whichever direction we choose collapses into a single PR off `trunk`.

## What changed (delta vs #78471)

**`@wordpress/components` gains a private, presentational `RichTextControl`**
- Owns only the chrome: `BaseControl` + label, the `contentEditable` element, and the `Popover.Slot` scaffolding plus the blur/focus selection heuristic that keeps the field selected while focus is inside a format popover it opened.
- **Zero `@wordpress/rich-text` dependency.** The editable behavior (value, formatting, keyboard shortcuts) is injected by the consumer through `editableRef` and `children`; selection is controlled via `onSelectedChange`.
- Exported as a private API for now (the public-vs-private and `@wordpress/ui`-future questions are deliberately out of scope for this spike).

**`@wordpress/dataviews` owns the rich-text "assembly"**
- The `richtext` DataForm control becomes the assembly: it calls `useRichText`, wires `FormatEdit` and the keyboard / input-event listeners, and renders the components shell.
- The rich-text glue (formerly the package internals: `FormatEdit`, the event-listener modules, `getAllowedFormats`) is vendored under `dataform-controls/richtext/`, where coupling to `@wordpress/rich-text` is acceptable.

**`@wordpress/rich-text-control` is removed.**

## Why this shape

The ref-cycle that makes a "clean" split look hard (`useRichText` produces the ref the shell needs, but `isSelected` feeds back into `useRichText`) resolves by making the shell a **controlled component**: the assembly owns `isSelected`, the shell drives the focus/blur transitions via `onSelectedChange`. Standard React data flow; state lives in the assembly, DOM heuristics live in the shell.

Net effect: `@wordpress/components` gains a reusable presentational primitive, `@wordpress/rich-text` stays small, dataviews owns the wiring, and there is no standalone package.

## Test coverage

Coverage is preserved and split along the new boundary:
- **Components** (`rich-text-control/test`): presentational shell — label/aria, className merge, focus-on-mount, `editableRef` attachment, and the controlled-selection / popover-slot blur heuristic (13 tests).
- **DataViews** (`richtext/test/control.js`): the integration test relocated from the package — keyboard shortcuts and format input rules end-to-end through the assembly + shell (13 tests).
- **DataViews** (`dataform-controls/test/richtext.tsx`): prop wiring (5 tests).

Verified locally: all three suites green (31 tests), `tsc --build` clean for components + dataviews, ESLint clean.

## Open questions / not done

- **Storybook story**: the deleted package shipped a wired story. A presentational shell story belongs in components; a wired demo belongs with the assembly. Deferred for the spike — happy to add once the direction is settled.
- **Public vs private** components export, and how this interacts with the `@wordpress/ui` migration.
