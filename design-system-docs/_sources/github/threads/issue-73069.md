# Issue #73069: ToolsPanelItem: hasValue silently fails when it returns a non-boolean (e.g., undefined), causing the control to not render

- URL: https://github.com/WordPress/gutenberg/issues/73069
- Author: ddryo
- Created: 2025-11-07T00:58:39Z
- Updated: 2025-11-10T04:59:40Z
- Comments: 4 of 4

## Body

### Description

the `<ToolsPanelItem>` `hasValue` API appears to expect a boolean, but it does not validate or coerce the returned value. When hasValue returns a non-boolean (e.g., undefined), the control fails to render and there is no console error or warning, making the issue difficult to diagnose.

## Examples

If you do the following, controls will not be rendered when hoge or foo are undefined.
```
<ToolsPanelItem
  hasValue={() => hoge || foo}
  /* ... */
>
  {/* control */}
</ToolsPanelItem>
```

This can avoid the problem if modified as follows.

```
<ToolsPanelItem
  hasValue={() => !!(setTransition || setHov)}
  /* ... */
>
  {/* control */}
</ToolsPanelItem>
```

However, it takes time to notice this because there are no errors in the console.


## Expected behavior:

- hasValue should reliably accept and require a boolean.

- If a non-boolean is returned, the component should either:

 ▫ Coerce to a boolean internally (Boolean(result)), or

 ▫ Emit a clear developer warning (and ideally fail in dev builds), so consumers can correct their code.

- Documentation and types should communicate the strict boolean requirement.

### Step-by-step reproduction instructions


1. Create a ToolsPanelItem and set hasValue to an expression that can evaluate to undefined, e.g. hasValue={() => hoge || foo} where both values may be undefined initially.

2. Render the control within the editor sidebar (e.g., a block inspector panel).

3. Ensure both operands are undefined at render time.

4. Observe that the control does not render.

5. Check the browser console: no error or warning is emitted.

### aaronrobertshaw on 2025-11-10T02:27:07Z

Thanks for the issue and PR @hbhalodia 👍 

I think there might be a misunderstanding about the expected behaviour here, but I'd love to understand if I'm missing something.

When `hasValue` returns `undefined`, the component should not render, and it currently doesn't. This seems like the expected and correct behaviour because:
1. `undefined` indicates no value exists
2. Optional `ToolsPanelItems` should only render when they have a value
3. Both `undefined` and `false` produce identical results: the item doesn't render

TypeScript already enforces the contract defining `hasValue: () => boolean`. If developers return non-boolean values, that should ideally be caught during development as a TypeScript violation.

I might be missing something about the use case though - could you help me understand when you'd want a control to render when `hasValue` returns `undefined`? 

Based on my current understanding, I'd lean towards closing this as not a bug because:
- The component works as designed
- The behaviour is functionally correct regardless of boolean or truthy/falsy values
- Adding Boolean coercion might be unnecessarily defensive (though I'm open to other perspectives)
- TypeScript types already document the expected return type

What do you think?
