## Body

## What?

As per #53278, we need to move away from `reakit` to use `ariakit` instead. This PR tackles part of that, by starting the migration of the `Composite` component.


## Why?

> [Reakit](https://reakit.io/) does not explicitly support React 18, so it is causing peer dependency warnings.
> Reakit has already been succeeded by [Ariakit](https://ariakit.org/), so it will not receive any more updates.

`Composite` is currently a simple wrapper around `reakit`, re-exporting its various component parts. It needs to move away from this and export `ariakit` instead.


## How?

**This is the first step in migrating `Composite` away from `reakit`:**

 * Refactors usages of `reakit` to `ariakit` in `@wordpress/components`, but without modifying the version exported by the `@wordpress/components` package
 * Temporarily exports the `ariakit` version of `Composite` via the private APIs

**It does not tackle the following, which will be follow-up tickets:**

 * Iteratively refactor all usages of the `reakit` composite components across Gutenberg
 * Remove the `reakit` implementation, and use the `ariakit`-based version instead, removing the `ariakit` private API export

> [!NOTE]
> Even though `Composite` is [currently exported from the components package](https://github.com/WordPress/gutenberg/blob/trunk/packages/components/src/index.ts#L59-L65) as `__unstable`, it is being used publicly, so we will have to proceed with caution!

## Testing Instructions

Despite the API changes, both [`AlignmentMatrixControl`](https://wordpress.github.io/gutenberg/?path=/docs/components-experimental-alignmentmatrixcontrol--docs) and [`CircularOptionPicker`](https://wordpress.github.io/gutenberg/?path=/docs/components-circularoptionpicker--docs) should continue to work as now.

https://github.com/WordPress/gutenberg/blob/21b6a3717c1b09c376f7a5d914b0953aa2cdcddd/packages/components/src/index.ts#L59-L64

If so, the main difference between state and store hooks is that state hooks include all state as direct properties of the state object and re-render the component on every state change. This can be achieved with the store with this code:

```js
function useCompositeState() {
  const store = useCompositeStore();
  const state = store.useState();
  return { ...store, ...state };
}
```

Besides that, state hooks accept only the initial state as an argument and some properties have been renamed (check Reakit's [`useCompositeState`](https://reakit.io/docs/composite/#usecompositestate) API reference and Ariakit's [`useCompositeStore`](https://ariakit.org/reference/use-composite-store) API reference). These must be converted on both the input and the output:

```js
function useCompositeState(props) {
  const store = useCompositeStore(convertInput(props));
  const state = store.useState();
  return convertOutput({ ...store, ...state });
}
```

The problem with the 3 `await new Promise( requestAnimationFrame );` is that they're prone to error.

Since this is just a way to add extra "waiting" before tests start, theoretically, it might happen that this added time is still not enough for us to be certain that the component has finished initializing its state.

As a more reliable alternative, we can look at how the component reacts to the state initialization. In other words, we can observe what in the component is being modified *after* the state initialization.

Luckily for us, there is one change that we can use: after the composite state initializes, each cell will get a `tabindex="-1"`, except the default one. Since `tabindex` by default is `0`, that means we can wait for it to change to `-1`, and that means state initialization has already finished.

```suggestion
	// This ensures the component has properly established its initial state.
	await waitFor( () => {
		expect( getCell( 'top left' ) ).toHaveAttribute( 'tabindex', '-1' );
	} );
```
