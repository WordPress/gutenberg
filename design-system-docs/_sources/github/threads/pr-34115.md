## Description
<!-- Please describe what you have changed or added -->

It's an experiment to avoid exposing a global `useSlot` from `@wordpress/components`. Instead, we would have `useSlot` bound to the create SlotFill pair when using `createSlotFill` helper.

The branch has some bugs I didn't explore in detail, but I would treat it only as an example for the public API changes for now.

I'm thinking about the alternative approach as well closer to how `createContext` and `useContext` in React work.

### youknowriad on 2021-08-17T14:26:47Z

URL: https://github.com/WordPress/gutenberg/pull/34115#issuecomment-900346538

So there's a few items to discuss here:

## 1 What does it mean to make `useSlot` stable?

I think the answer to that is that it's the first time we're making a "slot" instance public API (and potentially fills since we have slot.fills now). As of today, the exposed slot objects contains a few things I don't like: `ref` and `fills`, these seem too low level, at least they should be marked "internal". So the question is what should a "slot" object look like? Maybe just an object with `isEmpty` getter for a start. Not sure if we need anything else as a public API.

## 2 What kind of public APIs do we want for useSlot?

do we want:

```
const slotFill = createSlotFill();
const slot = slotFill.useSlot();
```
This is your proposal and kind of maps how something like `zustand` works.

or do we want a more classic approach:

```
const slotFill = createSlotFill();
const slot = useSlot( slotFill );
```
This is close to what we have in trunk with just the names removed. It's also exactly how `useContext` and `createContext` work.

## 3 How to deprecate the string names?

It depends on the approach chosen on the previous question (a or b) but in both cases we can make the name optional (an internal thing and potentially generate it)
