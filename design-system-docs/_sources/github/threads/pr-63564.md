### ciampo on 2024-08-08T18:11:42Z

URL: https://github.com/WordPress/gutenberg/pull/63564#issuecomment-2276393717

I pushed a few updates to the PR.

Some context: earlier today, when talking to @mirka , we realised that re-exporting Ariakti components directly would give us very little control on changes happening on the Ariakit side.

We analysed the range of possible approaches:
- on one side of the spectrum, we could continue to export Ariakit components as they are. This would be the quickest and leanest way, but it wouldn't give us any control on "filtering" Ariakit changes to the components package. For example, we wound't be able to detect / patch any breaking changes from ariakit.
- on the other end, we could wrap the ariakig components in a custom implementation, decide what props to expose / document, and write explicit prop types ourselves. This would represent more work and code on our end, but it would give us better type safety and more control when changes happen on the ariakit side.

**I experimented with the latter approach, and I reached the conclusion that it wouldn't be really feasible**. It would cause us to re-write a lot of Ariakit types (including some "internal" ones), basically re-creating a fork of ariakit, which would be time-consuming (and difficult) to maintain and keep up-to-date as needed.

For now, I decided to adopt a middle ground approach:

- I wrapped ariakit components in custom components, and exposed only the few props that are currently used by `Composite`'s consumers;
- I typed those props by re-using ariakit's types

This strategy still doesn't give us full control, since we're re-exporting Ariakit types — but it's better than before.

Also, this still doesn't fix Storybook arg's table — and so I went ahead and wrote it myself.

---

@WordPress/gutenberg-components  I'd love to hear opinions on this, especially in the light of more components (`DropdownMenu`, `CustomSelectControl`) that will likely incur in the same scenario.
