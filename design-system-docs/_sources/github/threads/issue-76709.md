## Universal page header component 

[Figma spec link](https://www.figma.com/design/a0Qx8VHAwrAhg8DcTi1HCk/Header-component---spec?node-id=33-3484&m=dev&t=nhUWFSy8fYysjpIv-1)


### Essential header elements

- Title (Heading LG (15/20)
- Header background color is the same as Page background (Default: wpds/color/background/surface)
- Border: Always present, 1px, neutral

<img width="1228" height="303" alt="Image" src="https://github.com/user-attachments/assets/4111511b-4648-427c-a6c0-cf2118f2962b" />

### Optional header elements

- Logo/Decoration: 20×20px
- Badge: Indicating status
- Tagline: Page summary, brief intro to product, etc
- Breadcrumb
    - When breadcrumbs are shown, the page title should be hidden (but still present) to avoid visually duplicating page info.
- Navigation: Optional
- Actions:
    - Button size is compact
    - Number of actions in the header: MIN 0, MAX 3
    - Only 1 primary button, up to 2 secondary buttons
    - Tertiary actions stay behind the ellipsis menu
- Controls slot:
    - An optional slot for search, DataViews controls and other needed actions
    - When navigation is not present, controls can float left or right

<img width="1392" height="552" alt="Image" src="https://github.com/user-attachments/assets/9d60197e-148a-4dfe-b8e6-a6beb7561250" />

### Aditional guidelines
- On scroll: Stickiness is optional
- Actions: Primary button is always positioned to the right

<img width="1262" height="309" alt="Image" src="https://github.com/user-attachments/assets/f22ba73f-4fc5-4196-90cd-6ebe2d56a4e4" />


### Responsiveness

- Long titles are truncated
- Everything except the primary action moves inside the ellipsis menu. If there was no ellipsis menu initially, one is generated.
- At a certain breakpoint the logo disappears and the hamburger is revealed.
- If space allows, Hamburger, Title, and Actions remain on one line.
- On scroll, the tagline/description disappears.
- Breadcrumb is always constrained to a single line. Once it's unable to shrink to fit any more, it moves to the line below.
- Navigation: Horizontal scroll
- If space allows, controls stay in line with navigation
- When there's no space, controls stack underneath the navigation and can float right or left.

> how about we just handle that with truncation?

Some thoughts: 

- Truncation is the nicest way visually, but it's tricky to implement in an accessible way — hopefully we'd be able to do that correctly;
- From personal experience, I usually see ellipses being used in the middle of the list, ie, `home / ... / current page`, rather than at the start. I guess it gives end users (including assistive tech) more context ([example](https://ui.shadcn.com/docs/components/base/breadcrumb))
- Implementing a responsive, "auto-collapse as many items as needed into ellipses" behaviour is going to be quite complex to get to work flawlessly.
- Should the badge (if present) ever break the line, or should it force breadcrumbs to shrink even further?
- Let's prepare for "worst case scenarios" where the viewport is very narrow (eg 320px), and have additional "last resort" measures for when `first item / ... / last item` doesn't fit. A few ideas:
    - cause the first item be absorbed into the ellipses (ie. `... / last item`)
    - could truncate the last item (ie. `... / last i...`)
- Should this "collapse items into ellipses" be applied also when breadcrumbs and actions are on the same line? If yes, to what degree? (ie. should it try the "last resort measures" above?)

### aduth on 2026-03-26T13:53:32Z

URL: https://github.com/WordPress/gutenberg/issues/76709#issuecomment-4135034153

I expect we'll want to create some separate issues eventually for discrete sub-tasks, like each new piece of functionality of the page component. Given this conversation has already felt rather fragmented across pull requests and issues, I'm not sure a new issue for high-level technical API would be helpful at this stage. A lot of the discussion that's already happened here regarding implementation constraints to the design have demonstrated the value of keeping the discussion consolidated. Also thinking about "close criteria", if this issue is specifically about design spec, then we can close it because it's done? Or we keep it open and think of it more as the high-level tracking issue for the page enhancements, or long enough to set us in a direction until we have a comprehensive set of subtask issues.

You raise good points about intentional _inflexibility_ and whether compound components imply a level of flexibility we don't want to actually support. 

For API design, it sounds like we're talking about a few approaches that could be mixed or matched:

Configuration props:

```tsx
<Page breadcrumbs={ [ { label: 'Parent', to: '/' }, { label: 'Current' } ] } />
```

"Slot" props: (current?)

```tsx
<Page breadcrumbs={ <Breadcrumbs items={ [ { label: 'Parent', to: '/' }, { label: 'Current' } ] } /> } />
```

Compound components:

```tsx
<Page>
  <Page.Breadcrumbs>
    <Page.BreadcrumbItem to="/">Parent</Page.BreadcrumbItem>
    <Page.BreadcrumbItem>Current</Page.BreadcrumbItem>
  </Page.Breadcrumbs>
</Page>
```

A few general considerations, also building on what you mentioned:

- On flexibility, compound components do imply some level of flexibility of rearranging contents. We intentionally support this kind of flexibility elsewhere in lower-level components, but it would be undesirable here when trying to enforce some uniformity of the page layout. We could technically limit this flexibility so that regardless of child order the layout is still in the expected arrangement, but this may add some complexity for us to implement and could cause some confusion if consumers expect rearrangement to work.
- In some cases we may want more flexibility. For supporting "logo/decoration", it feels impractical to try to support all the different types of content we might want to support here through a configurable API, since someone may want an image, an SVG element, an icon, or something else (`<picture` element? why not). I do worry about coherency if this means that some props are configuration/object-based and others accept elements.
- I think the responsive behaviors should play a role here too, since if we need to support something like "Everything except the primary action moves inside the ellipsis menu", that can be easier or harder depending on the API approach. Slot props in particular feel poorly-suited for this, and configuration props best-suited. I think it'll also vary by the component. For example, the Breadcrumbs truncation behavior may be handled by the Breadcrumbs component itself, so not really a concern for Page to coordinate. The actions collapsing, on the other hand, may need more direct awareness.

Personally where I'm leaning is a mixed approach of configuration props and slot props. Configuration props where we want strict control (max number of items, compact buttons, at most one primary action, etc.). Slot props where flexibility is expected and desirable.

Configuration props:

- Title (must be string for accessible page label, also likely browser tab title)
- Breadcrumbs
- Actions (as mentioned by @CGastrell in https://github.com/WordPress/gutenberg/issues/76709#issuecomment-4119811279)
- Navigation
- Badge
- Tagline

Slot props:

- Logo (imposing dimension constraints by wrapping container?)
- Controls

Example:

```tsx
<Page
  title="Page title"
  tagline="Page summary"
  logo={ <img /> }
  breadcrumbs={ [ { label: 'Parent', to: '/' }, { label: 'Current' } ] }
  badge={ { intent: 'success', label: 'Badge' } }
  actions={ [ { label: 'Action' }, { label: 'Primary CTA', variant: 'primary', onClick } ] }
  controls={ <div>whatever</div> }
  navigation={ [ { label: 'Menu item' }, { label: 'Menu item' } ] }
/>
```

While I was initially drawn to a fully compound approach, I think it ends up being way too difficult to understand the expected arrangement of the different parts, especially with things like Page.Icon, Page.Title, Page.Tagline, Page.Breadcrumbs.

At the moment, and just as an example, there is no way to add side effects to those clicks/navigations. But, TBH, I was just thinking on possibilities.

> The risk of adding flexibility to this level of abstraction is that the abstraction itself gets diluted to a point where it doesn't add much value.

I can agree to that, yes, that's why it has to be carefully thought and outweighed.

In the end, I'm all for providing an abstracted way to fully control how things are rendered, but then also allow for other uses that we just don't mess with. It's always been like that on libs: you either rely on everything taken care for you or you go custom and deal with all the things yourself. And there's a reason for this: if you find yourself too abstracted, a hack is the very first thing you'll need and then, almost immediately, all the goodies of the abstraction are no longer useful, just because you needed that one little thing. So, flexibility also provides a _valid_ way of hacking just the parts you need, and not having to ditch everything. Again, that's delicate and debatable, but also important.

Then it's up to us to live up to the promise to "take care of everything for you" when you rely on our abstractions. That's, in my experience, what has made libs/frameworks successful. Thinking on React for example and how it's been reliable since its origins up to this day, you do things the React way or you hack your way around things, both acceptable and useful depending on the case.
