## Body

## What?

This PR adds unit tests to validate `useCompositeState` behaviour.


## Why?

In order to ease [the migration away from `reakit`](https://github.com/WordPress/gutenberg/issues/53278), we need to maintain the current public `Composite` API. `reakit` exposes a `useCompositeState` function, which `ariakit` doesn't directly support, so [we need to port this](https://github.com/WordPress/gutenberg/issues/56548) to [the new `Composite` implementation](https://github.com/WordPress/gutenberg/issues/55224).

To ensure this work maintains existing behaviour, we need to have unit tests in place.


## How?

Tests are written against each prop and action provided by Reakit's `useCompositeState` implementation.

Additionally, tests are written for common use-cases to validate interaction and developer expectation.


## Testing Instructions

- Confirm that test coverage is complete
- Ensure that all tests run

I do favor the idea of having those thorough tests and being able to test in detail both `Composite` versions with the same suite. I think this can be a good tool to understand the gaps between the 2 implementations.

However, there are a couple of reasons why these tests shouldn't live here in the long term:
* This is testing external functionality. Those tests should live with the canonical underlying library, and not here.
* Let's say we find a gap between v1 and v2. How do we proceed? Will it block the migration until the gap is bridged upstream in `Ariakit`? I think that could potentially be a big unwanted blocker. And yet another pointer that a better place for those tests would be in the underlying library repository. 

So, running those tests against v1 and v2 is a good tool to understand any gaps as part of the migration, but I don't see a good reason to merge the PR and have these tests run all the time. 

With that in mind, I agree with @ciampo's idea of keeping a high-level test suite with general tests from the perspective of the consumer. We don't have to go above and beyond with those IMHO, as it's very easy to step into testing beyond our responsibilities.
