## Body

## What?

This removes the `allow-same-origin` sandbox attribute from the `SandBox` component, preventing scripts inside the sandboxed iframe from accessing the WordPress page's cookies and DOM. Callers that need same-origin access for nested embeds (like oEmbed previews) can opt in via a new `allowSameOrigin` prop.

## Why?

The `SandBox` component [currently uses](https://github.com/WordPress/gutenberg/blob/5ce0d8aabbc7b39b1180b8ba3da08e169417e367/packages/components/src/sandbox/index.tsx#L287) `sandbox="allow-scripts allow-same-origin allow-presentation"` on its iframe. The combination of `allow-scripts` and `allow-same-origin` means scripts running inside the iframe have full access to the parent page's origin, including cookies and the ability to make authenticated requests. For the Custom HTML block, whose content is directly user-controlled, this allows injected scripts to act as the logged-in user.

[This is not recommended](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe):

> When the embedded document has the same origin as the embedding page, it is strongly discouraged to use both `allow-scripts` and `allow-same-origin`, as that lets the embedded document remove the `sandbox` attribute — making it no more secure than not using the sandbox attribute at all.

## How?

A new `allowSameOrigin` boolean prop (default `false`) controls the iframe's isolation level. The `SandBox` wrapper delegates to one of two internal components based on this prop:

-   `<SameOriginSandBox>` (`allowSameOrigin={true}`): The sandbox attribute includes `allow-same-origin`, and the iframe content is written via `contentDocument.write()`. This code is intentionally kept identical to the pre-existing trunk implementation. The `contentDocument.write()` approach is needed because `srcdoc` sets the iframe's document URL to `about:srcdoc`, a local scheme that causes the browser to send no `Referer` header for nested iframe requests. This can break third-party embed providers like YouTube that check the referrer for domain authorization. Calling `contentDocument.open()` sets the document URL to the parent page's URL, so nested iframes send a valid `Referer`.
-   `<IsolatedSandBox>` (`allowSameOrigin={false}`, default): The sandbox attribute is `allow-scripts allow-presentation` (no `allow-same-origin`), and the iframe content is populated via the `srcdoc` attribute. This gives the iframe an opaque origin with no access to the parent page's cookies or DOM.

Only the embed block and cover block's video background opt in, because their HTML comes from the server-side oEmbed pipeline rather than directly from block attributes.

The oEmbed pipeline is safe to grant same-origin access because the HTML is not easily attacker-controlled. When the editor needs embed preview HTML, it calls [`getEmbedPreview(url)`](https://github.com/WordPress/gutenberg/blob/5ce0d8aabbc7b39b1180b8ba3da08e169417e367/packages/core-data/src/resolvers.js#L630), which makes a REST API request to `/oembed/1.0/proxy`. WordPress fetches the oEmbed response from the provider, runs it through [`wp_filter_oembed_result()`](https://developer.wordpress.org/reference/functions/wp_filter_oembed_result/) (which strips dangerous tags like `<script>`), and returns sanitized HTML. An attacker injecting a `core/embed` block only controls the `url` attribute. The actual HTML that reaches the Sandbox comes from this server-side fetch-and-sanitize pipeline.

In contrast, the Custom HTML block passes `attributes.content` directly to the [Sandbox's `html` prop](https://github.com/WordPress/gutenberg/blob/5ce0d8aabbc7b39b1180b8ba3da08e169417e367/packages/block-library/src/html/preview.js#L43) with no server-side filtering, so this is a much easier attack vector.

Note that this only affects script previewing within the editor. Front-end script behavior remains unmodified.

## Testing Instructions

First, try the following instructions on `trunk`. You should see the XSS behavior that dumps cookies and changes the current document's title on page load:

https://github.com/user-attachments/assets/63707f3a-8ab2-41ad-9dbb-d691450c7bf9

1. Insert a **Custom HTML** block, then click the "JS" tab. Insert this text:

    ```
    try { top.document.title = 'XSS'; } catch(e) { console.log('Blocked:', e); }; console.log('cookies: ', document.cookie);
    ```

    Dumping cookies is a stand-in for more malicious operations like CSRF requests to API endpoints.

2. Save the page and reload.
3. See that login cookies are echoed to console and the page's title changes.
4. Switch to this branch (`fix/sandbox-allow-same-origin`), and run the same test. Ensure that the XSS no longer fires:

### alecgeatches on 2026-04-13T20:52:46Z

URL: https://github.com/WordPress/gutenberg/pull/77212#issuecomment-4239557867

I was considering gating this on RTC being enabled, but I think this might be a good default. It honestly seems a bit off to me that the current `<SandBox>` implementation with `sandbox="allow-scripts allow-same-origin allow-presentation"` allows any HTML embedded in the page access to user cookies. That means:

- At present, any user with `unfiltered_html` can assume the identity another user who loads their post in the editor. See the test instructions in the PR for a simple reproduction.

    `unfiltered_html` is enabled by default for administrators [and editors](https://github.com/WordPress/wordpress-develop/blob/aa72dfed4432cfd875f77d2c475f772c6623cae5/src/wp-admin/includes/schema.php#L800). That means in standard WordPress **any editor user can steal the identity and act on behalf of any admin user** that visits their post. This is an easy vector for privilege escalation from editor to any other role. If other user types also are granted `unfiltered_html`, this is true for them as well.

- Any oEmbed code ALSO has full access to editor cookies. That means if any oembed provider has malicious code injected, it also has full `same-origin` access to cookies in the editor and to perform actions on their behalf.

From my investigation, it seems like the only way to fully overcome these limitations but still allow embeds to work is to host sandboxed content on another domain, e.g. `sandbox.mysite.com` that has `allow-scripts allow-same-origin` but no useful cookies to take.

Since we can't assume any subdomain setup for random WordPress hosts, we can't rely on this. However, our overall trust in "Sandbox"ed code is very high, and I think this change of restricting `allowSameOrigin` access in some situations (`core/html`) is a step in the right direction.

Thanks @alecgeatches for updating the PR. The approach where `IsolatedSandBox` is a new component and where the old code is left intact, it's much safer in terms of preserving all the past quirks and fixes that were accumulated over a few years.

> I don't think the `srcdoc` solution in `<IsolatedSandBox>` has the same issue.

I agree that we don't need the `trySandBox` handler on `load` that will re-populate the document with `document.write`. Browser will do this automatically for `srcdoc`.

But I suspect that the `checkMessageForResize` listener will get lost. It's been attached to the initial `Window` object (`defaultView`) but when the `iframe` is moved, that old `Window` will be destroyed and the `iframe` will get a new one. And the new one won't have the listener. The `useEffect` doesn't unmount a remount on move. It does in dev mode, as a "strict mode reappear stress test", but in production it doesn't.

This `iframe` reparenting behavior is described here in the HTML standard:

https://html.spec.whatwg.org/#the-iframe-element:html-element-post-connection-steps

The `iframe` HTML element removing steps are to destroy the child navigable, and the element post-connection steps are to create a new child navigable. That's the standard jargon for "recreating the `window`".

> Do we have any good reasons why only some dependencies should cause a rewrite?

I'm not sure, I just don't want to accidentally revert some past bugfix. The embeds (like YouTube or Instagram) are often weird and sensitive about details. The rewrite can potentially destroy some markup that was added dynamically by some script.

> I was considering gating this on RTC being enabled, but I think this might be a good default.

The `srcdoc` approach was known to break some embeds, I think it was YouTube. The problem is that a `srcdoc` document has an empty `document.referrer`, while `about:blank` document (used by the `document.write` approach) refers to the parent origin. Some scripts don't like that. This problem is described in GitHub comments of one of the past PRs, I can find it if needed.
