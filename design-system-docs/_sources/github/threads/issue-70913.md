# Issue #70913: Admin Materials and Surfaces

## Body

As we further develop the primitives that make up the overall admin system (#53322) it seems important to map out the main elements that compose it. This issue focuses largely on how things might work and how things are structured, not how they look.

We'll start, for the sake of the presentation, with defining **Materials**, **Concepts**, and **Screens**. Materials are the places where Concepts are rendered; Concepts are the interfaces for the various items a site needs to represent; and Screens are the dedicated routes that bring them all together and construct the various user flows.

The terminology is just an instrument to help us break things down. The main thing to capture here is that the admin is composed out of a few shared pieces to account for the needs of extensibility, personalization, flexibility, and consistency.

---

## The Materials

The overall Admin user interface is composed of a few core materials, grouped into **Base**, **Surfaces**, and **Overlays**.

### Surfaces

We define three main element that build up the various layouts of the admin screens.

- **Canvas**
The primary area for previewing and editing content (e.g., block editors).
- **Stage**
Harbors either a _Library_ of items (posts, pages, media, products, orders, patterns, fonts, etc) or _Settings_. This is also the main area for plugins to develop more customized interfaces.
- **Inspector**
Is meant to be a narrow (possibly fixed) width element for quick edit panels, style panel, editor inspector, plugin sidebars, etc.

<img width="1700" height="1239" alt="Image" src="https://github.com/user-attachments/assets/c1f60430-15da-4d3d-8ed2-320cbe4d2842" />

### Overlays

Includes modals, preferences, dialogs, and interfaces like command palette.

## The Concepts

Each surface can bring together a set of reusable, high-level concepts. These are primitives that define structure and functionality. Most of these already exist in code and have been the main focus of development as they tie in with the component and design system in encapsulating functionality, user interaction, accessibility affordances, etc. These are not meant to be exhaustive, just a high level grouping of the most common elements.

- **Navigation**
Menus (dropdowns, drilldowns), drawer, tabs, item groups.
- **Collection**
Lists, grids, tables, and alternate layout representations of `DataViews`.
- **Forms & Settings**
Structured fields, validation, form layout (e.g., `DataForm`, `ToolPanel`). (Fields API meets component system.)
- **Block Editor**
Context-specific editors for entities like posts, templates, and patterns.
- **Widget**
Small units laid out in a grid that connect with various functional components to create a personalized dashboard experiences.
- **Inserter**
UI for adding new blocks, new post types, new templates, etc.

## The Screens

With these building blocks in place, every Admin screen can be declared as a layout incorporating these surfaces and concepts. This modular approach helps us ensure consistency, flexibility, scalability, and clarity across the entire admin and plugin experience. The layouts themselves are not fixed but starting points, since they can be reconfigured by plugins or by the user through data view configuration.

And the way we would describe this as a layout is something like the following:
```yaml
Pages:
    Stage: Lists + Inserter + Tabs
        Default: List, [Table, Grid]
    Inspector: quick-edit
        Default fields: [ Title, Slug, Parent, [...] ]
    Canvas: block-editor
        Default view: Template, [Abstracted View]
```

That being said, my concern is how this will be implemented. Let's get into that.

Rewriting the entire WordPress admin in React is a flat-out bad idea... For WordPress.

### Here are several reasons why:

1. **React’s long-lived, but no longer leading status:** The JavaScript ecosystem evolves rapidly. React, now over a decade old, remains widely used, but newer frameworks like Solid, Svelte, or Qwik are leaner and often more performant. Committing WordPress’s admin to React risks locking us into a technology that may feel outdated midway through a major migration.
2. **Poor React adoption in the WordPress ecosystem:** Gutenberg was meant to attract large numbers of React developers. Instead, adoption has lagged. Most plugin and theme developers stick with PHP, jQuery, or lightweight JS. If React couldn’t gain traction merely with block development, a full-blown React admin rewrite is unlikely to succeed in talent adoption.
3. **PHP is enjoying a renaissance:** With PHP 8+, features like JIT, strong typing, enums, and attributes, plus modern frameworks like Laravel and Symfony, deliver powerful, developer-friendly PHP experiences. Ignoring this momentum in favor of a React-first admin diverges from broader PHP ecosystem trends and developer skills.
4. **Multi-Page Apps (MPAs) can deliver rich interactivity:** A lot of the rationale for React in 2015 was about SPAs being the only way to get a “modern app-like feel.” That’s just not true anymore. Laravel’s Livewire, Rails’ Turbo/Hotwire, and libraries like htmx or Alpine.js show us we can deliver rich, reactive user experiences while keeping the traditional server-rendered MPA model. This keeps things simpler, more accessible, and most importantly-closer to the PHP-based developer base that WordPress already has.
5. **WordPress’s superpower is backwards compatibility:** Thousands of plugins and extensions rely on the current admin architecture. A wholesale rewrite in React would be catastrophic for compatibility, fragmenting the ecosystem and forcing plugin authors to rebuild massive swaths of functionality. We would risk breaking trust with the developer community who rely on “the WordPress way” being stable and dependable.
6. **Maintenance cost and contributor fragmentation:** WordPress thrives because thousands of contributors can jump in and meaningfully contribute, whether they’re PHP developers, front-end builders, or plugin makers. A React-only admin narrows that funnel to a more specialized, more JavaScript-heavy, framework-specific skill set, potentially shrinking the contributor base. That’s not a recipe for longevity.
7. **The user experience can be modernized without a nuclear option:** Improving the design language, unifying patterns, and layering in progressive enhancements with modern JS where it makes sense is a far more sustainable path. We can ship a “modern admin” without burning the house down and without cutting off vast portions of our developer community.
8. **Modern CSS now packs a serious punch:** Features like CSS Grid, enhanced layout systems, custom properties (variables), scrollbars, blur effects, and more add flexibility and visual polish to interfaces all without heavy JavaScript or frameworks. **The CSS View Transition API** (via document.startViewTransition() and the @view‑transition rule) allows smooth, built-in transitions between page states even across page navigations without JavaScript animation frameworks. It’s supported in Chrome, Edge (same), Safari, though Firefox remains the last holdout.

### A Better Proposal

Focus on an incremental modernization strategy using:

- Modern PHP-driven architecture (Keep the “the WordPress way”)
- Interactivity via the WordPress Interactivity API (introduced in WP 6.5)
- A fresh, unified design system (Already in the works)

**Why the Interactivity API fits the bill**

- Native WP integration: Built in since WordPress 6.5, with no need for external frameworks 
- Declarative and hypermedia-aligned approach: Uses HTML directives (e.g., data-wp-on--click, data-wp-bind--value, etc.) for interactivity conceptually similar to HTMX, but purpose-built for WordPress
- Optimized performance: Ships only minimal JS (via Preact as fallback only when necessary), keeping page weight low 
- Backward‑compatible design: Works with existing server-rendered blocks, themes, and plugins without breaking the admin flow 
- State & interaction out of the box: Offers stores, state, actions, and callback patterns helping build interactive components like accordions, live search, filters, lightboxes without React complexity

### How this could look in practice

1. Adopt a new UI/UX design system - modular, accessible, and themeable.
2. Incrementally refactor admin UI components into modern PHP-rendered templates, styled via the design system.
3. Layer interactivity gradually -where richer interactions improve usability using the Interactivity API’s declarative directives.
4. Maintain plugin compatibility -existing hooks, filters, and structures remain intact.
5. Engage the dev community - encourage contributions using familiar PHP flows rather than demanding React expertise.

> This hybrid approach respects both the core strengths of WordPress (backward compatibility, PHP-centric workflows) and the given need to modernize admin UX. It also aligns with the ethos of hypermedia-driven enhancements without overhauling the entire stack.

**In summary:** A full React rewrite may look cutting-edge, but it threatens the broad community, the ecosystem, and WordPress’s future sustainability. Instead, modernizing via PHP + Interactivity API + modern CSS (including View Transitions) preserves backward compatibility, performance, and accessibility while delivering a polished, modern admin experience.

# In support of a modern Admin — without leaving PHP devs behind

I’m fully behind the Admin redesign and the Block Editor direction. The legacy Admin is objectively dated and pushes users away. A standardized, extensible Admin (Materials → Surfaces → Overlays; Canvas/Stage/Inspector) is the right foundation. Let’s pair that with a **PHP-first developer experience** and **progressive enhancement** so we don’t lose the ecosystem that made WordPress thrive.

---

## Why this matters

* **End users first.** Cohesive layouts, predictable settings, and consistent patterns are how we deliver a “pleasant, flexible, efficient” UI. The current Admin can’t get us there.
* **Developers are also users.** After 20+ years leading teams and shipping WP at scale: **React developers rarely pick WordPress**; the natural contributor base is still **PHP developers**. If we ignore that, we shrink the tent.

---

## A practical path that meets both worlds

### 1. Keep PHP at the core, enhance progressively

Server-rendered screens + **Interactivity API** for rich UX. Use React where it’s the best tool, but don’t require it for every screen.

---

### 2. Ship a declarative “Admin Schema”

A small, well-documented schema that describes a screen’s structure (Stage/Canvas/Inspector, Collections, Forms, DataViews, etc.). Think of it as the contract between PHP and UI.

```php
// functions.php or a plugin
register_admin_screen('pages', [
  'stage' => [
    'collections' => ['list', 'table', 'grid'],
    'inserter'    => true,
    'tabs'        => ['All', 'Drafts', 'Published'],
  ],
  'inspector' => [
    'panel'  => 'quick-edit',
    'fields' => ['title', 'slug', 'parent'],
  ],
  'canvas' => [
    'type'  => 'block-editor',
    'view'  => 'template', // or 'abstract'
  ],
  'behaviors' => [
    'resizableInspector' => true,
    'allowCmdClick'      => true,
  ],
]);
```

Or JSON if you prefer config-as-data:

```json
{
  "id": "pages",
  "stage": { "collections": ["list","table","grid"], "inserter": true, "tabs": ["All","Drafts","Published"] },
  "inspector": { "panel": "quick-edit", "fields": ["title","slug","parent"] },
  "canvas": { "type": "block-editor", "view": "template" },
  "behaviors": { "resizableInspector": true, "allowCmdClick": true }
}
```

---

### 3. Provide a PHP wrapper/configurator à la [Redux](https://redux.io/)-style DX

Not to copy [Redux](https://redux.io/), but to emulate the *packaging and mental model*: clear APIs, great docs, guardrails, presets, and instant results. Examples:

* `register_admin_screen()`, `register_admin_form()`, `register_admin_collection()`
* Opinionated presets for common screens (Posts, Pages, Media, Products)
* Auto-wiring of validation, capability checks, and accessibility

---

### 4. First-class migration adapters

* **Settings API ↔ Fields API** mapping layer so existing options pages can render with the new concepts.
* **ACF/Redux/Meta Box** adapters that read existing field groups and emit Admin Schema.
* **DataViews adapter** for custom list tables → Collections, including bulk/quick edit.

---

### 5. Tooling that respects how WP devs work

* **WP-CLI scaffolds:**

  ```bash
  wp admin screen scaffold --schema=pages.json
  ```
* **Codegen & AI assistant:** Feed schema, get PHP/JS templates, WP-components wiring, and test stubs.
* **No-JS fallback:** Core tasks (activate/deactivate/update) must remain operable if JS fails.

---

### 6. UX details that came up in this thread

* **Resizable sidebars/inspector** and **right-click / cmd-click** to open in new tabs.
* **Consistent keyboard shortcuts** and **sticky submit** for long forms.
* **Collapsible panels** with sensible defaults for simplicity *and* consistency.

---

## Why this balances risk and progress

* **Backward compatibility:** PHP remains the backbone; React is additive, not mandatory.
* **Lower barrier to entry:** PHP devs can be productive on day one using the Schema and wrappers.
* **Future-proofing:** If/when UI tech shifts, the Schema contract stays stable.

---

## Bottom line

Let’s modernize the Admin and embrace the Materials/Surfaces/Overlays model—*and* give developers a PHP-first, declarative, Redux-quality DX plus codegen/AI helpers to make building screens fast, consistent, and fun. That’s how we keep users happy and the ecosystem vibrant.

### lesley-pizza on 2025-11-18T05:08:16Z

URL: https://github.com/WordPress/gutenberg/issues/70913#issuecomment-3545058725

I really appreciate all the work being done here, and enjoyed reading everyone's concerns, and I hope those concerns are taken seriously.

I wanted to chime in with some thoughts about approach...

I'm not sure if there's a technical term for it. But I'm concerned about this "foundations-first" approach. It's similar to the "implementing a design system too early" concern.

I suspect it's already too late because of path dependence - I understand people are already committed, so it's hard to do things differently at this point. Also, there's something about pretty primitives that feels reassuring, and the chaos of a "use case-first" approach (which I advocate for below) can feel unwieldy in comparison.

But regardless, I think it's worth mentioning that instead of approaching the redesign "foundations first", we should approach it "use case-first".

## What is a use case-first approach?
The key point is to identify use cases and design for them.

Instead of designing abstract primitives, take some time to identify the 5-10 most common WordPress admins ("most common" can be replaced with whatever is the key criteria) and create mock ups of what the modern admin can look like for these people.

There are other ways of doing this of course, but this is what comes to mind for me. 

## Why adopt a use case-first approach?
If you've ever seen the [square hole video meme](https://www.reddit.com/r/ProgrammerHumor/comments/l2sfjp/devs_watching_qa_test_the_product/), you'll know how the best intentions with a good foundation can quickly lead to disappointment. (Worth caveating for the nitpickers that the reddit thread I linked to says "devs watching qa test the product" but it's the same mentality for "devs watching users use the product")

The problem with the foundations-first approach is that _anything_ makes sense in abstractions, it sounds very well thought out and looks very pretty. But it suffers from the "[no plan survives first contact](https://quoteinvestigator.com/2021/05/04/no-plan/)" problem.

In contrast, a use case-first approach skips straight to first contact. We see what is currently being done, and then seek to improve it.

Many startups have to build first (and even then they are told by mentors not to build too much before getting user feedback) and then fight tooth and nail to get user feedback, and change things along the way.

We don't have to do that.

We're in the enviable position of already having millions of users. I think figuring out what their daily use cases are and building with those things in mind is a much better approach.

## What a use case-first approach could look like in practice
**Caveat: This section is just an _idea_ of how it could look like in practice. There might be better ways of doing it. The main thing I'm advocating for is a use case-first approach, not dogmatic adherence to the suggestions below.**

We could start by showing screenshots of common WP admins - some with 10 admin notices and at least 20 plugins installed. We want to see different languages. We want to see different industries - lawyers, government agencies, hairdressers, food bloggers, local news, design agencies, and so on, sorted into buckets. We'd also make sure to consider the top 50-100 plugins and themes.

Then we would show before and after mock ups of how those same admins would look like with the redesign.

This sounds like a lot, but you really don't have to show 100 different mock ups. After doing the research, it'll become clear what the most common 5-10 WP admins look like.

I think getting support technicians and agency devs involved will be key, because those are the folks who are looking at different WP admins all day.

Then instead of having people argue about a completely rebuilt WP admin from the ground up, which understandably makes everyone nervous... 

Have them argue about what they want and don't want based on those Before and Afters. Have them argue about how their common use case was not represented and have them screenshot/screen record their own WP admins as an example. 

This might sound more chaotic (having to see 100s of WP admins), but it gives a much better idea of how people are actually using WordPress in their daily lives. And what all those people _actually_ need.

And once we have a clear idea of what we actually need to build, we can go back to step 1 and figure out the basic elements and components we need on day one to get us there. And, in the case of the [Square Hole meme](https://www.reddit.com/r/ProgrammerHumor/comments/l2sfjp/devs_watching_qa_test_the_product/), we would be able to know with some certainty that we didn't actually need multiple different holes, we just needed one square hole.

As an example, to me, the most valuable comment in this entire thread is [this one](https://github.com/WordPress/gutenberg/issues/70913#issuecomment-3120711066). Because it advocates for "regular people" and talks about specifics like the WP admin needing to work on a small screen. 

Maybe the proposed solution of resizeable panels might not be built, but it highlights the important reality that regular users are using WordPress on their small screens and might be something that needs to be considered right from the start.
