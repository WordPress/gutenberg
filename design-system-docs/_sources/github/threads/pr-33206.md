Summarizing a discussion about the unit tests that we had in the #core-js channel today: https://wordpress.slack.com/archives/C5UNMSU4R/p1626189861190800

JavaScript unit tests are run against Node versions 12 and 14.
The test fails in version 12 because version 12 doesn’t ship with full-icu data for the internationalization stuff whereas 14 does. The default changed for Node between versions 12 and 14 (see documentation links below).

https://nodejs.org/docs/latest-v12.x/api/intl.html#intl_options_for_building_node_js
https://nodejs.org/docs/latest-v14.x/api/intl.html#intl_options_for_building_node_js

We still support Node 12 until EOL which is in 2022.

https://github.com/jsdom/jsdom/issues/1626

Three options (from @nerrad):
a. Drop support for Node 12 (breaking with what we're following with other libraries)
b. Don't use Intl.NumberFormat yet?
c. Do the checks only have this warn in non browser environments?
d. Require Node 12 built with `--full-icu`

Option b seems wild to me in that we’d be limiting our usage of native browser APIs in a browser app based on non-browser constraints

Option c would be something like re-writing isValueNumeric to be naïve about localization in non-browser environments (i.e.,`typeof document === 'undefined’`)? But that doesn’t solve the fact that we want to unit test the Intl.NumberFormat code too right? Because to get the tests to pass we’d probably end up changing the test/values.js to run in a non-jsdom environment… Otherwise the behavior would stay the same.

Option a which seems like a big departure from the community for the sake of a small utility function.

Option d is a cumbersome requirement for users of our libraries. If we went with that though we could enforce it by doing something like the following:

```js
function hasFullIcu() {
  return new Intl.NumberFormat('pt-BR').format(1000.1) === '1.000,1';
}
```

The magical Option 🤩 that @gziolo came up with was to just scope the unittest to run in Node 14.

I'll go ahead and go with Option 🤩 🙂
