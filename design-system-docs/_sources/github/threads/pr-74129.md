## Body

## What?

Closes #73096

Updates `@wordpress/theme` package exports to correctly specify variants for the `/design-tokens.js` entrypoint.

## Why?

So that TypeScript can resolve the types, and presumably so this can be used in a CommonJS project environment which isn't compatible with loading the ESM variant of the package.

## How?

The `.d.ts` and `.cjs` files were already being built, we just needed to update the `package.json` to point to them, consistent with the `"."` main entrypoint.

Also includes a few semi-related housekeeping tasks:

- Avoids using DocBlock syntax for prebuilt file headers, since otherwise these will be picked up by TypeScript and used incorrectly to describe the return value of the default export.
- Updates the name of the Terrazzo plugin that generates this file to use `@wordpress/` as its scope, for consistency with other custom plugins, and because it's within the WordPress scope (not Terrazzo). These plugins aren't actually published anywhere, but if they were, we'd use the WordPress organization. We're not affiliated with Terrazzo.

## Testing Instructions

Verify improvement using [the "Are the types wrong?" site](https://arethetypeswrong.github.io/):

1. Build packages: `npm run build`
2. Change into the theme directory: `cd packages/theme`
3. Pack the package: `npm pack`
4. Upload the generated zip file to [the "Are the types wrong?" site](https://arethetypeswrong.github.io/)
5. Observe that the `/design-tokens.js` files are resolved in Node.js 16+
6. On the site, enter `@wordpress/theme` as the package name and click "Check"
7. Observe that the result for the published package is much worse, and `/design-tokens.js` doesn't resolve at all
