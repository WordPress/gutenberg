## Body

Sub-issue of #71196

## What problem does this address?

Configuring UI components to vary their appearance or behavior based on the current container or viewport size can be cumbersome, often requiring the use of [additional hooks](https://github.com/WordPress/gutenberg/blob/6263d4a01d392f197460c8ead57e77d7fb466361/packages/compose/README.md#useviewportmatch) and inline logic in the case of viewports, or completely custom code in the case of [container queries](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Containment/Container_queries).

In the WordPress context, a design system should provide built-in support for responsiveness:

- Defining common [design tokens](https://thedesignsystem.guide/design-tokens) for breakpoints
- Support both [media queries](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Media_queries/Using) and [container queries](https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Containment/Container_queries)
   - Container queries in particular can relevant in how information is presented in many different and constrained content areas in a WordPress interface
- Mechanisms for interfacing with the underlying design tokens in UI component usage

## What is your proposed solution?

- Define a set of design tokens for breakpoints, implemented as a group of [DTCG](https://www.designtokens.org/)-formatted tokens in [`packages/theme/tokens`](https://github.com/WordPress/gutenberg/tree/trunk/packages/theme/tokens)
- Provide an interface to design token breakpoints via:
   - React hooks similar to [`useViewportMatch`](https://github.com/WordPress/gutenberg/blob/6263d4a01d392f197460c8ead57e77d7fb466361/packages/compose/README.md#useviewportmatch), with added support for container queries
   - Optionally, support tighter integration with UI components prop interfaces by allowing consumers to define responsive variants as part of props interface (similar to [Chakra UI](https://chakra-ui.com/docs/styling/responsive-design))

This may make sense to live entirely within `@wordpress/theme` (as opposed to `@wordpress/ui`), as responsive support could pair nicely with viewport-dependent density configurations (see #73360), where `ThemeProvider` would also benefit from tight integration:

```tsx
<ThemeProvider density={ { default: undefined, large: 'comfortable' } } />
```
