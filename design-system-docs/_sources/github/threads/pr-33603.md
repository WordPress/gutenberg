> Wouldn't you set the width/height on the `img` component itself, probably?

I had a deeper look at how this component works. From what I understood:

- the `img` element (or any child of `AspectRatio`) is set to `position: absolute` with `width` and `height` set to 100%, so that it always fills up the surface area of its parent `AspectRatioView`.
- the parent `AspectRatioView` has `position: relative` and should be where the overall width/height should be set.
- the "padding" aspect ration hack is applied to the `AspectRatioResizer` component.

I believe that this way of enforcing an aspect ratio only works with setting the `width` of the external component (and not the `height`), since the "padding hack" used here uses a percentage value for the `padding-bottom` rule, which represents a fraction of the width of its parent.

While looking for other examples of similar components, I also found https://www.npmjs.com/package/react-aspect-ratio — where @sgomes is mentioned as the owner of the "original idea". This component, in a similar way to what we were discussing, only exposes the `ratio` prop and lets the user set the `maxWidth` via CSS

The issue is the `isValidElement` will allow you to cast the child to `ReactElement` which lets you access props etc. But `getValidChildren` only returns ReactNodeArray because it also handles the case where the children are `string`s for example, so the type has to be wider.

Maybe `getValidChildren` is unnecessary here and we can call `Children.only(children)` directly and then check it with `isValidElement`. `getValidChildren` seems semi-useless in this regard. In `HStack` component we end up force casting the children to `ReactElement` using `@ts-ignore`.
