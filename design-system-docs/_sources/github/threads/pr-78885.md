## Body

## What

Adds open/close motion to `@wordpress/ui` `Popover`.

- Applies the shared `dropdown-motion` slide/fade profile to `Popover.Popup` (WPDS motion tokens, `prefers-reduced-motion` respected).
- Adds an opacity fade to the optional `Popover.Popup` backdrop, matching `Dialog` overlay behavior.
- Splits the default popup into a borderless motion layer (`.popup`) and an inner surface (`.surface`) for visual chrome.

## Why

Popover should feel consistent with other overlay patterns (`Select`, `Dialog`) that already use the shared dropdown motion profile and backdrop fade.

One implementation detail made motion harder than dropping in CSS:

**Arrow alignment** — `transform` / `will-change: transform` on the popup makes it the containing block for `Popover.Arrow`. If the border lives on that same element, the arrow resolves against the padding box and sits ~1px inside the border while animating. Moving visual chrome to an inner `.surface` keeps the transformed motion layer borderless so the arrow stays flush.

> **Note:** This PR originally also fixed a close-time reposition bug (Base UI re-anchoring the popover to an `IconButton` close button mid-animation). Per review feedback, that fix has been reverted and will be tackled separately so the cause — not just the symptom — can be addressed (ideally reproduced with vanilla Base UI and filed upstream if applicable).

## How

**Motion**

- Compose `dropdown-motion` onto `.popup` for the standard slide/fade.
- Fade the backdrop with the same `:not([data-starting-style])` / `:not([data-ending-style])` guard as `dropdown-motion`, so the scrim doesn’t snap in when Base UI sets both `data-open` and `data-starting-style` on mount.

**Popup structure**

- `.popup` — borderless motion layer (`dropdown-motion`, transform / `will-change`).
- `.surface` — background, border, shadow, padding, and content (including `Popover.Arrow`). This split relies on `.surface` **not** establishing a containing block (no `transform` / `filter` / `contain` / etc.), so the arrow keeps resolving against `.popup`; an explicit CSS comment documents this constraint.

### Note: Toolbar variant story does not animate

The Toolbar variant story uses `variant="unstyled"` with custom inline styles to approximate toolbar chrome (high-contrast border, no shadow, compact padding). The unstyled variant intentionally skips the default `.popup` layer, which is where `dropdown-motion` is applied, so this story **does not** slide/fade on open/close.

This is not a regression from the motion work in this PR; it's how `unstyled` is defined today (blank positioning shell, no default surface or motion). We might want to set up a dedicated variant for this, but I'd consider it out of scope for this PR.

- It could make sense to have a default animation for Popover if we expect the component to be mostly used in a certain way, which would make a default animation apply correctly in most circumstances


Hope this helps to add context — all this to say, if you think the last point (if we expect `Popover` to be mostly used in the same way), then adding an animation could make sense.
