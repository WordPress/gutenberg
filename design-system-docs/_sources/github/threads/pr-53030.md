## What?
This PR introduces a basic horizontal `ProgressBar` component.

I'd love to get some design feedback since this is done from scratch and is using some component package colors by default, for consistency with the rest of the components. We're introducing some props to allow easier changing of the colors. 

## Why?
While it can be useful in various places, we're aiming to use this new component to replace the `Spinner` component that is currently utilized in the site editor loading experience. I've started work on this in #53032.

## How?
We're introducing a basic component with tests, stories, and README - all the basic pieces for a new component.

## ✍️ Dev Note

**Introducing a new experimental `ProgressBar` component**

A new experimental `ProgressBar` component has been introduced to the `@wordpress/components` package. 

The `ProgressBar` component supports two modes: 
* determinate - when a particular progress value has been specified (from 0 to 100)
* indeterminate - when a value hasn't been specified

The component is capable of switching between modes depending on the progress `value` prop that's passed to it.

The primary need and motivation for creating this new component is currently in the Site Editor, where it's already utilized for displaying the loading progress of the editor.

```js
function UnforwardedControl ({ props, ref }) {
  const { ..., id: idProp, ... } = props;
  const id = useInstanceId( Control, 'control', idProp );

  return (
    <div>
      ...
      <el ref={ref} id={id} .../>
      ...
    </div>
  );
}

export const Control = forwardRef( UnforwardedControl );
```

This allows consumers to operate in either way. They can provide their own ID, based on their own use-case, or they can use a ref and take the generated ID instead.

```suggestion
Specify a custom HTML `id` for the `progress` element. This is necessary when you want to accessibly associate a custom `label` with that element.
```

I think we can be a bit more clear that this is optional, and only for specific custom use cases.

On the other hand, I [checked](https://codesandbox.io/s/nice-https-f22hyt?file=/src/App.js) what the labeling priority is when there are competing labels, and it seems to be `aria-labelledby` > `aria-label` > `<label for="my-id">`. Therefore, if a consumer wants to do a `<label for="my-progress-bar">`, they're also going to have to remove the default `aria-label` prop, which is non-obvious 🤔 It would be more straightforward to use `aria-labelledby` or `aria-label` if they want to override the label. In this case, we probably shouldn't be calling out the `id` prop explicitly in our docs, as it'd be highlighting a non-recommended approach? (It will just be silently forwarded as part of the rest props.)
