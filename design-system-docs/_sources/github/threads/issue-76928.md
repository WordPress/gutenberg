# Issue #76928: UI: Define policy for exposing Base UI CSS variables and data attributes

## Body

## Context

From discussion on #76438: Base UI components expose public APIs beyond React props — specifically **CSS custom properties** (e.g. `--available-height`, `--anchor-width`, `--transform-origin` on the Positioner) and **data attributes** (e.g. `data-open`, `data-side`, `data-starting-style`).

## Decision

We agreed to **use Base UI's CSS custom properties and data attributes directly** — no aliasing or namespacing with a `--wp-ui-*` prefix. Gating them adds maintenance overhead with no practical benefit, especially since data attributes can't be gated at all.

However, these APIs **must be documented**, since they are part of the effective public API of each component.

## What needs to be done

### 1. Per-component documentation

Each `@wordpress/ui` component that exposes Base UI CSS variables or data attributes should document them. This includes:

- **CSS custom properties** available on specific sub-components (e.g. `--available-height`, `--anchor-width` on `Popover.Popup`'s positioner)
- **Data attributes** that can be used for styling (e.g. `data-open`, `data-side`, `data-starting-style`)

Open question: **where and how** should this documentation live?
- In the component's TypeScript types (JSDoc)?
- In Storybook stories / docs pages?
- In a dedicated section of the component's README?
- Some combination of the above?

### 2. Package-level documentation

Add a section to the `@wordpress/ui` package documentation explaining the overall policy:

- `@wordpress/ui` components are built on Base UI primitives
- Base UI exposes CSS custom properties and data attributes as part of its component API
- These are passed through directly (not aliased or namespaced)
- Consumers can rely on them for styling, but should be aware they originate from Base UI and may change if the upstream library changes
- Link to Base UI's documentation for each component as the authoritative reference

### 3. Audit existing components

Review all existing `@wordpress/ui` components to identify which Base UI CSS variables and data attributes are relevant and should be documented.

After looking at the current `@wordpress/ui` package structure, here's what I found and a concrete proposal:

**Existing patterns:**
- No per-component READMEs exist today — component folders contain `.tsx` files, `types.ts` (with JSDoc), and `stories/`
- JSDoc in `types.ts` is the established pattern for API docs
- `packages/ui/README.md` is the central hub covering cross-cutting concerns (design tokens, theming, controlled/uncontrolled patterns)

**Proposed approach:**

1. **Package-level policy → `packages/ui/README.md`**
   Add a new section (e.g. *"Base UI CSS Variables and Data Attributes"*) explaining the passthrough policy and linking to Base UI's docs. This is consistent with how other cross-cutting concerns are already documented here.

2. **Per-component CSS vars & data attributes → JSDoc block comment on the type itself in `types.ts`**
   Since CSS custom properties and data attributes aren't React props, they don't map to interface fields. A JSDoc block on the relevant type (e.g. `PopupProps`, `PositionerProps`) with a `@remarks` or dedicated section listing available vars/attributes keeps it co-located with the component API without polluting the props interface.

3. **Styling examples → Storybook stories**
   Interactive demos showing `data-open`/`data-side` driven animations are far more useful than prose. Stories already exist per component — adding a *"Custom Styling"* story variant would be low-friction.

Happy to open a PR implementing this for the `Popover` component as a reference, so the team can validate the pattern before rolling it out across all components.
