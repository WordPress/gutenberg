### Review thread 6

#### mirka on 2026-01-08T08:49:10Z

URL: https://github.com/WordPress/gutenberg/pull/74325#discussion_r2671459582
Path: packages/eslint-plugin/rules/no-setting-ds-tokens.js

I tried doing it both ways:

1. The rules themselves live in `@wordpress/ui`, and are included in the `@wordpress/eslint-plugin` config.
2. The rules themselves live in `@wordpress/eslint-plugin`.

(In the Stylelint equivalents, the rules live in `@wordpress/ui`, and are included in the `@wordpress/stylelint-config` config.)

I expected the first way to be preferable, as it matches how we set up the Stylelint equivalents. However, it turned out that the structural differences between `@wordpress/eslint-plugin` and `@wordpress/stylelint-config` give us different constraints, which kind of forces us to take different approaches.

In `@wordpress/stylelint-config`, we cannot expose individual custom lint rules in a way that a consumer can use just the theme token rules, without using the standard config sets. This means that, if we take approach number 2, consumers cannot use the theme tokens lints independently.

In `@wordpress/eslint-plugin`, we cannot add custom lint rules to the standard config in a way that _doesn't_ expose the individual lint rule from the package (at least until we migrate everything to the new [flat config files](https://eslint.org/docs/latest/use/configure/migration-guide#start-using-flat-config-files)). This means that, if we take approach number 1, the theme tokens lint rules would be exposed from **both** `@wordpress/ui` and `@wordpress/eslint-plugin`, which is confusing.

So all things considered, it was simpler to take approach number 2 here.
