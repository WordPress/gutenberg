## Description

<img width="697" alt="Screen Shot 2020-01-21 at 3 37 20 PM" src="https://user-images.githubusercontent.com/2322354/72843645-f2715380-3c68-11ea-8ed0-7ba7b29d4d14.png">

This update enhances the `BaseControl` component with the ability to render
as a `fieldset` DOM element. This is necessary for correct semantics + better
a11y support for use cases with multiple inner fields. An example would
be a collection of `radio` buttons.

We have a component, `RadioControl`, that falls under this exact use case.

With this update, we can adjust the inner `BaseControl` of `RadioControl` to
render as `fieldset`.

## How has this been tested?

This has been tested locally via Docker + WP, as well as Storybook.

## Types of changes
* Add an `as` prop to `BaseControl` to adjust for `fieldset` scenarios
* Add some CSS reset styles for `fieldset` rendering
* Apply `fieldset` rendering for `RadioControl`

@gziolo + @youknowriad Haii! In my latest push, I consolidated the label rendering logic into a dedicated component. I feel like this simplifies `BaseControl` quite a bit:

Before:
```jsx
{ label && id && ( hideLabelFromVision ?
  <VisuallyHidden
    as="label"
    htmlFor={ id }>{ label }</VisuallyHidden> :
  <label
    className="components-base-control__label"
    htmlFor={ id }>{ label }</label>
) }
{ label && ! id && ( hideLabelFromVision ?
  <VisuallyHidden
    as="label">{ label }</VisuallyHidden> :
  <BaseControl.VisualLabel>{ label }</BaseControl.VisualLabel>
) }

```

After:
```jsx
{ label && (
  <VisualLabel
    as={ VisualLabelComponent }
    hideLabelFromVision={ hideLabelFromVision }
    htmlFor={ id }
  >
    { label }
  </VisualLabel>
) }
```

This new implementation of `VisualLabel` merges and maintains the functionality of the previous one. It's also still available as a static property via `BaseControl.VisualLabel` to ensure backwards compatibility

> I don't really understand why the RadioControl has to be a fieldset while all other controls are actual controls "fields + labels". I guess the answer is related to a11y. but it makes me wonder if the issue is more on the consumer side and not on the reusable UI component.

Fieldset in general groups together controls. In the case of radio buttons, they directly relate, like described originally: Question plus a set of answers of which only one can be selected.

But you can also use fieldsets to group together pairs of label/inputs that are related to each other. For example, you could have two fieldsets, one for a billing address, the other for a shipping address. Both would have labels+input fields such as last name, first name, street address, zip code, city, etc., but one would have a legend of Shipping Address, and the other of Billing Address. Both are valid use cases for using fieldset/legend. In the case of radio buttons, strictly spec compliant speaking, this is required, in the case of sets of similar groups of fields, it is strongly recommended to do it this way.
