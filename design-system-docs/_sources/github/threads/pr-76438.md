## Body

## What?

Add `Popover` component to `@wordpress/ui`, based on [Base UI's Popover](https://base-ui.com/react/components/popover).

## Why?

We're building a new set of UI primitives — see https://github.com/WordPress/gutenberg/issues/71196.

The new Popover is designed to eventually replace the monolithic `Popover` from `@wordpress/components`. It is architecturally cleaner (compound components, design tokens, CSS Modules) while covering the same use cases.

## How?

- Wrap Base UI Popover primitives into seven compound sub-components: `Root`, `Trigger`, `Popup`, `Arrow`, `Title`, `Description`, `Close`.
- Cover the same use cases as the legacy `@wordpress/components` Popover. Storybook examples (21 stories) demonstrate each capability.

<details>
<summary>Implementation details</summary>

### Sub-components

| Sub-component | Role |
|---|---|
| `Popover.Root` | Provides open state and context |
| `Popover.Trigger` | Toggles popup on click (or hover via `openOnHover`) |
| `Popover.Popup` | Floating container — portal, positioning, collision avoidance, backdrop |
| `Popover.Arrow` | Optional arrow pointing toward the anchor (renders a default SVG when no children are provided) |
| `Popover.Title` | **Required** heading for accessibility (can be visually hidden). Uses `Text` with `heading-xl` variant |
| `Popover.Description` | Optional paragraph linked via `aria-describedby`. Uses `Text` with `body-md` variant |
| `Popover.Close` | Close button (deprioritized for initial focus) |

### Key features

| Feature | Implementation |
|---|---|
| Positioning | `side`, `align`, `sideOffset`, `alignOffset` on `Popover.Popup` |
| Arrow padding | `arrowPadding` prop (default `8`) prevents arrow/corner overlap |
| Collision avoidance | `collisionAvoidance`, `collisionBoundary`, `collisionPadding`, `sticky` |
| Custom anchor | `anchor` prop (Element, VirtualElement, RefObject, callback) |
| Controlled mode | `open` / `onOpenChange` / `defaultOpen` on `Popover.Root` |
| Modal / focus trap | `modal={true}` (full modal) or `modal="trap-focus"` (focus trap only). Requires `Popover.Close` inside the popup for focus cycling. |
| Backdrop | `backdrop` prop on `Popover.Popup` |
| Inline rendering | `container` prop with a local `display: contents` element (documented in Inline story) |
| Cross-document | `container` prop for iframe scenarios |
| Hover trigger | `openOnHover`, `delay`, `closeDelay` on `Popover.Trigger` |
| Style variants | `variant="default"` or `variant="unstyled"` |
| Viewport-constrained size | `--available-height` / `--available-width` CSS variables |
| Custom z-index | `--wp-ui-popover-z-index` CSS variable |
| Initial focus | `initialFocus` / `finalFocus`; close button deprioritized via shared hook |
| Title validation | Dev-only validation ensures `Popover.Title` is always present and non-empty |

### Design decisions

- `style` and `className` are forwarded to the **Positioner** element (for z-index and CSS variable access). Other HTML attributes go to the inner **Popup** element. Documented in `PopupProps` JSDoc; matches the Select component's pattern.
- Base UI CSS custom properties and data attributes are used directly (not aliased). See https://github.com/WordPress/gutenberg/issues/76649 for the broader policy discussion.
- JSDoc on `Root` serves as the component overview for Storybook — no `parameters.docs.description` needed.
- `Popover.Title` has no built-in margin. Consumers add spacing via `Stack` or inline styles, making the component more composable and avoiding unintended layout from visually hidden titles.

### Storybook stories (21)

Default, NoArrow, Positioning (all side×align combos), WithCloseButton, Controlled, Modal, Unstyled, OverlayPlacement, Inline, CollisionAvoidance, CrossIframe, CrossIframe (SlotFill), WithCustomZIndex, Anchor (4 anchor types), ToolbarVariant, ViewportConstrainedSize, OnOpenChangeDetails, InitialFocus, TrapFocus, HoverTrigger, InfoTip.

## Follow-ups

- [ ] Improve tooltip docs since with `Popover` we can have infotips/hovercards (see https://github.com/WordPress/gutenberg/pull/76705).
- [ ] **Title validation improvements**: the current dev-only validation only runs on mount (matching Dialog's behavior). A follow-up should add cleanup-based re-validation to catch conditionally rendered titles. This improvement should apply to both Popover and Dialog.
- [ ] Replace hardcoded backdrop `rgba` color with a WPDS overlay/scrim token when one is introduced (tracked via inline TODO).
- [ ] **Normalize `render` prop and ref forwarding** across all `@wordpress/ui` components. Currently three patterns coexist (explicit with fallback, implicit via rest, through Base UI). A follow-up should standardize on a single approach for consistency.

That's a good question, and in retrospect my opinion is likely softer than it came across. I'd sum up my feelings as revolving around vendor lock-in and developer experience. For example, we don't _fully_ pass through BaseUI props which would bind us closer to BaseUI, like [typings for the second argument of `render` (BaseUI's internal `state`)](https://github.com/WordPress/gutenberg/pull/74652#discussion_r2742908827). The two accessibility tests here claim to verify `aria-labelledby` / `aria-describedby`, but they only assert that the Title/Description elements received an `id`. Consider asserting that the rendered popup element has `aria-labelledby`/`aria-describedby` pointing at the corresponding Title/Description `id` (e.g., by selecting the popup and checking its attributes).
