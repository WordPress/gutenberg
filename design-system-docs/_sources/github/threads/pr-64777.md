Add exit animations to `Navigator` screen

## Why?
<!-- Why is this PR necessary? What problem is it solving? Reference any existing previous issue(s) or PR(s), but please add a short summary here, too -->

An exit animation can help the user understand the transition to a new screen better — and gives an additional sense of polish to the UI.

The animation specs (durations, delays, easing functions) are also updated following the latest motion guidelines (cc @nick-a8c)

## How?
<!-- How is your PR addressing the issue at hand? What are the implementation details? -->

  - Added a `useScreenAnimatePresence` hook which takes care of managing the screen's animation lifecycle
  - Use CSS transitions to animate the screen
  - Use `data-` attributes to set animation state on the DOM element, which is used to trigger the CSS transitions
  - Use CSS grid on the provider to force all screens to overlap, while also pushing the height of the container
  - Always render the screen root element, while conditionally rendering its contents
  - Updated tests to completely skip animations, that were causing errors and general flakiness
  - Added a note in the README about setting the wrapper height (related conversation in https://github.com/WordPress/gutenberg/pull/64798#discussion_r1733235033)

### ciampo on 2024-08-27T15:32:16Z

URL: https://github.com/WordPress/gutenberg/pull/64777#issuecomment-2312889359

> Animating presence will likely be a recurring need

That's true, although in many cases, animating presence [can be done with some recent CSS features](https://developer.chrome.com/blog/entry-exit-animations). But those can't be used with `Navigator` because we remove a `Screen`'s markup when the screen gets deselected.

> Not immediately sure if we should use a library like react-transition-group ([maybe](https://bundlephobia.com/package/react-transition-group@4.4.5) 1.7kB gzipped if we only needed the Transition component), or if we want to maintain our own for an even smaller size.

I'm conflicted — on one end, I don't like to reinvent the wheel if the problem has been solved well by third-parties. On the other, we're trying to [move away from `framer-motion`](https://github.com/WordPress/gutenberg/issues/60975) for smaller bundle size and better performance (using CSS native features as much as possible).

If we used `react-transition-group`, we'd need to use the `CSSTransition` component (`2.6kB`), since the `Transition` component is just the abstract logic.

Also, this specific type of animation will be much easier when [view transitions](https://developer.mozilla.org/en-US/docs/Web/API/View_Transitions_API) become more advanced and better supported in the next few years.

> How can we abstract this into something encapsulated and reusable, so we don't have to add in a bunch of ad hoc animation coordinating logic into a component every time we need an entry/exit animation?

I wonder if doing so would represent a form of early optimization. Maybe we can keep `Navigator` as-is, and re-discuss this topic if/when we have more real use cases for animating presence, so that we can better understand what type solution we'd need to implement?

### jsnajdr on 2024-09-02T14:06:15Z

URL: https://github.com/WordPress/gutenberg/pull/64777#issuecomment-2324838899

Here's how I understand the concept:

The `NavigatorProvider` no longer renders just one matching `NavigatorScreen`, but it can render two or even more. One is the real active one, the others are there only for effect. We could build a navigator that displays all parent screens using a `wasMatch` array, like this Apple Time Machine history UI 🙂

![ea02d34d-0309-4109-819a-e05eb5087624](https://github.com/user-attachments/assets/f0e46860-93c8-4589-9dfc-fa33cc76b8ce)

So, that determines the DOM structure and the baseline styles for navigator, even without any animations. The matching screens are displayed side-by-side, or they are all `display:none` except one, or are displayed as something else. The styles must be able to show the active screen as the active one and the other screens as inactive.

I don't like the `setWrapperHeight` helper very much. It feels very hacky. Instead, the base navigator styles should be able to display multiple screens at once without any helpers. When I remove `setWrapperHeight` from the code, I don't see any ugly effects in the Storybook examples.

There can be a behavior that the `wasMatch` value is reset to `false` after some timeout and the inactive screen is unmounted. That will be useful when the exit animation is implemented. But it's an optimization, not an essential feature. The navigator still works 100% when the `wasMatch` screen is rendered indefinitely.

When the base DOM structure and the base styles are established, the animations are merely an icing on the cake. The transition from active screen to inactive and vice versa are animated. Can be easily done with CSS animations.

I think that when you think about the PR as i) solid base DOM structure and styles + ii) simple animations on top, it's easier to understand.

And if we did this with `framer-motion`, it doesn't give us much extra, does it? Its `AnimatePresence` helper is useful, but that's all.

### ciampo on 2024-09-06T15:00:08Z

URL: https://github.com/WordPress/gutenberg/pull/64777#issuecomment-2334251092

> When I remove setWrapperHeight from the code, I don't see any ugly effects in the Storybook examples.

That's because, in the storybook examples, the `NavigatorProvider` component has a `height: calc(100vh - 2rem)` style applied.

If you remove the set `height` and remove `setWrapperHeight` too, you should notice that the screen animating out will have its contents cutoff if the screen animating in is not as tall.

Here is a video comparison (I slowed down the animation and added a background gradient to make things more evident)

| Without `setWrapperHeight` | With `setWrapperHeight` |
|---|---|
| <video src="https://github.com/user-attachments/assets/6d4d30af-1d0b-4a88-a8c9-300823ca2752" /> | <video src="https://github.com/user-attachments/assets/6658001e-2698-40cd-a2d8-02e7f0481825" /> |

Having said that, this comment made me reflect:

> I don't like the setWrapperHeight helper very much. It feels very hacky. Instead, the base navigator styles should be able to display multiple screens at once without any helpers.

And I realised that, instead of setting `position: absolute` on the screen transitioning out (which then causes the `NavigatorProvider` to jump, and the screen animating out to be possible cut off), we can use `display: grid` and have both screens (the one transitioning in, and the one transitioning out) overlap in the same grid cell, meaning that the tallest one will push the cell's height without the need for `setWrapperHeight`.

I applied this approach in [`8bca499` (#64777)](https://github.com/WordPress/gutenberg/pull/64777/commits/8bca499c4ed77bf7b45077ad380a8357a5424906)

If I understand correctly, this is not too different from how `Navigator` works.

The `NavigatorProvider` keeps all the logic, and lets every screen know what's the selected screen ID. So, every `NavigatorScreen` is always rendered (in the react sense).

Each screen, then, decides independently if its contents should be rendered in the DOM, and handles focus if/when needed.

> When the base DOM structure and the base styles are established, the animations are merely an icing on the cake. The transition from active screen to inactive and vice versa are animated. Can be easily done with CSS animations.
> I think that when you think about the PR as i) solid base DOM structure and styles + ii) simple animations on top, it's easier to understand.

Yup, that's basically what's happening with the `useScreenAnimatePresence` logic. And another good demonstration of this separation is that, with the latest changes, this PR didn't have to make any changes to the `NavigatorProvider` (where all the orchestration logic is).

The hook is basically a state machine that goes through the "animation lifecycle" of a navigator screen:

```
initial     →           animating in          →        visible
                             ↑                            ↓
                   removed from the DOM       ←      animating out
```     

> And if we did this with `framer-motion`, it doesn't give us much extra, does it? Its `AnimatePresence` helper is useful, but that's all.

Framer motion would basically replace the `useScreenAnimatePresence` hook, but everything else would still need to be kept around.
