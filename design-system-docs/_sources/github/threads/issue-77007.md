# Issue #77007: Autocomplete: trigger selection via lastIndexOf re-matches existing completed mentions

- URL: https://github.com/WordPress/gutenberg/issues/77007
- Author: lancewillett
- Created: 2026-04-02T16:18:03Z
- Updated: 2026-04-21T21:39:10Z
- Comments: 6 of 6

## Body

### Description

The `Autocomplete` component in `@wordpress/components` uses `lastIndexOf` to find where a trigger prefix (e.g., `@`) starts before the cursor. This always matches the **last** occurrence of the trigger character, even if that character is part of an already-completed mention token. When a user edits text near an existing `@mention`, the autocompleter re-triggers on the old `@`, and accepting a new completion corrupts the block content.

This is related to #42925 (re-triggering after selection), but covers a distinct scenario: **editing near previously completed mentions**. The root cause is the same naive `lastIndexOf` matching, but this manifests as block content corruption rather than a redundant popup.

### Step-by-step reproduction instructions

1. Register a custom autocompleter with `@` as the trigger prefix (or use the built-in user mention completer)
2. In a paragraph block, type `@username` and accept the autocomplete suggestion
3. Move the cursor to just after the completed `@username` mention
4. Type additional text, or place the cursor inside the mention text and type
5. The autocompleter fires again, matching the `@` from the already-completed mention
6. If a new completion is accepted at this point, the block content between the old `@` and the cursor is replaced, corrupting the block

### Expected behavior

The autocompleter should not re-trigger on `@` characters that are part of already-completed mentions. Only a freshly typed `@` should open the autocomplete popup.

### Actual behavior

The autocompleter fires on any `@` found via `lastIndexOf` before the cursor position, regardless of whether that `@` belongs to an existing completed token. Accepting a completion in this state replaces content between the old trigger and the cursor, corrupting the block.

### Technical detail

The trigger selection logic in `@wordpress/components/src/autocomplete/index.tsx` uses `lastIndexOf` (or equivalent) to locate the trigger prefix before the cursor. This approach has no awareness of whether the matched prefix is part of a previously completed token.

The `registerFormatType` mechanism that would give mentions format boundaries (allowing the autocompleter to distinguish completed vs. new triggers) is not always available. For example, `@automattic/editor-autocompleter` v1.4 disabled format type registration because it depended on `__experimentalCreatePrepareEditableTree`, which broke in Gutenberg 17.9.

### Suggested fix direction

The trigger selection should verify that the matched prefix is not part of an already-completed token. Possible approaches:

- Check format boundaries around the matched `@` to determine if it's inside a completed mention format
- Verify the text between the trigger character and the cursor does not contain whitespace (a fresh trigger like `@us` has no spaces; an old mention followed by new text like `@username some new text` does)
- Track completed mention positions and exclude them from trigger matching

### Affects

This affects any consumer that registers custom autocompleters with single-character trigger prefixes, including third-party plugins and custom editors built on Gutenberg.

### Environment info

Gutenberg trunk / WordPress 6.x with custom autocompleters registered via the `editor.Autocomplete.completers` filter.
