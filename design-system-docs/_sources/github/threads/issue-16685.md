# [TextControl](https://github.com/WordPress/gutenberg/tree/master/packages/components/src/text-control) / [TextareaControl](https://github.com/WordPress/gutenberg/tree/master/packages/components/src/textarea-control)

![image](https://user-images.githubusercontent.com/618551/61156362-d2dac080-a4b8-11e9-889d-2eceb07492b7.png)

## Audit
Opportunities I came across while reviewing this component.

- "TextControl" and "TextareaControl" were confusing names because I didn't understand what "control" meant. Not ideal names for someone looking for a simple text field component.
- "TextControl" could mean many different things.
- Two distinct components didn't feel necessary, and could be simplified.

## Suggestions

- Combine TextControl and TextareaControl into “**TextField**”. Because they are so similar, we can increase usability of the system by combining the two.
- **TextField** can have a `multiline` prop to enable a multiline text field. A `textarea` html element would be used in this case. This aligns with the [`aria-multiline` attribute](https://www.w3.org/TR/wai-aria-1.1/#aria-multiline).

# [FormTokenField](https://github.com/WordPress/gutenberg/tree/master/packages/components/src/form-token-field)

![image](https://user-images.githubusercontent.com/618551/61157117-d2dbc000-a4ba-11e9-8d04-e70e3f65936b.png)

## Audit
Opportunities I came across while reviewing this component.

- Based on the name, it's seems to unnecessarily imply a grouping with form elements.
- There's an opportunity here to generalize the "token" element into more reusable components, and not require a text field.

## Suggestions

- Consider renaming token to "**chip**" because it's more memorable, and I think more descriptive. "Tag" would also be acceptable but obviously a conflict with common WP language.
- Break this component down into several components: **Chip**, **ChipSet** (or ChipGroup), and **ChipTextField** (previously FormTokenField).

# [BaseControl](https://github.com/WordPress/gutenberg/tree/master/packages/components/src/base-control)

## Audit
I could use some feedback on this one. It took me a while to understand what it actually provided and how it relates to the input elements like Radio and Checkbox. I’ve learned that it provides a **label** and **help text** for some components. In the future, I'm sure it could provide validation and RTL handling perhaps. 

Different strategies I've found in other component libraries:

- MDC Material has [FormField](https://href.li/?https://github.com/material-components/material-components-web/tree/master/packages/mdc-form-field) which handles labels, and RTL for inputs, but no help text.
- Their React library, [MDC React](https://href.li/?https://github.com/material-components/material-components-web-react), does not provide FormField as a component ([intentionally it seems](https://href.li/?https://github.com/material-components/material-components-web-react/issues/929#issuecomment-502186555)). Things like help text are implemented as separate sub components as far as I can tell. For example, [TextField](https://href.li/?https://github.com/material-components/material-components-web-react/tree/master/packages/text-field) has its own TextFieldHelperText component.
- Material UI has [FormControl](https://href.li/?https://material-ui.com/api/form-control/#formcontrol-api) which handles help text as well as the label.
- Ant Design has [Form.Item](https://href.li/?https://material-ui.com/api/form-control/#formcontrol-api).
- [Evergreen](https://evergreen.segment.com/components/form-field) has FormField, which provides label, isRequired, description, hint, and validationMessage. Apparently it's already combined in their text input and select components.

These different strategies are interesting to me, but I don’t know why some libraries went the direction they chose, or what the pros/cons are. Whatever we decide to do, we should weigh the options and take into consideration that we need to add field validation to some of these components. Material seems to only provide validation on text input elements. Maybe that’s why they don’t provide a help text in their FormField? Do we really need validation on checkboxes and radios, etc.? Regardless, we should have a `helptext` prop on all applicable elements for ease of use.

## Suggestions

Aside from the features it provides, I think any of the names above are better alternatives for BaseControl (**FormField**, **FormItem**, **FormControl**, etc.)

# Props audit

## TextField

### Validation

Validation is complex. A simple strategy that many libraries employ is to just have a default non-error state and an error state. This means there is no "success" or "warning" state. I like the simplicity of this and seems easier to implement. It also mirrors what is available in native html5 validation. 

On the other hand, it can be useful to provide the user with encouraging feedback when the they correct the error with a "success" state.

We could start small and expand if we need a success state.

- **validationMessage** or **errorMessage** or **error**: the error message to display if the input is invalid.
- **variant**: if we need more states. Accepts _error_, _success_, and _warning_.

- **dense**: makes the field smaller, for denser layouts
- **prefix** and **suffix***: Text to display before/after input value
- **iconStart** and **iconEnd***: Icon located at the start/end of the input
- **characterCount***: display a character counter next to the field
- **required**
- **disabled**
- **readOnly**
- **placeholder**
