# Issue #22265: Slots do not support being rendered multiple times into the tree

- URL: https://github.com/WordPress/gutenberg/issues/22265
- Author: rmccue
- Created: 2020-05-11T11:22:53Z
- Updated: 2023-04-13T08:24:33Z
- Comments: 1 of 1

## Body

**Describe the bug**
Slots with the same `name` will only have Fills mounted into the last Slot to render. This makes Slots impossible to practically use in a list or table context; any place you're dealing with N items instead of 1.

**To reproduce**

Insert a Slot into a loop, then attempt to Fill it.

Trivial example: https://codesandbox.io/s/long-sunset-351g4?file=/src/App.js

**Expected behavior**

Fills should be rendered and mounted into each Slot, rather than just the last one.

**Additional context**

Let's say you're trying to recreate WordPress' list tables, which provide for custom columns, and for extensibility within columns themselves. The straightforward approach to this would be something like:

```jsx
<tbody>
	{ posts.map( post => (
		<tr key={ post.id }>
			<td>
				<strong>{ post.title.rendered }</strong>
				<div className="row-actions">
					<Slot name="ListTable.row.actions" fillProps={ { post } } />
				</div>
			</td>
			<td>
				{ post.author }
			</td>
			<Slot name="ListTable.row.column" fillProps={ { post } } />
		</tr>
	) ) }
</tbody>
```

Only the final row will have any custom columns or actions mounted into the Slots.

(Note: technically, every slot actually triggers a render of the Fill with the relevant props.)

As another example, maybe you want to have slots within a given block's UI. If multiple blocks of the same type are inserted into the editor, only the last block to render will have the fills rendered into it.

----

My assumption as to the cause is that when Slot renders, it sets the portal for the given key to its ref. If the portal changes, Fill unmounts itself from the previous portal, and mounts into the new portal. (I'm not intimately familiar with the code, although have rough knowledge of it.)

I believe this could be fixed by giving each Slot a unique ID (in the constructor), and registering a list of portals rather than a singular one.

This would leave the issue of how a Fill renders multiple times, as it would need to render `N=Slots.count` children rather than one. In most cases, `fillProps` is going to be necessary in loops, so `children` is a function; we can just call it multiple times. If `children` is a node though, `cloneChildren` is likely going to be required.

As I say though, not super familiar with the code, so that's just my vague thoughts. If that sounds reasonable, I can look at PRing it.

([Twitter discussion](https://twitter.com/rmccue/status/1259101066605494274) for reference.)
