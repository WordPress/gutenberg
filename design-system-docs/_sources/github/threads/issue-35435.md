## Body

### Description

When using the [VisuallyHidden](https://github.com/WordPress/gutenberg/tree/trunk/packages/components/src/visually-hidden) component, its contents are being displayed. The contents shouldn't be visible, as explained in the component's README file.

Original report [here](https://github.com/Automattic/woocommerce-payments/issues/3033).

### Step-by-step reproduction instructions

1. Install and activate [WooCommerce](https://wordpress.org/plugins/woocommerce/) and [WooCommerce Payments](https://wordpress.org/plugins/woocommerce-payments/)
2. Register a test account for WooCommerce Payments as explained [here](https://docs.woocommerce.com/document/payments/testing/dev-mode/)
3. Go to `/wp-admin/admin.php?page=wc-admin&task=woocommerce-payments--additional-payment-methods` and enable the new checkout experience (step 1)
4. When step 2 is displayed, notice things look fine
5. Install and activate Gutenberg
6. Go to `/wp-admin/admin.php?page=wc-admin&task=woocommerce-payments--additional-payment-methods`  again, and notice the UI is broken

Things look fine when commenting out [this style override](https://github.com/WordPress/gutenberg/blob/trunk/lib/client-assets.php#L319) from Gutenberg.

On WooCommerce Payments, we're using the VisuallyHidden component to add context for screenreaders for tooltips [here](https://github.com/Automattic/woocommerce-payments/blob/develop/client/components/payment-methods-checkboxes/payment-method-checkbox.js#L28).

### talldan on 2021-10-11T04:01:24Z

URL: https://github.com/WordPress/gutenberg/issues/35435#issuecomment-939658800

This sounds pretty complex.

I think the issue is that a plugin might be importing an older version of VisuallyHidden from WordPress that used scss styles. When the Gutenberg plugin is active those styles are no longer present in the components stylesheet because the new version of VisuallyHidden uses css-in-js (https://github.com/WordPress/gutenberg/blob/trunk/packages/components/src/visually-hidden/styles.js).

Sounds like a problem that might occur with other components that are rewritten to use css-in-js.

I imagine woocommerce and other plugins could probably solve this by using the latest version of `@wordpress/components`, but there still might be an underlying backwards compatibility issue here for plugins.

cc @ciampo.

### ciampo on 2021-10-12T07:54:14Z

URL: https://github.com/WordPress/gutenberg/issues/35435#issuecomment-940758050

Hey @a-danae , upgrading to the latest version is the correct thing to do here.

In general, we're in process of migrating the components internal styling system to Emotion. While this will practically be just an internal implementation detail, one consequence is that external code relying on hardcoded classnames can stop working. As a rule thumb, and to avoid further issues like this one, we shouldn't rely on the classnames of these components.

In any case, thank you for flagging and for being able to take care of the issue on your end! @talldan , I believe we can close this issue?
