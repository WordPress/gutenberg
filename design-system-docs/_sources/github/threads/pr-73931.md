## What?

Within `@wordpress/theme`, refines typography tokens:

- Normalize token names to use `kebab-case`, ensuring that DevMode code snippet references when imported in Figma reference the correct CSS property names. CSS property names already convert to `kebab-case` through the Terrazzo CSS plugin, so this has no effect on the resulting CSS property name.
- Normalize token names to use short-hand t-shirt size naming, e.g. `sm`, `md`, `lg` (consistent with tokens added in #73308).
- Adds font `weight` tokens

~Within `@wordpress/ui`, implements a new `Text` component whose purpose is to tie consumer usage to underlying typography design tokens, similar to how [`Box`](https://github.com/WordPress/gutenberg/pull/72984) is an abstraction to underlying dimension, border, and color tokens.~ **Edit:** After discussion, these changes were removed in b057f07981108dcdf1740e968b602cb9d7db5964 to be reserved for a follow-up pull request.

## Why?

- ~Convenience layer for consumers to use design tokens without reaching for custom CSS~
- ~This is already surfacing as an active need, see https://github.com/WordPress/gutenberg/pull/73875#discussion_r2607682790~
- Mature set of typography tokens which are consistent with other tokens (particularly in abbreviated, t-shirt size naming scheme)
- Support font weight tokens which already have present need in `Field` and `Badge` components

### mirka on 2025-12-23T20:49:07Z

URL: https://github.com/WordPress/gutenberg/pull/73931#issuecomment-3687928356

> I'd struggle to understand why some React components expose token-related props and others don't

I'm fine with this point specifically, because I think it's good that a component "has one job".

---

I share Marco's leaning towards keeping CSS/JS concerns separated, and avoid doing the same thing in multiple ways. I think that keeps things simpler, both for humans and AI.

To add to that, my concern would be about the _limitations_ of convenience styling components like `Box` and `Text`. If people think they should use these components over CSS, they are going to run into situations where they either have to nest DOM elements unnecessarily, or do deep nested `render` props (which gets harder to grok and predict behaviors). They're just not going to compose as nicely as CSS does. A plausible example would be if I wanted to render a `Select.Trigger` with `Box` and `Text` and `Stack` styles.

So although these convenience styling components can be convenient in some cases, the downside is that once you hit the limits, it may actually cause more fiddliness than if you had just started with CSS. The question is whether the conveniences outweigh the downsides.

Given the proven usage in Gutenberg, I think it's safe to say that `Stack` is more useful than not. It's hard to say for the other new components like `Text` or `Box`, but at a certain point it's going to be better to just use Tailwind or something, so I think we should be judicious about adding components that are simply design token aliasing.

tl;dr — I'm not strongly against them, especially since we have some leeway to retract them later. But if it were just me I would probably start without.
