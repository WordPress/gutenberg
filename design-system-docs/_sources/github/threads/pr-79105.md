## Body

## What?

Adds an opt-in `supports.editableRoot` block support. When the selected block opts in, the writing flow wrapper (the editor canvas body) becomes the contentEditable editing host, so the browser's native selection can extend across blocks. Enabled for the paragraph block to start.

## Why?

Cross-block selection currently relies on synthetic pointer handling that does not work with native selection on touch devices (notably iOS), where pointer events cannot be reliably intercepted. Making the wrapper a single editing host lets the native selection span blocks, while the editor should otherwise behave exactly as today.

## How?

1. **New `editableRoot` support key** (schema + docs), enabled on `core/paragraph`.
2. **`useEditableRoot`** flips the writing flow wrapper to `contentEditable` and holds focus while the selected block opts in; it never flips mid-keystroke, only on block-selection change.
3. **Selection-ownership event model**: handlers no longer rely on the event target. They use `ownsSelection( element )` / `subscribeOwnedListener` (rich text private APIs) so they work whether focus is on the block's editable element or on the wrapper host.
4. **Selection sync ownership**: rich text owns within-block sync (it always listens to `selectionchange` now, via a shared delegated listener); the writing flow observer owns cross-block multi-selection.
5. **Host-mode adaptations**: arrow navigation, clipboard, autocomplete ARIA, and the typewriter are made to work when the wrapper holds focus.

## Backward Compatibility

Blocks opt in (`supports.editableRoot`, paragraph only). The main risk is for extensions that add event handlers via the `editor.BlockEdit` (or `editor.BlockListBlock`) filter: when a block opts in, the writing-flow wrapper is the editing host and holds focus, so keyboard, input, and clipboard events target the wrapper (an ancestor of every block) rather than the block's own editable element. React handlers (`onKeyDown`, `onInput`, …) attached within a block therefore never fire, since the event originates above their subtree. Core's own handlers use a selection-ownership model (`ownsSelection` / `subscribeOwnedListener`) to handle this; if needed, we could add a back-compat layer that forwards `on*` React event handlers to the wrapper host.

## Alternatives Considered

**Drop `contentEditable` everywhere on uncollapsed selection.** Instead of promoting the wrapper to a single editing host, keep each block editable as today and simply turn `contentEditable` off on every block the moment the selection becomes uncollapsed (text remains selectable without `contentEditable`). Adding `tabindex` to the blocks keeps focus on the originating block. The appeal: the focusable element never moves to the wrapper, so the selection-ownership rerouting and its back-compat risk for `editor.BlockEdit` handlers largely disappear, and the host swap is transient (only during an active cross-block selection).

This was prototyped and tested. In **Chromium** it works: flipping `contentEditable` off mid-drag does not abort the selection, both pointer and keyboard selection extend across blocks, and with `tabindex` the focus and subsequent keystrokes stay on the block rather than falling to `<body>`. However, on **iOS Safari/WebKit** it fails: mutating `contentEditable`/focus during the active selection gesture **destroys the selection** — it disappears the instant it forms. Since native cross-block selection on iOS touch is the entire motivation for this work, this approach is disqualifying there. The wrapper-as-single-editing-host model in this PR avoids mutating editability mid-gesture, which is why it holds up on iOS.

## Testing Instructions

1. Add a few paragraph blocks.
2. Select text starting in one paragraph and dragging into another; the selection should span blocks natively.
3. Verify single-block editing, splitting/merging, copy/paste, and formatting behave as before.

### Testing Instructions for Keyboard

1. With the caret in a paragraph, use `Shift+ArrowUp`/`Shift+ArrowDown` to extend the selection across blocks.
2. Confirm arrow navigation, Enter/Backspace, and `Cmd/Ctrl+A` behave as before.
