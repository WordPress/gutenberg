# Issue #69925: ToggleGroupControlOption with an empty string ("") value does not display as selected

- URL: https://github.com/WordPress/gutenberg/issues/69925
- Author: spstrap
- Created: 2025-04-17T03:02:09Z
- Updated: 2025-04-23T06:19:49Z
- Comments: 11 of 11

## Body

### Description

When using ToggleGroupControlOption with a value of "" (empty string), the option does not appear selected, even when the value prop of the parent ToggleGroupControl is correctly set to "".

This makes it impossible to visually reflect the selection of an empty string value, even though the internal state is technically correct.

When value="" is passed to both ToggleGroupControl and ToggleGroupControlOption, the option should be visibly selected like any other value.

### Step-by-step reproduction instructions

1. Use ToggleGroupControl and pass a value of "".
2. Inside, include a ToggleGroupControlOption where value="".
3. Observe that the option does not appear selected, even though the value matches.

### t-hamano on 2025-04-17T07:51:33Z

URL: https://github.com/WordPress/gutenberg/issues/69925#issuecomment-2812089328

A simple workaround is to convert the falsy value to another string in the `ToggleGroupControl` component:

```jsx
<ToggleGroupControl
	value={ value || 'none' }
	onChange={ ( newValue ) => {
		setAttributes( {
			size: newValue === 'none' ? undefined : newValue,
		} );
	} }
>
	<ToggleGroupControlOption
		key="none"
		value="none"
		label="None"
	/>
</ToggleGroupControl>
```

### Mamaduka on 2025-04-17T08:06:37Z

URL: https://github.com/WordPress/gutenberg/issues/69925#issuecomment-2812121002

IIRC, this is an intentional choice. The `ToggleGroupControlOption` requires a string or a number; here, the usual assumption is that the string will be non-empty.

You can use the method suggested by @t-hamano if choosing an option should unset the state/attribute.

I propose closing the issue, since this is an intentional API design choice.

### spstrap on 2025-04-17T08:13:19Z

URL: https://github.com/WordPress/gutenberg/issues/69925#issuecomment-2812135631

@Mamaduka 

Thanks for the clarification.

However, I respectfully disagree that it's reasonable to assume the value will never be an empty string. In many practical use cases—especially when an option is optional or intended to reflect a "not selected" state—it's common to initialize the value as an empty string and only update it when a valid choice is made.

Designing the API to completely disregard empty strings feels unnecessarily restrictive, and it forces developers to implement awkward workarounds for what should be a valid and predictable scenario.

Supporting '' (empty string) as a valid state would make the component more flexible and robust.

Personally, I don't think this issue should be closed yet, as this might still impact real-world use cases that follow this pattern.
