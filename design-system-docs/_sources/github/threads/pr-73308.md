## Body

## What?

Adds a `Stack` component to the new `@wordpress/ui` package, a formalization of the ideas previously explored in experimental components ([`HStack`](https://wordpress.github.io/gutenberg/?path=/docs/components-hstack--docs) and friends), extended to use design system spacing tokens and density configuration.

Builds on #73215

## Why?

- Stacks are useful low-level building blocks that can be used to compose common page layouts using flexbox 
- In combination with density (a configurable theme aspect outlined in #71196), this can provide value beyond static spacing provided by current experimental stack components for more context-specific automatic padding adjustments (see https://github.com/WordPress/gutenberg/issues/72336#issuecomment-3499182839).

## How?

- Adds new "gap" tokens for content flow (`dimension.gap.flow.[x-small|small|medium|large]`)
- Adds new Stack component that exposes common flexbox configurability, but which builds on `gap` to tie to design system tokens, either numeric multiplier of base spacing (4px) or as a semantic token (`'small'`, etc.)
- Makes a few supporting changes:
   - Updates JSDOM for improved support for handling styles which reference CSS properties
   - Introduces convention for [CSS cascade layers](https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Styling_basics/Cascade_layers) as a formalization of extension layers
   - Fixes some issues with props merging in `Box`
   - Adds typings for CSS properties and CSS modules support
   - Configures TypeScript for Jest + Testing Library assertion types

## Testing Instructions

Verify in Storybook:

1. Run `npm run storybook:dev`
2. Go to http://localhost:50240/
3. In sidebar navigation, navigate to "Design System" > "Components" > "Stack" > "Default"
4. Use "Theme" button in Storybook toolbar to toggle to different densities like "Compact" and "Comfortable"
5. Observe that the gap varies based on density selection

### aduth on 2025-11-20T19:46:54Z

URL: https://github.com/WordPress/gutenberg/pull/73308#issuecomment-3559764297

The unit test failures seem to be stemming from the JSDOM upgrade, which I may end up spinning off into its own pull request to review independently.

```
Error: TestingLibraryElementError: Unable to find an accessible element with the role "link" and name "I'm an anchor link! (opens in a new tab)"

Here are the accessible roles:

  link:

  Name "I'm an anchor link!(opens in a new tab)":
```

It's an interesting nuance of computing accessible names and whether two adjacent elements are joined with any whitespace, where the browser renders these as `<span>I'm an anchor link!</span><span aria-label="(opens in a new tab)"></span>`. Apparently it's an [ongoing discussion in the spec of computing accessible names](https://github.com/w3c/accname/issues/225). After digging into it, I've determined the root cause to be an interaction between [`dom-accessibility-api`](https://github.com/eps1lon/dom-accessibility-api) (which powers the `getByRole` `name` matching) and JSDOM, where [`dom-accessibility-api` considers `getPropertyValue('display')`](https://github.com/eps1lon/dom-accessibility-api/blob/27845ffc0513a9c5e20236d3c3e6aa7ffdf04674/sources/accessible-name-and-description.ts#L412-L415) of an element. In earlier versions of JSDOM, a `<span>` would not report any value here, but in recent versions this is now `'inline'`. Thus, the computed name has no space between the link text and the "(opens in a new tab)".

My read of the [relevant specification](https://w3c.github.io/accname/#comp_name_from_content) is that this is a more accurate reflection of how a browser would be expected to behave:

> §2.6.4 Name From Each Child: For each rendered child node of the current node:
> [...]
> §2.6.4.3 Append the result to the accumulated text.
