## What?
<!-- In a few words, what is the PR actually doing? -->

This PR proposes an additional piece of logic to the new experimental `DropdownMenu` component, by letting nested submenus inherit the `placement` from their parent menus.

## Why?
<!-- Why is this PR necessary? What problem is it solving? Reference any existing previous issue(s) or PR(s), but please add a short summary here, too -->

The idea is that having nested submenus opening in the same "direction" is easier for the users both in terms of how the UI looks, but also in terms of UX and a11y (especially keyboard navigation) — here's [an example scenario](https://github.com/WordPress/gutenberg/pull/55625#issuecomment-1802018020).

### andrewhayward on 2023-11-17T17:12:36Z

URL: https://github.com/WordPress/gutenberg/pull/56213#issuecomment-1816796104

> ...it seems like this behaviour was intentional and aimed at aligning with how native submenus work on both macOS and Windows. Does that make sense to you?

I can't find anything specific from Apple on navigating menus with keyboards, but when a menu is close to the edge of the screen, <kbd>right</kbd> still opens submenus (visually to the left), and <kbd>left</kbd> closes them.

[Microsoft is also a little ambiguous on the matter](https://learn.microsoft.com/en-us/windows/win32/uxguide/inter-keyboard):
> **Arrow keys.** The arrow keys move input focus among the controls within a group. Pressing the right arrow key moves input focus to the next control in tab order, whereas pressing the left arrow moves input focus to the previous control.
> ...
> **Within a tab stop, the arrow key order should flow from left to right, top to bottom,** without exceptions. The arrow keys should cycle through all items in both directions without stopping.

[IBM however is rather more explicit](https://carbondesignsystem.com/components/menu/usage/):
> **Keyboard**
> Once the menu opens by pressing <kbd>Return</kbd> or <kbd>Enter</kbd> on the menu trigger, users can:
> \- Press <kbd>Up</kbd> and <kbd>Down</kbd> arrows to navigate between menu options
> \- Press <kbd>Return</kbd> or <kbd>Enter</kbd> or <kbd>Right</kbd> arrow on the item with the caret icon to reveal additional options
> \- Press <kbd>Return</kbd> or <kbd>Enter</kbd> on an item to select or deselect it
> \- Press <kbd>Escape</kbd> to close it

[As is the W3](https://www.w3.org/WAI/ARIA/apg/patterns/menubar/):
> <kbd>Right Arrow</kbd>:
> \- When focus is in a menu and on a menuitem that has a submenu, opens the submenu and places focus on its first item.
> ...
> <kbd>Left Arrow</kbd>:
> \- When focus is in a submenu of an item in a menu, closes the submenu and returns focus to the parent menuitem.

I'm not aware of an OS pattern that swaps this, outside of RTL contexts.

The documentation is at least consistent in this though!
> [Apple](https://developer.apple.com/design/human-interface-guidelines/menus#Submenus): **Use submenus sparingly.** Each submenu adds complexity to the interface and hides the items it contains.
> [Microsoft](https://learn.microsoft.com/en-us/windows/win32/uxguide/cmd-menus#submenus): **Avoid using submenus unnecessarily.** Submenus require more physical effort to use and generally make the menu items more difficult to locate.
> [IBM](https://carbondesignsystem.com/components/menu/usage/#submenus): While submenus can help tidy up a context menu and make its options clearer, introducing multiple levels of submenus can make the user experience more complex and harder to navigate. Avoid multiple levels of nesting when it comes to submenus.
