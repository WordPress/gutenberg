## What?
<!-- In a few words, what is the PR actually doing? -->
This PR is an attempt to address https://github.com/WordPress/gutenberg/issues/58299, and covers the following:

- Reverts the changes to the `CheckboxControl` component added in https://github.com/WordPress/gutenberg/pull/56158
- Tries an alternative labelling solution for the checkboxes in the Font Library modal without needing to adjust the `CheckboxControl` component

## Why?
<!-- Why is this PR necessary? What problem is it solving? Reference any existing previous issue(s) or PR(s), but please add a short summary here, too -->
To improve accessibility and usability of these checkboxes whilst maintaining the functionality of the `CheckboxControl` component.

## How?
<!-- How is your PR addressing the issue at hand? What are the implementation details? -->
The main challenge with the current implementation of the Font Library checkboxes is that the visible label can either be text or an image, depending on if the font face provides a preview image (e.g. an SVG). This logic cannot currently be passed to the `CheckboxControl` component, as the `label` prop only accepts a string (which I agree with).

Also, the older design for the font library checkboxes had the checkboxes to the right of the label, rather than the left. Now the design has been updated to be in line with the `CheckboxControl` component, where the checkbox is to the left of the label. This makes it much easier to use the existing functionality of this component.

The solution in this PR is to provide a label in the `CheckboxControl`, and then hide the label element that the component creates using CSS. The CSS should visibly hide the label while still allowing it to be accessed by screen-readers. This has worked well in my testing so far.

There has also been an `onClick` handler added to the `FontFaceDemo` component, which allows the checkbox to be toggled when this component is clicked. Otherwise, only the checkbox itself can be interacted with to toggle the checkbox value, and I don't think this is good for accessibility or usability.

This is one attempt at an alternative solution to handling these checkbox labels, and I'd love feedback on whether this is a good approach or if we should try alternatives.

Possible other alternatives:
- Use plain text as the label, and move the font demo to a separate element (e.g. a column layout, where the font demo sits to the right of the text label). This would require design input.
- Add `aria-labelledby` attribute to the `CheckboxControl`, and reference the `FontFaceDemo` element as the label
- Allow a custom label functionality to be passed to the `CheckboxControl` component (that doesn't allow the label to be `false`)

### ciampo on 2024-01-30T13:44:16Z

URL: https://github.com/WordPress/gutenberg/pull/58339#issuecomment-1916882628

One of the main pieces of feedback received on https://github.com/WordPress/gutenberg/pull/56158 was that we were allowing consumers of `CheckboxControl` to disable the `label` entirely by passing `false`.

With the latest suggested changes, users would still be able to do so by omitting the `label` prop. I know that this isn't much different (it's probably worse!) than having an empty label, but I wonder if we can do better to make sure that consumers of `CheckboxControl` provide a label for the control.

A few ideas that came to mind:

- have a runtime check that checks if there's a `label` with the `for` attribute targeting the checkbox `input`, and outputs a warning if it doesn't find one
- allow consumers to pass a classname to the label, so that it can styled with CSS
- change the type of label so that it accepts a `ReactNode` (or something similar). Consumers who need more flexibility would be able to pass a new `label` and would therefore have more freedom in styling it

In any case, we should make sure that consumers of `CheckboxControl` are able to specify the `id` of the underlying `input` element
