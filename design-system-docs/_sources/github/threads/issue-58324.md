# Issue #58324: Component versioning

## Body

Although we are committed to maintaining backward compatibility, there are inevitable times where we can only make drastic improvements by making drastic changes to a component's API.

To make way for these drastic changes while still maintaining back compat, we have recently been trying to establish a component versioning pattern.

1. When we design a new iteration of an existing component that involves drastic, breaking changes in the API, we give it a new numbered version and export it separately from the original. For example, if our original component was exported as `MyComponent`, the new version would be exported as `MyComponentV2`.
2. As a suggested convention for consumers, this can be imported in client code as `import { MyComponentV2 as MyComponent } from ...`.
3. The previous version(s) of the component will continue to work indefinitely.

## Development details

- **Bundle size**: Whenever possible, we will try to replace the underlying implementation for the previous version to reuse as much code from the new version's implementation. This will reduce bundle size bloat as we continue to maintain older versions in the same package.
- **Private while in beta**: We will lock our new components as a [private API](https://developer.wordpress.org/block-editor/reference-guides/packages/packages-private-apis/) until they are stable enough to be used outside of the Gutenberg codebase.

## In development

### 🔒 Private

These components are not yet stable enough for public use, but are being iterated on within the Gutenberg app.

- Composite (previously named `__unstableComposite`)
- DropdownMenuV2
- Tabs (previously named TabPanel, renamed to better align with [standard web terminology](https://www.w3.org/WAI/ARIA/apg/patterns/tabs/))
