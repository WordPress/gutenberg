# Issue #69012: Font size picker: custom font size step value for `em` and `rem` units is only `0.01`

## Body

### Description

The font size picker has [some simple logic](https://github.com/WordPress/gutenberg/blob/693e315bd00ac36828364bc0b0d8f1fe22b5963c/packages/components/src/font-size-picker/index.tsx#L123-L124) in place that is used to determine when a custom font size unit is 'relative' as in: 'em', 'rem', 'vw', or 'vh'.

When it's a relative unit, the value of the `step` prop changes but only for the slider. It doesn't for the input. As such, when changing units to `em` or `rem`, the steps of the input and of the range slider aren't aligned.

When using a the up and down arrow keys to change the `em` or `rem` values of a custom font size, the value chantes by only `0.01` at each key press. Which makes this control redious to use as it requires dozens of key presses or holding the key for a long time to eb able to amke a substantial change for the value.

Animat4ed GIF to illustrate:

![Image](https://github.com/user-attachments/assets/e754c113-4606-4d1c-b079-e52c954d4d8b)

Turns out, the font size picker `RangeControl` does pass an explicit [step prop](https://github.com/WordPress/gutenberg/blob/693e315bd00ac36828364bc0b0d8f1fe22b5963c/packages/components/src/font-size-picker/index.tsx#L269).

The `UnitConrol` [doesn't](https://github.com/WordPress/gutenberg/blob/693e315bd00ac36828364bc0b0d8f1fe22b5963c/packages/components/src/font-size-picker/index.tsx#L213-L236).

When the unit is `em` or `rem`, the input field step value is `0.01`. Instead, the range one is `0.1`.

This could be quickly fixed by simply passing an explicit `step` prop to the `UnitControl` similarly to the `RangeControl`.

However, I wonder why in the `UnitControl` logic that tries to determine the fallback `step` values from the selected units, the `em` and `rem` [default step value is 0.01](https://github.com/WordPress/gutenberg/blob/693e315bd00ac36828364bc0b0d8f1fe22b5963c/packages/components/src/unit-control/utils.ts#L15-L44) which seems to me too low in the first place.

### Step-by-step reproduction instructions

- Edit a post and select a Paragraph.
- Observe the font size picker in the inspector.
- Switch the font size picker to set a custom size.
- Select `px`.
- Inspect the source and observe the `step` attribute for both the input field and the ragne input is `1`.
- Select the `vw` or `vh` units.
- Inspect the source and observe the `step` attribute for both the input field and the ragne input is `0.1`.
- Select the `em` or `rem` units.
- Inspect the source and observe the `step` attribute is `0.01` for the input and `0.1` for the range slider.
- Expected: to be `0.1` for both.

@Rishit30G that's what I meant in the PR description with:
> As such, when changing units to em or rem, the steps of the input and of the range slider aren't aligned.

Re: the potential paths to solve this issues have both pros and cons:
- Setting both to `0.1` would not allow users to set accurate values like for example `1.375` em or `0.9375` rem.
- Setting both to `0.01` or even `0.001` would results in too many steps that would make the control extremely tedious to use especially for the slider.

See also https://github.com/WordPress/gutenberg/issues/68599#issuecomment-2633201929

I'm not sure the clear usability and accessibility issues of this implementation can be solved keeping the current UnitControl + RangeControl. Rather, I would consider to change the implementation.

The UI already provides a simple UI to set a preset size, whether it's the ToggleGroup or the custom select. Instead, this is a control to set a _custom_ size. Users need to enter accurate values here and since it's a _custom_ size, I'm not sure the editor should be opinionated here and force only one or two decimals.
The same consideration applies to other controls as wel, for example the line-height value where it's not uncommon the need to enter a value with 4 or more decimals.
Overall, I think this control should be changed to a new control: a simple input field where users can enter any valid value. The control should only make sure the value is valid. This would require some more work for a new control and design, of course.
