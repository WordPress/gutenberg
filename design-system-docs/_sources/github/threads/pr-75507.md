## Body

## What?

Improves the AGENTS.md setup for coding agents working on Gutenberg.

## Why?

Claude Code only reads `CLAUDE.md`, not `AGENTS.md`, so it was getting zero project context. The existing `AGENTS.md` also lacked sections on architectural decisions and common pitfalls, which are high-value for reducing agent mistakes.

## How?

1. **CLAUDE.md symlinks** — Created at root, `packages/components/`, and `packages/ui/` pointing to their respective `AGENTS.md` files.
2. **Architectural decisions section** — Covers package layering, block data model, data layer, styles system, and modularity. Links to full architecture docs.
3. **Common pitfalls section** — Covers `lib/compat/` targeting, private APIs in bundled packages, `block-editor` WP-agnosticism, and `@wordpress/scripts` genericity.

@youknowriad an eval is basically just a WordPress [test report](https://make.wordpress.org/test/handbook/test-reports/). You give an llm+harness a task and see how it behaves, then apply your context hack and give it the same task and see if the results are improved (accuracy, token count, time, whatever you were trying to "address" in the first place).


I think these changes were autogenerated by AI, which is itself problematic, but assuming they had been written with intent:

1. You notice that when asked to update a block pattern wtvr, it mangles the direct html instead of the updating the block-data.
2. Craft the prompt for eval e.g. "Change the buttons on {X} to links. The blocks should still be styled as buttons, and have a large enough target to pass WCAG. Update {X location} to change {x button} and {y buttons} blocks to links"
3. **Turn off your memory** run the prompt, and record the results.
4. Reset the diff, add your context hack that you're hypothesizing e.g from the diff: `**Block data model**: Blocks are in-memory tree structures during editing, serialized as HTML with comment delimiters (`<!-- wp:name -->`). Work with the block tree via APIs, not the serialized HTML.` then rerun the test. Did it do a better/faster,cheaper job? 
5. Unless you're up-to-date on various agent cards, usually good to test against a few other harness/models too. E.g the `ALL CAPS` in the slopfile are particularly damaging to GPT-5 models (like the gratis copilot one given to FOSS contributors and powering Copilot PR review ).

Fun litmus: if the friction you're experiencing doesn't feel like it's worth the effort of a basic eval, it's probably not worth addressing via AGENTS.md - especially not in a public repo.

### mirka on 2026-02-19T16:13:51Z

URL: https://github.com/WordPress/gutenberg/pull/75507#issuecomment-3928276945

> is this experience based on using Claude Code on this repo (where the AGENTS.md had no effect other than polluting discovery when the model greps for context on its own for the last 4 months)?

At least for the AGENTS files we added to `@wordpress/components` and `@wordpress/ui`, the exact process was:

1. Someone put together several realistic prompts that a designer or developer could use on an LLM ("Confirm before permanently deleting a post. What WordPress component should I use?", "Build a login form", etc). 
2. These were our test prompts to first check how they work with the current repo setup. Most of the time, at least two different people tested the same prompt in their own environments, to reduce the chance of accidental success/failure. Sometimes they revealed a gap, sometimes they already worked fine. When there were gaps, we tried making improvements to the repo setup.
3. Finally, we used the same prompts to confirm that those improvements were actually effective. (Then repeat until we found an improvement that actually works.)

> In terms of structure/wording (documentation for agents needs to be a lot more explicit about what has to be done and especially what should not be done, in a writing style that is very different from documenation aimed at humans).

This is specifically referring to [this section](https://github.com/WordPress/gutenberg/blame/94bff7de7848d7fb27c2e0261cbe15696e1840be/packages/ui/AGENTS.md#L7-L9), which was revealed as a gap in the iterative process explained above. I think this was the third iteration of this wording, until the agent actually stopped the user for confirmation instead of silently proceeding to build what the user asked for.

The test prompt in this case was "Write a login form component (WP compatible) that uses components and form validation primitives from the `@wordpress/ui` package in the `packages/ui` folder". This was a real prompt where someone mistakenly believed they should already start using this new components package. Tested with Cursor, Opus 4.5.

+## Architectural decisions

+-   **Package layering**: Three editor layers — `block-editor` (generic, WP-agnostic) → `editor` (WordPress post-aware) → `edit-post`/`edit-site` (full screens). Lower layers MUST NOT depend on higher ones.
+-   **Block data model**: Blocks are in-memory tree structures during editing, serialized as HTML with comment delimiters (`<!-- wp:name -->`). Work with the block tree via APIs, not the serialized HTML.
+-   **Data layer**: Uses `@wordpress/data` (Redux-like stores). Edit entities through `core-data` actions (`editEntityRecord` / `saveEditedEntityRecord`), not direct state manipulation.
+-   **Styles system**: Three-layer merge — WordPress defaults < `theme.json` < user preferences. Use Block Supports API and CSS custom properties (`--wp--preset--*`), not hardcoded values.
+-   **Modularity**: Packages are available both as npm packages and WordPress scripts (`wp-*` handles). Production packages must work in both contexts.
+
+For full architecture details, see `docs/explanations/architecture/`.
+
+## Common pitfalls
+
+-   PHP features in `lib/compat/` MUST target a specific `wordpress-X.Y/` subdirectory.
+-   Avoid using private APIs in bundled packages (packages without `wpScript` or `wpModuleExports`). Private APIs are intended for Core usage; bundled packages may also be imported via npm into plugin scripts, causing incompatibilities.
+-   `block-editor` is a WordPress-agnostic package. NEVER add `core-data` dependencies or direct REST API calls to it.
+-   `@wordpress/scripts` (the `build` package) is a generic build tool used both in Gutenberg and by plugins targeting WordPress Core directly. Avoid Gutenberg-specific changes in it.
```
