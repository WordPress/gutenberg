## What?

Restructures design token JSON files to improve consistency of token structure and align to expected conventions:

Example:

`color.semantic.bg-surface.neutral.resting` ➡️ `wpds-color.bg.surface.neutral`
`color.semantic.fg.interactive.neutral.strong.active` ➡️ `wpds-color.fg.interactive.neutral-strong-active`

Builds on #73858

This is aimed at serving as an alternative to #73407, reflecting assumptions about how we want to represent tokens within the source tokens themselves.

## Why?

- Align how we think about these conceptually to how we structure them in the raw DTCG JSON structure
  - Have a common token naming scheme that applies consistently to all tokens, including color
  - Removes explicit "resting" states so that we don't have to have convoluted code to handle this
- Reflect the "wpds" prefix in the raw DTCG structure, used both in how Figma generates code snippets in DevMode, as well as how we output to CSS

## How?

- Adds "wpds-" prefix to all top-level token groupings
- Removes "semantic" as a top-level key in token files (flattens semantic tokens to the top-level)
- Un-nests color tokens structures like `surface.neutral.resting`, eliminating default states in the process (`resting`)

## Testing Instructions

Observe that there is no impact to `packages/theme/src/prebuilt/css/design-tokens.css` (aside from code comment correction), even after running `npm run --workspace @wordpress/theme build`.

Since this builds on #73858, optionally test how the resulting `color.json` is imported into Figma if you have means to do so, where the resulting variables look like e.g. `wpds-color/bg/interactive/neutral-strong-active` .

> * Primitives are included again,

It's not my preference, but it is expected, yes. We can't really "hide" values when using the raw DTCG JSON like this.

> * There's no scoping,

This was somewhat surprising, but it does at least scope for valid fields for the type (i.e. can't use dimension values for colors). But yeah, this does regress slightly that it no longer scopes stroke colors to stroke fields, for example.

Through some reverse-engineering, I know that Figma _can_ support us controlling this, through [additional extension values](https://www.designtokens.org/tr/2025.10/format/#extensions-0). Specifically, they have a `com.figma.scopes` extension value that we can probably use to customize this. I think I'll save this for a follow-on enhancement, though, since I'm eager to not let these restructurings sit for very long.

> * There's no descriptions?

This is rather surprising, actually. Since we use [the standard `$description` field](https://www.designtokens.org/tr/2025.10/format/#description), I'm surprised Figma doesn't use this. Might be something they'll support later? Maybe I can submit a feature request 😅

### aduth on 2025-12-10T19:33:24Z

I'll be happy to address feedback asynchronously, but since this is a pretty large restructuring prone to merge conflicts (already had to reconcile #73793), I'm hesitant to leave this open longer than it needs to be and will plan to merge this as-is.

To put some potential concerns at ease:

- This feels like a restructure we should want regardless of Figma import workflows. In particular, this matches how we're prefixing CSS properties, and it ensures that we have one overarching naming scheme (now documented) for design tokens, bringing color tokens into alignment with the rest of our tokens rather than treating it unique.
- The role of the Figma plugin has always been to transform tokens from our desired source format to a desirable workflow for Figma consumption. We could always revisit this down the line (even after its removal in #73860), and how we choose to structure the source files doesn't really fundamentally change anything. If anything, this alignment makes those transformations a lot simpler.
