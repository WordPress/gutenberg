# Issue #67795: Enforce DropdownMenu to follow the ARIA menu pattern or add linting to make sure it does

## Body

### Description

Splitting this out from https://github.com/WordPress/gutenberg/pull/67647#issuecomment-2531712162

There have been several cases where extraneous content such as paragraphs with descriptions or other extraneous content have been used inside the ARIA menu rendered by DropdownMenu. 

ARIA menus can only contain menuitems (including the menuitemradio and menuitemcheckbox variants), groups and separators. No other content type is allowed within an ARIA menu.

It would be good ot prevent such misusage and breakage of the ARIA pattern by enforcing this constrain via code or, at the very least, by adding some linting rule to prevent extraneous content from being used inside a DropdownMenu.

@afercia, I worked on PR [#69410](https://github.com/WordPress/gutenberg/pull/69410) for quite some time and creating a comprehensive lint rule for this proved challenging.

The first three scenarios are straightforward with static analysis:
1. Checking direct children under DropdownMenu (ensuring they're MenuGroup, etc.)
2. Flagging wrong direct children (like divs) 
3. Handling fragments as direct children

However, the complexity increases significantly with render props, especially when they return custom components like `BlockSwitcherDropdownMenuContents`. Even when these components are defined in the same file, linting across component boundaries becomes challenging. And if the component resides in another file, it becomes even more difficult for the linter to determine what a custom component actually returns.

Given these challenges, I believe I can fix the two incorrect implementations by raising a PR rather than attempting to create an exhaustive linting rule that may be difficult to maintain. 

This can be fixed by removing the top level div and i don't think it would create any drastic visual difference.
