# Issue #45949: `NumberControl`: introduce `string` as a type for the `value` prop

- URL: https://github.com/WordPress/gutenberg/issues/45949
- Author: ciampo
- Created: 2022-11-21T16:57:10Z
- Updated: 2022-11-26T14:48:25Z
- Comments: 0 of 0

## Body

The `value` prop in `NumberControl` hasn't been yet typed, since it sits in a difficult spot: should it be a `number` or a `string` ?

After debating, we reached the conclusion that it should be a `string`:

- native HTML `input` elements deal with strings, afterall;
- controlled components usually pass `''` to represent an empty value (they can't pass `undefined`, since that would make the component uncontrolled).

Since currently `NumberControl`'s `value` is typed as `number | string`, here's the plan of action:
- [x] Wrap up TypeScript migration of stories and tests (https://github.com/WordPress/gutenberg/pull/45990)
- [ ] Rewrite the internals in `NumberControl` to remove as much as possible the duality of the `number|string` types, and instead assume  that `string` will be the main type (https://github.com/WordPress/gutenberg/pull/45982)
  - [ ] In the process, we may want to extract some basic utilities outside of each single components (number to string / string to number conversions), and move them to the shared `utils` folder. 
  - [ ] If needed, add unit tests to make sure that both `string` and `number` values for the `value` prop are handled correctly
- [ ] Find and update all derived components to use `string` instead of `number`. If possible, keep iterating up the chain of derived components, until only `string` is used
  - [ ] `UnitControl`
  - [ ] `RangeControl`
  - [ ] `AnglePickerControl`
  - [ ] ...
- [ ] When all usages are migrated to `string`, deprecated the `number` type for `value` — starting from the "leaves" derived components, and walking backwards all the way towards `NumberControl`. The code handling the `number` case will left around for backward-compat.
