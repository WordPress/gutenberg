## Body

## What?

Fixes #69252

## Why?

`FormTokenField` with `__experimentalValidateInput` and `tokenizeOnSpace` has two bugs:

1. **Space key always prevented:** When typing a value that fails validation and pressing space, `addCurrentToken()` sets `preventDefault = true` *before* knowing whether `addNewToken()` succeeded. This prevents the space character from being typed into the input, making it impossible to type multi-word values that don't yet pass validation.

2. **Paste bypasses validation:** When pasting comma/space-separated values, `addNewTokens()` (called via `onInputChangeHandler`) never runs tokens through `__experimentalValidateInput`, allowing invalid tokens to be added.

## How?

- `addNewToken()` now returns `boolean` (`true` on success, `false` on validation failure)
- `addCurrentToken()` uses the return value to decide `preventDefault` for typed input (selected suggestions still always prevent default)
- `addNewTokens()` filters tokens through `__experimentalValidateInput`

## Testing Instructions

1. Render a `FormTokenField` with `tokenizeOnSpace` and `__experimentalValidateInput={ (v) => /^[A-Z]/.test(v) }`
2. Type `hello ` (lowercase, space) → the space should appear in the input (not tokenized)
3. Type `Hello ` (uppercase, space) → should create a "Hello" token
4. Type `Apple,banana,Cherry,` → only "Apple" and "Cherry" should be added as tokens

### Testing Instructions for Keyboard

- Verify space key types normally when validation fails with `tokenizeOnSpace`
- Verify Enter key still works for valid tokens
- Verify comma key still prevents default (comma is always a separator)

This PR introduces a regression: `addCurrentToken()` no longer prevents default on failed validation

When `__experimentalValidateInput` rejects the token, `addNewToken()` now returns `false`, so `preventDefault` becomes `false` for **both** keys:

- Space: correct — the space character should be typed into the input.
- Enter: regression — Enter's default browser action (e.g., submitting a parent `<form>`) is no longer prevented. The current trunk behavior is to silently swallow Enter when validation fails, which is the expected UX.

As a potential way to get around it, make `addCurrentToken()` aware of whether the caller wants default prevented on failed validation:

<details>
<summary>Implementation</summary>

```tsx
function addCurrentToken( {
    preventDefaultOnFailedValidation = true,
} = {} ): boolean {
    let preventDefault = false;
    const selectedSuggestion = getSelectedSuggestion();

    if ( selectedSuggestion ) {
        addNewToken( selectedSuggestion );
        preventDefault = true;
    } else if ( inputHasValidValue() ) {
        const wasAdded = addNewToken( incompleteTokenValue );
        preventDefault = wasAdded || preventDefaultOnFailedValidation;
    }

    return preventDefault;
}
```

Then in `onKeyDown`:

```tsx
case 'Enter':
    preventDefault = addCurrentToken();
    break;
// ...
case 'Space':
    if ( tokenizeOnSpace ) {
        preventDefault = addCurrentToken( {
            preventDefaultOnFailedValidation: false,
        } );
    }
    break;
```

</details>


We should also consider adding a test that proves this regression, and then confirms it's been fixed:
- test should pass on `trunk`
- test should fail on the current version of the PR
- test should pass again once the regression is fixed in the PR

While reviewing again, I realized there are two small problems with the current rejoin behavior, and I think we can add a fix that addresses both at once. I asked an AI agent to explain the issue and the proposed fix eloquently.

### Problem A — separator normalization is lossy

```tsx
const separatorChar = tokenizeOnSpace ? ' ' : ',';
const remaining = [ ...failedTokens, tokenValue ].join( separatorChar );
```

Under `tokenizeOnSpace`, the split regex is `/[ ,\t]+/` (commas still split items), but the rejoin always uses space. So if the user pastes `Apple,banana,Cherry,` into a `tokenizeOnSpace` field, they get `banana ` back — the user value was modified, and the commas turned into spaces, which is unexpected.

Comma is a valid separator in **both** modes, so rejoining with `,` unconditionally avoids the rewrite without breaking either mode.

### Problem B — `tokenValue` mixed with `failedTokens` blocks recovery

When the paste has no trailing separator, the trailing segment is treated as in-progress and rejoined alongside the failed segments. Assuming the custom validation requires tokens to start with a capital letter, when the user pastes `Apple,banana,Cherry`:

- `Apple` is added, `banana` is rejected, `Cherry` is held back as in-progress.
- Rejoin produces `'banana,Cherry'` in the input.
- Pressing comma now calls `handleCommaKey` → `addNewToken('banana,Cherry')` — i.e., it tries to tokenize the **whole string with the comma in it** as one token, which the validator rejects. Same dead-end on Enter.
- The user has to manually delete the comma or fix `banana` first before they can recover.

Better behavior: when there are upstream failures, also commit the trailing in-progress segment (if it would pass validation). The user is then left with only the rejected items, separated by commas, and can fix them in place. For `Apple,banana,Cherry` they'd see `Apple` and `Cherry` as tokens and just `banana` in the input.

### Suggested change

A precheck lets us decide whether to include `tokenValue` in the single `addNewTokens` call (calling it twice in the same handler would be unsafe — `addNewTokens` reads `value` from closure, so a second call would see stale state and overwrite the first call's `onChange`).
