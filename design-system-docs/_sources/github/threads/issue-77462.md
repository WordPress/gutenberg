## Body

Stabilization review of `@wordpress/theme`, aggregating the original assessment with a fresh validation pass against the current source (v0.13.0). Items shipped since the first pass are listed as done.

## Done

- [x] **I4** — Refactor color-space registration to avoid module-level side effects ([#77653](https://github.com/WordPress/gutenberg/pull/77653)).
- [x] **A6 (parsing)** — Throw a clear error when the seed color is unparseable ([#77653](https://github.com/WordPress/gutenberg/pull/77653)).
- [x] **T-M1** — Add `--wpds-motion-duration-*` and `--wpds-motion-easing-*` tokens ([#76097](https://github.com/WordPress/gutenberg/pull/76097)).

## Bugs

- [x] **B3** — Static legacy overrides can move out of the provider. `legacyWpComponentsOverridesCSS` contains only `var(...)` references; emit it once at `:root` in the prebuilt CSS. `legacyWpAdminThemeOverridesCSS` should only be emitted when `color.primary` is user-provided (WP Core already provides the defaults). https://github.com/WordPress/gutenberg/pull/78664
- [x] **B4** — Deduplicate `addFallbackToVar` between `postcss-plugins/add-fallback-to-var.ts` and `postcss-plugins/ds-token-fallbacks.mjs`. https://github.com/WordPress/gutenberg/pull/78666

## API design

- [x] **A1 + A2** — Make `ThemeProvider` a public runtime export. Drop the type-only re-export from `index.ts`, remove `ThemeProvider` from `privateApis`, and migrate consumers in `packages/boot` and `packages/ui/**/popup.tsx` off `unlock( themePrivateApis ).ThemeProvider`. `useThemeProviderStyles` can remain private. https://github.com/WordPress/gutenberg/pull/78958
- [x] **A5** — Asymmetric tone coverage: `caution` only has `surface*` / `fgSurface*` entries while other status tones have `stroke*` entries. Either add `--wpds-color-stroke-surface-caution(-strong)` or document the intentional asymmetry. https://github.com/WordPress/gutenberg/pull/79198
- [x] **A6 (contract)** — Tighten the documented input contract for `color.primary` / `color.bg` (currently "hex, `rgb(...)`, or CSS color keyword") to match the runtime, or relax the docs. Today the runtime accepts anything parseable in sRGB. https://github.com/WordPress/gutenberg/pull/79148
- [x] **A7** — Review React peer dep range (`react: ^18.0.0`) for React 19 compatibility before stabilizing. (**Update:** https://github.com/WordPress/gutenberg/issues/77462#issuecomment-4615105300)
- [x] `ThemeProvider`: Rename `color.bg` to `color.background` https://github.com/WordPress/gutenberg/pull/79007

## Architecture and implementation

- [x] **I2** — Set custom properties via inline `style` on the wrapper instead of injecting a per-instance `<style>` element. Removes the doubled-class specificity hack, removes the `<style>` element in the common case, and removes one DOM node per provider. For `isRoot`, write to `document.documentElement.style` in a `useLayoutEffect` with cleanup — no need for `:root:has(...)`. https://github.com/WordPress/gutenberg/pull/78678
- [x] **I3** — Don't serialize `data-wpds-root-provider=\"false\"` on every non-root provider. Use `data-wpds-root-provider={ isRoot || undefined }` (or drop the attribute altogether after **I2**). https://github.com/WordPress/gutenberg/pull/79253
- [x] **I5** — Document the memoization contract for `getCachedBgRamp` / `getCachedAccentRamp`. `buildAccentRamp(seed, bgRamp)` keys on both arguments and relies on the upstream `bgRamp` memo to keep references stable. Worth a comment near the cache declarations. https://github.com/WordPress/gutenberg/pull/79459

## Description

Issue-style stabilization list for `@wordpress/theme`, focused on the remaining work before the package can be marked stable. Items are grouped by category and ordered roughly by priority within each category.

Priority key:

- **Block stabilization** — Should be fixed before marking the package stable.
- **High** — Should be fixed soon; likely to affect consumers or the public contract.
- **Medium** — Important polish or contract clarification.
- **Low** — Cleanup, docs, or follow-up hardening.

## Package boundary and publishing

- [x] **P1 — Block stabilization — Protect the public CSS import from tree-shaking.** `package.json` currently has `"sideEffects": false`, but the documented `import '@wordpress/theme/design-tokens.css'` is a side-effect import. Change `sideEffects` to include CSS files, ideally with an explicit allowlist such as `"*.css"` / `"**/*.css"` or the exact published CSS paths. https://github.com/WordPress/gutenberg/pull/79551

- [ ] **P2 — Block stabilization — Clean the npm publish surface.** `npm pack --dry-run` currently includes tests, stories, fixtures, snapshots, and declarations for internals. Narrow `files`, exclude test/story declaration output, and keep only intentional public artifacts in the package. https://github.com/WordPress/gutenberg/pull/79552

- [ ] **P3 — Block stabilization — Verify every exported type path exists.** Some package export `types` entries point to `.d.ts` files while this checkout generates `.d.mts` files. Align `package.json` with the actual publish output and add a package validation check for all `exports` targets. https://github.com/WordPress/gutenberg/pull/79553

- [ ] **P4 — Medium — Document raw token JSON as internal.** Raw token JSON intentionally mixes primitive/internal tokens with semantic/public tokens, so it should not be treated as a public API. Keep `tokens/*.json` unpublished/unexported, and document CSS custom properties plus generated runtime metadata as the public token surfaces.

- [ ] **P5 — Medium — Prefer public subpath imports internally.** Replace internal imports such as `@wordpress/theme/src/prebuilt/css/design-tokens.css` with the public `@wordpress/theme/design-tokens.css` where possible, so the repo reinforces the stable API boundary.

- [ ] **P6 — Medium — Add `npm pack --dry-run` to release/package verification.** Treat package contents as a release gate: no tests, stories, snapshots, accidental internals, or missing export targets.

- [ ] **P7 — Low — Update package metadata.** Consider package keywords that reflect the stable purpose: design system, design tokens, theme, WordPress.

## API design

- [ ] **A1 — Block stabilization — Make the public API boundary explicit in documentation.** Document which root exports and subpath exports are semver-protected, and which files are generated implementation details. Do not add standalone type exports just for `ThemeProviderProps` / `ThemeProviderSettings`; Gutenberg packages generally do not expose component prop types as dedicated public exports.

- [ ] **A2 — High — Resolve the generated `Target` / `focus` documentation mismatch.** The docs treat focus like a target, but `--wpds-color-stroke-focus` sits outside the normal target grammar. Either document it as an exception or adjust the generated docs/model so the naming story is consistent.

- [ ] **A3 — Medium — Keep `ThemeProvider` wrapper customization out of scope.** Do not add `className`, `style`, `as`, `render`, or `ref` props unless there is a concrete use case. The wrapper uses `display: contents`, so exposing wrapper customization would create a misleading API.

- [ ] **A4 — High — Restrict custom seed colors to fully opaque colors.** Treat only fully opaque colors as supported for now. Reject alpha and `transparent` inputs in the runtime contract, update tests accordingly, and document the accepted syntax clearly.

## Runtime and implementation

- [ ] **I1 — Medium — Document the single-root-provider contract.** Multiple `isRoot` providers are already unsupported, with a dev warning and unit tests. Make that explicit in stable docs: render at most one root provider per document.

- [ ] **I2 — Low — Document the `:has()` root corner-radius implementation.** `:has()` is supported by evergreen browsers and is not a stabilization blocker. Keep the CSS implementation unless there is a non-browser-support reason to move it to JavaScript; document the implementation rationale if it remains split from color/cursor root forwarding.

- [ ] **I3 — High — Finish static legacy CSS variable migration.** Move static `--wp-components-*` aliases to generated root CSS if they are always default aliases. Emit `--wp-admin-theme-color*` only when `color.primary` is user-provided, unless every provider really needs to emit defaults.

- [ ] **I4 — Medium — Keep `display: contents` behavior covered by integration tests.** The provider wrapper should remain unfocusable. Maintain focus-trap and portal coverage in consuming UI components.

- [ ] **I5 — Low — Remove stale private API metadata.** `packages/private-apis/src/implementation.ts` still lists `@wordpress/theme` even though the package no longer appears to expose private APIs. Remove the stale allowlist entry if unused.

- [ ] **T1 — High — Include all intended Stylelint rules in the shared config.** `@wordpress/stylelint-config` includes `no-unknown-ds-tokens` and `no-setting-wpds-custom-properties`, but not `no-token-fallback-values`. “side effect” here was meant more in the bundler/tree-shaking sense, not in a strict sense that the CSS file runs JS.

With the help of an ai agent, here's a more eloquent explanation:

> `@wordpress/theme/design-tokens.css` does not expose a consumed JS export; importing it is intended to make the bundler emit/apply global CSS that defines the `--wpds-*` variables at `:root`. That is the observable effect of the import. Since the package currently has `"sideEffects": false`, bundlers that honor that metadata can consider CSS files safe to prune. Webpack’s docs explicitly recommend including CSS files in the `sideEffects` allowlist for this reason.

So my idea for the fix is to keep JS files tree-shakeable, but add `"sideEffects": [ "*.css" ]` or a narrower package-specific CSS path to mark CSS as side-effectful
