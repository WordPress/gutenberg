## Body

## What?
Refactors the ColorPicker component to preserve hue and saturation values when colors become achromatic (pure black, white, or grayscale).

## Why?
Fixes #47504 — Previously, when dragging the lightness slider to 0 (black) or 100 (white), the hue and saturation values would reset to 0, losing the user's selection. This made it frustrating to work with the HSL inputs.

## How?
- Lifts HSLA state from `HslInput` to the main `ColorPicker` component via a `mergeHSLA` utility that preserves hue for all achromatic colors, and saturation only at lightness extremes (black/white) where it has no visual effect
- Adds `lastProducedHexRef` to distinguish internal changes from external prop updates
- Switches the Picker from RGB to object-based HSL color pickers (`HslColorPicker`/`HslaColorPicker`), eliminating string conversion and regex parsing on every drag event
- Simplifies `HslInput` to be stateless (receives `hsla` prop directly)
- Routes HSL inputs through a dedicated `onHSLChange` handler that accepts the user's explicit HSLA values without merging, keeping the picker responsive at achromatic positions

## Testing Instructions
1. Open any block with a color picker (e.g., Heading block → Text color)
2. Switch to HSL input mode
3. Set a hue (e.g., 180) and saturation (e.g., 67)
4. Drag lightness to 0 (black) or 100 (white)
5. ✅ Hue and saturation should be preserved
6. Drag lightness back to 50
7. ✅ The original color should return
8. Set a chromatic color, then type a mid-gray hex (e.g., `808080`)
9. ✅ Saturation should reset to 0 (not preserve the stale value)

## E2E Tests
Added Playwright e2e tests (`test/e2e/specs/editor/various/color-picker-hsl.spec.js`) covering:
- Preserving hue/saturation when lightness is set to white (100)
- Preserving hue/saturation when lightness is set to black (0)
- Preserving hue/saturation across multiple achromatic round-trips

**Note on picker cursor behavior in HSL mode:** When the picker is in HSL mode and the color reaches pure black, the cursor can snap to the bottom-left corner. This doesn't occur in Hex or RGB modes. I explored switching from `HslColorPicker` to `HsvColorPicker` (both from react-colorful) to see if using the HSV picker's native HSVA internal state would avoid the snap — the theory being that it would skip the lossy HSL→HSV conversion that react-colorful performs internally. The HSV picker rendered the cursor outside the canvas, possibly due to differences in its internal coordinate mapping, so I reverted.

The snap is likely caused by react-colorful normalizing saturation to 0 during its internal HSL→HSV conversion at `v=0` (black). A potential fix could involve maintaining parallel HSVA state or patching react-colorful's conversion, but that may be out of scope for this PR. Open to suggestions if anyone has ideas.

The achromatic handling is preserving the previous saturation whenever `externalHSLA.s === 0`. For non-black/white grays (e.g. `#808080`), forcing `s` back to a non-zero previous value makes `internalHSLA` represent a *chromatic* color, so the picker/HSL inputs can display a tinted color that does not match the incoming hex prop.

Consider only preserving `h` (not `s`) when `s === 0`, or preserving `s` only in the special cases where saturation cannot affect output (e.g. `l === 0` or `l === 100`).
```suggestion
			// Achromatic — preserve the user's hue, and only preserve
			// saturation when it cannot affect the rendered color
			// (pure black or pure white). For other grays, keep s = 0
			// so internalHSLA matches the incoming color.
			setInternalHSLA( ( prev ) => {
				const shouldPreserveS =
					externalHSLA.l === 0 || externalHSLA.l === 100;
				return {
					...externalHSLA,
					h: prev.h,
					s: shouldPreserveS ? prev.s : externalHSLA.s,
```
