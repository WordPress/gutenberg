## Body

Unification of both `SlotFill` registries (context providers) into one that handles both types. The two types of `Slot` are distinguished by a `type: 'children'` or `type: 'portal'` field.

Also the `Fill` component is now only one. It looks at the type of the currently registered slot and conditionally renders a portal.

Only the `Slot` components remain separate for now, because their implementation and even the prop types are wildly different.

This is still a draft, to verify how unit and e2e tests are going.

@ciampo Yes please, I believe the PR is ready, I just did not yet get to write some detailed description and comments. If you can make sense of the rather big diff, please go ahead.

The idea is to merge both registries/providers into one, with records discriminated by a `type: 'children' | 'portal'` field. I decided to name the types as children/portal internally, because that IMO makes more sense than "bubbles virtually". `children` slot/fills work by saving the `children` JSX markup to a registry in fill, and rendering the markup in slot. `portal` slot/fills work by creating a portal element in the slot, and then rendering a portal markup in the fill.

The `Fill` component is also unified into one. The old `Fill` always rendered both sub-`Fills` next to each other, so the unification is straightforward.

The `Slot` unification is harder, and I'm not doing it here. The problem is mainly with types, and they differ rather radically between the two types.

The only major issue was with the `useSlotFills` hook, because it started causing infinite loops. There is a new unit test for that that creates a loopy situation and verifies that the loop doesn't happen. The loop happens when:
1. `Fill` (of `children` type) registers `children` markup.
2. That triggers `useSlotFills` rerender because a new fill was added.
3. `useSlotFills` rerender triggers a rerender of `Fill`, and the component has a new `children` prop.
4. That prop is updated in the registry, triggering a `useSlotFills` rerender again.

Previously it didn't happen because the `useSlotFills` hook listened only to the "bubbles virtually" registry, while the `children` update updated only the "base" registry. The events didn't meet. But now they both happen in the same registry.

I fixed that by creating a `useObservableValueWithSelector` hooks that triggers a rerender only when the fills array length changes.

Thanks, I was able to reproduce and found the cause. It's not `SlotFill` at all, but a subtle change in how `@wordpress/data` works with the `isFullfilled` callback for resolvers.

The breaking change is #70806. The Jetpack `getVideo` resolver has an `isFulfilled` callback that detects a placeholder video ID and does no resolution in that case:

https://github.com/Automattic/jetpack/blob/trunk/projects/packages/videopress/src/client/state/resolvers.js#L176-L194

The difference is that before #70806 the `isFulfilled` callback was checked before dispatching `startResolution` and `finishResolution`. No state update at all was done when `isFulfilled` returned `true`.

Now even the `isFulfilled() === true` case is wrapped with `start/finishResolution`. The reason is to signal to `resolveSelect` that the resolution has started and finished. And for consistency with other resolvers: now all calls to resolving selectors will dispatch these actions, no matter what is the internal implementation.

This all means that the rendering loop I described in https://github.com/WordPress/gutenberg/pull/68056#discussion_r3180796646 gets triggered. Individual `getVideo` causes a state update, and it also triggers a re-render of the parent that uses `useDashboardVideos`, namely the `isFetching` flag. Because even placeholder videos are now "fetching".

FYI @Mamaduka who was also involved in #70806. Maybe we could partially revert the PR, if we find another solution to the `resolveSelect` problem? Maybe the `resolveSelect` implementation could call `isFulfilled` and return early?

One downside of #70806 is that `isFulfilled` is now quite redundant. Exactly the same result can be achieved by doing the check inside the resolver function itself, and do nothing at all if the condition matches. The function of `isFulfilled` used to be that it avoided the `start`/`finishResolution` and `isFetching` machinery completely.
