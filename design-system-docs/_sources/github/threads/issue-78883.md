# Issue #78883: `@wordpress/ui` Button lacks distinct `:active` (pressed) styling

- URL: https://github.com/WordPress/gutenberg/issues/78883
- Author: jameskoster
- Created: 2026-06-02T14:14:02Z
- Updated: 2026-06-09T09:40:07Z
- Comments: 6 of 6

## Body

The `@wordpress/ui` `Button` component does not provide visual feedback specific to the pressed state. `:hover`, `:active`, and `:focus` all share the same styles, so clicking a button looks the same as hovering it. There is no clear “pressed” moment before the click completes.

## Current behavior

In `packages/ui/src/button/style.module.css`, interactive states are grouped:

```css
&:not([data-disabled]):is(:hover, :active, :focus) {
	background-color: var(--wp-ui-button-background-color-active);
	color: var(--wp-ui-button-foreground-color-active);
	border-color: var(--wp-ui-button-border-color-active);
}
```

The `-active` custom properties map to design tokens whose descriptions also combine hover, focus, and pressed (e.g. `--wpds-color-bg-interactive-brand-strong-active`: “hovered, focused, or active”). So the component and tokens treat “active” as one state, not a separate pressed state.

In Storybook, click and hold a button: it should look different from hover alone, but today it does not.

## Why this matters

1. Buttons should respond at the moment of interaction, not only on hover. Without distinct `:active` styling, clicks can feel unresponsive, especially on touch devices where hover is absent and press is the main cue.
2. Hover is exploratory (“what happens if I click?”). Press is commitment (“I am clicking now”). Using the same styles for both removes an important layer of feedback and makes the UI feel flat.
3. The legacy `Button` in `@wordpress/components` does distinguish `:active` from `:hover` — for example, primary buttons use a darker background on press (`$components-color-accent-darker-20`) than on hover (`$components-color-accent-darker-10`). As `@wordpress/ui` replaces `@wordpress/components`, we risk regressing a behavior users already expect.
4. Gutenberg relies heavily on buttons in toolbars, inspectors, and dialogs. In those contexts, subtle but reliable press feedback helps users trust that their action registered. Especially for icon-only and compact buttons where color change alone may be hard to notice.
5. The token docs define an `active` state as “hovered, pressed, or selected.” That works for token naming, but components still need to decide how to map CSS pseudo-classes. `Button` currently collapses them entirely; we should decide intentionally whether pressed needs its own token(s), or some other treatment.

## Possible directions
* Add new color tokens and mimic `Button` in `@wordpress/components`.
  * If we do this we should ensure all button variants include `:active` styles that differ from hover and focus.
* A non-color based approach, e.g. a subtle scale animation.
* Something else?

Thanks for the ping. I like the effectm and also, thanks for the outstanding contribution and easily reviewable videos!

However I don't think we should land that effect unless we have a clear plan for _motion_ in general. Although innocent looking, it feels important to have some grounding principles for how this world behavies. I mean that almost literally: what is the button made of, can it fold, whats its weight, where is the light source coming from? It sounds extreme for a few lines of CSS, but the principle is important mostly because of the knock-on effects: 

* What about radios, checkmarks, sliders? 
* How about secondary, tertiary buttons, segmented controls? 
* How about inputs, should they move?
* If we were to make a marketing video of this, exploding the DOM into a 3D view as shown from the side with elevation, how would the button behave in that space, when pressed?

To be clear: this feedback is not blocking towards the idea that our componentry gets exactly this physicality, as I said I like it. But I'd love to see a much broader exploration that answers these questions in a bit more of a holistic way. We might find the answer really compelling, and then we can apply it across the range of the componentry.

_For the near term_, I think we can augment the active state with a slightly darker color, if need be. What does tokens offer us here?

To keep the initial token count relatively small we opted for a single token shared across hover, active, and focus states. Matching the existing design would mean adding a new set of tokens, so ideally we do that only if we're confident it's the right design long-term. Otherwise we risk polluting the system with a bunch of confusing superfluous tokens.
