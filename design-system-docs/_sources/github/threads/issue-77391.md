# Issue #77391: UI: Add truncation support to Text component

- URL: https://github.com/WordPress/gutenberg/issues/77391

- Updated: 2026-06-23T07:24:08Z

## Body

## What problem does this address?

The `@wordpress/ui` `Text` component doesn't provide any built-in support for truncation behavior, requiring developers to implement this themselves (e.g. #77012, #77372). From a design system perspective, we should seek to ensure consistency and provide baseline support for how content is truncated.

## What is your proposed solution?

Add props for:

- Enabling truncation (e.g. `truncate`, a `boolean`)
- Controlling number of lines (e.g. `numberOfLines` or `lineClamp`, a number)

In adding support, we should also remove existing workarounds, like those in the pull requests referenced above (#77012, #77372).

We should be careful to consider scope creep and what's minimally necessary to provide baseline functionality and consistency for such a low-level component.

For background, the `@wordpress/components` `Text` component composes options from the `Truncate` component, which provides a lot of control over specific truncation behavior ([ellipsis string, trimming behavior, character limit, line limit](https://github.com/WordPress/gutenberg/blob/c08f001fcd657b1299501177e8b3a8a0d49d50af/packages/components/src/truncate/types.ts#L13-L57)). Many of these are rarely (or never, in the case of `ellipsis`) used, and arguably could be counter-productive to the design system's intent of providing consistency.

`truncate` and `numberOfLines` are the most regularly used options today. Other component libraries like [Chakra UI's `Text` component](https://chakra-ui.com/docs/components/text#truncation) provide exactly this amount of customization as well.

**Open question:** Is this a good enough combination of (a) being commonly used, (b) being difficult to implement without, and (c) prone to being implemented inconsistency, in order to warrant the maintenance cost and scope inflation to implement baseline support?

I was looking into implementing this, but came to the conclusion that we probably don't need it 🤔

Here are the props for the current `Truncate` component in `@wordpress/components`:

- `ellipsis` (default: `…`) — It's unlikely that anything else should be used.
- `ellipsizeMode` (default: trims at the end) — There's no evidence in the repo that anyone ever wants to trim at the beginning or the middle.
- `limit` (default: `0`) — Max number of characters to display. We shouldn't be using this anyway because "number of characters" is not a useful way to think in multilingual apps.
- `numberOfLines` (default: `0`) — Fair, but only two instances in the repo are actually setting a line limit other than 1.

So basically what our redesigned `Truncate` component would look like is a utility for the standard `text-overflow: ellipsis`/`overflow: hidden`/`white-space: nowrap` combo. And _maybe_ a utility for `-webkit-line-clamp`, which is a bit more complicated, but the need for multiline clamping is rather rare.

All in all, since there are no real consistency concerns here, and the styling is pretty straightforward, I would lean towards recommending CSS. Perhaps we could have a doc page on truncation styles with code snippets, but given that it will just be a generic set of snippets, it's possibly unnecessary now that agents can simply generate them when prompted.

### mirka on 2026-06-23T07:24:08Z

URL: https://github.com/WordPress/gutenberg/issues/77391#issuecomment-4776749693

After an in-person chat with @joedolson, I have some updated thoughts about our strategy here.

To recap his guidance:

- Should we truncate _every_ overflowing string by default? No. (For example, control labels like in buttons are important and would be better shown in its entirety.)
- Should we add tap stops to _every_ truncated string so the full string can be accessed? No. (Tab stops are not free — they definitely add cost to the user experience, so they should be used judiciously.)
- Middle truncation (not head or tail) is likely going to be the most useful for arbitrary long strings like filenames or paths.

Which for me, basically boils down to: There's no easy global rule we can apply to everything — each individual case needs to be evaluated from a design standpoint. The best we can do as a design system here is to have good documented guidance, and provide any necessary tools.

And speaking of necessary tools, the importance of middle truncation suggests that we do in fact need a `Truncation` component, since it's not something that can be done by a CSS snippet.
