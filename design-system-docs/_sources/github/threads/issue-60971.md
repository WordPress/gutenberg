### ciampo on 2024-12-08T07:41:37Z

URL: https://github.com/WordPress/gutenberg/issues/60971#issuecomment-2525470816

I had a chat with @jameskoster on this topic, here are some notes:

- of the spec [above](https://github.com/WordPress/gutenberg/issues/60971#issuecomment-2374037583), two components are higher priority than others — the ones used in the "Simple date range with calendar UI" scenario
  - a "datetime input" component, that uses a native `input[type="datetime-local"]` element under the hood
  - a calendar UI that shows 2 months side-to-side and allows for date range selection

The rest of the componentry (presets dropdown, combo dialog UI) is not a high priority and can — for the time being — be implemented directly where the components are used.

Regarding how we can add these components to the `@wordpress/components` package, I see two approaches: we could try to retro-fit as much as possible of the new componentry into the existing components (for example, the "datetime input" could be a new version of `TimePicker`, and we could add support for date range in the existing `DatePicker` calendar UI?), or we could consider creating a new version of date time components — more modular and supporting date range picking.

Personally, I like the idea of rethinking the date/time family of components in a way that is more modular and takes range into account from the start, removing any coupling from the WordPress settings (present in the current `TimePicker` component).

@WordPress/gutenberg-components , do you have any thoughts/preferences ?

### ciampo on 2024-12-11T06:25:07Z

URL: https://github.com/WordPress/gutenberg/issues/60971#issuecomment-2533742177

After a chat with @mirka , this is a potential plan:

- For the "datetime input", folks can use `<InputControl type="datetime-local" />` to display a native [date time picker](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/input/datetime-local); it should allow passing attributes like `min`, `max`, `step`. We'd obviously need to do some testing to make sure it covers all usages needs, and we will need to look into how to best tweak its appearance to ensure it adheres to the proposed design across all browsers (the least changes needed, the better);
- For the calendar UI, although we currently have `DatePicker`, we're considering the creation of a new `Calendar` component in the `@wordpress/components` package that would start as a private component and will eventually replace `DatePicker`. The component could support both single date and date range picking (which could be determined by the type of `value` passed to the component, ie. a single string vs an array), and allow its consumers to specify how many months are shown, their orientation (horizontal vs vertical), etc.
- For the "Presets only" scenario, we're not sure that `menu` semantics are the right choice — the user is not picking from a set of actions of functions, but rather choosing a value from a list of options. In that sense, `listbox`  semantics may be a better fit, which means using `SelectControl` / `CustomSelectControl`
- In general, we expect consumers of the components to compose the individual components and implement the necessary coordination between them on their end — meaning that we don't plan on creating specific components targeting scenarios liks "Simple date range" or "Simple date range with calendar UI"
- For the most complex scenarios (the "Combo" ones), consumers of the package would need to implement a custom `dialog` popover (using, for example, `Button` and `Popover` components), including an inline listbox for the presets (TBD how exactly to implement that), two instances of `<InputControl type="datetime-local" />` and a `Calendar` component
