## Body

## What?

Updates Storybook configuration to include the base design system styles automatically in Storybook stories for `@wordpress/ui` components.

## Why?

Improves developer experience and reduces likelihood for error, so that they don't need to be imported in individual stories.

## How?

Augments existing `WithRTL` lazy-loaded styles Storybook decorator to include UI component dependencies stylesheet containing tokens.

### jsnajdr on 2025-12-15T08:21:42Z

URL: https://github.com/WordPress/gutenberg/pull/73938#issuecomment-3654370434

Currently our UI components rely on someone else (theme) defining the design system CSS variables like `--wpds-dimension-base`. There is no fallback, the value will remain undefined if the CSS variables are not defined. The `theme` package has the `design-system.css` stylesheet that provides these variables.

The typical usage of the UI components will be inside some WordPress plugin, where your code lives in an environment that's been already set up. In the Gutenberg editor, in WP Admin. Only in usage outside WP you need to worry about including the `design-system.css` stylesheet yourself.

Trying to automagically include the stylesheet whenever you use an UI component can introduce some dangerous footguns:
1. A React app doesn't own the entire DOM document, it's mounted in some root element. And there can be multiple apps running inside one document, peacefully, without really knowing about each other. If we append any stylesheet at all, it shouldn't be scoped to the entire document (`:root`), but only to the React root.
2. The `ui` package is designed to be bundled. On any page, there will be several copies. If all of these bundled copies have their own "ensure that the default styles are added" code, that's an unnecessary bloat.
3. The `ui` package can be bundled in several different versions on the same page. If each of them tries to ensure that a default stylesheet is present, how does that work? Will we end up with multiple different stylesheets? Or which one wins?

### jsnajdr on 2025-12-15T18:13:48Z

URL: https://github.com/WordPress/gutenberg/pull/73938#issuecomment-3656972836

> all of those comments apply to how we're injecting styles for components as well?

Component styles are typically CSS modules. Although they are injected in global scope, the CSS classes are uniquely mangled and don't conflict with each other. Version A of the component brings A-hashed styles, version B brings B-hashed styles. The hash is computed from the stylesheet content, so if you change anything in the content, there is a new hash. The styles share the same namespace, but don't know about each other.

The deduplication also relies on these hashes. The `<style data-wp-hash>` element is inserted only if the same `data.wpHash` style is not present.

The design token CSS variables are different, they are global. Versions A and B of the `ui` package would want to set a different set of global variables, and that's a conflict that needs to be resolved somehow, or prevented. That's why I think it's better to separate the CSS variables from the `ui` package and reserve them only for the `theme` package.

> What would be your proposed path forward?

One good way to provide defaults in an encapsulated way is a post-processing step that adds a fallback to every token usage. Transpile `var( --wpds-color-bg-interactive-brand-strong )` into `var( --wpds-color-bg-interactive-brand-strong, #3858e9 )`. This way, if you don't have the default stylesheet, the default styles are still there. The defaults are encapsulated and they don't leak into any global scope. And they are space-efficient, the fallback value is usually small.

### aduth on 2025-12-30T13:50:37Z

URL: https://github.com/WordPress/gutenberg/pull/73938#issuecomment-3699409936

> Is listing `@wordpress/theme` as a `devDependency` in `package.json` the best way to reflect the relationship between the two packages? Would it make more sense to mark it a (non-dev) dependency?

In the strict sense, it is a `devDepenency`, as there's nothing in `@wordpress/ui`'s runtime code that actually depends on `@wordpress/theme`. 

But I hear what you're saying since it's effectively an implied dependency that someone makes the theme tokens available. Making it a `dependency` could prevent some people from having to install it themselves since it'd be installed alongside `@wordpress/ui`, but that's kinda an abuse of transitive dependencies that won't work everywhere (e.g. [pnpm's module isolation](https://pnpm.io/blog/2020/05/27/flat-node-modules-is-not-the-only-way)). It's better that it be an explicit dependency of one's own project if we're expecting them to include an import statement to `@wordpress/theme` somewhere in their code. 

What might make more sense is to mark it as a `peerDependency`, although even then I'm not sure it necessary makes sense to do, since a lot of (most?) projects may be expecting their components to be used in a WordPress context and not need to manage `@wordpress/theme` themselves.
