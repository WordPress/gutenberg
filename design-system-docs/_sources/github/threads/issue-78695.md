# Issue #78695: UI: Consider nesting CSS layers

- URL: https://github.com/WordPress/gutenberg/issues/78695
- Author: mirka
- Created: 2026-05-26T19:09:22Z
- Updated: 2026-06-09T19:41:46Z
- Comments: 3 of 3

## Body

## Problem

Consumers of `@wordpress/ui` will generally not need to explicitly place wp-ui CSS layers in their app's layering order. 

But if they do want or need to do that, they would have to place all four of our internal layers in the correct order. This is fragile and prone to drift.

## Proposed fix

One way to mitigate that would be to _nest_ the layers on our end.

So what currently looks like this:

```css
@layer wp-ui-utilities, wp-ui-components, wp-ui-compositions, wp-ui-overrides;

@layer wp-ui-components {
  /* the styles */
}
```

Would be nested like this:


```css
@layer wp-ui {
  @layer utilities, components, compositions, overrides;

  @layer components {
    /* the styles */
  }
}
```

This way, a consumer that really wants to explicitly interleave wp-ui layers with their own would only have to place the `wp-ui` layer name. And it will also make it harder for consumers to accidentally place just the `wp-ui-components` layer thinking it's the entire wp-ui layer stack (actually happened [here](https://github.com/Automattic/wp-calypso/pull/110579/changes#r3306119318)).

## Issue comments

### aduth on 2026-05-27T19:00:17Z

URL: https://github.com/WordPress/gutenberg/issues/78695#issuecomment-4557744542

This seems like it'd address a number of problems with little-to-no downsides I can think of.

- No top-level ordering means that a downstream project can easily define their own order relative to the design system's own styling, with a single reference to the design system cascade order
   - This is also better than the current scenario because we wouldn't define a default order. Since the spec prevents reordering layers, it's not currently possible for downstream projects to define the order of design system cascade order, because the order is already defined.
- And in doing so it removes any risk that they'd make a mistake in the intended order of the design system layers
    - And also allows us to add additional layers in the future if needed without risk for breaking existing layer ordering
- It doesn't prevent downstream styles from adding to the existing layers (questionable whether this is desirable, but it's a feature that exists today and would continue to work)

Potential downsides to consider:

- Backwards-compatibility for existing usage: This would only really affect a project if it's already trying to define layer ordering, or inject styles into the design system layers. Both of which would be pretty rare. And in fact, I don't know that projects defining design system cascade in their own layer reordering would even work anyways, since layer orders can't be changed (per spec). 

Seems like a net-win to me.

### mirka on 2026-05-28T20:10:38Z

URL: https://github.com/WordPress/gutenberg/issues/78695#issuecomment-4567809293

> Although if we are reevaluating the CSS cascade, it might be worth revisiting whether to use cascade layers at all.

My current understanding is that we kind of do need to use layers, if we're going to be continuing the runtime style injection strategy of appending style tags to `head`. If we had a stylesheet that consumers were supposed to load, then the consumer has control over the load order so they can make consumer stylesheets come later than the library stylesheet — no layers needed. But we don't, which means there's no way to control the order of the styles in the document.

In practice, that will almost always mean that library styles win (if consumer styles were in a normal stylesheet), or at best unpredictable (if consumer styles were also appended to `head` at runtime). So the consumer will be forced to artificially increase specificity for any style overrides that should've otherwise been straightforward.

This can already be observed in consumer override sites for Emotion components, which have a similar problem.
