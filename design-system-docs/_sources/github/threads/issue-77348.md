## Body

Related: #50459

## What problem does this address?

`@wordpress/ui` is meant to contain design system primitives for building interfaces. Increasingly this includes a cohesive set of overlay componentry built on BaseUI primitives. The use-cases for Menus are numerous, the goals of which have been outlined in earlier issues such as #50459.

A `Menu` component already exists as part of this previous work, but lives within `@wordpress/components`, and uses a different underlying technical architecture from how the rest of the design system is built.

## What is your proposed solution?

The existing `Menu` component should be adapted into `@wordpress/ui`. Much of the work here is already done and doesn't need to be started over, but migrating it to `@wordpress/ui` and adopting its conventions helps ensure a cohesive collection of UI components that work well together, which is particularly important for overlays components (see #76487). The foresight of the existing implementation to delegate the bulk of its internal implementation to underlying libraries like Ariakit should limit the scope of the effort.

Scope:

- Migrate `Menu` from `@wordpress/components` to `@wordpress/ui`
   - As a private component, I am expecting we should be able to remove the implementation from `@wordpress/components` as long as we update existing usage instances within Gutenberg
- Adapt component to adopt `@wordpress/ui` conventions:
   - Adopt BaseUI underlying components like [Menu](https://base-ui.com/react/components/menu)
   - Convert from Sass to CSS modules
