As discussed in [comment](https://github.com/WordPress/gutenberg/pull/37465/#issuecomment-1021217979) Introduce new prop to configure date format at the consumer end based on their requirements.


> It was also discussed that tying the date format (`DD-MM-YYYY` vs `MM-DD-YYYY`) to the time format (12 vs 24 hours) is not ideal — and I agree! I personally think that the two formats should be chosen and matched independently from each other.
> 
> So, what next?
> 
> We could remove the is12Hour check (similarly to what has been done so far in this PR) and introduce a new prop to allow consumers of the component to change the date format — although we'd first need to define a couple of things:
> 
> what would be the default date format? To this question, I'd argue that the default date format should be the same that is intended for the component to have by default today — which is `DD-MM-YYYY`
> what values should the new prop assume? This is the hard part. I believe that it would be wrong to assume that the only allowed values should be `DD-MM-YYYY` or `MM-DD-YYYY`(for example, what about `YYYY-MM-DD`). We should, therefore, probably have allow a set of possible values to choose from.
> A simpler approach would be to merge a quick fix in this PR (switch the logic of the is12Hour check), and tackle the additional of a new prop to format the date in a separate PR.

When discussing in #37465 around which values should this prop assume  one of the proposed solutions was to use [the PHP/WordPress syntax](https://wordpress.org/support/article/formatting-date-and-time/).

Here's my thoughts:

- While I see the advantages of using the same syntax, I think it would be best to use a formatting syntax that is more standard within the JS community and that aligns more closely with the technology that we're already using under the hood (currently [`moment.js`](https://momentjs.com/docs/#/displaying/), although there are lightweight alternatives using the same syntax, like [`day.js`](https://day.js.org/docs/en/display/format))
- most importantly, I don't think it makes much sense to allow for such a level of customization. The new prop would be used in the `DatePicker` / `DateTimePicker` component mainly to **change the order of the day / month / year inputs**. It wouldn't make much sense, in my opinion, to allow any further customisation than that.

In the light of the above, I propose this as the initial set of values for the new date format prop:

- `DD-MM-YYYY` (default value)
- `MM-DD-YYYY`
- `YYYY-MM-DD`

What do folks think?
