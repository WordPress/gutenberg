Fixes #70611. 

I haven't thoroughly tested every single full-screen modal but this doesn't seem to break the ones I looked at. Imo it's preferable for the solution to not require adding props to control modal height, or the components using the modal to add custom styles. If we can get away with fixing modal so its children can control their height, that's the most straightforward path.

This PR may affect some consumers using modal components.

For example, take a look at Font Library. Font Library has an absolutely positioned footer at the bottom and applies custom styles to `components-modal__content`, but these styles are overridden, causing some scrolling to break.

<img width="1405" height="742" alt="font-library" src="https://github.com/user-attachments/assets/332dda92-642a-423e-a010-5fb523671705" />

Look at the search results for WP directory: https://wpdirectory.net/search/01KBJ59HDJRNEMKNNFNCMKE7SP

For example, these styles exist:

```css
.rsssl-modal .components-modal__content{
  margin-top:45px;min-height:250px;padding:0
}
.yoast-gutenberg-modal__no-padding .components-modal__content{
  padding:0
}
```
I'm not sure if these modals are full-screen or not, but it's possible that styles like this could be overwritten unintentionally.

I can think of three approaches, any ideas?

1. `.components-modal__frame.is-full-screen .components-modal__content`: Reduce the specificity of this CSS by using a `:where clause`, etc.
2. Introduce a prop such as enableFullHeight to the Modal component without using CSS.
3. Maintain the current implementation, but publish a dev note for the 7.0 release
