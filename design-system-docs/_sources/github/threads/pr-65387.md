> > Ideally padding-right reduces to 4px when the suffix (> icon) is present. This will maintain alignment with trunk.

> Well, the icon is currently not part of the Tabs component itself, it's just part of its children. There's no trivial way to achieve this with the current setup, however we could consider adding support for this icon in the component itself, maybe as a prop of `Tabs.Tab` (e.g. `withArrow`), or as a more generic `icon` prop if we think it's worth it. If we do so, the dynamic padding is easier to implement and less messy. What do you think?

I personally like to keep separation of concerns — meaning that `Tabs` should only know about tab-specific things, and otherwise offer easy ways for its consumers to extend it.

The risk of adding an `icon` prop is that folks may start to want flexibility on where to render it, and so we could end up in a situation like `Button`, where we have an `icon` and `iconPosition` prop, and folks still sometimes just render a custom icon as part of `children`.

I have a couple of ideas:

### Adding a `suffix` prop

Maybe we could strive a good balance by adding a `suffix` prop:
- when such a prop is defined, the corresponding padding is not applied to the tab (maybe we could still make it available via a CSS prop, in case the consumer wants to apply that same padding);
- it allows consumers to extend `Tabs.Tab`, but at the same time it doesn't add a very specific prop (`icon`) and a ad-hoc layout rule (the different padding)

The consumer of `Tabs.Tab` could then also make their own reusable version which always shows a chevron and can be reused across their app.

### Adding a `showChevron` (name TBD) prop

This is a more specific alternative, but it still feels "generic" enough to `Tabs` functionality. We'd need to understand if that applies at all to the horizontal orientation too.
