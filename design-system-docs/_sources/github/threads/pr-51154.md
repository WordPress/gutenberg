## What?
<!-- In a few words, what is the PR actually doing? -->

Needs #51264 to be merged first.

This PR refactors usages of `DropdownMenu` and `Dropdown` across the repository, removing the need for passing explicitly the `variant: "toolbar"` prop — the components are expected to pick the correct visual variant automatically when rendered inside a `Toolbar`.

## Why?
<!-- Why is this PR necessary? What problem is it solving? Reference any existing previous issue(s) or PR(s), but please add a short summary here, too -->

For a few reasons:

- the components' [internal context system](https://github.com/WordPress/gutenberg/blob/trunk/packages/components/CONTRIBUTING.md#context-system) is designed to tackle this kind of necessity, where a component would react in different ways automatically based on the context it's rendered in
- using `popoverProps`  less explicitly allows for cleaner code. I also think that the requirement of "dropdown menus needing to render differently when in a toolbar" should not be achieved by expecting that the consumers of the component explicitly set a prop.

Most importantly, the new version of `DropdownMenu` that is in the works already relies on the components context system for switching visual style. Updating the "legacy" version of the component should ensure a smoother transition to the new component.

## How?
<!-- How is your PR addressing the issue at hand? What are the implementation details? -->

- The `Toolbar` component now uses the components context system to set a `variant` for `DropdownMenu` and `Dropdown` components.
- The `DropdownMenu` and `Dropdown` components now connect to the components context system, look for the `variant` property passed via context, and set it appropriately on the underlying `Popover` component
- Therefore, we can safely remove all of the instances where `variant: "toolbar"` is explicitly set in the block editor, since all dropdowns should now render with the correct style variation automatically.
- Finally, while in the process of removing `variant` props, I've also replaced instances of the `position` prop with the `placement` prop, since the `position` prop is gradually being phased out

@ciampo I pushed a commit that implements passing the components context to the Fill. How it works:
1. Slot is rendered with a `fillProps` value that is a list of context providers to use, with context values. The context values come from the Slot's component tree.
2. Fill reads the `fillProps` value and wraps the filled markup with it. Now the inner components see both the context from the Fill's component tree, and also the Slot's context that's been teleported there.

Here's the alignment matrix control with the correct dark border color: the `variant: 'toolbar'` value has really been teleported!

<img width="409" alt="Screenshot 2023-06-05 at 12 56 32" src="https://github.com/WordPress/gutenberg/assets/664258/d89912c6-0cf5-46b5-9457-c10bca38dcde">

Open problems:
- the context system is currently a private property of the `@wordpress/components` package, it's not exported in any way and invisible from outside. But I needed the `block-editor` to have access to it, because it's one of the contexts that the `BlockControl` fill and slot is configured to teleport.
- I'm exporting and using the raw `ComponentsContext` value. As opposed to the custom `ContextSystemProvider` component, which merges the contexts coming from the parent tree and the `value` prop and exposes the merged value downstream. That's probably the better option -- a task to do when polishing the patch for production.
