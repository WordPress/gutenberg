# Save & Submit

Guidelines for saving settings and submitting forms.

Editing a document, such as a post and its blocks, follows a different model: changes apply to the content straight away and are saved together with the document. These guidelines don’t cover that model.

## Choose one save model per surface

Before designing anywhere people change settings, such as a screen, a panel, or a modal, make a deliberate choice: does the surface **collect changes behind an explicit “Save changes” button**, or does it **save automatically** as the user makes changes?

Pick one for the entire surface. **Do not mix the two.** A page where some fields save instantly while others wait for a button leaves the user unable to tell what has actually been saved and what is still pending. This is the core reason mixed saving feels unreliable. Mixing also undermines the unsaved-changes prompt: a warning that only covers some of the fields gives false reassurance about the rest.

A surface is a region whose save state is communicated by a single control: either one Save button, or the absence of any. Usually that is the whole screen, panel, or modal. A screen can occasionally be split into separate surfaces, for example a card of instantly applied switches beside a form with its own Save button, but only when the regions are visually distinct and each makes its model obvious. Treat this as the exception, not a way to mix models within one form.

-   **Manual save** is the usual choice in WordPress. It is the right one when changes are interdependent and should apply together, when saving has side effects that are better batched into a single action, or when the environment submits a whole form at once (for example, classic WordPress admin screens, or third-party pages that post to PHP).
-   **Autosave** suits surfaces whose fields can be validated and persisted independently and asynchronously, such as a list of preferences that each take effect on their own (for example, the block editor’s Preferences modal). Changes save as they’re made, so there is no Save button, and no unsaved-changes prompt unless an edit fails to save.

Choose the model that fits how the surface’s data is saved, and commit to it across every field on the surface.

## Manual save model

Edits are held locally and applied together when the user clicks a single primary **Save changes** button.

<Canvas of={ SaveSubmitStories.SaveFormLayoutCard } />

### Saving

-   While saving, the [`Button`](https://wordpress.github.io/gutenberg/?path=/docs/design-system-components-button--docs) switches to its `loading` state and can’t be clicked again.
-   A [Snackbar](https://wordpress.github.io/gutenberg/?path=/docs/components-snackbar--docs) confirms a successful save.

### No unsaved changes

When all changes are saved, the Save button is disabled. A disabled Save on a form with no changes is a familiar convention and needs no explanation. If a disabled state does need explaining, use inline text, not a [`Tooltip`](https://wordpress.github.io/gutenberg/?path=/docs/design-system-components-tooltip--docs): tooltips aren't available to screen readers or on touch devices.

### Unsaved changes on exit

If the user navigates away with unsaved edits, prompt them to confirm before leaving so their changes aren’t lost. This guard belongs to the manual save model. An autosave surface only needs it while a text field holds an edit that failed to save (see [Autosave model](#autosave-model)).

-   **Only ask when something would be lost.** Prompt only while there are unsaved edits. Once the user saves, or changes a field back to its saved value, navigation is free again.
-   **Inside the app, use an [`AlertDialog`](https://wordpress.github.io/gutenberg/?path=/docs/design-system-components-alertdialog--docs).** Hold the navigation (switching between adjacent pages, following a breadcrumb or opening a record) and ask “Discard unsaved changes?” with the `irreversible` intent, because leaving discards the edits and can’t be undone. Offer two choices: “Keep editing”, which cancels the navigation and is the safe default, and “Discard changes”, which continues. Don’t add a “Save and leave” option: a save can fail validation, and the dialog is the wrong place to show that.
-   **When leaving the app, rely on the browser.** Reloading, closing the tab or following an external link can only be guarded with the `beforeunload` event, which shows the browser’s own warning. Its wording can’t be customized, so don’t try to imitate it.
-   **Dialogs and drawers that hold a draft close only through their actions.** Give them a footer with Cancel and Save, and omit the close icon and closing by clicking outside, so the user always makes an explicit choice. Cancel discards the draft without asking again, because choosing it is the decision. If the user presses Escape with unsaved edits, ask with the same dialog before closing.

### Invalid fields, partial saves, and failed saves

Keep the Save button enabled when fields are invalid, so that clicking it can explain what needs fixing. When it is clicked:

-   Show each error message right below its field.
-   Move focus to the first invalid field, scrolling it into view.
-   Don’t send the save until the errors are fixed.

A form’s native validation does this for you: wrap the fields in a `<form>` and make Save a `type="submit"` button, so pressing Enter in a field submits too. Controls built on `ControlWithError` show their message and move focus. They also show a message as soon as focus leaves an invalid field, so place Save above the fields, for example in the card or page header, where a new message can’t push it away mid-click. If the save goes through but only some changes succeed, show a single [`Notice`](https://wordpress.github.io/gutenberg/?path=/docs/design-system-components-notice--docs) at the top of the form that says what saved and what still needs attention. List every area that needs attention in that one `Notice`, and never show a success message and an error message together.

If the save fails entirely, keep the user’s edits so they can retry, and show the reason in the `Notice`.

## Autosave model

Each change is persisted as it is made. There is no Save button, and no unsaved-changes guard while every change has saved.

<Canvas of={ SaveSubmitStories.AutosaveFeatureList } />

-   **Switches, selects, and radios** save immediately on change.
-   **Text and number fields** save on blur, or debounced after the user stops typing, never on every keystroke.
-   **Per-field errors.** If a save fails, show the error at the field and let the user retry. A failure on one field must not block editing the others.
    -   For a switch, select, or radio, return the control to its saved value, so it never shows a state that wasn’t saved.
    -   For a text or number field, keep what the user entered so it isn’t lost, and mark the field as not saved until a retry succeeds.
    -   After “Try again”, move focus to the field it retried. The retry removes its notice, and focus would otherwise fall back to the page.
-   **No global Save button.** It implies pending state that this model doesn’t have.
-   **No unsaved-changes prompt while everything has saved.** The exception is a text or number field that failed to save: the field holds the user’s only copy of the edit. If the user navigates away, keep that edit so they can retry when they come back, or ask “Discard unsaved changes?” before throwing it away.

Because autosave depends on fields saving independently, it isn’t suitable when several fields must be validated or applied together. Those cases call for the manual save model.

## Switches

A switch implies immediate effect, like a light switch, so **only use a switch where flipping it takes effect immediately**:

- **On an autosave surface, use a switch.** Flipping it saves the change. Use [`SwitchControl`](https://wordpress.github.io/gutenberg/?path=/docs/design-system-components-form-switchcontrol--docs) for turning features on and off.
- **In an editor, such as the block settings sidebar, use a switch.** The change applies to the content straight away, even though it is saved with the document later.
- **On a manual-save surface, don’t use a switch.** Nothing happens until the Save button is clicked, so a switch would either save on its own, mixing the two models, or wait for the button and contradict what it implies. Use [`CheckboxControl`](https://wordpress.github.io/gutenberg/?path=/docs/design-system-components-form-checkboxcontrol--docs) for the same on and off choices, so they are applied together with the rest of the form.

Keep switch labels short. Name the setting, such as “Lazy loading”, or lead with a verb, such as “Allow comments”. Use the switch’s `description` or the card title to provide more context.
