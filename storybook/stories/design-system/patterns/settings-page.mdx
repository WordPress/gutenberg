# Settings Page

Templates for settings screens, composed from the admin-ui `Page`, `@wordpress/ui` components, `@wordpress/theme` tokens and DataViews. Start from the template closest to your settings, then replace the fields.

These templates are starting points, not requirements. Not every settings page needs to match one exactly: adapt the structure to what your settings need, and combine or depart from the templates where that serves people better.

Several of the `@wordpress/ui` components they use, including `Button`, `ButtonLink`, `Dialog`, `Drawer` and `AlertDialog`, are still marked “Use with caution”, so their APIs may change. Treat the templates as the direction settings pages are heading, not as a recommendation to migrate existing screens yet.

## Building blocks

Every template uses the same parts:

-   **`Page`** from `@wordpress/admin-ui` provides the header: a title or breadcrumbs, optional section navigation, and the actions area where Save lives.
-   **`Card`** from `@wordpress/ui` groups related settings. Give each card a short title, and a description when the title alone doesn't say what the settings affect. The Structure section below covers when to use one. Cap form cards at `--wpds-dimension-surface-width-xl` so fields stay a readable length, and give tables of records `--wpds-dimension-surface-width-2xl` so their columns fit.
-   **`DataForm`** from `@wordpress/dataviews` renders the fields, so labels, descriptions, validation and spacing stay consistent.
-   **`DataViews`** from `@wordpress/dataviews` lists records people can add and edit.
-   **`Dialog`**, **`Drawer`** and **`AlertDialog`** from `@wordpress/ui` hold record editors and confirmations.
-   **Snackbars** confirm saves that have no other visible effect. `SnackbarList` comes from `@wordpress/components`, since `@wordpress/ui` doesn't offer an equivalent yet.

Each example's code shows its template. The helpers it imports, such as the manual-save draft, the sample fields and the in-canvas router, live alongside it in `storybook/stories/design-system/patterns/settings-page/`.

## Structure

Plan a settings page like a document's outline before choosing how it looks. The headings decide how assistive technology reads the page and lets people jump through it, and the same kind of content should get the same treatment wherever it appears.

-   **Put each group of related fields in a card.** A card bounds a group and separates it from the groups around it. Keep the card even when a page has a single group, so every settings page reads the same way.
-   **Title each card after its group of fields.** The page title is the `h1`, and on a page without sections the card titles are `h2`s.
-   **Add sections when cards form larger groups.** A section heading sits on the canvas above its cards, as an `h2` with an optional description, and the cards inside it take `h3` titles. Use `Text` with `variant="heading-lg"` for the section heading. Each section gets its own heading, and a page with only a few cards needs none.
-   **Don't skip heading levels**, and don't choose a level for its size. The level follows the structure, so a card title looks the same whether it's an `h2` or an `h3`.

## Saving

These templates use the manual save model from [Save & Submit](?path=/docs/design-system-patterns-save-submit--docs), the usual choice for settings: edits are held in a draft until the user clicks “Save changes”. Autosave suits pages of independent preferences that each take effect on their own. If you adopt it, remove the Save button rather than mixing the two models on one page.

-   **One “Save changes” button per page**, in the `Page` header actions. It covers every field on that page and nothing else.
-   **Disabled only when there is nothing to save**, with a “No unsaved changes” tooltip, and busy while saving.
-   **Invalid fields don't disable Save.** The fields sit in a `<form>`, and Save submits it: invalid fields show their errors below them and the first one takes focus, and nothing is saved until they're fixed. The record editors work the same way.
-   **Edits made while saving stay unsaved.** People can keep typing while a save is in progress. Once it finishes, anything they changed in the meantime is still an unsaved change, and a record editor stays open to hold it.
-   **Checkboxes, not switches, for on/off settings.** A switch implies the change takes effect immediately, which isn't true until Save is clicked. Switches belong on autosave surfaces.
-   **A snackbar confirms the save.** Errors belong next to the field, or in a `Notice` at the top of the form when a save fails or only partly succeeds.
-   **Pages that only list records have no page-level Save.** Each record editor saves on its own, and the header holds the action that adds a record.
-   **Leaving with unsaved edits asks first.** Switching pages, following a breadcrumb or closing a record editor with Escape asks “Discard unsaved changes?”, and reloading or closing the tab shows the browser’s own warning. Try it in any template by changing a field, then navigating away. See [Unsaved changes on exit](?path=/docs/design-system-patterns-save-submit--docs#unsaved-changes-on-exit).

## Focus after navigation

Moving between adjacent pages and subpages replaces the page, including the link that was just used. Without help, keyboard focus falls back to the start of the document and screen readers don't announce the new page.

Admin pages built on `@wordpress/boot` handle this for you: when a navigation removes the focused element, focus moves to the new page's `Page` region, and screen readers announce it by name. The region takes its name from `title`, so a subpage whose breadcrumbs replace the title needs an `ariaLabel` naming the page, such as "Card payments". Don't move focus yourself on those pages. If your app routes without `@wordpress/boot`, do the same after each navigation that loses focus.

The templates' in-canvas router follows the same behavior. Try it by following a breadcrumb with the keyboard.

## Adjacent pages

Peer sections of one settings area, such as General, Payments and Emails, switched with the `Page` `navigation`. Use it when the sections are independent and each one is substantial enough to deserve a page.

-   Keep the page title the same across adjacent pages; the navigation shows which page is current, so the title doesn't need to name it.
-   Each page has its own draft and Save. Saving one page doesn't save another.
-   Pass a router link through `components.link`, so switching pages doesn't reload the screen.

## Subpages

A subpage holds detail that would crowd the main page, such as the credentials for each payment gateway. Open it from the page body with a full-width row at the bottom of the card: an unstyled `ButtonLink` with a trailing chevron to signal that it navigates. A status badge in the row tells people what they will find there.

When a card leads to several subpages, put the rows in a list:

-   **Use a `ul`, named by the card title.** Render the title as a heading, and point the list's `aria-labelledby` at it, so screen readers announce “Payment gateways, list, 3 items”.
-   **Keep `role="list"` on the unstyled list.** Safari drops list semantics when the bullets are removed.
-   **Name each link after its destination.** The row label matches the subpage's heading, so the link's name is just “Card payments”. Show the status in a `Badge` and connect it with `aria-describedby`, so screen readers announce it as a description rather than as part of the name.

On the subpage, breadcrumbs replace the title and lead back to the parent page. Repeat the row's status next to the breadcrumbs with the `Page` `badges` prop, and update it from the saved settings, not the draft, so it changes when people click Save.

## Records

Some settings are lists of records, such as API keys, webhooks or redirects. These examples use API keys. Show them in a `DataViews` table, and choose how each record opens by the size of its editor.

<Markdown>{ `
| Editor | Use when |
| --- | --- |
| Subpage | The editor is long, has its own sections, or people need to link to a record. |
| Dialog | The editor is short and people should stay focused on one record. |
| Drawer | The editor is medium-sized, people benefit from seeing the table, or the record has secondary actions. |
` }</Markdown>

### Records that open a dialog

The dialog saves on its own. Cancel discards the draft, and Save applies it, closes the dialog and confirms with a snackbar. The same dialog adds new records.

The footer actions are the only way out: there is no close icon, and clicking outside does nothing, so people always choose between keeping and discarding their edits. Pressing Escape closes an untouched dialog, but asks first when there are unsaved edits.
