# Notice announcements

Standalone notices do not announce their content. Use `Notice.List` to announce notices as they are added or changed. Visual `intent` and announcement urgency are independent.

## Static information

Leave static notices without an announcement. Users can read the message and reach its actions through normal navigation.

<Canvas of={ AnnouncementStories.StaticNotice } />

## Announce a list of notices

Keep `Notice.List` mounted, including when it is empty, and render keyed `Notice.Root` children inside it. The list stacks its children with a small gap. It announces added notices and changes to their messages, including when a new save result replaces a message under the same key. Notices present when the list mounts stay silent.

<Canvas of={ NoticeStories.DynamicNotices } />

The default announcement joins the plaintext content of `Notice.Title` and `Notice.Description` with a space if the title already ends in Unicode sentence-ending punctuation, or `. ` otherwise. The supplied text is preserved. Actions, dismiss buttons, descriptions inside `Notice.Actions`, and content hidden with `hidden` or `aria-hidden="true"` are excluded. For complex content or content rendered outside the notice, use `spokenMessage` on `Notice.Root` to provide a complete, punctuated announcement that excludes technical details.

Announcements are `polite` by default, including error notices. Set `politeness="assertive"` on a notice only when its message needs immediate attention. Set `politeness="off"` to skip announcements for a notice. These props only affect notices inside `Notice.List`.

```jsx
<Notice.List>
	{ notices.map( ( notice ) => (
		<Notice.Root
			key={ notice.id }
			intent={ notice.intent }
			politeness={ notice.isUrgent ? 'assertive' : 'polite' }
		>
			<Notice.Title>{ notice.title }</Notice.Title>
			<Notice.Description>{ notice.description }</Notice.Description>
		</Notice.Root>
	) ) }
</Notice.List>
```

The list does not move focus, and notices continue to announce while focus is inside the list. If your application moves focus to a new notice, set `politeness="off"` on that notice when adding it to avoid announcing the same content twice. This leaves announcements for other notices enabled. Removing a notice does not announce it or repeat the remaining notices. Give each notice a stable key. Use a new key for a new notification, including a repeated message.

The list renders separate, visually hidden live regions for polite and assertive messages. Keep live-region roles off the visible notices and do not also call `speak()` for the same update.

## Announce from the application

For a standalone dynamic notice, or an announcement tied to an application event rather than a change to visible text, use `speak()` from `@wordpress/a11y` in the event handler or lifecycle callback that handles the update. Pass an explicit message containing the relevant title and description. Exclude action labels and technical error details. Do not also add a live-region role to the visible notice, which could cause duplicate announcements.

Import `@wordpress/a11y` during application startup, before announcements are needed. Its main entrypoint creates shared live regions when the document is ready; `speak()` updates those regions. In a standalone app, wait until the document is ready before sending the first announcement. The WordPress script entrypoint uses the same setup. The script-module entrypoint requires the host to provide the live regions.

### Urgent errors

Use `speak( message, 'assertive' )` when an error needs immediate attention, such as a failed save or an editor crash. Keep keyboard focus where it is. Select **Save changes** to simulate a failed save. **Try again** clears the simulated error.

### Non-urgent updates

Use `speak( message, 'polite' )` for updates that can wait until the screen reader finishes speaking. An error in one dashboard widget, while the rest of the dashboard remains usable, can also use a polite announcement.

Select **Save draft** to show and announce a new notice. **Dismiss** removes the visible notice. Neither action label is included in the announcement.

<Canvas of={ AnnouncementStories.PoliteStatus } />

## Using a live region directly

An application can instead manage its own live region. Mount an empty region before the update, then populate it. Use `role="status"` for non-urgent updates and `role="alert"` for important, time-sensitive messages. Include the relevant title and description, and keep actions outside the region.

```jsx
// Keep this region mounted before the save completes.
<div role="status">
	{ isSaved ? 'Draft saved. Your draft has been saved.' : '' }
</div>
```

The [WAI-ARIA alert pattern](https://www.w3.org/WAI/ARIA/apg/patterns/alert/) notes that most screen readers announce dynamically inserted alerts. This special behavior does not apply to every live-region role. Do not rely on inserting a populated `role="status"` element to announce its contents. Keeping the region mounted first is the more reliable pattern for both roles.

Use one announcement mechanism for each update. Do not combine this live region with a `speak()` call for the same message.

## Migrating existing notices

`Notice.Root` only uses `spokenMessage` and `politeness` inside `Notice.List`. Standalone notices stay silent.

-   If the notice is static, no replacement is needed.
-   For dynamic notices, keep a `Notice.List` mounted and add notices to it. Existing notices are not announced when the list first mounts.
-   If the previous `spokenMessage` differed from the visible text, retain that message on the notice inside the list.
-   For event-based announcements, call `speak()` where the application handles the update, as shown above, or update an existing live region.
-   Choose `polite` or `assertive` based on urgency, independently of the notice's visual intent.

This change applies to `@wordpress/ui` `Notice`. The `@wordpress/components` `Notice` API is unchanged.

Test dynamic announcements with the browsers and screen readers your application supports. Automated tests can check live-region content and the message and politeness passed to `speak()`, but cannot verify speech output.

See the [`@wordpress/a11y` API](https://github.com/WordPress/gutenberg/tree/HEAD/packages/a11y#api) and the [WAI-ARIA status role](https://www.w3.org/TR/wai-aria-1.2/#status).
