# Adversarial review: intent-log sync engine (2026-08-05)

An independent critical review of the branch against three questions: fidelity
to the architecture draft, invasiveness, and test meaningfulness. Findings
were confirmed in code (several by executing the engine). Line numbers are
from the working tree at commit 7fd02053b56.

Scope note: `git merge-base trunk HEAD` returns a stale local trunk tip; the
true branch point is `a74e27c398f`. Against that base the branch is 87 files,
~19k lines of code plus a 36k-line frozen vector file.

## Question 1 — Fidelity to the architecture draft

**Verdict.** The three-plane separation is largely real and the best part of
the work: the polling transport genuinely no longer interprets payloads (JS or
PHP), and the status log is unusually honest about scope. But two of the
draft's headline guarantees are quietly weaker than claimed: the "mismatch →
post lock" degradation does not actually produce a lock at bootstrap time, and
the offline policy "never lose work, merge clean, review the rest" is violated
by at least three confirmed paths (a transport recovery path that discards
queued intents and kills polling, a merge-concurrency case that silently voids
other actors' work, and a proposal lane that no user can reach). Several
status-log claims overstate the code (compaction, exactly-once ingest, typing
plan, materialize round-trip).

### Findings (ranked)

**1.1 (High) The promised post-lock fallback never engages at bootstrap
mismatch — the degraded state is "no sync AND no lock."**
ARCHITECTURE.md:176-189 promises that a client that cannot speak the announced
engine "falls back to WordPress native post locking… with a notice." Reality:
`resolveEngineAdapter()` returns null → `getSyncManager()` returns `undefined`
with only a `console.warn` (`packages/core-data/src/sync.ts:52-72`). But
`isCollaborationEnabledForCurrentPost`
(`packages/editor/src/store/private-selectors.js:639-660`) reads only
`window._wpCollaborationEnabled` + syncConfig — it never consults the adapter
resolution — and the post-locked modal returns null whenever it's true
(`packages/editor/src/components/post-locked-modal/index.js:206-208`).
`collaborationSupported` is flipped false for `DOCUMENT_SIZE_LIMIT_EXCEEDED`
but not for engine mismatch (`packages/core-data/src/reducer.js:726-741`).
Server-side, heartbeat lock info is still stripped because
`wp_is_collaboration_enabled()` stays true (`collaboration.php:431`). Concrete
scenario: server announces an engine this client build lacks (plugin
unregistered it, or protocol bump); two such clients open the same post;
neither syncs, neither is locked, both save — silent last-write-wins
overwrite, which is exactly the corruption constraint 3 forbids. The
per-request 409 path IS handled well (modal + no retry), so this hole is
specifically the bootstrap path — the one the status log calls "post-lock
posture." Recommendation: dispatch `SET_COLLABORATION_SUPPORTED: false` (or an
equivalent signal) on adapter-resolution failure so the classic lock machinery
re-engages, and add the promised visible notice.

**1.2 (High) Transport error recovery calls a compaction the intent-log engine
cannot perform — throws inside the catch handler, discards queued work, and
permanently stops polling.**
`polling-manager.ts:824-828`: on any network error with pending updates and
`endCursor > 0`, the transport does `updateQueue.clear()` then
`state.session.createCompactionUpdate()`. The intent-log codec throws there by
design (`intent-log-session.ts:321-328`). The throw happens inside `catch` of
async `start()` invoked as `void start()` (`polling-manager.ts:551-555, 871`),
so it becomes an unhandled rejection: the queue is already cleared (typed
intents lost), `setTimeout(poll, …)` never runs (sync silently dead for all
rooms), and the disconnected-status dispatch below the recovery loop is
skipped (UI stuck on "connecting"). Trigger: one transient network
failure/timeout while an intent-log user is typing — the most ordinary failure
there is. This is also a layering violation: "recover by re-sending full
state" is a Yjs-engine assumption baked into the transport; intents already
have server-side `intentId` dedup, so plain `restore()` is the correct, safe
recovery for this engine. No test covers it — the polling tests stub the codec
with `jest.fn()` (`test/polling-manager.test.ts:87`). Recommendation: make
recovery codec-driven (e.g. optional `createRecoveryUpdates()`; default =
restore), and add a regression test with the real intent-log session.

**1.3 (High) "Never lose work, merge clean, review the rest" — three confirmed
divergences.**
(a) *Silent voiding under concurrent merge* (`rebase.js:546-556` +
`reducer.js:99,158,264`): `set_attr`/`transform_block`/`move_block`/
`insert_block` targeting a block absorbed by a concurrent `merge_blocks` sail
through rebase and are **voided** at apply (`missing-target`), not escalated —
demonstrated by execution; the identical situation under `remove_block`
escalates (`target-deleted`). SPEC.md:146-147 promises the drop "can never
silently swallow another actor's work." 13 of 19 voids in the frozen vectors
are `missing-target`, so this is a routine path, not a corner.
(b) *The proposal lane goes nowhere a user can reach*: escalated intents live
in an in-memory array (`intent-log-session.ts:183, 374`) lost on reload; the
only surfacing is a notice carrying `{reason, isLocal}` with no content
(`resolvers.js:236-256`); the escalated text has already vanished from the
author's editor (dropped from the optimistic doc). Server proposal rows are
durable in postmeta, but nothing ever reads them back for review, and no test
at any level retrieves parked content. Today "review the rest" operationally
means "the loser's text disappears from every screen; a snackbar apologizes."
Known-open UI, yes — but the recoverability *substrate* (a queryable proposal
store with a retention guarantee) is also absent, which is architecture, not
UI.
(c) *Frame/txn state does not survive request boundaries*
(`class-wp-intent-log-planner.php:745-748`): a batch split across two HTTP
requests (crash/retry) loses `dependent-on-escalated` linkage — dependents
void instead of escalating, and a txn unit can be torn (head escalated, tail
applied/voided). Recommendation: escalate identity-addressed intents under
merge priors; persist proposals with an explicit retention rule and expose a
read API; persist unit/frame settlement state or reject continuation of
settled txnIds.

**1.4 (High) The v1 capture layer silently abandons the spec'd text model —
the engine that was validated is not the engine that runs.**
INTEGRATION.md:83-104 specifies rich-text-coordinate diffs with a cursor hint,
split/merge/format derivation, and explicitly flags HTML-index diffing as the
pitfall in the old code (INTEGRATION.md:69). The shipped bridge does exactly
the flagged thing: it diffs serialized HTML strings by common prefix/suffix
with no cursor hint (`intent-log-bridge.ts:157, 289-340`; the `aa|a→aaa`
ambiguity the hint exists for is unsolved), maps everything to a single
`content` field, and never derives `split_block`/`merge_blocks`/`format_text`
(`intent-log-bridge.ts:30-38`). Consequences: text offsets count tag/entity
characters, so concurrent clean merges can interleave *inside markup* and
produce invalid HTML (nothing validates the merged string); the field
dimension, split/merge semantics, and format-clipping rules — the most
carefully specced and vector-frozen parts of the engine — are unreachable from
the production path (the tested path is unreachable, the reachable path is
untested); and the measured escalation profile (SPEC.md:277-287) describes an
intent mix production never generates. This is documented as "v1" but nowhere
is it stated that it invalidates the engine-level validation story for the
shipped system. Recommendation: at minimum, add adversarial tests for
concurrent HTML-space merges (formatting vs typing in one paragraph) and state
the gap in ARCHITECTURE.md; the real fix is the phase-1 rich-text-coordinate
capture.

**1.5 (High) The server does not serialize ingest — the total order the whole
design rests on is not enforced.**
`WP_Intent_Log_Engine::handle_updates()`
(`class-wp-intent-log-engine.php:191-316`) does load→plan→insert with no lock,
transaction, or CAS. Two concurrent pollers (the normal case) both plan
against log length N; the loser's transformed payloads are committed with
wrong bases; replicas replaying the interleaved log diverge from the
dispositions issued. Yjs tolerated this (commutative merges); an intent log
cannot. This undermines "convergence via a single server-assigned total order"
(SPEC.md) at its root. Recommendation: per-room mutex (`GET_LOCK` on room
hash) or expected-log-length CAS around load→plan→commit — prerequisite to any
real-world claim.

**1.6 (Med-High) Compaction is claimed in the draft and absent in the code;
every poll replays the whole log.**
ARCHITECTURE.md:106-107 says "`maybe_compact` = snapshot at seq + trim below
all-client cursor floor." No `maybe_compact` exists anywhere in `lib/`;
`should_compact` is hardcoded false (`class-wp-intent-log-engine.php:349`);
nothing ever trims. Worse, every poll — including empty catch-up polls — runs
`load_room`, decoding every row since seq 0
(`class-wp-intent-log-engine.php:335, 391`), O(session-length) per client per
second, with postmeta growing one row per keystroke (two per void).
Client-side the replica log and proposals array also grow unbounded.
Recommendation: snapshot rows + settled checkpoints, skip `load_room` for pure
reads, implement the trim — and correct the status log until then.

**1.7 (Medium) Swappability is real for *selecting* between the two built-ins,
weaker than advertised for *adding* a third.**
The class-swap/config-change claim holds for yjs-relay↔intent-log (verified:
registry + filters + settings + 409 fence all work). But a third engine author
must: implement the entire manager-level `SyncManager` surface, not a session
codec — the adapter interface itself admits it's transitional
(`engines.ts:37-41`); stub or throw on yjs-shaped codec members
(`getInitialUpdates`, `createCompactionFromUpdates`, numeric `clientId` —
`session.ts:97-120`); survive the transport's compaction-recovery assumption
(finding 1.2); copy the intent-log's pattern of smuggling bootstrap through
`get_updates_since` (no genesis hook on the interface); fabricate
`should_compact`/`total_updates` (relay concepts required by
`interface-wp-sync-engine.php:101-107`); add their own asset enqueue; and
modify or bypass `WP_Sync_Save_Server`, which hardcodes `_crdt_document`
(`class-wp-sync-save-server.php:35,128` — `materialize()` is not on the
interface and has no production caller). Layering residue in the other
direction: the yjs engine imports wire helpers and the type enum *from the
transport directory* (`engines/yjs-relay/session.ts:19-23`), inverting the
claimed dependency direction.

**1.8 (Medium) Engine-lineage 409 fence has a hole: the server's own genesis
write doesn't stamp lineage.**
Lineage is stamped only on client-supplied updates
(`class-wp-http-polling-sync-server.php:417-421`), but an intent-log room's
first write is the engine's genesis snapshot row during a read poll
(`class-wp-intent-log-engine.php:334-335, 460-493`). Poll under intent-log →
flip site to yjs-relay → new clients pass the lineage check (null) and append
Yjs rows into a room already containing intent-log rows — the exact
cross-engine corruption the fence exists to prevent. Recommendation: stamp
lineage on any first storage write, engine-initiated included.

**1.9 (Medium) Status-log claims contradicted by code.**
(a) "Ingest is idempotent per intentId / voided markers make redelivery
exactly-once": duplicates *within one batch* double-apply — demonstrated:
`serverIngestBatch(server,[i1,i1])` → `[applied, applied]`, log length 2
(`rebase.js:1002-1008`; the dedupe reads a dispositions map populated only
after planning). (b) "materialize() round-trips block markup": container
blocks serialize children *outside* their wrapper markup
(`class-wp-intent-log-engine.php:576-586` emits `[wrapped-text, null, …]` with
the close tag before child placeholders); only flat paragraphs are round-trip
tested. (c) "Proper typing lands with the Phase 2 adapter"
(`packages/sync/tsconfig.json:8-13`): Phase 2 landed; the exclude remains, and
the hand-written `.d.ts` files have already drifted (`client.d.ts` omits
`catchUp`/`flushClient`; `engine-types.d.ts:53-63` omits `docCache`, which
`serverDocAt` requires). (d) SPEC.md:233-235 "Formats never escalate" is
false: `format_text` under replace-class priors escalates (`rebase.js:678,
695-710`, demonstrated). (e) Text offsets: SPEC.md:307 flags UTF-16-vs-PHP as
open; the PHP twin ships with byte offsets
(`class-wp-intent-log-document.php:24-26`, `strlen`/`substr` throughout) and
ASCII-only vectors — any multibyte character desynchronizes client and server
offset arithmetic. Not an open item once real users type "é".

## Question 2 — Least-invasive approach

**Verdict.** The footprint discipline on shared Gutenberg surface is genuinely
good — core-data changes total ~85 lines across 4 files, editor ~20 lines
across 2, and the large transport rework was mandated by constraint 2 and
improves trunk (Yjs fully removed from the provider). The avoidable weight is
elsewhere: identity management exists in triplicate (three genesis-hash
implementations, three id-assignment actors reconciled by similarity
heuristics), a hand-rolled SHA-256, hand-maintained lockstep `.d.ts` files
that have already drifted, and a layer of race-papering machinery in the
manager (1200 ms delayed re-push) that would rot in a merged product. Most of
the parallel machinery is a consequence of one root decision — tree-diff
capture with a build-free stamper instead of the action-level capture
INTEGRATION.md designed — which is defensible for a prototype but should be
named as the thing that gets deleted, not hardened.

### Findings (ranked)

**2.1 (Med) Identity logic in triplicate, one copy untested.** Genesis hashing
exists in `packages/sync/src/engines/intent-log/sync-id.js:59-63`,
`class-wp-intent-log-planner.php:61-66`, and the build-free stamper
`lib/experimental/collaboration/sync-id.js:59-75`. Only the first two are
pinned by `test-vectors/sync-id.json`; the stamper's WebCrypto mirror has no
unit test and can drift silently (one e2e compares outputs). The stamper is
also a third concurrent writer of `metadata.syncId` alongside the bridge's
mint/adopt (`intent-log-bridge.ts:397-477`) and the server's genesis, mutually
reconciled by heuristics (`textsAreSimilar` with magic constants `<=4` and
`2*(prefix+suffix)>=shorter`, `intent-log-bridge.ts:373-395`) — mis-adoption
is identity theft with no proof, only similarity. Smaller alternative:
mint/stamp in exactly one place (the manager, which already sees every tree
and can push ids), import the engine's `genesisSyncId` rather than mirroring
it, and delete the standalone stamper; cost: the stamper's "works before any
session connects" property, which matters only until the sync package owns the
editor session anyway. Also note the spec/impl gap: all three implementations
pin `revisionId=0`, so the "pure function of an immutable saved revision"
(SPEC.md:41-47) is actually "function of current path," which weakens the
identity story across content generations.

**2.2 (Med) Hand-rolled SHA-256 (126 lines) where WebCrypto or a one-line
dependency would do.** `sha256.js` is correct (differential-tested against
`node:crypto` during review, including padding boundaries and astral UTF-8)
but the repo itself can't tell: every tested input is ≤22 bytes — a single
padded block — so the multi-block loop and 55/56-byte padding boundary are
unpinned in-repo while real genesis inputs will cross them. If sync minting
must be synchronous, keep it but add NIST known-answer tests and a >55-byte
frozen vector.

**2.3 (Med) Hand-written lockstep `.d.ts` instead of typing the code.** Seven
declaration files (~270 lines) mirror the JS engine because of the tsconfig
exclude; drift is already present (finding 1.9c). The smaller alternative —
enabling `checkJs` for the directory or a one-time TS conversion — costs a day
and deletes a whole failure mode the status log itself flagged (esbuild
`declare` gotcha, ARCHITECTURE.md:331-333).

**2.4 (Med) Manager machinery that papers over the push/echo race — would
persist into product.** `intent-log-manager.ts:595-612`: a 1200 ms
`setTimeout` re-dispatch to close the "editor echo overwrote our identity
push" window, guarded by a `pushSeq` counter — timing-based correctness in the
sync path, untestable deterministically. Adjacent per-keystroke costs:
full-tree `JSON.stringify` canonicalization twice per capture plus per-attr
`JSON.stringify` comparisons (`intent-log-manager.ts:168-170, 530-534`;
`intent-log-bridge.ts:651-655`), on top of the stamper's full-tree walk per
store change and the client's admitted O(pending × slice) replan. Individually
fine for a prototype; together they make every keystroke O(document) several
times over. The `editorIds`/`docTombstones`/`retainedIds` staleness machinery
(`intent-log-manager.ts:85-97, 340-353`) is well-commented and necessary
*given* tree-diff capture — it is the strongest argument that action-level
capture (INTEGRATION.md seam 1) is the smaller system.

**2.5 (Low-Med) Parallel PHP ingest harness ships in production.**
`WP_Intent_Log_Planner::create_server/server_doc_at/server_ingest_batch`
(`class-wp-intent-log-planner.php:875-961`) duplicate the engine's
settled-filter logic (vs `class-wp-intent-log-engine.php:236-249`) and are
called only by tests — two ingest implementations that can diverge. Move to
the test suite or delete.

**2.6 (Low) Dead weight inventory.** Unused/decorative: `ESCALATION_REASONS`
referenced nowhere in PHP (`class-wp-intent-log-planner.php:34-46`); dead
payload fields validated and carried but never read by any decision path —
`observedVersion` on attrs (the "versioned register" doesn't actually
version-check; conflict is purely concurrency-window — `rebase.js:713-740`),
`merge_blocks.joinOffset`, `removedText`; `materialize()` has no production
caller; deprecated Yjs constants on the transport
(`class-wp-http-polling-sync-server.php:52-123`); empty
`prototypes/sync/package-lock.json`; five "Undocumented declaration." stubs in
`packages/sync/README.md`; `void record;` (`intent-log-manager.ts:420`);
`loadCollection` no-op; the dev/test surface (`getBaseDocument`, `getSeq`,
`getPeers`) shipped on the production session interface. Pre-existing but
touched: `get_storage_post_id` creates a junk storage post per garbage room
name even on requests that 403 (`class-wp-sync-post-meta-storage.php:339`).

**2.7 (Acceptable) The invasive changes that were the right call.** For the
record: the provider narrowing (`polling-manager.ts`,
`http-polling-provider.ts`, `types.ts`) is the one big shared-surface rework,
it was required by constraint 2, claimed zero wire change, relocated its
behavioral tests with the code, and leaves trunk better whether or not
intent-log survives. The core-data escalation hook is one optional callback
(though putting user-facing notice copy inside a core-data resolver,
`resolvers.js:236-256`, is a small layering wart — editor copy belongs in
`editor`).

## Question 3 — Meaningful test coverage

**Verdict.** The pyramid is excellent at the bottom and thin at the top, and
the headline numbers overstate assurance in a specific, structural way: the
three load-bearing oracles (convergence, prediction parity, effect
verification) are substantially self-referential — both sides of every
comparison run the same `planBatch`/`applyIntent`, so the bug class the engine
exists to prevent (transform misplacement) is falsifiable only by a few dozen
hand-pinned scenarios, not by the sweeps or the 1011-intent vectors. Meanwhile
the four scenarios most likely to lose a user's words in the field — offline
typing, tab close with pending intents, engine flip with unsaved work,
formatting conflicts — have between zero and mock-only coverage. Also, 1283 is
not the engine's test count: the engine directory holds 90 test blocks; the
larger figure counts looped matrix iterations and the whole package suite.

### Findings (ranked)

**3.1 (High) The oracles guard plumbing, not semantics.** `verifyEffect`
(`simulator.js:538-726`) derives expectations from the *transformed* payload
plus the reducer's own clamps (`Math.min` at 658, 670-671, 702-703) and
deliberately ignores `removedText` — if `transformOne` maps an edit to the
wrong offset, the reducer splices the wrong place and the oracle verifies the
wrong splice. It also never checks formats outside `format_text` itself
(`shiftFormatsForInsert/Delete`, `reducer.js:45-72`, have zero direct
assertions anywhere — a sign error passes the entire suite), never checks
sibling order for `insert_block`/`move_block` (parent-only, 580-599), and
never checks collateral damage outside the target block. Convergence compares
the server's *cached* head (`simulator.js:519`; the "fresh replay" docstring
at 736 is inaccurate — the true genesis replay lives only in
`merge-matrix.test.js:245-249`) and both sides share one reducer. Prediction
parity is parity "by construction" (SPEC.md:184-186): same pure function, same
inputs — it catches outbox/cursor/cache plumbing drift, and structurally
cannot catch a bug in `planBatch` itself. Recommendation: an independent
effect model (expectations from pre-state + *original* intent + `removedText`),
direct format-shift tests, and order assertions.

**3.2 (High) Confirmed engine bugs the suite cannot see** (all demonstrated by
execution): intra-batch duplicate `intentId` double-applies
(`rebase.js:1002-1008`; vectors contain 133 whole-batch redeliveries and zero
mixed-fresh-and-duplicate batches); concurrent-merge voiding of
attr/move/transform work (finding 1.3a; generator makes it routine, oracles
blind because voids are "accounted"); nested `insert_block` payload reusing an
existing descendant id passes the root-only check (`reducer.js:128-130`) and
creates duplicate identities that silently retarget all later intents
(generator never emits children, `simulator.js:256-268`); syncIds containing
`::` break the frame-key algebra (`rebase.js:95-113`), silently skipping rules
5/6 for that block.

**3.3 (High) Coverage-gap table (merged across jest/PHPUnit/e2e).**

| Behavior | Status |
|---|---|
| Transport failure/offline during typing → reconnect | jest-only with mocked codec+fetch (`polling-manager.test.ts:1224,1275`); no e2e `setOffline`; the intent-log path through recovery **crashes** (finding 1.2) and is untested |
| Unload/reload with pending unsent intents | **Nothing.** Only reload tested is post-save |
| Undo/redo vs remote intents | **Nothing** for intent-log; undo handlers are inert `jest.fn()`s (`test/intent-log-manager.ts:63,71`) |
| Rich-text formatting sync | Engine-level `format_text` well tested but **unreachable** from the bridge; the reachable HTML-in-text path has zero tests at any level |
| Multi-tab same user | Not covered (manual observer script only); plus a real hole: same-user tabs may share `client_id`, collapsing sessions into one actor and skipping transforms between them (`class-wp-http-polling-sync-server.php:264-274`, planner:714) |
| Permission revoked mid-session | Pre-existing jest 403 handling only; no intent-log-specific test; fate of pending intents unasserted |
| Compaction/growth bounds | Nothing to test — not implemented (finding 1.6); the client-side *throw* is tested, growth is not |
| Escalated-work recoverability | **No test at any level retrieves parked content**; e2e asserts a notice substring only; jest reads only `.reason` |
| Nested blocks / moves / paste | Bridge-unit-only; the 1251-line block-gauntlet and undo e2e suites run only under yjs; PHP materialize breaks containers (finding 1.9b) and is round-trip tested on flat paragraphs only |
| Engine flip mid-session | e2e asserts the modal only; no-retry and queue-restore pinned at jest with mocks; fate of unsaved work unasserted; the "both ways, mid-content-lifetime" swap test the draft calls "the proof" of constraints 1-3 does not exist as specified |

**3.4 (Med) Frozen vectors are strong where cheap, near-empty where the PHP
twin is weakest.** Real strengths: `frame-conflict` 38,
`dependent-on-escalated` 128, 48 txn units with rule-4 settlement, 133
redeliveries, `set_property` conflicts 17 — rules 4/5/6 are genuinely frozen.
But the rule-2 range geometry — the offset arithmetic PHP will most plausibly
get wrong, and the place byte-vs-UTF-16 bites — has 1-3 examples each
(`range-crosses-split` 1, `position-in-deleted-range` 1,
`concurrent-replace-overlap` 1, `concurrent-insert-in-range` 3), zero
cycle/missing-parent/duplicate-id voids, zero nested structure, ASCII only.
The generator never touches the last code unit of any field, never splits at
0/len, never nests or reparents (`simulator.js:188-232, 256-268, 308-319`).
And **no JS test replays `planner.json`** — regeneration rewrites the
cross-language contract with nothing on the JS side objecting. Recommendation:
hand-authored vector cases per rule-2 reason, multibyte cases, boundary
offsets, and a JS-side replay of the frozen file.

**3.5 (Med) E2e assertions are dominated by eventual-consistency loops the
suite itself admits can mask corruption.** spec:118-122 documents a real bug
(canvas flicker) that the store-level `toPass` loops missed; only test 2 got a
DOM-stability assertion in response — every other test still polls store
selectors, and "stay converged" checks re-verify counts, not contents. The
flagship save-flow test asserts substring containment plus a two-string leak
blocklist (`_wrapper`, `attrVersions`), which passes over ghost blocks or any
other leaked key. The engine restore is `afterAll`-only under `workers: 1` — a
mid-suite crash leaves the site on intent-log and poisons every subsequent
collaboration spec. The conflict e2e's escalation is probabilistic (100
ms-delay typing race) — flake-prone gate on the suite's only conflict
coverage.

**3.6 (Low-Med) Tautology audit — mostly clean, three soft spots.** The
integration suites are honestly constructed: fakes sit at real seams and the
real engine core runs underneath (`test/intent-log-session.ts` drives two
sessions against the real `serverIngestBatch`; the bridge test runs end-to-end
through the same in-memory twin the PHP vectors replay — the best part of the
suite). Soft spots: manager tests hand-author all wire rows (drift from PHP
row schema undetected); the session tests' `connect()` helper *reimplements*
the transport-ordering guarantee rather than exercising the real manager
(rows-then-dispositions is pinned separately against a mock session, never
together below e2e); `merge-matrix` imports `verifyEffect` and
`ESCALATION_REASONS` from the code under test; polling-manager tests mock the
codec entirely (which is how finding 1.2 survived).

## The 5 things to fix first

1. **Serialize server ingest per room and validate intent payloads**
   (`class-wp-intent-log-engine.php:191-316`; planner/document typed-param
   crash sites). Without a total order actually enforced and a 400 on
   malformed payloads, everything downstream is provisional and any
   contributor can 500 the room.
2. **Fix the transport error-recovery path for non-compacting engines**
   (`polling-manager.ts:824-828`): codec-driven recovery, restore-not-clear
   for intent-log, regression test with the real session. This is the shortest
   path from "transient wifi blip" to lost work today.
3. **Make bootstrap engine mismatch actually degrade to a lock** (or at
   minimum flip `collaborationSupported` and show the notice) — constraint 3's
   current bootstrap behavior is no-sync-no-lock silent overwrites.
4. **Close the two demonstrated planner-policy holes in both twins +
   vectors**: merge-absorbed-block voiding (escalate instead) and intra-batch
   duplicate double-apply — then add the missing rule-2/boundary/multibyte
   vector cases and a JS-side replay of `planner.json`.
5. **Pin the text coordinate space end to end** — UTF-16 vs PHP bytes, and
   rich-text vs HTML-string capture. Until offsets mean the same thing in the
   browser, the bridge, and PHP, every text-merge guarantee is ASCII-demo-only;
   this decision gates the capture rewrite, the format story, and the vector
   freeze.

**Overall:** a high-discipline prototype with an unusually honest paper trail,
a genuinely clean transport seam, and the right testing instincts (frozen
cross-language vectors, real in-memory twins, regression tests that encode
actual bugs). Its weaknesses cluster exactly where prototypes always hide
them: concurrency, failure paths, growth bounds, non-ASCII text, and the gap
between the engine that was validated and the capture layer that actually
feeds it. None of the findings look fatal to the architecture; several are
fatal to the current status log's stronger claims.
